Decision: Generics are monomorphization-only, expanded before IR from always-explicit type, const and function arguments with each inhabited instance checked as concrete code, because inference and bound solving add complexity and unpredictability to the trust path and the behavior witnesses need concrete direct calls, and this decision stands unchanged because x1 settles function-typed parameters on the existing rule ("Function-typed parameters are generic parameters (FN-2) ... each instance is a direct call", Rule 10), instead of inferred instantiation or dictionary-passing generics that share one runtime body across instances.

Decision: Function and nominal instantiation cycles must forward the complete argument vector unchanged in position and kind, including function arguments, even where a finite permutation cycle would be safe, because a growing recursive instance would not terminate and the syntactic cycle check decides that boundary without executing a search, and this decision stands unchanged because x1 says nothing about instantiation cycles, instead of a more precise termination analysis or a depth, time or fuel limit.

Decision: No type argument supplied to a function, a nominal, or an interface group may be or contain a reference or a range reference at any depth after substitution, because value semantics is closed under wrapping and a type parameter through which a reference could be stored would put a reference inside an aggregate by abbreviation, and this decision is added because x1 Rule 1 states the closure in terms of type parameters directly ("there is no type parameter, wrapper, or variant payload through which a reference can be stored", with `Option<&T>` rejected whatever T is) and x1 Rule 7 makes a range reference a reference kind that is "never a stored value", which together replace the exclusion list of `Slice<'r, T>`, `MutSlice<'r, T>`, `arena<'r, T>`, `Heap<'s>` and `Arena<'s, bytes, align>` leaves that the live tree never recorded as a decision of its own, instead of a written list of loan-bearing and provider leaves to exclude, or admitting such an argument and rejecting only those instances that store it.

Decision: A type parameter's bound is a capability filter on its argument, read as what the argument must be able to do: a parameter written with no bound requires nothing and admits every type, `T: drop` requires an argument that can be dropped, and `T: copy` requires one that can be copied, and what the bound requires of the argument is what it grants the body, so under `T: copy` the body may duplicate the value, use it bare, and drop it, under `T: drop` it may `move` it at most once and may drop it, and with no bound it must consume it exactly once and may never drop it, the bound being optional and never inferred, an absent bound meaning no capability, because a bound after a type parameter naturally reads as what the argument must be able to do, so the type with the fewest capabilities writes nothing, while the class-named spelling `T: linear` read as a demand that the argument be linear although it accepted every class, instead of the class-named bounds `T: copy`, `T: affine` and `T: linear`, under which every type parameter had to write a bound.

Decision: Ordered parameter groups are declared with `interface` and concrete argument groups with `binding`, and a group introduction in a function or nominal header is explicitly prefixed `interface`, including a group with no header parameters, because an unbounded type parameter and a zero-parameter group otherwise both have the spelling `<F>` and grammar selection would depend on name resolution, instead of keeping the `formal` and `actual` keywords or deciding whether a bare header name imports a group by looking up that name.

Decision: Forwarded groups, concrete argument groups and qualified member calls keep their existing argument-position spelling without an `interface` prefix, because those positions do not declare type parameters and have no corresponding ambiguity, instead of adding a marker at every use of a group.

Rejected:
- Keeping the bounds `T: linear` and `T: affine`: rejected because they read backwards, a bound after a type parameter saying what the argument must be, so that `T: linear` reads as "T must be linear" while it accepted every class.
- A word for the no-capability case, such as `T: any`: rejected because the absence of a bound already says that nothing is required of the argument.
- Give a group import priority over an unbounded type parameter when their grammar lookahead overlaps: rejected because parser priority would change the meaning of a declaration according to an unrelated declaration and would leave `<T>` without one syntactic meaning.
