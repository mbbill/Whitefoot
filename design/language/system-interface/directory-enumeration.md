Decision: Directory enumeration transfers a bounded batch of records into the caller's validated view and advances the supplied directory cursor, because a writer-visible handle-owned window would require another draining interface and entry-lifetime rules while the caller-owned window reuses ordinary range contracts, instead of returning a borrowed entry or handle-owned window one item at a time.

Decision: An enumerated name reaches source only as bytes, self and parent entries are reported unfiltered, and no order is fixed, because turning a name into a host string or path value would reintroduce a path model, filtering out the self and parent entries would cost a second host call for a batch holding only them while a descending program must exclude them anyway, and a fixed order would promise what hosts do not provide, instead of filtered, ordered, path-valued entries.

Decision: A directory batch returns its outcome, numeric endpoint and entry count separately with unconditional endpoint bounds, because a caller that ends a view loan before matching a saved outcome can retain ordinary numeric result facts without the deferred transport of an enum payload's fact through a later local match, instead of a special directory-result proof producer or an impossible bounds-failure branch.
