Decision: Overlap permission is judged on a pair of adjacent statements of one block, and a run of statements may all overlap only when every pair of statements the run contains may overlap, because every statement is judged by the paths it actually reads and writes, so a statement standing between two calls is itself a judged member of the pairs around it rather than a form that must be classified or that ends a candidate group, instead of a window of call members with separately classified interposed statements.

Decision: The interference vocabulary of the overlap judgment is the call-site overlap judgment itself: the first statement's write paths must be disjoint from the second statement's read and write paths and the second's write paths from the first's, a consumption of a by-value argument counts as a write of that argument's place, read against read never denies, and two indexed or ranged positions on one storage are taken to overlap unless their indices or ranges are proved distinct, because the judgment that decides whether one call's own arguments may be used together is the same judgment that decides whether two statements may run together, and because a sibling amendment proposes a new node `language/effects/call-site-check` whose third decision already states that one overlap judgment serves the call site, reference invalidation, and the permission for two adjacent statements to overlap, so that if the owner approves that node this decision is the parallelism-side consumer of it and should be trimmed to name the shared judgment rather than restate its content, under the tree's normalize-upward filter, instead of a separate parallel aliasing model or a permission model built on loans held by borrow-written arguments.

Decision: The paths of both statements are interpreted in the state before the first statement, and the first statement's `ensures` is what carries the second statement's indices back into that state, because an index that names a position only after the first statement has run, such as the slot an append has just filled, would otherwise be compared as if it were distinct from the position that statement wrote, and because this decision is added from x1 Rule 13, "The paths of both statements are interpreted in the state before the first statement, so the first statement's `ensures` maps the second's indices into that state, so an index that is live only after an append is not distinct from the append slot", which the tree holds no decision on today, instead of interpreting each statement's paths in its own entry state.

Decision: An overlap that is not proved disjoint denies permission, and a path the implementation cannot resolve overlaps every path, because a silent empty footprint would grant permission by omission, instead of defaulting an unresolved path or an unrecognized access to no effect.

Rejected:
- Judging only consecutive call statements, with a statement of any other form ending the candidate group: rejected because permission then turned on the spelling and adjacency of calls rather than on what the statements access, measured as a 1.9 times wall-time difference between two programs with byte-identical output.
- A separate aliasing model for parallel permission, whether by reliance edges, schedule-parametric ownership, treating exclusive borrows as writes, or a weakened overlap rule: rejected because each one either duplicates the ordinary path-overlap judgment or weakens it.
- Defaulting an unclassified statement or an unresolved path to an empty footprint: rejected because permission would then be granted by omission.
- Replaced decision "Sibling-call permission is judged over a window of checked calls together with every statement between them, with data dependencies, effect footprints, loans, and control exits all quantified over the window ... instead of adjacent-pair enumeration": rejected because x1 Rule 13 decides the same question differently, "Two adjacent statements of one block may overlap when the first's write paths are disjoint from the second's read and write paths and vice versa ... Permission composes: any run of adjacent statements that pairwise may overlap may all overlap", and the defect the window was built against is gone with it, since under x1 every statement has read and write paths, so an intervening statement is a pair member rather than an unclassified form that terminates a group and permission no longer turns on whether a statement happens to be a `let`-bound call, while the window's own grounds, that judging call pairs alone made permission depend on adjacency rather than semantics, are preserved in the first refused alternative above.
