Decision: 编译器是用来迭代这门语言的研究工具：一个 safe-Rust 的 crate，内部接口随实验需要随时改动，实现方式简单、用普通的数据结构，没有稳定的产物格式、回放、发布机制或产品级的资源控制，因为目标是在真实程序上快速验证语言和性能想法，在真正的使用者出现之前搭建产品化结构只会拖慢这件事，而禁止 unsafe 代码让编译器自身的内存安全由 Rust 保证、不必靠人工审查，而不是一个有稳定 crate 边界和经检查产物的产品级工具链。
> 通俗解释：现在的编译器是做实验用的，不是拿去卖的产品。所以它就是一个 Rust 代码包，里面怎么拆、怎么调用都可以说改就改；能用简单办法就用简单办法；不搞中间文件格式、不搞版本发布流程、不搞大规模工程才需要的资源管控。原因是我们要的是快速试想法，产品那套架子在没人用之前只会拖后腿。另外整个编译器不用 unsafe，这样编译器自己不会有内存错误，不用靠人盯着。被否决的是一开始就按 LLVM 那种正式产品的架构来搭。

Decision: 编译器只依据规范里的规则来接受和下沉源码，只走一条语义检查路径和一条下沉路径，绝不通过识别某个函数的名字、签名或代码形状、某个项目、某个语料库或某个测试来做决定，因此任何一致性用例、分期计划或配置档都不能左右接受与否，因为靠识别特定程序来实现的能力是一种这门语言并不存在的特例，并且这会让测试和语料库取代规范来定义语言，而不是按形状匹配的特例或由语料库驱动的接受。
> 通俗解释：编译器判断一个程序能不能通过，只能看语言规范写的规则，不能"认出"某个特定程序然后给它开后门，比如看到函数叫 base64 或者代码长得像某个测试用例就特殊处理让它通过。所有程序走同一条检查和翻译路径。原因是语言里根本没有"这个程序特殊"这条规则；如果编译器靠识别程序来做事，语言就变成由测试和样例程序定义的了，而不是由规范定义。这条主要防的是为了让测试变绿而打补丁式地作弊。

Decision: 规范允许但编译器尚未实现的合法源码，以一个明确的"未支持能力"停下，绝不报告为非法源码，因为把编译器的缺口报告成语言层面的拒绝，等于从实现这一侧改写了语言，而不是把未支持的源码误报为非法。
> 通俗解释：如果一段代码按语言规范是合法的，只是编译器还没做到，编译器必须明说"这个功能还没支持"，不能说"你的代码有错"。否则用户会以为语言不允许这么写，编译器就悄悄替语言改了规则。

Decision: 一次拒绝要指出它违反的编号规则和位置，同一个编译器可执行文件对同一份源码每次都以同样的方式拒绝，任何接受路径都不依赖超时、燃料、工作预算、启发式提前失败或哈希遍历顺序，而在多处违规中先报哪一处不属于语言的一部分，因为编写者依据规则和位置来行动，依赖时间、预算或遍历顺序的接受是碰巧的接受，而两个正确的检查器可能合理地先遇到不同的违规，而不是规定一个可移植的首个报错顺序或有预算的检查。
> 通俗解释：报错必须说清楚违反了哪条规则、在哪一行，这样写代码的人才知道该改什么。同一个编译器对同一份代码，今天拒绝明天也必须拒绝，不能因为机器快慢、算了多久或哈希表遍历顺序不同而结果不同，那样的"通过"只是运气。至于一份代码有好几处错时先报哪一处，不做规定，因为两个都正确的检查器完全可能先撞见不同的错误。

Decision: 每个编译出来的程序都会链接的运行时——计算调度器、完成运行时（completion runtime）与耗尽地板（exhaustion floor）——是人工审查过的纯 C 代码，位于这个 crate 的 safe-Rust 保证之外，因为它是直接与主机的线程、环形队列（ring）和端口打交道的目标代码，而这个研究性编译器及其运行时将来会被自举的编译器取代，所以现在为它引入一门经检查的运行时语言或一套约束（confinement）策略是不换来任何东西的工作，而普通的工程质量仍然是必须的，而不是采用一门经内存安全检查的运行时语言，或者制定一套 unsafe 约束策略。
> 通俗解释：编译出来的每个程序，都要链接一份运行时代码，包括负责并行调度的部分、负责异步 I/O 完成通知的部分，以及负责在栈或堆耗尽时兜底的部分。这部分代码是用纯 C 语言写的，靠人工审查保证质量，不在 Rust 编译器自身"不写 unsafe 代码"这条保证的覆盖范围之内。原因是，这部分代码本来就要直接操作操作系统提供的线程、io_uring 之类的环形队列和网络端口这些底层机制，没法完全用安全 Rust 表达；而且这个编译器和它带的运行时都只是研究阶段的产物，将来会被一个用 Whitefoot 自己写成的编译器取代，现在花力气把运行时也做成内存安全检查语言、或者专门定一套"unsafe 代码要如何被约束"的政策，这些投入将来都用不上，但这不代表可以随便写：普通的工程质量要求（review、测试等）仍然必须满足。被否决的做法是现在就采用一门有内存安全检查的运行时语言，或者现在就写一份关于 unsafe 代码如何被约束的正式政策。

Rejected:
- 一个有稳定 crate 边界、序列化产物和回放的产品级"经检查产物"工具链：被否决，因为它在解析器和后端都还不存在的时候就让 crate 和关卡的数量成倍增加，并且定下了一套没有任何使用者的协议。
  > 通俗解释：早期曾有过一版把编译器按正式产品来设计的方案：拆成很多模块、把检查结果存成文件再读回来。它被否决是因为连最基本的解析器和后端都还没写出来，就先堆了一堆模块和检查关卡，还定了一套根本没人用的文件格式。
- 在这个编译器的可信路径里加固前端以抵御恶意输入、以及让后一阶段重新验证前一阶段已经保证的结果：被否决，因为这个编译器的存在是为了迭代语言，最终会被自举的编译器取代，所以在它上面做纵深防御是不换来任何东西的工作，而快速迭代所需要的普通工程质量仍然是必须的。
  > 通俗解释：现在这个编译器是试验品，将来会用 Whitefoot 自己重写一个正式的。所以不用把它当成对外发布的产品来防恶意输入，也不用让每一步都去复查上一步已经保证过的事，这些活现在做了就是白做。但这不等于代码可以随便写，该有的工程质量还是要有，否则反而拖慢迭代。
- 把已被取代的系统接口清单状态放在编译期开关后面继续保留，好让差分测试证明早先程序的产物没变：被否决，因为编译器只实现一份规范，也就是当前这份，所以一个能重建旧清单的开关没有任何使用者，只是多出一些要维护的代码路径。
  > 通俗解释：以前的 agent 在编译器里留了三个开关，可以把系统接口表"倒回"到旧版本规范的样子，用来做新旧对比测试。但编译器只需要实现当前规范，没人会去用旧版本的表，这些开关纯粹是多余的代码，所以删掉。
