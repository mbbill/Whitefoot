Decision: 可选的优化器事实（optimizer fact）绝不会改变一个已被接受程序的可观察行为，因为后端在不重新检查的情况下信任所发出的属性，所以一个错误的属性就是一次静默的错误编译（miscompile），只有正确的事实关闭（facts-off）参照才能将其暴露出来；因为每个事实族的性能收益都是通过与同一个事实关闭参照进行比较测量而归因得到的；并且因为一个行为有所不同的事实开启（facts-on）构建，将会重新引入调试版与发布版的分裂——即一份源代码却发布出两个不同的程序，而不是按事实选择下沉路径；language 树的根节点持有与之相匹配的规则：事实绝不会改变接受结果。
> 通俗解释：可选的"优化器事实"（编译器优化阶段额外分析出、只用来提速的辅助信息）绝不能改变一个已经被接受的程序运行起来的实际表现。原因是：后端在使用这些信息（术语叫"属性"）时是直接相信它、不会重新核实的，一旦某条信息是错的，就会在没有任何报错的情况下生成一个行为不对的程序（这叫"静默错误编译"），而只有关掉这些辅助信息、用最朴素的版本作对照，才能发现问题；而且，每一种辅助信息带来的性能提升，都要靠和这个"关闭版本"比较测量出来。如果开启这些信息后程序行为会变，那就等于回到了"调试版和发布版行为不一致、一份源码却对应两个不同程序"的老问题。因此这里没有采用"根据是否有这些辅助信息走不同的代码生成路径"的做法；而且语言层面的根本规则也要求：这些事实绝不能影响一个程序是否被接受。

Decision: 一个事实族只有在其收益已针对一个正确的事实关闭构建完成归因，并且经受住了刻意植入错误事实的对抗性测试之后，才可以授权一项优化，因为后端所信任的属性一旦错误就是一次错误编译，而没有基准的测量什么也归因不了，而不是仅因为其发出的结果看起来正确就启用一个事实通道。
> 通俗解释：一项优化器辅助信息想要被允许用来做优化，必须先满足两个条件：一是它带来的性能提升要经过和"关闭这些信息"的版本对比测量出来，二是要故意在测试里塞入错误的信息、看编译器是否还能扛得住这种"找茬"测试。原因是，后端一旦信任某条信息，一旦这条信息是错的就会导致错误编译，而没有对照基准的性能测量根本说明不了任何问题。被否决的做法是：只要这个信息看起来产生得没问题，就直接开放使用，而不做上述两项验证。

Decision: 检查器（checker）是可信计算基（trusted computing base）的一部分，一次错误的证明义务履行是编译器健全性（soundness）缺陷，须在代码和测试中修复，因为一致性测试所表达的期望陈述的是语言本身而非编译器，而不是修改一致性测试的判定结果去迁就编译器的行为。
> 通俗解释："检查器"是编译器里负责核实各种证明是否成立的部分，这里规定它属于"可信计算基"，也就是必须无条件信任其正确性的那部分代码。如果检查器错误地判定某个证明义务已经满足，这就被当作编译器本身正确性上的缺陷，需要通过修改代码和补充测试来修复。原因是：一致性测试所描述的是"语言规定应该怎样"，而不是"编译器现在做了什么"。因此被否决的做法是反过来修改一致性测试的判定结果，让它去迁就编译器当前的（错误）行为。

Decision: 编译器是一个用 safe Rust 编写的、可变的单一 crate，其内部接口可以随语言实验的需要而改变，因为一种永久性的、经检查的产物（checked-artifact）架构把研究阶段的边界当成了产品协议，在解析器（resolver）或后端都还不存在之前就让 crate 和关卡（gate）的数量成倍增加，而不是一个拥有稳定 crate 边界的永久性产物编译器。
> 通俗解释：整个编译器目前就放在一个可以随意修改的 safe Rust 代码包（crate）里，内部各部分之间怎么调用可以随语言实验的需要说改就改。这样做是因为，如果一开始就把编译器拆成多个模块、要求它们之间的接口像产品一样稳定不变（即"经检查的产物架构"），会把研究阶段本该灵活变化的边界当成正式的产品约定，结果在连解析器（负责读懂源码结构的部分）和后端（负责生成最终代码的部分）都还没做出来之前，就已经堆出一堆代码包和检查关卡。被否决的做法正是那种"拥有稳定 crate 边界的永久性产物编译器"。

Decision: 经过检查的内存表示是下沉的唯一权威来源，任何序列化或回放（replay）形式都不被赋予这种权威地位，因为使用同一内核进行的序列化与回放并没有增加独立的语义证据，反而在任何真正的产物消费者存在之前就强加了一套协议，而不是强制要求产物回放。
> 通俗解释：编译器在内存里保存的、已经通过检查的程序表示，是唯一有资格被继续翻译成机器码的东西；如果把这份表示写到文件里再读回来（序列化和回放），这个读回来的版本并不会因此获得同等的权威性。原因是，用同一个编译器内核做序列化和回放并不能带来任何新的、独立的证据来证明程序是对的，反而在还没有真正需要读取这种存档格式的使用者之前，就强行定下了一套格式规范，徒增负担。被否决的做法是要求必须支持这种"产物回放"。

Decision: 产物、回放、稳定协议、发布机制以及产品级的资源控制，都属于后续的加固工作而不是编译器的先决条件，因为它们在无助于研究目标的情况下拖延了第一个可执行编译器的到来，而相称的独立测试已经保留了有用的正确性约束，而不是一整套产品级的、经检查的产物工具链。
> 通俗解释：像"产物"（编译结果的存档格式）、回放、稳定的协议、正式发布用的配套机制，以及产品级别的资源限制这些东西，都属于以后再做的加固工作，而不是现在编译器能不能用的前提条件。原因是，如果现在就要求把这些都做好，会拖慢做出第一个能真正跑起来的编译器的进度，而这对当前的研究目标没有实际帮助；与此同时，规模相称的独立测试已经能保证需要的正确性。被否决的做法是要求一整套产品级别的、带完整检查产物机制的工具链。

Decision: 一致性测试用例是独立的证据，绝不构成一种接受权威，因为唯有带编号的规范才定义源语言的行为，若存在第二种权威就会让测试来定义语言，而不是由语料库（corpus）驱动生产环境中的接受判定。
> 通俗解释："一致性测试"是一批写好"应该被接受还是应该被拒绝"这类预期结果的测试程序，用来检验编译器有没有照规范做事。这条决定规定，这些测试用例只是用来验证的证据，本身并不能决定一个程序该不该被接受——唯一说了算的是那份带编号的规范文档。原因是，如果测试用例也能说了算，就等于有了第二个可以定义语言规则的权威，容易造成规范和测试互相打架。被否决的做法是让"语料库"（也就是这批测试用例的集合）直接驱动生产环境里的接受判定。

Decision: 对实现所做的任何按阶段或切片（slice）的划分，都只描述构建与测试的顺序，绝不会成为一种规范性的准入配置（profile）、一份函数或签名的允许列表，或是一条备用的编译器路径，因为按外形或按身份、而非按规则实现的能力，是这门语言并不存在的特例，而不是由配置（profile）来把关接受与否。
> 通俗解释：把编译器的实现工作按阶段或按切片划分，只是为了安排"先做什么、后测什么"的开发顺序，绝不能变成一种正式规定——比如规定哪些程序形态可以被接受、列出一份"允许使用的函数或签名清单"，或者搞出一条编译器走的"备用路径"。原因是，如果一项能力是靠代码长得像什么、或者是不是某个特定的函数/项目来实现，而不是靠明确的规则来实现，那就等于语言里存在一种"看脸"的特例，而这门语言的设计里本不该有这种特例。被否决的做法是用这种阶段配置来把关一个程序能不能被接受。

Decision: 名称解析之后发生的拒绝，必须确立一次真实存在的、带编号规则的违反，并且对单个编译器可执行文件而言必须是确定性的，而在相互竞争的"第一个错误"之间做出的选择并不属于这门语言身份的一部分，因为编写者依据的是一条规则和一个位置，但两个正确的检查器完全可能合法地先遇到不同的违反之处，而不是规定一种可移植的首错误顺序。
> 通俗解释："名称解析"是编译器把代码里用到的名字（比如变量名、函数名）对应到它们真正指的是哪个定义的过程。这条决定规定，名称解析完成之后如果编译器要拒绝一个程序，必须是因为它确实违反了规范里某条编号规则，而且同一个编译器可执行文件每次判定都要给出一样的结果；但如果程序里同时存在好几处错误，编译器具体先报告哪一个错误，不算是这门语言身份的一部分。原因是，编写者真正需要的是"违反了哪条规则、出错的位置在哪里"，而两个都写对了的检查器完全可能因为内部检查顺序不同，先撞见不同的错误。因此被否决的做法是硬性规定一种所有编译器都必须遵守的、可移植的"报错先后顺序"。

Rejected:
- 一个 Python 参照模型关卡（gate）：被否决，因为它消费的是一棵历史遗留的、玩具级的语法树，既没有运行 Rust 编译器，也没有与之进行比较，因此不能证明其工作流程和维护成本是合理的。
  > 通俗解释：曾经有一种做法是用一个 Python 写的参照模型作为把关环节，但它处理的只是一棵早期遗留下来的、玩具级别的简化语法树，既没有真正运行过 Rust 编译器，也没有拿它的结果和 Rust 编译器做比较，所以没法证明维护它、运行它所花的功夫是值得的，因此这个做法被放弃了。

Decision: 编译器尚未实现、但本身符合规范的合法源码，会作为一种明确的未支持能力而停下，绝不会被报告为无效源码，因为把编译器的缺口报告成语言层面的拒绝，等于从实现一侧改写了语言，而不是把未支持的源码误报为无效源码。
> 通俗解释：如果一段程序写法本身完全符合规范、是合法的，只是编译器目前还没把这个功能做出来，那编译器应该明确说"这个能力还不支持"，而绝不能报告成"你的代码写错了"。原因是，如果把编译器自身的功能缺口说成是语言规则不允许，那就等于是从实现这一边偷偷改写了语言的定义。被否决的做法正是把"编译器还没实现"这种情况误报成"源码无效"。

Decision: 总体目标项目是 ripgrep，目标是取得公平的端到端两倍性能，并且在这个循环中性能优先，因此一旦缺失某项性能能力，下游的扩展就会停下来，直到其所属的那一层被修复为止，而不是被绕开实现，因为设立这个目标项目正是为了暴露语言的普遍缺陷，并把性能收益归因于生成的代码，而在缺失能力之上继续编写下游代码，只会把阻塞点掩藏在一次集成之中，而不是把 SQLite 作为总体目标项目，也不是把交付一个完工的工具当作完成标准。
> 通俗解释：这个项目挑选 ripgrep（一个真实存在的命令行搜索工具）作为检验编译器整体能力的目标程序，要求编译出来的版本要公平地比参照实现快两倍左右，并且在朝这个目标推进时，性能问题要优先解决：如果发现编译器缺少某项能提升性能的能力，就应该先停下来修好这个底层缺失的能力，而不是绕开它、在上层硬凑代码继续往下写。原因是，设立这样一个目标项目，就是为了借助一个真实、复杂的程序暴露语言设计里的普遍问题，并且能把性能上的提升明确归功于编译器生成的代码本身；如果在能力缺失的情况下还硬着头皮往下游写代码，缺失的问题就会被绕过去、被藏进后续的整合工作里，不容易被发现。被否决的做法有两种：一是改用 SQLite（另一个更复杂的真实软件）作为总体目标，二是把"做出一个功能完整的工具"本身当作项目完成的标准。
