Decision: 该下沉方式仅依据经过检查的语句，就能识别出一个逐字节遍历（byte-walk）循环，并为其设置一条建立在一次探测（probe）操作之上的循环头快速路径，该探测操作会报告接下来有多少次迭代是可证明无效应的；一旦识别失败或出现任何表示形式不匹配，就会零改动地回退到普通的下沉方式，且接受判定从未被征询过，因为另一条候选路径——通过重新构造合法的标量（scalar）形态使向量化器（vectorizer）将其加宽——已经被一项预先登记的对照实验关闭：该实验表明，同一编译器编译的 C 语言对照版本得不到提前退出（early-exit）向量化，受保护的逐字节加载也从不会融合成宽加载，而不是依赖后端的向量化器。
> 通俗解释：这条决定是说，编译器在下沉（把检查过的源码翻译成底层代码）阶段，只根据已经通过检查的语句本身，就能认出"逐字节遍历"这种循环模式（比如逐个字节地扫描一段数据找目标），并给它加一条特殊的"循环头快速路径"：先做一次"探测"操作，提前算出接下来有多少次循环肯定不会产生任何副作用（比如提前判断能不能安全地一次跳过一大段）。如果没能认出这种模式，或者数据的具体表示对不上，就原样退回普通的翻译方式，不做任何改动，而且这个识别过程完全不影响程序是否被接受编译。之所以这样做，是因为另一条本来更常规的思路——把这种逐字节的循环写法改造成向量化器（能把多个数据打包用一条指令处理的优化技术）自己就能识别并加宽处理的形式——已经被一次预先设定好评判标准的对照实验否定了：用同一个编译器编译一段等价的 C 语言代码作对照，发现向量化器对这种"可能提前退出"的循环根本不会做向量化，被安全检查保护着的逐字节读取也从来不会被合并成一次读多个字节的宽读取。所以这里没有依赖后端的向量化器来自动完成这件事，而是专门为这种循环手写了一条快速路径。

Rejected:
- 重新构造该标量循环，使后端自身的向量化器将其加宽：被否决，因为同一编译器上一项预先登记的 C 语言对照实验表明，得不到提前退出向量化，受保护的逐字节加载也从不会融合成宽加载。
  > 通俗解释：这条被否决的方案是尝试把这种逐字节处理的循环改写成普通的标量循环写法，指望编译器后端自带的向量化器能自动识别出来并把它加宽、批量处理。之所以放弃，是因为用同一个编译器做的一次预先设定评判标准的 C 语言对照实验表明，这种"可能提前退出"的循环根本得不到向量化，受安全检查保护的逐字节读取也从来不会被合并成一次处理多个字节的宽读取，所以指望向量化器自己搞定是行不通的。
