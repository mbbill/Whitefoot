Decision: 每个工作线程都拥有一个容量固定的 offer 槽位双端队列（deque），一次 offer 就是向发起该 offer 的线程自己的 deque 执行一次 push，空闲线程会窃取其中最旧的一条条目，而一次 join 会先收回自己发起的 offer 并就地内联运行它，然后才会等待一个已被窃取的 offer，因为在按 lane 扫描的设计下，一次 offer 无论最终是被接受还是被拒绝，都要付出一次对每个 lane 的竞争性扫描以及一次互斥锁与条件变量的握手代价，在细粒度下比顺序执行慢多达 48.6 倍，而按线程各自持有 deque 的设计，则让一次 offer 只需两次本地存储，并把全部同步开销转移到窃取操作上——窃取操作的次数取决于负载的不均衡程度而非 offer 的发生频率，而不是每次 offer 都去扫描一个由各 lane 组成的共享数组。
> 通俗解释：每个工作线程都自己拿着一个容量固定的"双端队列"，用来存放自己想交出去（offer）的工作；提交一份工作，就是把它塞进自己队列的一端，闲着没事做的线程会去偷别人队列里最旧的那一份。等到本来提交工作的那个线程要等结果（join）时，如果这份工作还没被偷走，它就自己先干完这份工作，只有真被偷走了才需要等待。这样设计的原因是：如果换成"所有线程共享一份 lane 表格、每次提交都去扫一遍"的老办法，无论工作最后有没有被接手，每次提交都要付出一次全体扫描外加一次锁和条件变量的握手代价，实测在粒度很细（工作量很小、次数很多）的场景下比顺序执行慢了将近 49 倍。而让每个线程各管自己的队列，提交工作只需要两步简单的本地写入，真正的同步开销全部转移到了"偷"这个动作上，而偷的次数只跟负载是否不均衡有关，跟提交的频率无关，代价小得多。因此被否决的做法是维护一个所有线程共享、每次提交都要扫描的 lane 数组。

Decision: 一个已满的 deque 会拒绝这次 offer，于是该调用会就地内联运行，因此被拒绝的总是嵌套最深、悬而未决的那个 fork，其容量同时也充当粒度下限（grain floor），无需另外调校任何常量，因为对提升（promotion）操作进行限速固然可以限制拒绝的代价，却既无法在粗粒度下抬高上限——此时开销已经被摊销——也无法解除偏斜状况的阻塞——在这种状况下，调用者会在自己交出去的那一半任务上睡眠等待，而要提升最旧的那个悬而未决的 fork 点，就需要保留所有 fork 点，这正是一个 deque 所做的事，而不是采用心跳式的提升关卡（gate）。
> 通俗解释：如果一个线程自己的队列已经满了，新的一次 offer 就会被拒绝，这份工作干脆就地做掉；由于队列是"后进先出"再加"被偷的是最旧的"这种结构，被拒绝的永远是嵌套最深、最后才产生的那个分支（fork），队列的容量本身也就自然而然地起到了"最细能切多小"的下限作用，不需要另外去调一个参数。之所以不采用"心跳式提升关卡"（一种按时间节奏、限制把工作提升为可被偷取状态的速率的机制）这种做法，是因为它虽然能控制拒绝发生的代价，但既没法在工作量本来就大、开销早已被摊薄的情况下把承载上限提高，也解决不了任务分配严重不均、调用者只能干等着自己交出去的那一半任务完成的问题；而且，如果要优先提升"最早产生、还悬而未决"的那个分支，就必须把所有分支的信息都保留下来，这其实就是一个双端队列在做的事情，等于绕了一圈又做回同样的事。

Decision: 一个正在等待的 join 会持续工作而不是睡眠，先耗尽自己的 deque，然后再去窃取，只有在哪里都没有工作可做时才会挂起（park），因为一个睡眠中的 joiner 会浪费程序已经拥有的这个线程，而不是让 join 睡眠在一个条件变量上。
> 通俗解释：一个线程在等待自己交出去的工作完成（join）时，不会干等着睡觉，而是先把自己队列里剩下的工作干完，再去别的线程那里偷点活干，实在没有任何工作可做了才会真正休眠（挂起）。原因是，如果让等待中的线程直接睡觉，就白白浪费了程序本来已经拥有、随时可以拿来干活的这个线程资源，所以没有采用"join 时睡在一个条件变量上等通知"的做法。

Decision: 计算任务运行在持久化的原生 worker 线程及其普通栈之上，一次 join 会在发起 join 的线程上直接执行一个尚未被窃取的目标，一个已被窃取的目标，会让发起 join 的线程先去运行并窃取其他计算任务，然后才进入一条有界的自旋（spin）、让出（yield）与条件等待（condition-wait）慢路径，而一个可能会挂起的用户调用，则始终留在其调用者的栈上，绝不会被发布给某个计算 worker，因为在一次计算未命中（miss）时把发起 join 的栈挂起（park），在四个和八个 worker 的情况下实测落后 8% 到 9%，而且只有依靠一个可切换栈的池、一台受管理栈的状态机，以及一个穷尽式的调度枚举器，才能让人信任它，而不是采用一种"未命中即挂起"的调度器，在任意一个先完成自己目标的 worker 上恢复被挂起的栈。
> 通俗解释：计算类的任务一直跑在固定不变的、原生系统线程和它们各自的普通调用栈上。等待某个任务完成（join）时，如果这份工作还没被别的线程偷走，就直接在当前线程上把它做完；如果已经被偷走了，当前线程就先去做别的、还能偷到的计算工作，实在没活干了才进入"先短暂自旋等一下、再让出 CPU、最后靠条件变量等待"这样一条较慢的兜底路径。而那种执行中可能会挂起等待的用户调用，则始终留在发起它的那个线程自己的栈上，绝不会被拿去交给别的计算线程执行。这样设计是因为，曾经尝试过"没抢到活就把当前线程的栈整个挂起，等别的线程干完了再把它接回来恢复运行"的办法，实测在四个和八个工作线程时反而慢了 8% 到 9%，而且要让人放心地用这种办法，还得额外造一整套可以切换的栈池、一台管理栈状态的复杂机制，以及一个能穷举所有调度情况的验证工具，成本太高，所以没有采用。

Decision: 在一次 I/O join 处，调用者会先推进完成过程，然后在自己的栈上通过原生后端等待，既不切换栈，也不在这次 join 中帮忙执行计算任务，与此同时，其他 worker 会继续完成那些已经发布出去的计算任务，因为 I/O 保持着它自己"先提交、后 join"的单一下沉路径，其操作记录留在提交时所在的帧（frame）中，而要从一次 I/O join 中帮忙执行任务，就需要用到运行时已经不再具备的可切换栈，而不是采用单一的调度核心，把每一次 I/O join 都挂起，再通过计算运行时来收割（reap）结果。
> 通俗解释：等待一个 I/O 操作（比如读写文件、网络请求）完成时，调用者会先推进这个操作走向完成，然后就留在自己原来的栈上、通过操作系统原生的机制等待结果，既不会切换到别的栈，也不会趁着等待的空档去帮忙做别的计算任务；与此同时，别的工作线程仍然会照常去完成那些已经发布出去的计算工作。这是因为 I/O 操作走的是"先提交、再等待"这一条独立的下沉路径，操作的相关记录就保存在提交它的那个函数栈帧里；如果想让等待 I/O 的线程也能顺便帮着做计算任务，就需要用到"可以在线程之间切换的栈"这种机制，而这套机制在当前的运行时里已经不存在了。因此被否决的做法是设计一个统一的调度核心，把每次等待 I/O 都先挂起，再靠计算运行时把结果收回来。

Decision: 通过 `make -C compiler sched-deque-test` 运行、并在 ThreadSanitizer 下重复执行的 deque 压力探测（probe），是这个运行时的并发检查手段，而对于它触及不到的边界情况，则由单独的启动、join、完成与耗尽测试来覆盖，因为已被淘汰的枚举器，建模的是那台已经不复存在的受管理栈状态机，而一个作用于原生线程上的探测，能在它所观察到的执行过程中发现竞态（race），但并不宣称拥有枚举器曾具备的那种穷尽式覆盖，而不是继续保留一个针对运行时已经不再采用的调度方式的枚举器。
> 通俗解释：现在检验这套并行运行时有没有并发问题（比如数据竞争）的主要办法，是运行一个叫 `sched-deque-test` 的压力测试，并且在 ThreadSanitizer（一种能检测多线程数据竞争的工具）下反复跑；至于压力测试本身覆盖不到的情况，则另外用启动、join、完成、耗尽这几类单独的测试来补上。原因是，以前用过一种"穷举所有可能调度顺序"的枚举工具，但它是针对一种如今已经不再使用的"受管理栈状态机"设计的，那套机制现在已经废弃了；而现在这种在真实系统线程上做压力测试的办法，虽然只能在它实际观察到的那些执行顺序里发现问题，不能像旧枚举器那样保证穷尽所有情况，但也不需要再去维护一个针对已经过时的调度方式的枚举器了。

Rejected:
- 一个由 worker lane 组成的固定数组，通过对每个 lane 执行一次比较并交换（CAS）外加一次互斥锁-条件变量握手来进行扫描：被否决，因为无论最终是被接受还是被拒绝，每一次 offer 都要付出这次扫描和这次握手的代价，在最粗粒度的单元（cell）上每次 fork 耗费 48.8 纳秒，在细粒度下则比顺序执行慢多达 48.6 倍。
  > 通俗解释：这种做法是让所有工作线程共用一份固定大小的表格，每次提交工作都要挨个扫描每一个位置、做一次"比较并交换"的原子操作，再配上一次锁和条件变量的握手。但不管这次提交最终有没有被接手，这套扫描加握手的代价都要付出一次，实测哪怕是在开销相对不敏感的粗粒度场景下，每次分支也要花掉将近 49 纳秒，而在工作量很小、次数很多的细粒度场景下，反而比顺序执行慢了将近 49 倍，所以被放弃。
- 一个心跳式关卡（gate），依据自上次提升以来完成的本地工作量来限制提升的速率：被否决，因为它能限制拒绝的代价，却无法在开销已经被摊销的粗粒度场景下抬高上限，也无法解除偏斜状况的阻塞——在这种状况下调用者会在自己交出去的那一半任务上睡眠等待，而且要提升最旧的那个悬而未决的 fork，就需要保留所有 fork 点，这正是一个 deque 所做的事。
  > 通俗解释：这种做法是按照"距离上次把工作提升为可被偷取状态以来，本地已经做了多少工作"来控制提升的速率，就像按心跳节奏来限速。它确实能控制"提交被拒绝"这件事的代价，但在工作量本来就大、开销已经被摊薄的场景下，它没法把承载能力的上限再往上提；在任务分配严重不均、调用者只能干等着自己交出去的那部分任务完成的场景下，它也解决不了阻塞问题；而且如果真要优先提升最早、最久悬而未决的那个分支，就必须把所有分支信息都保留下来，这其实就是双端队列本身在做的事，所以这个办法没有被采用。
- 在一次计算未命中时把发起 join 的栈挂起，并在任意一个先完成该目标的 worker 上恢复它：被否决，因为在排版（layout）程序上、四个和八个 worker 的情况下，实测落后 8% 到 9%，而且只有依靠一个可切换栈的池、一台受管理栈的状态机，以及一个穷尽式的调度枚举器，才能让人信任它。
  > 通俗解释：这种做法是在等待的工作没抢到手时，直接把发起等待的那个线程的栈整个挂起来，等哪个工作线程先做完了目标任务，再把这个挂起的栈接回去恢复运行。但实测在一个实际的排版程序上、用四个或八个工作线程时反而慢了 8% 到 9%，而且要让人信得过这套机制，还得额外搭一整套可切换的栈池、一台专门管理栈状态的机制，以及一个能穷举所有调度可能性的验证工具，成本太高，所以被放弃。
