Decision: 一个非入口函数，可以在其签名之后携带一个契约（contract）块，该块会被完全编译消除，其中共享的 define 缩写在前，随后是任意数量的 requires 与 ensures 子句，每条子句都单独证明，如果这个块出现，就必须至少包含一条子句，因为早先分离的 requires 块和 ensures 块，其拼写方式与可执行代码相同，导致读者看不出它们会被擦除，一个两者都需要用到的缩写不得不被写两遍，而且 ensures 没有办法为函数的结果命名，而不是采用一个以单个布尔检查结尾的、单一的最终要求块。

Decision: 一个 define 是一个仅用于证明的缩写，会被逐字代入到每一条用到它的子句中，它从不运行、不存储值，也不进行快照，因为同一个缩写会在两个不同的时刻被读取：requires 是在调用之前，ensures 则是在被调用函数返回之时，没有任何单一的存储值能够在这两个时刻都正确，而不是把它求值一次后存入一个隐藏槽位。

Decision: 每个函数都会在签名中为其结果命名，以便 ensures 能够引用它，一条关于 Result 的成功值的后置条件，会写作 `Ok(value: name)` 来绑定其中的负载（payload），因为结果名代表的是整个值，而检查器所追踪的算术事实，却存在于其内部的整数负载之上，而不是采用一个未命名的结果，或是一种只针对负载的约定。

Decision: 每一条 requires 子句，都会在调用点、依据调用之前那一刻的状态单独加以证明，而当两条子句在 define 展开之后，指明的是相同的运算、类型、常量、参数与字面量时，它们就是同一个目标，因为一个已经被证明过一次的目标，无论它在何处再次出现都必须被识别出来，而不是按拼写形式或按代数范式来匹配目标。

Decision: 一个其若干要求相互矛盾的函数实例是合法的，只是不可被调用而已：编译器依然会检查它的结构、所有权、效应以及返回形态，并用一个具备正确调用约定的不可达桩（stub）取代其函数体来下沉，且不发布任何后置条件，因为项目负责人选择了让契约面具有清晰含义，而不是与早先的模型保持兼容，而不是把这样的实例当作源码错误加以拒绝。

Rejected:
- 一个带有局部绑定、并以单个布尔检查收尾的单一最终要求块：被否决，因为它的拼写方式与可执行代码相同，导致其会被擦除这件事无法被看见，一个同时被 requires 和 ensures 用到的缩写不得不被写两遍，而且结果没有名字。
- 一个单一的模式识别器，专门匹配 base64 容量这种形态并省略其检查：被否决，因为它在自己认得的那一种形态上是对的，但只会报告通过或失败，从不说明缺失的是哪个事实、失败的是哪个前提，因此凡是它无法归类的情形，都不能安全地失败。
