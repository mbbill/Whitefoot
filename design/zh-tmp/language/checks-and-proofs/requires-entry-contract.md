Decision: 一个非入口函数，可以在其签名之后携带一个 requires-and-ensures 块——规范中称之为契约（contract）块——该块会被完全编译消除，其中共享的 define 缩写在前，随后是任意数量的 requires 与 ensures 子句，每条子句都单独证明，如果这个块出现，就必须至少包含一条子句，因为早先分离的 requires 块和 ensures 块，其拼写方式与可执行代码相同，导致读者看不出它们会被擦除，一个两者都需要用到的缩写不得不被写两遍，而且 ensures 没有办法为函数的结果命名，而不是采用一个以单个布尔检查结尾的、单一的最终要求块。
> 通俗解释：这条规定说的是：一个非入口函数（不是程序最外层入口的函数）的签名后面，可以跟着一个 requires-and-ensures 块，规范里管它叫“契约（contract）”块，这个块在编译时会被整体删掉，不会留下任何运行时代码；块里先写共享的 define 缩写，然后是任意数量的 requires（调用前必须成立的条件）和 ensures（返回时保证成立的条件）子句，每条子句都单独证明，只要这个块出现，就至少要写一条子句。这样设计的原因是：之前把 requires 和 ensures 分成两个独立的块，写法跟真正会执行的代码一模一样，读者根本看不出它们其实会被整个擦掉；而且如果两边都要用到同一个缩写，就得把它重复写两遍；再加上 ensures 没有办法直接称呼函数返回的那个结果。被否决的方案，是用一个以单个布尔判断结尾、内部用局部变量的单一“最终要求块”来代替。

Decision: 一个 define 是一个仅用于证明的缩写，会被逐字代入到每一条用到它的子句中，它从不运行、不存储值，也不进行快照，因为同一个缩写会在两个不同的时刻被读取：requires 是在调用之前，ensures 则是在被调用函数返回之时，没有任何单一的存储值能够在这两个时刻都正确，而不是把它求值一次后存入一个隐藏槽位。
> 通俗解释：这条规定说的是：define 只是一个专门用于证明的“缩写”，编译器会把它原样、逐字地代入到每一处用到它的子句里，它从来不会真正运行、不会把值存起来，也不会给某一时刻拍个快照。原因是：同一个缩写，requires 是在函数调用之前读它，而 ensures 是在被调用函数返回的那一刻读它，是两个不同的时间点，任何一个“只存一次”的固定值都不可能在这两个时刻都保持正确。被否决的方案，是把这个缩写求值一次，存进一个看不见的隐藏变量里，供两边共用。

Decision: 每个函数都会在签名中为其结果命名，以便 ensures 能够引用它，一条关于 Result 的成功值的后置条件，会写作 `Ok(value: name)` 来绑定其中的负载（payload），因为结果名代表的是整个值，而检查器所追踪的算术事实，却存在于其内部的整数负载之上，而不是采用一个未命名的结果，或是一种只针对负载的约定。
> 通俗解释：这条规定说的是：每个函数都要在签名里给它的返回结果起一个名字，这样 ensures 子句才能引用它；如果后置条件是针对 Result 类型成功那一分支里的值，就要写成 `Ok(value: name)` 这种形式，把里面真正的数据（payload）绑定出来。原因是：结果的名字代表的是整个返回值这个“容器”，而编译器实际追踪的那些算术事实（比如某个数不超过多少），是挂在容器内部那个整数数据上的，两者不是一回事，所以都需要能被引用到。被否决的方案，是干脆不给结果起名字，或者只约定“只处理内部数据”这一种简化做法。

Decision: 每一条 requires 子句，都会在调用点、依据调用之前那一刻的状态单独加以证明，而当两条子句在 define 展开之后，指明的是相同的运算、类型、常量、参数与字面量时，它们就是同一个目标，因为一个已经被证明过一次的目标，无论它在何处再次出现都必须被识别出来，而不是按拼写形式或按代数范式来匹配目标。
> 通俗解释：这条规定说的是：每一条 requires 子句，都是在调用发生的那个位置、按调用前一瞬间的程序状态单独证明的；而判断两条子句算不算“同一个目标”，要看它们把 define 缩写展开之后，涉及的运算、类型、常量、参数和字面量是不是完全一样。这样规定的原因是：一个目标一旦被证明过一次，不管它以后在代码里以什么面貌再次出现，都应该被识别出“这个已经证过了”，不用重复证明。被否决的方案，是按照子句写出来的字面拼写去匹配，或者先把算式化成某种统一的代数标准形式再匹配。

Decision: 一个其若干要求相互矛盾的函数实例是合法的，只是不可被调用而已：编译器依然会检查它的结构、所有权、效应以及返回形态，并用一个具备正确调用约定的不可达桩（stub）取代其函数体来下沉，且不发布任何后置条件，因为项目负责人选择了让契约面具有清晰含义，而不是与早先的模型保持兼容，而不是把这样的实例当作源码错误加以拒绝。
> 通俗解释：这条规定说的是：如果一个函数实例的多条 requires 要求互相矛盾（不可能同时成立），这在语言里是合法的，只是这个函数实际上永远没法被调用而已；编译器仍然会照常检查它的结构、所有权规则、副作用声明和返回值形态是否正确，只是会用一个调用约定正确、但函数体换成“不可能执行到”的占位代码（stub）来代替原来的函数体，并且不会对外发布任何后置条件。这样做的原因是：项目负责人认为契约这个层面的含义应该清晰明确，宁可这样处理，也不去迁就跟旧模型保持兼容。被否决的方案，是把这种自相矛盾的函数实例直接当作源码错误拒绝掉。

Rejected:
- 一个带有局部绑定、并以单个布尔检查收尾的单一最终要求块：被否决，因为它的拼写方式与可执行代码相同，导致其会被擦除这件事无法被看见，一个同时被 requires 和 ensures 用到的缩写不得不被写两遍，而且结果没有名字。
  > 通俗解释：这个被否决的方案是用一个带局部变量、并以单个布尔表达式结尾的“最终要求块”来统一表达要求。之所以被否决，是因为它的写法跟真正会执行的代码几乎一样，读者根本看不出它其实会被整体擦除；requires 和 ensures 都要用到的缩写还是得重复写两遍；而且这种写法里返回结果也没有名字可以引用。
- 一个单一的模式识别器，专门匹配 base64 容量这种形态并省略其检查：被否决，因为它在自己认得的那一种形态上是对的，但只会报告通过或失败，从不说明缺失的是哪个事实、失败的是哪个前提，因此凡是它无法归类的情形，都不能安全地失败。
  > 通俗解释：这个被否决的方案是写一个专门的模式识别器，专门认出 base64 编码里计算容量的那一种固定写法，然后省略掉对它的详细检查。之所以被否决，是因为它虽然在自己认识的这一种写法上是对的，但只会告诉你“通过”或“不通过”，从来不说明到底缺了哪个事实、哪个前提没能满足；结果是凡是它认不出来的情形，都没办法得到一个说得清楚、让人放心的失败提示。
