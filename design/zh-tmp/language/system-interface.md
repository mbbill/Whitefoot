Decision: 系统访问通过带类型的入口输入和普通的被拥有资源进行，走普通所有权，没有单独的能力类别，也不为表达系统状态发明任何语言机制：对语言来说系统对象就是普通对象，一个系统对象缺少某种能力时，重新设计成更好的所有权关系（比如一个交出被拥有资源的工厂），而不是用内部可变性或新的语言特性去打补丁，因为那些替代方案各自伪造了身份、隐藏了访问、把不相关的资源串行化了、或引入了另一个生态的契约，而为了迁就某一个接口的形状而添加的机制会成为所有权模型上的永久漏洞，而不是裸描述符、环境函数、单一进程对象、照搬的 WASI 契约或用于系统状态的内部可变性。
> 通俗解释：文件、目录、网络连接这些系统资源，在语言里就是普通的被拥有的值，谁拿着谁负责，和其他对象没有任何区别。以前 agent 多次犯的错误是：某个系统 API 设计得不顺手，就想在语言里加"内部可变性"之类的机制来表达系统状态。这条明确禁止这种做法：接口不顺手就重新设计对象之间的所有权关系（比如用一个工厂对象来发放资源），不能动语言。原因是为一个接口开的口子会永远留在所有权模型上。

Decision: 资源契约陈述的是结果、所有权、清理、容量关系与目标平台保证，而完成（completion）与主机调度则属于下沉阶段关心的事，因为一个源码契约必须在这门语言不含调度器的情况下也可被检查，而不是把调度纳入源码模型之中。
> 通俗解释：这里的"契约"指函数或资源附带的前置条件、后置条件说明。对于文件、网络连接这类系统资源，它的契约只描述结果是什么、归谁所有、怎么清理、容量方面的限制，以及在目标平台上能保证什么，但不去描述"什么时候真正完成"以及"操作系统怎么调度"这些细节——那些留到下沉（把源码翻译成机器码）阶段再处理。这样规定是因为，源码层面的契约必须能够在语言本身根本不包含调度器的情况下被检查通过，就像检查一份合同条款不需要知道快递公司具体怎么排班送货。被否决的做法是把调度机制也写进源码层面的模型里。

Decision: 参数与路径会保留目标主机原本的字节，转换必须显式进行，而携带范围的操作，会暴露其精确的窗口与结果关系，因为一个仅支持 Unicode 的路径模型，无法表示每一种主机路径，而一个窗口是隐式的操作，是无法针对它进行证明的，而不是采用字符串类型的路径和隐式窗口。
> 通俗解释：命令行参数和文件路径在程序里会原样保留操作系统给出的原始字节，如果要把它们转换成文本字符串，必须显式地做这一步转换，不会自动进行。凡是操作一段数据范围（比如读取缓冲区的一部分）的函数，都必须清楚交代这段范围具体是多大、结果和这段范围是什么关系。这样规定的原因是：不同操作系统的文件路径不一定都能用 Unicode 文字表示（比如有些系统允许路径里出现任意字节），如果强行只支持 Unicode 字符串，就会有些合法路径没法表示；另外，如果一个操作涉及的数据范围没有写清楚，编译器就无法针对它写证明。被否决的做法是把路径一律定为字符串类型，并且让操作范围保持隐式、不用写明。

Decision: 每个编译单元恰好有一个 `command fn main`，它请求带标签的命令输入的任意有序子集，有一个命名的 `ExitStatus` 结果，不带契约，且不能从源码调用，因为两种 main 形式让一个声明同时承担互不兼容的普通调用和进程入口两种角色，而在只有一个不可调用的入口、没有外部接口、入口上没有契约的前提下，每一个要求都属于某个内部调用，无陷阱边界就不需要任何只针对入口的运行时例外，而不是第二个可从源码调用的 main 或一个带检查的进程入口包装器。
> 通俗解释：程序入口只有一种写法：一个 `command fn main`，想用哪些系统能力就在参数里按标签列出来，返回退出状态，不能写前置条件，程序自己也不能调用它。这样一来所有前置条件都出现在程序内部的调用上、都能在调用点证明，入口处不需要运行时检查参数，也就不存在语言不允许的运行时崩溃点。

Rejected:
- 在源码中使用原始系统调用号与整数文件描述符：被否决，因为它们会暴露可伪造的身份、一张隐式的全局描述符表、需要手动的 close、较弱的效应精确度、较差的 Windows 可移植性，以及一堵未经检查的指针墙；它们仅在编译器自有的目标代码内部依然被允许使用。
  > 通俗解释：这个备选方案是让程序直接用底层的系统调用编号和普通整数当作文件句柄（类似 C 语言的做法）。它被否决，是因为这样的整数很容易被伪造或用错，背后还依赖一张看不见的全局对照表，需要程序员自己记得手动关闭，很难被效应清单精确追踪，在 Windows 上表现也不好，而且往往需要不受检查的裸指针操作。这种写法目前仍然只允许出现在编译器自己生成的目标代码内部，程序员写的源码里用不到。
- 诸如 args、open、stdin 与 spawn 之类、可以被任何函数调用的隐式环境自由函数：被否决，因为它们会隐藏访问，违反"无全局状态"规则地创建出跨函数通道，并使得系统使用在签名中不可见。
  > 通俗解释：这个方案是像很多语言那样，提供一些像 args、open、stdin、spawn 这样"随处可调用"的全局函数，不需要显式传入什么就能访问系统。它被否决，是因为这种全局函数会把系统访问藏起来看不见，相当于在函数之间开了一条不受管控的秘密通道，违反了"不允许全局状态"的规则，而且函数签名里完全看不出它用到了系统资源。
- 一个被永久保留的仿射 Process 对象，由每一个系统操作向它借用：被否决，因为这样一来，每个操作就会争抢同一个唯一持有者，从而错误地把文件、输出、网络、时钟与 worker 都串行化了，而共享它则需要一把中心锁，或者隐藏的别名。
  > 通俗解释：这个方案是设一个代表"整个进程"、只能用一次的（仿射）Process 对象，所有系统操作都要向它借用一下才能进行。它被否决，是因为这样所有操作都得排队争抢这同一个对象，结果原本毫不相关的操作——比如读文件、打印输出、发网络请求、看时钟、启动 worker 线程——都被硬生生地变成了只能一个接一个做，没法同时进行；要是想让大家共享这个对象，又得引入一把全局锁或者不安全的别名机制。
- 照搬 WASI 的源码契约：被否决，因为它会引入仅支持 Unicode 的路径、不保证调用者缓冲区或零拷贝路径、与 Component Model 成本绑定的异步机制，以及一套为跨语言组件而选定、并不完整的线程与进程表面；对于它能够提供的那些操作，WASI 仍然是一种可能的目标实现方式。
  > 通俗解释：WASI 是 WebAssembly 的一套现成系统接口标准。这个方案是直接照搬 WASI 定义的接口来当作本语言的源码契约。它被否决，是因为 WASI 只支持 Unicode 路径、不保证调用者提供的缓冲区能被直接使用或零拷贝传输、它的异步机制和另一套叫 Component Model 的规范绑在一起会带来额外成本，而且它的线程和进程支持并不完整，那是为了方便多语言组件互通才选的，不完全适合这里。不过对于 WASI 确实能提供的那些具体操作，将来仍然可以把 WASI 当作一种底层实现方式来使用。
