Decision: 目录枚举是一次性尝试，把一批数量有限、可移植的记录，转移到调用者已验证的 buffer 范围之中，同时推进目录自身的位置，句柄只拥有一个游标，不拥有任何存储，因为一个自己持有窗口的句柄，需要系统层并不分配的存储、需要再调用一次来把它排空，还需要一条针对它仍持有的条目的生命周期规则，而把结果转移到调用者范围的做法，则完整地重用了既有的、一次性尝试的文件读取契约，而不是采用一个句柄自持窗口、逐条产出条目的方式。
> 通俗解释：读取一个目录里的文件列表（类似 `ls`）时，采用的做法是一次性尝试：把数量有限的一批、格式统一的记录，直接搬进调用者事先准备好并且已经检查过的那块内存范围里，同时把目录内部"读到哪儿了"的位置往前推进；代表这次读取操作的句柄，本身只保留一个游标（也就是一个位置书签），不额外存放任何数据。这样做是因为，如果让句柄自己保留一批条目，就需要系统层本来不会分配的额外存储空间，还得多调用一次函数才能把这些数据取出来，并且还得专门定一条规则来说明这些暂存的条目能被使用多久。而直接搬进调用者的内存范围，则可以原封不动地沿用已经有的、同样是"一次性尝试"的文件读取方式，不用再发明一套新机制。被否决的做法是让句柄自己保留一段窗口式的数据，一条一条地往外吐。

Decision: 一个被枚举出的名字，到达源码层面时只会是字节，代表自身和父目录的条目会被不加过滤地报告出来，并且不固定任何顺序，因为把一个名字变成主机字符串或路径值，将会重新引入一个路径模型，过滤掉自身和父目录条目，将需要为一个只包含它们的批次多付出一次主机调用，而一个向下递归的程序无论如何都必须排除它们，而固定的顺序则会许诺一些主机根本不提供的东西，而不是提供经过过滤、排序、以路径值表示的条目。
> 通俗解释：从目录里读出来的每一个文件名，在源码层面只是一串原始字节，不会自动变成文本字符串或路径类型。代表"当前目录"和"上一级目录"的那两个特殊条目（常见的 `.` 和 `..`）会照样原样报告出来，不会被过滤掉，并且返回的条目也不保证任何固定顺序。这样规定的原因是：把文件名转换成主机字符串或路径值，会重新带回之前已经放弃的那一套路径模型的麻烦；如果要过滤掉那两个特殊条目，遇到一批结果恰好只包含它们的情况时，就得多向操作系统发一次请求去确认，而且一个要递归遍历子目录的程序反正也必须自己排除这两项，所以过滤没有必要；至于固定顺序，那会等于向使用者承诺一些操作系统本身根本不保证提供的东西。被否决的做法是提供经过过滤、排好序、并且是路径类型的条目。
