Decision: 每一个编译单元都恰好有一个 `command fn main`，它可以按顺序请求带标签命令输入中的任意子集，拥有一个具名的 `ExitStatus` 结果，不携带任何 contract，并且不能从源码中被调用，因为两种 main 形式会让同一条声明兼任互不相容的普通调用角色和进程入口角色，并因此需要一个特殊的可执行文件要求边界，而一个源码层面不可调用的入口，能同时消除这种歧义，以及那唯一一处由 contract 引发的运行时陷阱例外，而不是再设一种不带标签、可从源码调用的 main。
> 通俗解释：每个编译单元（可以理解为一个程序）都必须恰好有一个特殊的 `command fn main` 函数，作为整个程序的入口。它可以按自己需要的顺序，从一组带标签的命令输入（比如命令行参数）里挑任意一部分来用，必须返回一个专门命名的 `ExitStatus`（退出状态）结果，不能带 requires/ensures 这样的契约，并且不能像普通函数那样被程序内部的代码调用。这样规定是因为，如果同时允许两种 main（一种是普通的、能被调用的函数，另一种是专门的命令入口），同一个名字就要兼顾两种互相冲突的身份——既是可以被随便调用的普通函数，又是程序真正开始运行的那个特殊起点——这就需要额外一套规则专门判断"这是不是可执行文件真正的启动点"。而只允许一种、且不能被源码调用的入口，就同时解决了这种身份混淆问题，也顺带去掉了那唯一一处"因为带契约而允许运行时崩溃退出"的特殊例外。被否决的做法是再设立第二种不带标签、可以被源码普通调用的 main。

Rejected:
- 两种 main 形式，一种是不带标签、可从源码调用的函数，另一种是命令函数，按单元各自选择：被否决，因为这样一来，同一条声明就要兼任互不相容的角色，并且在程序启动时需要一个特殊的可执行文件要求边界。
  > 通俗解释：这个方案是允许每个程序自己挑选用哪种 main：一种是普通的、可以被源码里其他代码调用的函数，另一种是专门的命令入口函数。它被否决，是因为不管挑哪种，都会导致"main"这个声明需要同时扮演两种互相冲突的角色——既可能是普通函数，又可能是进程真正的启动点——这就必须在程序启动的地方额外加一套特殊规则来判断到底是哪一种，增加了不必要的复杂性。
