Node: compiler/storage-representation

Decision: A boxed runtime-capacity shape is thin: `Box<Slots<T>>`, `Box<Ring<T>>` and `Box<Array<T>>` are each one pointer to one block laid out `[len | cap | elements]`, exactly as the inline constant-capacity form lays out the same shape, a `Ring` storing `head` beside `len` and an `Array`, whose `len` equals its `cap` [WIN-1], storing that one runtime number once, because every access has had its bound discharged before lowering [OP-4, DIAG-2] so a hot loop never reads `len` at all and a second word carried beside the pointer would be kept live for a check the emitted code does not make, the element address is the block address plus an offset whose block address a loop hoists once, one emitter and one address computation then serve the inline and the boxed placement of each shape, and `grow` reallocates the header and the elements as one object, instead of a fat descriptor beside the owner holding pointer, length and capacity, which is the layout a language that checks bounds at every access needs.

Decision: The constant-capacity form carries the same header ahead of its elements so that the two placements share one layout, because a runtime-capacity block cannot put its header after elements whose count is a runtime number, and two layouts would mean two emitters, two address computations and two readings of one measure, while [OP-9]'s ceiling bounds a shape's size and alignment and fixes no field order, so the header-first arrangement stays under the ceiling the rule computes, instead of keeping elements first inline and header first in the box.

Decision: No shape carries a word no measure of it needs: a `Slots` carries no `head` and the two shapes get two emitted types, because [OP-9] prices a constant-capacity `Slots<T, N>` at its elements plus one word and a constant-capacity `Ring<T, N>` at its elements plus two, so a shared window record with a dead origin word spends memory the writer did not ask for and hides a disagreement with the published ceiling, instead of one window record serving both shapes.

Decision: `grow` [OP-10] is implemented as one allocation, one memmove of the header and the elements, and one free, because the emitted module declares `malloc` and `free` alone and [STOR-7] makes the copying route legal at every value, no judgment depending on the block's address, so the copying form is correct today and a `realloc` form is a pure performance choice with no correctness lever, instead of declaring a third allocator entry before a measurement shows the copy costs anything.

Rejected:
- A fat descriptor beside the owner, the pointer, length and capacity kept in the binding, which is the layout Rust's `Vec` uses: rejected because that layout exists to serve a bounds check at every access, which this language never performs, so its extra words would be kept live through loops that read none of them, a growth would have to write two places, and the boxed and inline forms of one shape would need two emitters.
- A `realloc`-based `grow`: rejected because nothing yet measures the copy as a cost and the route would add a third allocator entry to every emitted module; it is the obvious later change once a measurement asks for it.
- Letting the boxed and inline forms differ in layout so that each is locally convenient: rejected because every window operation, subscript and measure read would then exist twice, and the two copies are exactly where a boundary defect hides.
