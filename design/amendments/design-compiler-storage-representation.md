Node: compiler/storage-representation

Decision: A boxed runtime-capacity shape is thin: `Box<Slots<T>>`, `Box<Ring<T>>` and `Box<Array<T>>` are each one pointer to one allocation whose shape-specific header precedes its elements, in the same header-first representation family as the inline constant-capacity form, with compile-time measures omitted rather than stored, a `Ring` storing `head` beside `len` and an `Array`, whose `len` equals its `cap` [WIN-1], storing that one runtime number once, because the owner and every call or capture that transports it then carry one ABI word, construction and release own one allocation, and the measures and elements move together under the same ownership boundary; the [verified port audit](../../research/investigations/access-effects/PORT-NOTES.md) found that the displaced implementation instead allocated a descriptor and an element block. [OP-4, DIAG-2] discharge every partial access before lowering, so this representation need not carry a separate owner-side measure solely to perform a dynamic bounds check; a source operation that reads a measure still reads its header word. This choice does not assume that unused values in another representation remain live after optimization, instead of a fat owner descriptor that carries the block pointer and one or more measure words beside it.

Decision: The constant-capacity form carries its stored measure header ahead of its elements so that inline and boxed placements use one header ordering and one element-address rule parameterized by the shape's stored header words, because fixed header offsets from the allocation base locate both measures and elements without placement-dependent owner metadata or recovery of the allocation base from a trailing header, and a common header-first representation lets the ordinary measure, subscript, move and release helpers cross the placement boundary without changing the represented shape. Different layouts could share helper implementation through placement-specific adapters; their cost is the additional offset, type and measure-source cases and the evidence needed for both, not two necessarily independent emitters. [OP-9]'s ceiling bounds a shape's size and alignment and fixes no field order, so the header-first arrangement stays under the ceiling the rule computes, instead of keeping elements first inline and header first in the box.

Decision: No shape carries a stored word no measure of it needs: a `Slots` carries no `head` and the two shapes get two emitted types, because [OP-9] prices a constant-capacity `Slots<T, N>` at its elements plus one word and a constant-capacity `Ring<T, N>` at its elements plus two, so a shared physical window record with an origin word changes the owner size and the published ceiling even when an optimizer can eliminate unused SSA values, instead of one physical window record serving both shapes.

Decision: `grow` [OP-10] is implemented as one allocation, one memmove of the header and the elements, and one free, because the emitted module's existing allocation ABI is `malloc` and `free` and [STOR-7] makes the copying route correct at every value, no judgment depending on the block's address. A `realloc` route can remain a later performance alternative without changing the source representation decision, instead of making a third allocator entry part of the selected lowering now.

Rejected:
- A fat descriptor beside the owner, carrying the block pointer and the shape's measure words: rejected because it widens the owner, call and capture ABI beyond one word and separates the owner-side metadata from the common inline header representation. It can own one element allocation, make a measure access direct, let unused local values disappear under optimization, and share lowering helpers with the inline form; those benefits do not provide the selected one-word owner or put the measures and elements under the same in-block representation. Keeping a one-pointer owner around a separately allocated descriptor instead restores the two-allocation/release route the selected layout removes. The [retained comparison](../../research/investigations/access-effects/PORT-NOTES.md#automatic-approval-review-holds-during-integration) leaves relative parallel performance unresolved, so speed is not a ground for this rejection.
- A `realloc`-based `grow`: rejected because the existing `malloc`/memmove/`free` route is representation-complete and target-independent under [STOR-7]. `realloc` may reduce copying for some workloads, but selecting it requires separate performance and target-ABI grounds rather than a correctness claim about this layout.
- Letting the boxed and inline forms differ in layout so that each is locally convenient: rejected because measure sources, header offsets and element-address formulas would become placement-dependent and require evidence across both representations. Shared helpers can limit code duplication, so the cost is the extra representation cases and their validation rather than two necessarily complete emitters.
