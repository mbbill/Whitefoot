Decision: A consuming use of a place invalidates every live reference whose path has that place as a proper prefix, because [REF-2] lists "a proper prefix of `p`'s path is written, moved out of, or released" as the invalidating actions and adds that "a move never re-roots an existing reference: after `let w = move v;`, references formed from `v` are invalid"; the checker named that event and never raised it, so `let p = &v[1_u64]; let w = move v; deref(p)` was accepted, instead of leaving the move to the consumed binding's own liveness, which refuses a later use of `v` and says nothing about a reference formed from it.

Decision: A reference whose path is the consumed place itself is not invalidated by that consume, because [REF-2]'s action is stated over a *proper* prefix and a whole-value move is what the owner's own liveness answers, instead of widening the action to the place itself, which would refuse a reference the rule leaves valid.

Decision: The window an [OP-10] bound-ending operation invalidates references into is the place below the row entry's first part or measure step, so `writes(window.filled)` and `writes(window.len)` both name the window `r`, because [OP-10] states that `take_back`'s and `remove_at`'s `ensures` do not carry `i < r.len` across the call "so such references die there" and the row never names the window bare; comparing the substituted entry itself against a reference path asked whether `r.filled` contains `r[0]`, which no step pair answers, so no reference into the operand ever died, instead of listing the operand places separately, which would duplicate the substitution the entries already carry.

Decision: That invalidation reaches a reference strictly below the window and not one naming the window itself, because [REF-4] forms the bound-carrying references as `&r[i]` and `&r[lo..hi]` and [OP-10] ends exactly those bounds, while a reference to the window names the window whatever its boundary is -- a callee that received `&Slots<T, n>` and called `take_back` through it still holds it -- instead of invalidating every reference the window contains, which refuses the operand of the operation that ran.

Decision: An argument whose operand mode is a reference standing in an `own` parameter position is refused citing TYPE-7 with the mechanical fix `deref(.)`, and every other mode disagreement stays [TYPE-5]'s, because [TYPE-7] says "A reference binding used where a value of its referent type is expected is a hard error citing TYPE-7" and the operand mode is exactly what tells the implicit read from an ordinary mismatch, instead of citing TYPE-5 for both, which sent a writer to the type rule for a spelling the reference rule owns and names the repair for.
