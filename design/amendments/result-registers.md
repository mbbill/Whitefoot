Node: compiler/result-registers

Decision: A stored aggregate result crosses the call boundary as its LLVM first-class value when each scalar leaf of its representation gets its own return register on every admitted target, which allows at most three integer-class words and two floating leaves, and a larger one keeps the caller's destination pointer, because a call the host optimizer does not inline otherwise stores its small result into caller memory that the caller reloads, while beyond that budget LLVM silently returns the value through a hidden pointer after all, or on x86-64 returns a third floating leaf through the x87 stack, which passes through memory and turns a signaling NaN into a quiet one, so the [result-register investigation](../../research/investigations/result-registers/DESIGN.md#demotion-probe) bounds register leaves rather than bytes, instead of a destination for every aggregate, every aggregate by value, a byte bound, `fastcc`, or packing leaves into integer words. The budget is that of x86-64, the smallest among admitted targets, so every target shares one ABI, and a linked definition whose result fits returns the same value through an LLVM definition over its C body.

Decision: A callee constructs a register-returned result in its own `%wf.result` frame slot, exactly where the destination form constructs it in caller storage, and every return branches to one block that loads the slot and returns it, because storage plans, frame qualification and construction then stay those of the destination form, and LLVM's scalar replacement builds one phi per field at that block, whereas separate returns merge into one phi of whole aggregates that LLVM does not break up after inlining, which grew the measured hash-map lookup from 144 to 250 instructions in the [first prototype](../../research/investigations/result-registers/DESIGN.md#lowering), instead of loading the result at each return. A caller stores the returned value into the storage its plan selected, and parameters, their facts and storage plans are unchanged.

Rejected:
- A destination for every stored aggregate: rejected because every call that stays out of line pays a store and a reload of its small result, measured on the surviving hash-map `find`, `insert` and `remove` calls, while a register return pays neither.
- Every stored aggregate by value: rejected because LLVM returns a value with more integer leaves than return registers through a hidden pointer anyway, so larger results gain nothing and their first-class copies are lowered one element at a time, and on x86-64 a third floating leaf would lose a signaling NaN's bits in the x87 stack.
- A 16-byte bound: rejected because four 32-bit fields and a 16-byte array fit it and are still returned through a hidden pointer on x86-64, three 32-bit floats fit it and lose bit-exactness through the x87 stack, and three 64-bit words exceed it yet return in registers.
- A 16-byte bound added to the leaf budget: rejected because it sends 24-byte three-leaf results such as `(u64, Option<u64>)` through memory although they return in registers, and the maintained programs return such results.
- `fastcc` for internal functions: rejected because the destination is an IR parameter that no calling convention removes, and linked C bodies share the callable ABI.
- Packing a result of at most two words into integer registers, as C and Rust do: rejected because it needs per-target coercion rules and packing code at every boundary, while every surviving small result in the maintained programs already fits one register per leaf; reconsider when a surviving result needs more integer leaves than registers.
- A per-target budget, eight integer and eight floating leaves on AArch64: rejected because emitted signatures, linked definitions and their tests would then differ by target, while no maintained program shows a surviving result between the two budgets.
