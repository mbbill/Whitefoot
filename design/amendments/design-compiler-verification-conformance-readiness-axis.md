Node: compiler/verification

Decision: The conformance corpus carries no toolchain-readiness axis: `runnable` is the only manifest status, any other value is a manifest error, and the native adapter's outcomes are pass and fail alone, because a case whose declared verdict this toolchain does not reach is a defect of the toolchain and the corpus is what states the language's required behavior, instead of the `pending` and `xfail` statuses and their `Skip`, `Xfail` and `Xpass` outcomes, which let a case sit outside the gate indefinitely while the manifest still claimed to declare its verdict.

Decision: A case that stops as unsupported without declaring `unsupported` fails, because the corpus has no status for a capability gap now, so an unsupported stop is an ordinary failure rather than a verdict comparison, instead of reporting it as a distinct outcome, which would reintroduce the readiness axis under another name.

Decision: The native conformance adapter reaches `accept` and `reject` through the ordinary compiler front end exactly through complete semantic publication, while `run` and `unsupported` continue through ordinary lowering and selected-target compilation, because [STOR-6] begins after complete source-semantic acceptance and expressly makes an unrepresentable target object a target stop rather than a source verdict, so compiling every accepted source to one incidental host target would turn that host's address domain into an unstated language ceiling; the driver exposes this boundary as a projection of the same borrowed front-end continuation that full compilation consumes, instead of a second checker or an adapter-specific acceptance path.

Rejected:
- Keeping `xfail` for a case whose expectation is the correct specification behavior the toolchain does not yet produce: rejected because that is exactly the defect a gate exists to report, and a non-failing report of it is a gate that stays green while the compiler is wrong.
- Requiring every `accept` and `reject` fixture to pass selected-target qualification and backend emission: rejected because that makes a post-acceptance [STOR-6] stop replace the source verdict the fixture owns; target qualification remains covered by direct compiler tests and by every `run` case that must produce and execute a native image.
- Implementing source conformance with a parser or semantic checker inside the adapter: rejected because the ordinary compiler front end already owns canonical source, resolution, monomorphization and semantic publication, and duplicating any of those judgments would create the second acceptance path the compiler root refuses.
