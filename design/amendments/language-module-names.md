Decision: Exactly one module.wfm inside a module's directory declares the module named by that directory's canonical root-relative path and contains its complete public signatures, types, capabilities, effects, proof clauses, private type support, file-local aliases and a doc entry for each declared function, but no executable function bodies, while .wf definitions have no independent publication switch, because a caller and an implementer need one complete handwritten contract with its description, public-contract review must remain separate from executable body edits, and directory organization must not disagree with a separately declared module name, instead of a thin export list, publication scattered across implementation files, interface fragments, undocumented declarations, executable bodies in the public interface or namespace remapping.

Decision: Top-level declarations and struct fields default to module-private and only module.wfm permits explicit public publication, with no private modifier, no publication through an alias, and public rejected wherever it creates no access route, on a member of a private type or in .wf, because adding representation detail must not implicitly expand the callable or field API and an explicit publication surface supports focused change review, instead of default-public interfaces with private exceptions, different defaults for top-level declarations and struct fields, or modifiers that publish nothing.

Decision: One visibility rule serves executable code and annotations: every name and field selection in a body, contract, invariant, proof premise, effect row or function-kind formal must be accessible where it is written, public signatures, contracts, effect rows and formals close over accessible declarations and published fields, and a field that clients' contracts must name is therefore published, normally as public readonly, because the interface must state what its contracts depend on so that changing such a field is an explicit interface change, and one lookup rule needs no role-dependent exception, instead of letting annotations name private fields of complete interfaces, adding named specification projections, or allowing getter calls in contracts.

Decision: The fixed pkg qualifier denotes the source's owning selected root, with the primary root located by the sole graph and external dependencies retaining explicit names and identities, because one package-oriented spelling works for applications and libraries while library-internal paths must survive an importer's choice of dependency name, instead of user-selected app/lib/project prefixes, interpreting every imported source against the primary root or searching for another graph; external dependency-name binding and library composition are deferred beyond the single-package implementation.

Decision: Each registered module uses only directory/module.wfm for its interface and direct .wf records beside it for its implementation, because a module's own contract and bodies should share one work location without repeating its directory name or maintaining another member-file map, instead of sibling name.wfm files, repeated directory/name.wfm files, multiple supported layout forms, recursive child collection or arbitrary file-to-module assignment.

Decision: Direct implementation files contribute to one shared local declaration inventory, child directories with their own module.wfm define separate path-qualified modules, and directory prefixes without module.wfm are naming locations rather than modules, because files organize one private implementation while a separate complete interface establishes another module boundary, instead of routing internal calls through .wfm, per-file modules, namespace blocks or implicit ancestor ownership.

Decision: External references and field selections resolve to canonical qualified identities and require an edge in the source module's root-graph adjacency row, exposing only the target's public declarations and fields regardless of parent/child or cross-branch relationships, because one dependency authority and explicit name bindings separate permission from API meaning without transitive visibility or family privileges, instead of source dependency lists, implicit access to earlier modules, graph-defined name aliases, mandatory forwarding or ancestry-based dependency rules.

Decision: An initial alias header in a .wfm or .wf file binds module or declaration names from complete accessible root-qualified paths for that file alone, resolving pkg and external names in the source's owning context and preserving original identities and grammar-selected domains without alias chaining, specialization, publication or graph edges, because long names need local abbreviations while shared alias state would couple independent files and make interfaces depend on implementation context, instead of requiring full paths at every use, rebinding pkg, module-wide alias headers, wildcard imports, block aliases or public re-exports.

Decision: Module declaration names are visible throughout their module independently of file and item order while aliases remain file-local and other local binders remain lexical, with constant/group dependencies, finite instantiation and layout separately checked, because shared declarations need stable visibility while a moved definition must still preserve its resolved local abbreviations and inventory membership grants no value or proof, instead of declaration-before-use for non-function module declarations or treating forward visibility as validity.

Decision: Implementations of callables declared in .wfm bind to the interface identity and must have exactly the same normalized signature, bounds, labels, effects and contracts without repeating public, documentation excepted, while type and constant definitions including private support are reused directly from the interface, because an interface edit is a change the implementation must acknowledge in the same written form, a definition that merely refined its declaration could offer callers nothing since they read only the declaration, and repeating a checked header costs little, instead of FN-4-style refinement, unchecked header drift or a separate body-only binding form.

Decision: Every public source-defined struct has one complete definition in .wfm, with explicit public fields and unmarked private fields plus any private supporting types and constants needed to close that definition, while implementation-only types may remain in .wf, because one field list and declaration order avoid duplicated or merged representations while supporting both direct data access and private state, instead of whole-record-only publication, a name-only public declaration with a separate .wf representation, a public projection matched to a second full definition, private field extensions or implicit heap handles; imported capability derivation and executable qualification remain required.

Decision: Struct field operations require access to the fields they explicitly name and retain ordinary ownership, effects, readonly and opaque checks, with construction outside the declaring module requiring every field to be public and not readonly and consuming extraction or destructuring requiring legal treatment of every unbound part including private fields covered by .., because the complete interface representation makes residual obligations checkable without granting private access or leaving a linear resource unconsumed, instead of banning all external extraction from mixed-field types, defaulting private constructor fields, permitting holes or adding separate read/write/move publication modifiers; a consuming field move still kills its whole owner and a private linear remainder requires an operation inside the module.

Decision: All variants of a public enum are public and those of a private enum private, with no per-variant modifier, while payload fields retain field privacy and residual-release obligations, public interface groups publish their complete formal vectors and public bindings publish their complete checked bundles, because a self-contained closed-case or callable-bundle API needs its full shape while private representation can remain behind a public struct, instead of a variant marker that can only repeat its enum's visibility, hidden enum cases requiring a new non-exhaustive matching mechanism, payload privacy that discards linear resources or selectively hidden formal parameters.

Decision: User variants belong to their enum type and constructor qualification retains that owner, while match and result-route labels resolve against their already known owner, because distinct modules and enums must not compete in one global variant inventory, instead of global constructor-name uniqueness or symbol-aware parsing to guess an owner.

Decision: Registered source paths use normalized lowercase module components, reject symlinked ownership and case-folding collisions, and aliases bind complete pkg-qualified identities without introducing private names or fields, because deterministic module membership must not depend on host path resolution or filesystem enumeration, instead of following multiple physical aliases into one source module or giving different hosts different inventories.

Rejected:
- Replaced decisions that top-level functions are visible throughout one closed unit while other declarations retain lexical visibility: rejected because shared per-module inventories make top-level meaning independent of file organization and prevent unrelated module names from colliding while keeping local scope lexical.
- Thin descriptors selecting public definitions whose complete signatures and contracts live only in .wf: rejected because the clarified consumer needs the handwritten .wfm itself to contain the full API; avoiding checked repetition no longer meets that requirement.
- Both a public .wfm declaration and an implementation-side pub/export permission: rejected because interface declaration already owns publication and a second editable visibility switch obscures that authority.
- Treating interface declarations as trusted theorem imports: rejected because declaration correspondence, body proof and current recursive summary availability remain necessary.
- Treating filesystem uniqueness as complete name validation: rejected because declarations across files and child namespace components can still collide, and root/path ambiguity must be diagnosed consistently rather than resolved by host lookup order.
- Implicitly inheriting interface aliases in implementation files: rejected because a private abbreviation edit would then affect several files and a file's written names would require another file's local context.
- Letting contracts, invariants, proof premises and effect rows name private fields of a complete interface while executable code cannot: rejected because clients would depend on fields the interface does not mark as API and resolution would need a role-dependent rule; publishing the field states the dependency where the interface is reviewed.
- Named specification projections and effect regions that clients use instead of field paths: rejected because they only keep client source unchanged when a published representation changes, which the module goals do not require; reopen for a type that must publish one quantity without publishing the storage that holds it.
- Definitions that refine their declarations under FN-4: rejected because callers read only the declaration and gain nothing from a weaker requirement, stronger guarantee or narrower row, while an interface edit must reach its implementation explicitly.
- A public marker on each variant of an enum: rejected because it can only repeat the enum's own visibility.
