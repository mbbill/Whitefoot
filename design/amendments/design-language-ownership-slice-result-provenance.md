Node: language/ownership/slice-result-provenance

Decision: This node is retired with no node text after the change, the node file being deleted, because candidate x1 removes the slice value whose origins this node tracked, and what survives moves to two proposed nodes in the same revision, language/ownership/range-reference, which decides the replacement range form and how two ranges are separated, and language/ownership/no-stored-references, which carries the prohibition this node's boundary decision enforced for slices alone.

Rejected:
- Retired decision, a direct slice carries a finite static set of ultimate storage origins, direct formation creates a singleton, formation over a parent view preserves every parent origin and appends the child's relative range, every operation preserves the complete set, and a call computes its result's origin set from signatures alone: rejected because x1 makes a range an ordinary path rather than a value, Rule 2 listing `[lo..hi]` (range) as a path step alongside fields, `deref`, index, and payload steps, so a range reference's origin is the path it is written as, while Rule 4 with Rule 15 forbid returning a reference at all, so no call ever computes a result origin set; the successor decision on how two ranges are separated is in language/ownership/range-reference.
- Retired decision, the boundary is direct slices only, with generic arguments that hide loans or providers and stored slice content rejected rather than approximated: rejected because x1 Rule 1 makes the same prohibition universal and type-level instead of a checker boundary, stating "Every struct, enum, tuple, `Array`, `Slots`, `Ring`, `Box`, and generic instantiation holds only owned values. This is recursive and closed under wrapping: there is no type parameter, wrapper, or variant payload through which a reference can be stored", with `Option<&T>` "rejected, whatever T is", so there is no hiding position left to approximate or refuse case by case, and the surviving prohibition is normalized upward into the proposed node language/ownership/no-stored-references.
- Retired refusal of an explicit return-origin annotation, an alternative inside a removed mechanism: rejected because no reference is returned (x1 Rule 4), so there is no return origin to annotate.
- Retired refusal of a body-derived exact origin summary, an alternative inside a removed mechanism: rejected because no reference is returned either, and x1 Rule 10 keeps the signature-complete caller boundary by substituting actual argument paths into the callee's declared effect row, stating "Recursion is checked through contracts, never by unfolding bodies".
- Retired refusal of per-leaf origin metadata inside generic or stored values, an alternative inside a removed mechanism: rejected because x1 Rule 1 forbids the stored reference outright rather than tracking it.
- Retired refusal of a fresh call or arena token authorizing returned arena storage, an alternative inside a removed mechanism: rejected because x1 Rule 16 makes an arena usage rather than a type, stating "A pool is a `Slots` (or `Box<Slots<T>>`) plus indices used as handles; an arena is the same storage used with `place_back` as allocation and `truncate(0)` as reset", so there is no arena supplier whose storage a returned view would have to be authorized against.
