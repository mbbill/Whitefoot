Node: language/parallelism/loop-permission

Decision: A counted loop's permission admits at most one accumulator combined by one operation from a fixed associative set, and enclosing storage writes use either one proved constant-coefficient affine element map per resolved root or a proved disjoint subrange of an adjacent stride partition with loop-invariant runtime stride and base, consuming retained source proofs, because reductions delivered the measured parallel win and runtime-width stencil rows and block-local workspaces need ordinary helper calls on ranges whose independence does not depend on worker count, and because the admitted forms are unchanged and x1 affirms them in Rule 13, "The existing counted-loop forms (per-element maps, adjacent ranges passed to a helper, admitted reductions) keep their permissions, with the ranges written as range references", while nothing else in this line is replaced, the single accumulator, the fixed associative operation set, the one affine map per resolved root, the loop-invariant runtime stride and base, the denial of whole-source access and of incompatible maps, and the refusal of arbitrary scatter all being outside x1, which neither names them nor supplies a different answer, instead of unbounded multi-accumulator reductions, limiting every enclosing write to one element map, or general index search. Whole-source accesses to mapped or assigned storage and incompatible maps of overlapping storage still deny permission; arbitrary scatter is not admitted. The range argument and its limits are in research/investigations/range-loans/DESIGN.md.

Decision: An iteration's partition of enclosing storage is a range reference formed from that storage and passed to the helper as an ordinary argument, and cross-iteration independence is the ordinary disjointness of two ranges on one storage, because a range reference is a path like every other path, so one disjointness argument then serves a call's two arguments, two adjacent statements, and two iterations of a loop, and because this decision is added from x1 Rule 13's "with the ranges written as range references" together with Rule 7, which gives the form and its type, "A range reference `&x[lo..hi]` has the parameter type `&[T]`: a reference kind with measure `len`, formed only from an indexable or from another range reference, never a stored value", and the worked helper `fn kernel(part: &[Int]) writes(part)`, while the disjointness argument itself is unchanged in substance, x1 Rule 13 judging ranges "using the same path-overlap and index/range-disjointness judgment as Rule 10", which is the same half-open non-overlap argument the current rule makes for `[s*i+b, s*i+b+s)`, instead of an exclusive view descriptor whose loan is a mechanism only the loop rule uses.

Rejected:
- Replaced wording of the first decision, "a proved exclusive subrange" of an adjacent stride partition: rejected because x1 removes exclusive loans and permission markers on references (Rule 2: "There is no `uniq` or `mut` marker on references"; "Not in this candidate": "`&uniq`, `&mut`, or any permission marker on references", "slice types as first-class values"), leaving disjointness of paths as the whole content of the condition, so the line now reads "a proved disjoint subrange" and only those two words change with the mechanism underneath them.
- Replaced vehicle for an iteration's partition, the exclusive `[VIEW-2]` formation whose endpoint domain is retained that the current rule uses: rejected because the range reference of x1 Rule 7 carries the same partition as an ordinary path and is judged by the ordinary disjointness rules, which changes no loop that is admitted.
