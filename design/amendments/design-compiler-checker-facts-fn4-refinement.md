Decision: [FN-4]'s contract refinement uses the same finite S4 premise establishment and MSR-4/AUTO implication judgment as an ordinary call requirement. Each query is declaration-local: it alpha-renames the contract datums into distinct synthetic entry-parameter, exit-parameter, and result identities, installs only the selected side's clauses as hypothetical premises, and asks the shared entailment engine to discharge one goal. The query publishes no function summary and lends no premise to either callable body, whose own FN-9 proof remains independent. Each accepted query is retained at its binding or raw-argument site with its premise-clause and goal-clause identities, disposition, selected root, and an isolated term/goal/derivation inventory; dense identities never cross between queries, because this boundary keeps FN-4 on the specification-fixed proof vocabulary and limits while satisfying DIAG-2's retained-check requirement; it does not introduce a second solver or an implication shortcut.

Decision: For every actual `requires` goal, the formal `requires` set is the premise set. For a formal unrouted `ensures` goal, the premise set is every actual unrouted clause; for a formal routed goal, it is every actual unrouted clause plus clauses on that exact result ordinal, variant, and field route, because this is the set available whenever the promise is selected: an unrouted relation holds at every normal return, while a routed one cannot support another route. The synthetic result identity at a routed ordinal has the selected payload type rather than the declared whole-Result type, and all other result ordinals retain their declared types. This is the stated weaker-precondition/stronger-postcondition substitution rule: every caller that satisfies the interface can satisfy the implementation, and every relation promised through the interface follows from what the implementation publishes. Entry, exit, and result identities remain distinct even when they have the same selected type, preventing an exit-state relation from satisfying an entry-state promise merely by spelling.

Decision: A bound call retains two distinct identities: the actual `FunctionId` is its direct executable target, while its instantiated formal signature, row, requirements and postconditions are its acceptance and publication boundary [FN-5], because direct-call lowering must preserve the selected implementation while no stronger actual contract may become an undeclared caller-visible interface. Immediate call judgments such as [OP-12] inspect that formal boundary, and the checked call retains the formal requirement occurrences instead of recovering contracts from the executable target later. Formal postcondition publication likewise cites both the actual's verified [FN-9] relation and the accepted [FN-4] implication without merging their query-local derivation identities.

Rejected:
- Retaining premise membership as the permanent FN-4 check: rejected because it safely under-approximated the language while the declaration proof context was absent, but rejects fixed-affine implications the current rule expressly admits, such as `x <= 10` establishing `x <= 11`.
- Keeping structural equality of the two clause sets until the proof context is wired: rejected because [FN-4] newly states that a supplied function *may* refine rather than match, so equality denies every refinement the language admits, which is the case the rule was amended for.
- Adding a separate declaration-contract implication solver: rejected because the existing S4/MSR-4/AUTO engine already defines the complete admitted family, and a parallel implementation could disagree on acceptance or termination limits.
- Reusing one synthetic identity for entry parameters, exit parameters, or results of the same type: rejected because it would prove false refinements across semantically distinct contract states.
- Recovering a bound call's contracts from its executable `FunctionId`: rejected because that selects the actual's stronger contract instead of the authoritative instantiated formal and makes acceptance depend on an implementation detail [FN-5].
