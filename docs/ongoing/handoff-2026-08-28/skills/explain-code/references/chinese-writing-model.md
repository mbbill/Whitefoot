## 1. 读者应该获得什么体验

把文章写成一位熟悉主题的技术作者在带读者逐步理解机制。假设读者有判断力，但不假设他已经知道本文要讲的概念。

读者应该随时知道三件事：这一节在回答什么问题，例子与机制有什么关系，当前结论在哪些条件下成立。

文章可以有作者的判断和取舍，但不要把个性写成口头禅。作者的存在应体现在选择了哪个例子、为什么跳过某些细节、哪些地方属于推测，以及为什么增加一个可选章节。

## 2. 文章怎样展开

### 开头

先给读者一个可以抓住的问题，再引出概念。常用入口包括：

- 最近出现的一项功能或接口，让人自然追问它如何实现；
- 一段简短历史，说明问题为什么会发展到今天；
- 一个读者可能遇到的现象，而背后机制并不直观；
- 一个需要权衡的实际问题，例如速度与成本、内存与计算量。

两三段内说明本文要讲什么。需要提到前置文章时，把它写成可选材料，本文仍应独立成立。

### 递进顺序

长篇技术文章通常按以下顺序展开：

1. 简要定义；
2. 必要背景；
3. 直观机制；
4. 完整例子；
5. 实现细节；
6. 不同方案或案例；
7. 对比与权衡；
8. 总结和开放问题。

不要机械套用八节。主题简单时可以合并，但必须保留“先建立共同理解，再进入具体差异”的方向。

### 章节

长文使用 `## 1.`、`### 2.1` 这类编号。标题直接说明这一节的任务，例如：

- `## 1. 先定义什么是推测解码`
- `## 2. 普通自回归生成为什么慢`
- `### 5.1 延迟下降不等于计算量下降`
- `## 7. 可选部分：几种实现方式`
- `## 8. 总结`

章节开头承接前文，或直接提出本节要回答的问题。复杂章节结束后，用一小段收束核心结论，不要写口号。

### 可选深度

先完成主线，再增加专门细节。某部分不影响理解核心结论时，可以明确告诉读者“只关心工作原理，可以在这里结束；下面讨论实现差异”。

## 3. 中文句子怎样写自然

### 先找动作

翻译腔常把英文动词变成中文抽象名词。改写时先找出真正执行动作的人或系统，再把动作写出来。

不自然：

> 该方案的替换决策发生在性能验证完成之后。

自然：

> 团队完成性能测试后，换掉了这个方案。

不自然：

> 这一结构为设计理由提供了一个可检查的位置。

自然：

> 这套结构让设计理由可以长期保存，也能接受检查。

### 给句子明确主语

中文可以省略已经明确的主语，但不能连续依靠抽象指代维持句子。

少用：`这一点`、`这种方式`、`这些结果`、`该机制`。能够直接写出 `linter`、`训练过程`、`团队`、`目标模型` 时，就不要让读者回头寻找指代。

不自然：

> 约束塑造了当前设计。

自然：

> 正是这些约束，让团队选择了当前方案。

### 使用中文里的常见搭配

优先写：

- “按时间排列”，不要写“以时间为主键”；
- “当前方案”，不要写“现行方案”；
- “换掉方案”或“更换设计”，不要反复写“重新决策”；
- “回溯 Git 历史”，不要写“沿 Git 历史向前追溯”；
- “让人信以为真”，不要写“产生错误信心”；
- “官方没有公布具体实现”，不要写“实现细节没有被共享”；
- “这个名字借用了……的类比”，不要写“这个名字描述了过程的形状”；
- “结果只适用于这个基准”，不要写“结论是 benchmark-specific 的”。

### 控制句子长度

一句话只承担一个主要判断。条件、机制和结果同时出现时，先保留最紧密的一组，其余拆开。

不要为了显得有文采而省略条件，也不要把所有限定词塞进一个长句。中文技术文章的流畅，来自清楚的先后关系，不来自少用句号。

### 避免假中文

以下表达通常需要重写：

- 不必要的“进行……的实现”“完成……的构建”；
- 连续多个“的”组成的名词串；
- “赋能、抓手、闭环、沉淀、链路、方法论”等商业黑话；
- “不仅是……更是……”“值得注意的是”“从某种意义上说”等机械句式；
- 为了显得亲切而频繁使用“我们不妨”“大家都知道”“顺便说一句”；
- 把英文段落的每个连接词逐一翻成“然而、因此、换句话说”。

## 4. 段落怎样衔接

每个段落通常只做一件事：定义概念、解释机制、解读图表、补充限制、连接前后内容或给出例子。

可以使用以下自然衔接，但不要机械重复：

- “先看一个例子。”
- “问题出在这里。”
- “再来看目标模型怎样验证这些结果。”
- “回到前面的缓存例子。”
- “这里需要区分两件事。”
- “到这里，核心机制已经完整了。”
- “下面再讨论几种实际实现。”

单句段落可以强调转折或边界，但不要连续堆叠。相邻两句共同解释一个事实时，放在同一段通常更自然。

## 5. 术语与中英文混排

### 首次出现

术语首次出现时，根据读者背景选择以下形式：

- `检索增强生成（Retrieval-Augmented Generation，RAG）`
- `键值缓存（KV cache）`
- `推演（rollout）`

后文统一使用一个名称，不要在中文、英文全称和缩写之间来回切换。

### 保留英文的情况

以下内容保留原样：

- 命令、代码、API、配置项和字段名；
- 文件名、目录名、模型名、库名和协议名；
- 团队或目标读者通常直接使用的术语。

实际格式字段写作 `Facts`、`Moves`、`.alt/`。正文说明可以写“事实记录”“变更记录”“备选方案目录”。不要为了中文化而让说明与真实文件对不上。

### 优先用中文的情况

普通说明中优先使用已经稳定的中文表达，例如“基准测试”“提交记录”“代码差异”“当前节点”“训练阶段”“推理阶段”。

文本图中的说明性标签也要翻译；只有标识符、字段名和代码保持英文。

### 排版

- 中文与英文、数字之间留一个半角空格。
- 中文标点放在行内代码之外。
- 英文缩写不重复复数形式，例如“多份 ADR”，不写“ADRs”。
- 标题中的代码标识使用反引号，不用中文引号代替。

## 6. 例子、图表和公式

例子不是装饰，而是让读者实际走一遍机制。尽量在后文继续使用同一个例子，减少读者重新建立背景的成本。

每个重要图表按三步处理：

1. 出现前说明要观察什么；
2. 给出图、表、公式或代码；
3. 出现后解释结论和限制。

纯 Markdown 可以使用 ASCII 图、对比表、短公式、带注释的代码或前后对比。长文中的主要视觉材料可以写成“图 1”，短 README 不必强行编号。

公式之后解释每个变量，并把公式重新接回具体例子。不要让推导在公式结束处突然中断。

### 控制代码篇幅

先用最小例子讲机制，再用代码说明怎样落地。完整程序只有在读者确实需要复现时才加入。

如果代码超过约 40 行，先问三个问题：删掉初始化和样板代码后，核心机制还剩什么；能否用十几行关键片段表达；完整程序是否更适合放在可选部分或单独文件中。

代码出现后，必须指出关键行、输入、输出和读者应观察的现象。不能用“代码如下”代替讲解。

比较多个系统时，先说明共同框架，再逐一指出每种实现改了哪些环节。最后用一张表或一段话收束差异。

## 7. 事实、推断与限制

### 已公开事实

资料、代码或论文明确说明的内容，直接指出来源主体：

- “技术报告使用了……”
- “聊天模板会插入……”
- “实现会在达到预算后停止生成……”

### 推断

需要推断时，说明证据和不确定性：

- “一种可能的实现是……”
- “从公开的聊天模板看，这个设置很可能会……”
- “这说明……，但报告没有给出两者的具体对应关系。”

不要用“可能”掩盖没有依据的猜测。

### 限制

把限制放在结论旁边：

- 训练细节没有公开；
- 报告分别描述了两个阶段，却没有说明它们如何连接；
- 结果只适用于当前基准和配置；
- API 价格不等于原始计算量；
- 相同标签背后可能采用不同机制。

不要把所有限制推到文章末尾统一处理。

## 8. 常见失败模式

### 翻译稿

表现：语法正确，但抽象名词多、主语模糊、搭配不像中文；章节之间依赖“然而、因此、换句话说”连接。

修改：找出真正的动作和主语；使用中文常见搭配；必要时重新断句，不要逐句对应英文。

### 产品文案

表现：强调“革新、赋能、强大”，却不解释机制、证据和代价。

修改：把承诺换成工作方式、适用条件、测量结果和限制。

### 学术摘要

表现：一句话包含背景、方法、结果和意义；引用替代了解释；被动句过多。

修改：先用普通中文讲清机制，再补术语、公式和来源。

### 参考手册

表现：定义和命令连续罗列，读者看不到为什么需要它们，也不知道结果说明什么。

修改：恢复核心问题、完整例子和命令后的解释。

### 代码吞掉讲解

表现：为了提供“完整例子”，正文出现大段初始化、样板代码和测量框架；读者需要先读懂 API，才能理解机制。

修改：先换成最小概念例子或数据流图，只保留决定机制的代码行。完整可运行版本移到可选部分。

### 匿名教材

表现：内容正确、结构整齐，但每节语气完全相同，没有作者的范围选择、判断或阅读引导。

修改：增加少量真实的作者导航，例如说明为什么选择这个例子、哪一节可以跳过、哪里属于推断。不要增加闲聊。

### 表面模仿

表现：频繁写“先说结论”“这里要注意”“换句话说”，却没有真正降低理解成本。

修改：只保留承担讲解任务的过渡句。

### 过度压缩

表现：定义之后直接给结论，隐含必要背景，或列出多个机制却不完整讲解任何一个。

修改：补上最少的背景，并完整走通一个例子。

### 过度解释

表现：同一结论反复改写却没有增加信息，支线淹没主线。

修改：只有在换用图、例子或更精确边界时才重述。

## 9. 终稿检查表

### 结构

- 开头是否给出具体问题，并在两三段内说明文章主题？
- 不阅读其他材料，能否理解本文？
- 每一节是否为下一节补足了必要信息？
- 专门细节是否放在核心机制之后？

### 讲解

- 核心术语是否用普通中文定义？
- 是否有一个完整、具体的例子？
- 例子是否直接解释机制，而不是被 API 样板代码淹没？
- 每个重要图表是否都得到引入和解读？
- 稠密章节之后是否有必要的收束？

### 中文

- 句子是否写清主语和动作？
- 是否存在英文语序、抽象名词串或生硬搭配？
- 是否有更自然的中文动词可以替代“进行、实现、完成、提供”？
- 中英文术语是否统一，排版是否规范？
- 文本图中的说明性标签是否已经翻译？

### 技术诚实

- 是否区分资料明确写出的事实与作者推断？
- 不公开的细节和只适用于特定基准的结论，是否就近说明？
- 结论是否保留原有条件，没有为了流畅而说得更绝对？

### 文风

- 文章是否像中文技术作者直接完成，而不是英文翻译稿？
- 作者导航是否来自真实选择和判断，而不是口头禅？
- 是否避开产品宣传、学术摘要、参考手册和匿名教材的语气？

任何一项答案为“否”，都先修改，再交稿。
