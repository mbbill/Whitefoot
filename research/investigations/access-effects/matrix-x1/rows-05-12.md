Derived against `CANDIDATE-X1.md` (frozen 2026-09-18). Rule 5 is `Box<T>` on the
single global heap, affine, `*b` a path. Rule 12 is joins intersect facts, union

Cells below follow the rule file's "Protocol for a derivation cell". Only runtime

### 5-5: Box inside Box: relinking an owned structure

Question: can a structure whose edges are owning `Box` values be relinked in
place (rotation, splice, reversal), which is the case where one Box must be
moved out of another Box's field?

Strongest program:
```text
struct Node { key: Int, left: Option<Box<Node>>, right: Option<Box<Node>> }

// the standard three-edge right rotation on an owned subtree
fn rotate_right(root: own Box<Node>) -> own Box<Node>
{
    l = move (*root).left          // (1) move a Box out of a field of a heap object
    (*root).left = move (*l).right // (2)
    (*l).right   = move root       // (3)
    return l
}
```

Ordinary program (differs materially: no move-out is needed):
```text
// bottom-up construction: every statement writes into a field or moves a whole local
left  = Box::new(Node { key: 1, left: None, right: None })?
right = Box::new(Node { key: 3, left: None, right: None })?
root  = Box::new(Node { key: 2, left: Some(move left), right: Some(move right) })?
```

Trace:
- Rule 2 admits the paths: "A path starts at a local variable or a parameter and
  continues through fields, `*` (Box content), `[i]` (index, Rule 7), or
  `[lo..hi]` (range, Rule 7)." Rule 5 confirms "`*b` is a path (Rule 2)", so
  `(*root).left` is a path.
- Statement (1) is a move out of that path. Rule 6's closing paragraph: "There is
  no `take` operation and no partial move out of any place: the only ways to move
  a value out of storage are consuming a whole local (`move x`), the window
  operations, and the atomic update." `(*root).left` is not a whole local, it is
  not a `DynBox` window operation, and the atomic update is written in Rule 6 only
  as `buf[k] = f(buf[k])` on an indexed slot. Under this sentence statement (1) is
  rejected, and so is statement (2).
- Rule 12 states the same prohibition independently: "No place is ever partially
  moved: every path is either wholly present or the program cannot name it."
- But Rule 8's own worked example performs exactly this move: `fn use_it(c: own
  Conn) { ...; close(move c.f) }   // consuming the struct as a whole and closing
  its File is required`. `c.f` is a field of a place, not a whole local, and the
  comment presents the move as required rather than rejected. If that example is
  normative, statements (1) and (2) are admitted and `rotate_right` is accepted
  verbatim, at zero cost. If the Rule 6 sentence is normative, no owning-Box
  structure can ever be relinked, and the ordinary program above is the only shape
  a Box structure can have: build it once, never restructure it.
- A second, independent ambiguity blocks the same program: Rule 2's path grammar
  has no selector for an enum variant payload, yet Rule 1 blesses `struct Node {
  value: Int, left: Option<Box<Node>> }` and Rule 12 blesses
  `slots: DynBox<Option<Entry>>`. There is no stated way to name the `Box` inside
  the `Some` without moving the whole `Option`, which is the same partial move.
- Assigning *into* a field is not affected: statement (3) writes a whole local
  into `(*l).right`, which is an ordinary write, and Rule 5's own line
  `holder.child = move c   // a Box in a struct field: ordinary ownership`
  confirms it.

Rewrite and cost: under the strict (Rule 6 / Rule 12) reading the structure moves
to a `DynBox` arena with `u64` handles (Rule 16). Rotation becomes three field
writes through slot references, which is legal because Rule 3 says "Writing the
storage at p's path or below it (a content write) does not invalidate p", so no
move-out occurs at all. Cost against the C++ pointer rotation: each of the three
slot references needs `h < len_of(a.buf)` and the handles come out of node fields,
so Rule 11's ban on quantified facts leaves no invariant to discharge them and
Rule 7 forces the test - three compares plus three predictable branches plus three
writer-supplied unreachable arms per rotation, and the loss of parallel allocation
recorded in 5-16. Under the permissive (Rule 8 example) reading the rewrite is
"none needed" and the cost is zero.

Rules consistent: no - Rule 6's "no partial move out of any place" and Rule 12's
"wholly present or the program cannot name it" contradict Rule 8's `move c.f`
example.   Task achievable: rewrite - only through the Rule 16 arena, at a compare
per relinked edge, unless the permissive reading holds.
Depends on: Rule 1, Rule 2, Rule 3, Rule 6, Rule 8, Rule 12, Rule 16 (provisional,
for the rewrite).
Verdict: undecided-rule-gap

### 5-6: Box inside DynBox: a stable object in a moving window

Question: does putting a `Box` in a `DynBox` slot preserve a reference to the heap
object across container growth, the way `vector<unique_ptr<T>>` preserves a `T*`
in C++?

Strongest program:
```text
buf: DynBox<Box<Node>>              // the C++ "stable element address" idiom
k = pick(...)                        // runtime, data-determined
p = &(*(buf[k])).value               // path buf -> buf[k] -> *(buf[k]) -> .value
for i in 0..m {
    push(&buf, Box::new(mk(i))?)     // library push (Rule 6): may replace the block; writes(buf)
    *p = *p + 1                      // rejected from the first iteration on
}
```

Trace:
- Forming `&buf[k]` requires `k < len_of(buf)` (Rule 7: "Reading `buf[k]` or
  forming `&buf[k]` requires the fact `k < len_of(buf)`"), and Rule 2 lets the path
  continue through `*` into the heap object.
- Rule 6 defines the library growth: "a DynBox plus a `push` that, when
  `len_of == cap_of`, allocates a larger DynBox, moves `[0, len_of)` across, and
  replaces the old one", declared `writes(buf)`.
- Rule 3: validity is "invalidated when any proper prefix of p's path is written,
  moved out of, replaced, or freed, by a statement or by a call". `buf` is a proper
  prefix of `*(buf[k]).value`, so `p` is invalid after the push and `*p` is
  rejected. Rule 10 clause 3 gives the same result at the call.
- The decisive point is that Rule 5's address stability buys nothing here: Rule 5's
  own line `c = move b   // p invalid (Rule 3); the heap object did not move`
  already says invalidation is path-shaped, not address-shaped. The `Node` really
  does stay put; the rule still rejects the reference.

Rewrite and cost: two rewrites, and which one is free depends on whether element
order is observable.
1. Re-form the reference inside the loop (`p = &(*(buf[k])).value` after each
   push). Cost against C++: one bounds compare (often free - see 12-14, where Rule
   12's "facts about indices below n survive" keeps `k < len_of` across the push),
   one load of the block base, one load of the `Box` pointer out of slot `k`, every
   iteration, where C++ holds one register. Two dependent loads per use is a real
   cost in a pointer-chasing loop.
2. Take the `Box` out of the window first: `b = swap_remove(&buf, k)` is a
   sanctioned move out of storage (Rule 6 lists "the window operations"), `b` is
   then a local root, and `p = &(*b).value` has no prefix inside `buf`, so the
   pushes cannot invalidate it. Put it back with `push_nogrow(&buf, move b)`
   afterwards. Cost: O(1) - one slot load, one slot store, one length decrement at
   entry and the mirror at exit; zero per-iteration cost. But `swap_remove`
   permutes the container (the last element lands in slot `k`), so every other
   handle into `buf` changes meaning. There is no order-preserving take-out: Rule 6
   says "Assigning `buf[k] = x` where the old value is affine releases the old
   value", which destroys the node instead of yielding it, and the atomic update
   `buf[k] = f(buf[k])` cannot hand the old value back to the caller because Rule
   15 makes `f`'s committed result its only output.

Rules consistent: yes - Rule 3's prefix rule and Rule 6's window operations give a
coherent answer.   Task achievable: rewrite - free when element order is not
observable (swap out the Box), otherwise two loads and a compare per access.
Depends on: Rule 2, Rule 3, Rule 6, Rule 7, Rule 10, Rule 15, Rule 12 (for the
surviving bound).
Verdict: rejected-real-cost

### 5-7: Indexing through a Box path, and measure facts across a move

Question: does routing an indexable thing through a `Box` change what must be
proved, and what happens to a runtime measure fact when the `Box` is moved?

Strongest program:
```text
b: Box<DynBox<f64>>                 // a heap buffer behind an owning pointer
n = len_of(*b)
if mid <= n {
    par { kernel(&(*b)[0..mid], &src); kernel(&(*b)[mid..n], &src) }
}
h = Holder { data: move b }          // ownership transfer into an aggregate (Rule 5)
use((*(h.data))[mid])                // needs mid < len_of(*(h.data))
```

Trace:
- Rule 7: "`Box<array<T, N>>` is indexed through the path `(*b)[i]` and is not a
  separate case", and its indexable list includes "a range reference into either".
  A `DynBox` behind a `Box` is reached the same way, so `&(*b)[lo..hi]` needs only
  Rule 7's `lo <= hi <= len_of(*b)`, discharged by the written test plus
  `n = len_of(*b)`.
- The `par` is accepted by Rule 13's "disjoint ranges" judgment; the Box hop adds
  no obligation and no instruction - `(*b)[i]` is one extra dependent load of the
  block pointer, exactly what the C++ `unique_ptr<vector<double>>` form pays.
- `h = Holder { data: move b }` consumes `b`. Rule 12: "every path is either
  wholly present or the program cannot name it", so `*b` can no longer be named and
  the fact `len_of(*b) == n` is unusable. Rule 11 lists the ways facts are
  established (measure comparisons, refinement facts from a dominating branch,
  loop invariants, `use` steps, callee contracts); none of them transfers a fact
  from `b` to `h.data` across a move, and Rule 3's analogous sentence for
  references is explicit that nothing is re-rooted: "A move never re-roots an
  existing reference". So `mid < len_of(*(h.data))` must be re-established by
  Rule 7's escape: "when the proof is unavailable the program tests the measure,
  which is ordinary data."
- The contrast worth recording: for `Box<array<T, N>>` the bound is the constant
  `N`, a property of the type rather than of a path, so no move can invalidate it
  and the same program costs nothing.

Rewrite and cost: re-test the measure once after the transfer, or perform the
transfer before establishing the fact. Cost against unchecked C++: one load of the
header length, one compare, one not-taken branch, per ownership transfer - not per
access, because the re-established fact then covers every later index. Against
safe Rust, which bounds-checks the index itself, the cost is zero.

Rules consistent: yes.   Task achievable: yes - the strong program (parallel
ranges through a Box) is accepted outright; only the post-transfer bound needs one
compare.
Depends on: Rule 2, Rule 3, Rule 11, Rule 12, Rule 13.
Verdict: accepted-fine

### 5-8: Box of a linear value: unboxing it and surviving allocation failure

Question: can a linear resource live behind a `Box`, given that Rule 8 requires it
to be consumed explicitly on every exit path?

Strongest program:
```text
linear type File;   fn close(f: own File)
struct Conn { f: File, n: u64 }          // linear by containment (Rule 8)

fn stage(c: own Conn) -> Result<u64, Err>
{
    b = Box::new(move c)?                // (1) allocation may fail
    if bad(&(*b).n) { close(move (*b).f); return Err(E) }   // (2) early exit must discharge
    close(move (*b).f)                                       // (3) normal exit
    Ok((*b).n)
}
```

Trace:
- Rule 8 states both the obligation and the intent that `Box` can carry it:
  "Linear values must be consumed by an explicit operation on every exit path; the
  compiler never releases them", and in the same rule's examples, `Box<File>
  // linear: must be taken apart and its File closed`.
- Statements (2) and (3) are the "taking apart": a move out of `(*b).f`. Rule 6
  forbids it - "There is no `take` operation and no partial move out of any place:
  the only ways to move a value out of storage are consuming a whole local
  (`move x`), the window operations, and the atomic update" - and Rule 12 repeats
  it as "No place is ever partially moved". `move b` consumes the Box as a whole,
  but no rule says what that does to a linear payload; Rule 5 says "at scope exit
  the compiler releases its memory recursively (Rule 8); there are no destructors",
  and Rule 8 says the compiler never releases linear values, so whole-Box
  consumption cannot be the discharge either. Rule 8's own `close(move c.f)`
  example performs the forbidden partial move on a struct local, so the rule text
  supports both answers and settles neither for `Box`.
- Statement (1) is a second, independent gap. Rule 5 gives the allocation
  signature as `b = Box::new(Node { ... })?   // allocation can fail:
  Result<Box<Node>, Oom>`, and Rule 14 says "Allocation returns a `Result` and
  never traps." On the `Err(Oom)` edge the payload that was moved into `Box::new`
  appears nowhere in the result, so the linear `Conn` is lost on that edge, which
  Rule 8 forbids. No rule gives `Box::new` a value-returning error arm. Read
  strictly, a linear value can never be put into a `Box` at all, which contradicts
  Rule 8's assertion that `Box<File>` exists and must be taken apart.

Rewrite and cost: keep linear resources in a pre-reserved `DynBox` pool instead of
individual Boxes. `push_nogrow` has no `Result` (Rule 6 gives it only
`requires len_of(buf) < cap_of(buf)`), so no failure edge can swallow the value;
removal uses `pop` or `swap_remove`, which Rule 6 lists among the sanctioned moves
out of storage and which yield `own Conn` for `close`. Rule 6's scope-exit
requirement - "A DynBox whose element type is linear is itself linear (Rule 8) and
must be truncated to zero by the program before it can go out of scope" - is met by
draining first: `while len_of(buf) > 0 { close_conn(pop(&buf)) }`, after which the
truncation is a no-op. Cost against C++ `vector<Conn>` with destructors, or Rust
`Vec<Conn>` with `Drop`: the drain loop emits the same loads, calls and length
decrements that RAII emits - zero. The reservation must be sized up front, which
is the one real constraint, not a per-operation cost.

Rules consistent: no - Rule 8 requires `Box<File>` to be taken apart while Rule 6
and Rule 12 forbid the only operation that could take it apart, and Rule 14's
allocation signature drops a linear payload on the failure edge.
Task achievable: rewrite - a pre-reserved pool carries linear resources at zero
runtime cost, but `Box` of a linear value is unresolved.
Depends on: Rule 5, Rule 6, Rule 8, Rule 12, Rule 14, Rule 15.
Verdict: undecided-rule-gap

### 5-9: Effect rows over Box paths; two Boxes never alias

Question: can an effect row name what a callee does to a heap object and its
subtrees precisely enough that the caller keeps its unrelated references, and what
does Box ownership contribute to the disjointness judgment?

Strongest program:
```text
struct Node { value: Int, l: Box<Node>, r: Box<Node> }        // non-optional children: see 5-5 on Option payloads

fn rebuild_left(n: &Node, seed: Int)  writes(n.l), reads(n.value)   // frees the old left subtree and installs a new one
fn merge(a: &Node, b: &Node)          writes(a), writes(b)

p = &(*((*root).r)).value        // a reference into the right subtree
rebuild_left(&*root, 7)          // substituted write path: (*root).l
use(p)                           // still valid
merge(&*b1, &*b2)                // b1, b2 are distinct Box locals
```

Trace:
- Rule 9 admits the rows: "An effect row lists `reads(path)` and `writes(path)`
  where each path starts at a reference parameter and may continue through fields,
  `*`, and whole-index or range positions supplied as arguments", and "member paths
  are allowed" per its `update` example. Freeing a subtree is expressible because
  "`writes` covers writing, replacing, moving out of, and freeing the storage at
  the path."
- `p` survives the call: Rule 10 clause 3 invalidates only "A live reference
  outside the call whose path has a proper prefix among the call's write paths".
  The write path is `(*root).l`; `p`'s prefixes are `root`, `*root`, `(*root).r`,
  `*((*root).r)`. `(*root).l` is not among them, so `p` stays valid, and Rule 3
  agrees. Sibling-subtree precision costs nothing at runtime and is exactly what
  the C++ caller cannot assume without inspecting the callee.
- `merge(&*b1, &*b2)` carries two write effects. Rule 10 clause 1: "Two effects on
  overlapping paths where at least one is a write must be proved disjoint
  (different roots, or indices or ranges proved distinct)". `b1` and `b2` are
  different roots, so the paths do not overlap and there is no obligation at all.
  Rule 5's "Box<T> owns exactly one heap object" plus Rule 1's ban on stored
  references means two live Box locals can never denote the same object, so the
  no-alias conclusion that C++ needs `restrict` or a runtime guard for is free, with
  no check emitted.

Ordinary program (the rejected shape, for the record):
```text
merge(&*root, &*((*root).l))     // rejected: (*root).l is a proper prefix of *((*root).l)
```
Rule 10 clause 1 rejects the nested pair. Rewrite: perform the two writes as two
statements rather than one call; Rule 10's pairwise comparison applies at a call,
while a function body is checked against its own row (Rule 9: "every statement's
effect and every callee's substituted row must be covered by the declared row"), so
the sequential form is accepted. Cost: one extra call boundary unless inlined; the
same total work, no extra memory traffic.

Rewrite and cost: none needed for the strongest program.

Rules consistent: yes.   Task achievable: yes - subtree-precise effects and free
no-alias between distinct Boxes.
Depends on: Rule 1, Rule 2, Rule 3, Rule 5, Rule 10.
Verdict: accepted-fine

### 5-10: The call-site pairwise check on two runtime-selected heap nodes

Question: can a call operate on two nodes of a heap structure that were selected
at runtime, which is what every link edit in a mutable graph needs?

Strongest program:
```text
// P3: splice node m between two runtime-selected nodes a and b
fn link(x: &Node, y: &Node)  writes(x.next), writes(y.prev)

// with Box edges, the two references cannot even be formed:
a_ref = find_node(&*root, key_a)      // rejected before the call site is reached
b_ref = find_node(&*root, key_b)
link(a_ref, b_ref)
```

Ordinary program (the arena form, which is the only one that reaches Rule 10):
```text
a: Arena<Node>                         // Rule 16
i = a.buf[cur].next                    // handles read out of node fields: data-determined
j = a.buf[i].next
link(&a.buf[i], &a.buf[j])             // substituted: writes(a.buf[i].next), writes(a.buf[j].prev)
```

Trace:
- The Box form never reaches Rule 10. Rule 4: a reference "cannot be assigned into
  any aggregate (Rule 1), cannot be returned, and cannot be captured by a function
  value that is stored or returned", and Rule 15 repeats "A function returns owned
  values only." A search over a Box structure therefore cannot hand back either
  node, and Rule 1 forbids parking them in a struct. The only references in scope
  are those the caller writes out as literal paths from distinct roots, so
  "operate on two runtime-selected nodes" is not expressible over Box edges at all.
  This also makes Rule 10's pairwise check nearly vacuous for Box structures -
  everything reachable is trivially disjoint by root.
- In the arena form, Rule 10 clause 1 applies: `a.buf[i].next` and
  `a.buf[j].prev` overlap at the root `a.buf` and both are writes, so they "must be
  proved disjoint (different roots, or indices or ranges proved distinct)". Rule
  10's own line is the precedent: `two(&v[i], &v[j])   // accepted only with the
  fact i != j`. The handles came out of node fields, so Rule 11 offers nothing -
  "There are no quantified facts over array elements" - and the call is rejected.
- Forming `&a.buf[i]` at all needs `i < len_of(a.buf)` (Rule 7), likewise `j`.

Rewrite and cost:
```text
if i < len_of(a.buf) { if j < len_of(a.buf) { if i != j { link(&a.buf[i], &a.buf[j]) }
                                             else       { link_self(&a.buf[i]) } } }
```
Rule 11's "refinement facts from a dominating branch" supply all three facts, and
Rule 7 sanctions the bounds tests ("the test establishes the fact; one compare, no
trap"). Duplicating the body into a same-node arm is free by the candidate's own
cost rule. Cost against a C++ pair of raw pointers: three compares and three
predictable branches per link edit, plus two writer-supplied arms that never run;
against safe Rust with indices into a `Vec`, the two bounds compares are the same
ones Rust emits and only the `i != j` test is extra. Per-hop traversal cost is
recorded in 5-16.

Rules consistent: yes - Rule 4 and Rule 10 agree, the first by making the
dangerous call unformable and the second by demanding the disjointness proof.
Task achievable: rewrite - only through Rule 16 handles, at three compares per
link edit.
Depends on: Rule 1, Rule 4, Rule 7, Rule 11, Rule 15, Rule 16 (provisional).
Verdict: rejected-real-cost

### 5-11: Facts and contracts about heap objects; recursion through Box

Question: what can be said about a heap structure as a fact, and what does
recursion over `Box` children need to be proved?

Strongest program:
```text
struct Node { value: Int, l: Box<Node>, r: Box<Node> }

fn sum(n: &Node) -> Int  reads(n)
    contract { ensures result >= 0; }
{ ... sum(&*((*n).l)) + sum(&*((*n).r)) ... }      // recursion through contracts

b: Box<DynBox<Int>>
n = len_of(*b)
f(&other)                    // writes(other): an unrelated root
use((*b)[n - 1])             // the fact still holds
g(&*b)                       // writes(*b): the fact is gone unless g's ensures restores it
```

Trace:
- Rule 10: "Recursion is checked through contracts, never by unfolding bodies", so
  `sum` is checked once against its own row and contract. The candidate states no
  termination obligation on user recursion, so none is imposed here; if one were,
  Rule 11's fact forms ("affine comparisons over measures and integer values,
  refinement facts from a dominating branch, loop-header invariants ... explicit
  `use` steps ... and callee contracts") contain no measure that could express the
  depth of a heap structure.
- What replaces the missing structural fact is a structural guarantee: Rule 1
  forbids a stored reference anywhere in an aggregate and Rule 5 says a Box "owns
  exactly one heap object", so an owned Box structure is a forest and a descent
  cannot revisit a node. Nothing has to be proved because nothing can be shared.
- Fact survival across calls is path-shaped: Rule 11 says "A fact that mentions a
  path is invalidated when that path is written (by statement or call) unless the
  callee's `ensures` re-establishes it." `writes(other)` does not mention `*b`, so
  `len_of(*b) == n` survives `f` with no re-test - the property that makes
  interleaved unrelated calls free.
- The limit: no fact can state "every handle stored in this structure is in
  bounds" - Rule 11's "There are no quantified facts over array elements ("for all
  i ...") and no per-slot occupancy facts" - and Rule 12 prescribes the substitute:
  "occupancy that is determined by data is stored as data". With Box edges the
  substitute is unnecessary (ownership is the invariant); with Rule 16 handles it
  becomes the per-hop compare recorded in 5-16.

Rewrite and cost: none needed.

Rules consistent: yes.   Task achievable: yes - recursive descent and contract-
checked recursion over Box structures need no invariant the candidate cannot write.
Depends on: Rule 1, Rule 5, Rule 9, Rule 10, Rule 12.
Verdict: accepted-fine

### 5-12: Conditional and loop-carried Box moves at a join

Question: may an affine Box be consumed on some incoming edges of a join, and who
pays for deciding at runtime whether it was?

Strongest program:
```text
b = Box::new(Job { .. })?
for i in 0..n {
    if ready(i) { consume(move b) }      // consumed on a data-determined edge, inside a loop
    step(i)
}
// scope exit: Rule 8 says the compiler releases b recursively - on which edge?
```

Ordinary program (the same shape without the back edge):
```text
b = Box::new(Job { .. })?
if c { consume(move b) }                 // accepted: b simply cannot be named after the join
other_work()
```

Trace:
- Rule 12: "At a join, facts are intersected (a fact survives only if it holds on
  every incoming edge)" and "No place is ever partially moved: every path is either
  wholly present or the program cannot name it." At the loop header `b` is present
  on the entry edge and gone on the back edge, so after the header the program
  cannot name `b`; the loop body names it in the second iteration, so the loop is
  rejected.
- Rule 8 makes the release side just as hard: an affine value is "consumed at most
  once; at scope exit the compiler releases their memory recursively". After a
  data-determined consumption the compiler would need a runtime flag to know
  whether to release, and this candidate provides no such flag and no destructor
  (Rule 5: "there are no destructors"). The diamond case needs none: the release is
  placed on the edge that still holds `b`, which is statically identified, so the
  ordinary program above costs nothing.
- Reference targets at the same join behave as Rule 2 says: `p = if c { &*b1 }
  else { &*b2 }` gives `p` the target set `{*b1, *b2}`, and "every check on it must
  hold for every member of the set", so a later `writes(b1)` invalidates `p` even on
  the run where `p` names `*b2`.

Rewrite and cost: decide as data, act once.
```text
hit = n
for i in 0..n { if ready(i) && hit == n { hit = i } ; step(i) }
if hit < n { consume(move b) }
```
Cost against C++: a moved-from `unique_ptr` is null and its destructor tests that
null on every exit - the flag C++ pays for is exactly what this rewrite removes,
so the rewrite is never worse and is usually better. Against Rust: the identical
loop is rejected by the borrow checker too, and the idiomatic `Option::take()`
rewrite costs a null store plus a null test. The added `hit == n` compare per
iteration is eliminable by breaking out of the loop at the first hit. For the
reference-target case the rewrite is to duplicate the tail into both arms of the
`if`, which the candidate's cost rule makes free.

Rules consistent: yes - Rule 12's "wholly present" clause and Rule 8's scope-exit
release agree exactly when the consuming edge is statically identified.
Task achievable: yes - via the data-carried decision, at no runtime cost.
Depends on: Rule 2, Rule 3, Rule 5, Rule 8, Rule 11.
Verdict: rejected-zero-cost

### 5-13: Parallel work over an ownership forest

Question: does Box ownership give parallel divide-and-conquer over a heap
structure without any runtime guard, and where does it stop?

Strongest program:
```text
struct Node { v: Int, l: Box<Node2>, r: Box<Node2> }

fn rewrite(n: &Node2, seed: Int) -> Result<u64, Oom>  writes(n)      // allocates internally

par { rewrite(&*((*root).l), s1)?; rewrite(&*((*root).r), s2)? }     // both arms write and both allocate
```

Trace:
- Rule 13: "`par { A; B }` is accepted when A's write paths are disjoint from B's
  read and write paths and vice versa, using the same path-overlap and
  index/range-disjointness judgment as Rule 10." The substituted write paths are
  `*((*root).l)` and `*((*root).r)`; they diverge at two distinct fields, which is
  Rule 10's accepted `two(&a.x, &a.y)   // accepted: distinct fields` shape. No
  index disjointness has to be proved, because there is no index.
- Both arms allocate. Rule 14: "Allocation and release carry no effect entry and
  never make two parallel arms conflict", with its own example `par { a =
  build(&x)?; b = build(&y)? }`. The heap is "provided by the trusted base,
  internally synchronized", and "Addresses are not observable, so allocator
  concurrency does not affect program determinism" - so the parallel build is
  deterministic without the program naming a lock.
- Nothing is emitted at runtime for the acceptance: no guard, no range test, no
  dependency edge. This is the strongest positive result in row 5. Rust reaches the
  same place by splitting `&mut`; C++ reaches it only on the programmer's word.
- Where it stops: `par { work(&*b_i); work(&*b_j) }` with `i`, `j` chosen at
  runtime cannot be written at all, because Rule 4 forbids returning the references
  a search would produce (see 5-10). The arena rewrite that restores runtime
  selection needs `i != j` proved, and it loses the parallel allocation above,
  because Rule 16's `alloc` declares `writes(a.buf)` and two such arms overlap
  under the same Rule 13 test. That trade is derived in 5-16.
- Reads compose freely: Rule 13's `par { s1 = stats(&v); s2 = stats(&v) }` line
  makes read/read overlap legal, so parallel traversal of a shared subtree is
  accepted even when both arms walk the same nodes.

Rewrite and cost: none needed. The one shape that must be avoided is a shared
mutable accumulator across the arms, which Rule 13 rejects (`par { push(&v, 1);
stats(&v) }`); the rewrite is per-arm results recombined after the `par`, which is
the same two-buffer fork-join the rule file already records under known costs.

Rules consistent: yes.   Task achievable: yes - recursive parallel tree work at
zero runtime cost, including allocation in both arms.
Depends on: Rule 4, Rule 10, Rule 14, Rule 16 (only for the recorded limit).
Verdict: accepted-fine

### 5-14: One heap, fallible allocation, unobservable addresses

Question: with one global heap and no observable addresses, can a program still
ask whether two owning handles denote the same object, and what does a failed
allocation cost mid-construction?

Strongest program:
```text
// shared object registry: one logical object reached through two index structures
b1 = lookup_by_name(...)        // some owning handle
b2 = lookup_by_id(...)
if same_object(b1, b2) { ... }  // no such operation exists
```

Ordinary program (allocation failure during a recursive build):
```text
fn build(d: u64) -> Result<Box<Node>, Oom>
{
    l = build(d - 1)?
    r = build(d - 1)?           // if this fails, l is still owned on the early-return edge
    Box::new(Node { l: move l, r: move r })
}
```

Trace:
- Rule 14 closes the identity question in one sentence: "Addresses are not
  observable, so allocator concurrency does not affect program determinism." A
  pointer comparison would observe an address, so there is no Box identity test,
  and Rule 1's ban on stored references means a registry cannot keep two handles to
  one object in the first place - two live Boxes are two objects (Rule 5: "owns
  exactly one heap object").
- The ordinary program is accepted and free: Rule 5 `b = Box::new(Node { ... })?
  // allocation can fail: Result<Box<Node>, Oom>`, Rule 14 "Allocation returns a
  `Result` and never traps", and Rule 8 "at scope exit the compiler releases their
  memory recursively" - the `?` edge is statically identified, so `l` is released
  with no flag and no user code, which is what Rust's `?` plus `Drop` and C++'s
  `unique_ptr` unwinding already do. (For a linear payload this edge is unresolved;
  see 5-8.)
- Rule 14 also removes allocation from the effect algebra entirely, so a failed or
  succeeding allocation invalidates no fact and no reference: nothing in Rule 3 or
  Rule 11 is triggered by `Box::new`.

Rewrite and cost: carry identity as data. In a Rule 16 pool the handle *is* the
identity, so `i == j` is one compare on values the program already holds and the
cost is zero; the registry task is naturally in that form, since Rule 4 forces
lookups to return indices anyway. If the structure must stay Box-based, identity
has to be a stored word: four to eight bytes per node and a load plus a compare per
test, against a C++ pointer compare that stores nothing. Since the task that needs
identity is exactly the task that needs multiple access paths, and multiple access
paths already force handles, the free rewrite is the one that applies.

Rules consistent: yes.   Task achievable: rewrite - identity is expressed as a
handle or a stored id, not as an address.
Depends on: Rule 1, Rule 4, Rule 5, Rule 8, Rule 16 (provisional, for the free
rewrite).
Verdict: rejected-zero-cost

### 5-15: Returning owned Boxes; find-then-mutate without returned references

Question: with references unreturnable, how does a program reach a node it just
found in a Box structure, and what does that cost?

Strongest program:
```text
// the C++/Rust one-walk form
p = find(&*root, k)          // wants to return &Node
(*p).value = v
```

Ordinary program (the accepted form):
```text
fn update(t: &Node, k: Int, f: fn(x: &Val) writes(x))  writes(t)
{
    if (*t).key == k { f(&(*t).value) }
    else if k < (*t).key { update(&*((*t).l), k, f) }
    else { update(&*((*t).r), k, f) }
}
update(&*root, k, bump)
```

Trace:
- Rule 4 rejects the strongest program at the signature: a reference "cannot be
  returned", and Rule 15 states the same positively: "A function returns owned
  values only." Rule 4's prescribed substitute is an index - "A function that
  "finds" something returns an index or other owned data; the caller forms the
  reference" - which works for a `DynBox` because the index is an owned value that
  re-derives the place in one address computation. A Box structure has no index
  space, so the owned surrogate would be a path word plus a second walk: O(depth)
  extra loads per lookup, a real cost.
- The accepted form avoids the surrogate by doing the work where the node is
  found. Rule 10 licenses the callback: "Function-typed parameters carry a full
  signature with its own row and contract, and a call through one uses that row",
  so `f`'s `writes(x)` is substituted at the call and covered by `update`'s own
  `writes(t)` under Rule 9's body check. One walk, no returned reference, no
  re-derivation.
- Rule 15's other clause, "Passing a large value in and back out is expressed as a
  reference parameter with a `writes` entry, not as move-and-return", does not bite
  for Box: a Box is pointer-sized, so moving one in and out is a register move.
  Returning `own Box<Big>` is in fact the candidate's zero-copy way to hand back a
  large owned value, since a by-value `Big` return has no assumed zero-copy ABI.

Rewrite and cost: the callback form above. Against C++ or Rust passing a lambda,
the cost is one indirect call per found node when the instantiation is not
specialized, and zero when it is; there is no per-hop cost, no second traversal and
no extra memory. The task shape changes (the operation is pushed into the search
rather than pulled out of it), which the candidate's cost rule does not charge for.

Rules consistent: yes.   Task achievable: rewrite - do the work at the point of
discovery; the only exposure is an unspecialized indirect call.
Depends on: Rule 4, Rule 9, Rule 10, Rule 7 (for the DynBox index substitute).
Verdict: rejected-zero-cost

### 5-16: Box versus arena handles for shared and cyclic structure

Question: a mutable compiler graph needs back edges, node reuse and parallel
construction; what does moving from Box edges to Rule 16 handles cost?

Strongest program:
```text
// P3: doubly linked nodes in a pool, built in parallel, traversed by edge
struct Node { data: u64, next: u64, prev: u64, gen: u32 }     // edges are data (Rule 1)
struct Arena<T> { buf: DynBox<T> }
fn alloc<T>(a: &Arena<T>, x: own T) -> u64   writes(a.buf)
    contract { requires len_of(a.buf) < cap_of(a.buf);
               ensures result == len_of(deref(entry(a.buf))); ensures len_of(a.buf) == result + 1; }

par { i = alloc(&a, n1); j = alloc(&a, n2) }        // rejected
h = a.buf[cur].next                                 // traversal hop
if h < len_of(a.buf) { if a.buf[h].gen == expected { use(&a.buf[h]) } else { stale_arm() } }
par { map(&a.buf[0..mid]); map(&a.buf[mid..n]) }    // accepted
```

Trace:
- Box cannot express the structure at all. Rule 1 is recursive and closed: "there
  is no type parameter, wrapper, or variant payload through which a reference can
  be stored", so a back edge cannot be a reference; and Rule 5's "Box<T> owns
  exactly one heap object" makes a second owning edge a double owner. A graph is not
  an ownership forest, so Rule 16's handles are the only rendering.
- Traversal: `h` comes out of a node field, so it is data. Rule 11 - "There are no
  quantified facts over array elements ("for all i ...") and no per-slot occupancy
  facts" - leaves no invariant that could discharge `h < len_of(a.buf)`, and Rule 7
  prescribes the test: "when the proof is unavailable the program tests the measure,
  which is ordinary data." One compare, one predictable branch and one
  writer-supplied arm per hop.
- Reuse and staleness: Rule 16 says "A stale index that is still in bounds names
  the current occupant of that slot: a logic error, not a memory error. Programs
  that need to detect it keep a generation number as data." The compiler-graph task
  requires that a relation to a deleted node not silently become a relation to its
  replacement, so the generation word is mandatory for this task: four bytes per
  node, one load and one compare per dereference.
- Parallel allocation is lost. Rule 16's `alloc` declares `writes(a.buf)`; under
  Rule 13's test, "A's write paths are disjoint from B's read and write paths", the
  two arms overlap at `a.buf` and the `par` is rejected. The Box form of the same
  two allocations is accepted by Rule 14, "Allocation and release carry no effect
  entry and never make two parallel arms conflict". Choosing handles to get shared
  structure therefore gives up the parallel allocation that Box had.
- Parallel node-data work is gained. `par { map(&a.buf[0..mid]); map(&a.buf[mid..n])
  }` is accepted by Rule 13's "disjoint ranges: accepted" line with Rule 7's range
  references - a contiguous pool admits P3's parallel map over all nodes, which a
  scattered Box graph could never express, since Rule 4 forbids collecting the node
  references a worker split would need.

Rewrite and cost, against a C++ pointer graph with `new` per node:
- per hop: one compare plus one not-taken branch (bounds), and with staleness
  detection one load plus one compare (generation); the address computation
  `base + h * size` replaces a pointer load, which is a wash or better for locality;
- per node: four bytes of generation, against zero;
- parallel construction: rewritten as per-worker arenas plus a merge that rebases
  handles - one addition per stored handle at merge time, or a two-level handle
  which costs one extra dependent load on every hop thereafter;
- against a correct safe C++/Rust rendering (a generational slot map), all of the
  above except the free-list bounds compare is what that rendering also pays.

Rules consistent: yes.   Task achievable: rewrite - the graph is expressible with
handles, but parallel allocation is not recoverable without splitting the arena.
Depends on: Rule 1, Rule 4, Rule 5, Rule 7, Rule 11, Rule 13, Rule 14,
Rule 16 (provisional - this cell relies on it for the whole rendering).
Verdict: rejected-real-cost

### 12-12: Repeated, nested and loop-carried joins

Question: when joins stack up - nested branches inside a loop, a reference rebound
every iteration - what does the repeated intersection lose, and can the writer
recover it without runtime work?

Strongest program:
```text
n = len_of(buf)
i = 0
p = &buf[0]                                   // requires 0 < n
loop {
    invariant h: i <= n;
    invariant g: len_of(buf) == n;
    if i == n { break }
    if pred(i) {
        k = classify(i)
        if k < n { hit = k } else { hit = 0 }  // inner join
    } else {
        hit = i                                // outer join
    }
    p = &buf[hit]                              // rebound every iteration
    use(p)
    i = i + 1
}
```

Trace:
- Rule 12: "At a join, facts are intersected (a fact survives only if it holds on
  every incoming edge)". The three edges reaching `p = &buf[hit]` give `hit == k &&
  k < n`, `hit == 0` with `0 < n` from `i < n`, and `hit == i && i < n`. All three
  support `hit < n`, so the intersection keeps it; combined with the carried
  `len_of(buf) == n` it discharges Rule 7's `hit < len_of(buf)`. The repetition
  costs nothing because each edge established the same shape of fact, and Rule 11
  admits that shape: "affine comparisons over measures and integer values" and
  "refinement facts from a dominating branch".
- The back edge is the one join that cannot be removed, and Rule 11 answers it
  with the written invariant: "loop-header invariants `invariant name: affine_expr
  compare_op affine_expr`", which its own example calls "carried by the writer,
  checked at every iteration". That is a compile-time obligation, not a runtime
  branch, so a loop-carried fact costs nothing to keep.
- The reference is rebound every iteration, so by Rule 2 its target set at the
  header is the set of all `buf[hit]` it may name, and "every check on it must hold
  for every member of the set". The set is not finitely enumerable when the index
  varies, and the rule file gives no representation for that case; the verdict does
  not turn on it, because the two checks that matter are uniform over the set:
  validity is prefix-shaped (Rule 3: "invalidated when any proper prefix of p's
  path is written", and the prefix is `buf` for every member), and the bound was
  discharged when each member was formed (Rule 7: "forming `&buf[k]` requires the
  fact `k < len_of(buf)`"), while later use of an already valid `p` is a content
  access, which Rule 3 says does not disturb validity.
- What the intersection does lose is any fact whose shape is outside Rule 11:
  "There are no quantified facts over array elements ("for all i ...") and no
  per-slot occupancy facts". "Slot j is the one this branch filled" survives no
  join, and Rule 12 prescribes the substitute in the same breath: "Structures whose
  occupancy is decided by data keep that occupancy as data."

Rewrite and cost: for every join that is a source-level branch, tail duplication
recovers the fact exactly - copy the join's successor into each predecessor, where
the fact is still live. The candidate charges nothing for this: "Runtime
performance is the only cost ... duplicated code are not costs." For a loop header,
peeling or unrolling is the same free device, and anything it cannot reach is
carried by an `invariant`. Only facts outside the invariant grammar force real
work, and then the cost is what C++ pays too: one stored count or tag word and one
load to read it back (`vec.size()`, a discriminant byte).

Rules consistent: yes - intersection plus the invariant form plus data-carried
occupancy cover every join shape the cell could build.
Task achievable: yes - nested and loop-carried joins are free; only unstatable
fact shapes become a stored word.
Depends on: Rule 2, Rule 3, Rule 7, Rule 11.
Verdict: accepted-fine

### 12-13: Joins feeding par arms

Question: when a `par` arm's argument comes out of a join, the target set
multiplies the disjointness obligations - does that cost parallelism?

Strongest program:
```text
for t in 0..steps {
    p = if flip(t) { &cols.a[lo..mid] } else { &cols.b[lo..mid] }
    q = if flip(t) { &cols.b[mid..hi] } else { &cols.a[mid..hi] }
    par { kernel(p, &src); kernel(q, &src) }        // writes(p), writes(q), reads(src)
}
```

Trace:
- Rule 2 gives `p` the target set `{cols.a[lo..mid], cols.b[lo..mid]}` and `q` the
  set `{cols.b[mid..hi], cols.a[mid..hi]}`, with "every check on it must hold for
  every member of the set".
- Rule 13 requires "A's write paths are disjoint from B's read and write paths and
  vice versa, using the same path-overlap and index/range-disjointness judgment as
  Rule 10". That is four pairs here. Two of them are different roots (`cols.a`
  versus `cols.b`), which Rule 10 clause 1 accepts as "different roots"; the other
  two are `a[lo..mid]` versus `a[mid..hi]` and the same for `b`, which are "ranges
  proved distinct" from `lo <= mid <= hi`, exactly Rule 13's
  `par { kernel(&v[0..mid], ...); kernel(&v[mid..n], ...) }` line. `reads(src)` in
  both arms is read/read, which Rule 13 allows. The `par` is accepted with the
  target sets in place: the join multiplied the obligations and every member still
  discharged them.
- The failing variant is instructive: make `q`'s else arm `&cols.a[lo..mid]`. At
  runtime the two arms never coincide, because both conditionals test the same
  `flip(t)`, but that correlation is not a fact the candidate can carry - Rule 11's
  forms are affine comparisons over measures and integer values, and Rule 12
  intersects each `if` independently at its own join, keeping nothing that relates
  the two. Rule 2's "every member" clause then rejects a `par` that is in fact
  always disjoint.
- Rule 12 speaks of "control-flow joins" and "every incoming edge". The two arms of
  a `par` are not alternative incoming edges - both execute - so the arms' `ensures`
  both hold afterwards; the rule file does not say this in so many words, and
  reading the end of a `par` as a Rule 12 join would intersect the arms'
  post-conditions and destroy every parallel reduction's result. This cell's verdict
  does not turn on it: the program above needs no post-`par` fact.

Rewrite and cost: hoist the branch out of the `par` - that is, duplicate the `par`
into each arm of one conditional:
```text
if flip(t) { par { kernel(&cols.a[lo..mid], &src); kernel(&cols.b[mid..hi], &src) } }
else       { par { kernel(&cols.b[lo..mid], &src); kernel(&cols.a[mid..hi], &src) } }
```
Each `par` now sees literal paths with no target sets and the same disjointness
proof succeeds. Cost: one branch the original already executed, duplicated code
that the candidate does not charge for, and full parallelism retained - zero.
This rewrite is always available, because Rule 4 guarantees a reference's target
set can only ever come from a source-level join (a reference "cannot be returned"
and "cannot be assigned into any aggregate", so no call and no stored value can
hand a multi-target reference to a `par`), and a source-level join is always
duplicable, a loop header by peeling or unrolling by two.

Rules consistent: yes.   Task achievable: yes - joins never cost parallelism,
because the branch can always be moved outside the `par`.
Depends on: Rule 2, Rule 4, Rule 7, Rule 10, Rule 11, Rule 13.
Verdict: accepted-fine

### 12-14: Joins around allocation failure and container growth

Question: what survives the two joins that allocation creates - the `Ok`/`Err`
split and the grow/no-grow split inside a container push?

Strongest program:
```text
n0 = len_of(v)
q  = &v[j]                     // j < n0
r  = push(&v, x)               // library push (Rule 6): may allocate a larger block, may fail
match r {
    Ok  => { ... }
    Err(Oom) => { ... }
}
// after the match join:
use(&v[j])                     // needs j < len_of(v)
use(q)                         // rejected on both edges
```

Trace:
- The `Ok` edge gives `len_of(v) == n0 + 1` and the `Err` edge `len_of(v) == n0`.
  Rule 12 intersects them, and its own worked example states the surviving form:
  "after the join: `len_of(buf) >= n`, where n was `len_of` before" and "facts about
  indices below n survive". So `j < n0 <= len_of(v)` holds on both edges and
  `use(&v[j])` needs no test - this clause is what makes container growth free for
  every pre-existing handle, and 12-16 depends on it.
- Rule 14 keeps the allocation itself out of the way: "Allocation and release
  carry no effect entry", so nothing about the `Err` edge is special - it is an
  ordinary branch, and "Allocation returns a `Result` and never traps" means there
  is no hidden exit.
- The reference does not survive. Rule 6 says the library push "allocates a larger
  DynBox, moves `[0, len_of)` across, and replaces the old one", declared
  `writes(v)`, and Rule 3 invalidates `q` because `v` is a proper prefix of `v[j]`.
  It is invalidated on the `Err` edge too, since the caller judges by the
  substituted row and not by which internal path ran (Rule 10 clause 3: "A live
  reference outside the call whose path has a proper prefix among the call's write
  paths becomes invalid after the call"). The intersection therefore cannot restore
  it, and no tail duplication helps, because the grow/no-grow split is inside the
  callee and never appears as a source branch at the caller.
- Partial-construction cleanup across the failure join is free: on the early-return
  edge the affine parts already built are released by the compiler at scope exit
  (Rule 8), and the edge is statically identified, so no flag is needed. The
  loop-carried version of that is the one that fails; see 5-12.

Rewrite and cost: keep the index rather than the reference and re-form `&v[j]`
after the push. The bound is already proved by Rule 12's surviving-index clause, so
the rewrite costs one load of the block base pointer per re-formation and no
compare. Rust's borrow checker rejects the identical program and its idiomatic
rewrite is the same index-then-reindex; unchecked C++ keeps the pointer and is
wrong precisely when the vector grew.

Rules consistent: yes - Rule 12's intersection, Rule 3's prefix rule and Rule 14's
effect-free allocation give one answer with no gaps.
Task achievable: yes - index facts survive growth and failure; only the reference
is re-formed, at one load.
Depends on: Rule 3, Rule 6, Rule 8, Rule 10, Rule 14.
Verdict: accepted-fine

### 12-15: Joins and owned returns; result-routed contracts

Question: a search returns an owned index plus a bound, and the caller immediately
branches on it - does the join intersect away the very fact that makes the index
usable?

Strongest program:
```text
fn find(v: &DynBox<Entry>, key: Int) -> Option<u64>
    reads(v)
    contract { ensures when Some: result < len_of(v); }

match find(&v, k) {
    Some(i) => { p = &v[i]; update(p) }      // the bound lives on this edge
    None    => { insert_new(&v, k) }
}
use_after(i)                                  // nothing about i survives the join
```

Trace:
- Rule 11 provides the routing: "Contracts use `requires`, `ensures`, and
  `ensures when Variant:` for result-routed relations". Rule 12's intersection
  never bites, because the fact is delivered on the edge where the index is used -
  the `Some` arm - which is Rule 4's own prescribed program: "`match find(&v, k) {
  Some(i) => { p = &v[i]; ... }  None => ... }   // caller re-derives, one address
  computation".
- Forming `&v[i]` needs `i < len_of(v)` (Rule 7); the contract supplies it, so the
  caller emits one address computation and no compare. That matches C++'s
  `Entry* p = find(...)` and beats safe Rust's `v[i]`, which bounds-checks at the
  use.
- Rule 15 is what forces this shape - "A function returns owned values only" and
  "Positions found by a search are returned as indices with a bounds relation in
  `ensures` (Rule 4)" - so the interaction is by construction rather than by luck:
  the only thing a callee can return is owned data, and the only thing that makes
  owned data usable across the caller's branch is a variant-routed relation.
- What the join does lose is the fact after the match. Nothing relates `i` to
  `len_of(v)` on the `None` edge, so code below the match cannot index with it.
- Second shape: Rule 15's "Passing a large value in and back out is expressed as a
  reference parameter with a `writes` entry". If the callee writes that parameter on
  one internal path only, the caller's facts about it are gone on both edges (Rule
  11: "A fact that mentions a path is invalidated when that path is written ...
  unless the callee's `ensures` re-establishes it"). The `unless` clause is the
  repair: the callee states `ensures len_of(out) == ...` and the fact is
  re-established by contract rather than re-tested by the caller.

Rewrite and cost: do the work inside the arm that owns the fact (free - duplicated
code is not a cost), or carry the not-found case as data in the index itself,
returning `len_of(v)` as the sentinel with a single `ensures result <= len_of(v)`,
which is Rule 12's "Structures whose occupancy is decided by data keep that
occupancy as data" applied to a result. Cost: at most one compare to separate the
sentinel, which is the same compare C++ makes against `end()`.

Rules consistent: yes.   Task achievable: yes - the result-routed contract makes
the search-then-use pattern free.
Depends on: Rule 4, Rule 7, Rule 11, Rule 15.
Verdict: accepted-fine

### 12-16: Joins over pool allocation: free list, generations, surviving handles

Question: a pool allocates either from a free list or by growing, and later frees
and reuses slots - do the handles it hands out stay proved in bounds across all the
joins, and what does the reuse cost?

Strongest program:
```text
struct Node { data: u64, next: u64, gen: u32 }        // all-Copy payload: plain slot assignment
struct Pool { buf: DynBox<Node>, free_head: u64 }      // free_head == NONE when the list is empty

fn obtain(p: &Pool, x: Node) -> u64   writes(p.buf), writes(p.free_head)
    contract { ensures result < len_of(p.buf); }
{
    if p.free_head != NONE {
        h = p.free_head
        if h < len_of(p.buf) {                        // the free list is data, not a fact
            p.free_head = p.buf[h].next
            p.buf[h] = x                              // reuse edge
            return h
        }
        // writer-supplied arm the rules force: a corrupt free head
        return alloc_grow(p, x)
    }
    return alloc(p, x)                                // Rule 16: ensures result == len_of(entry), len == result + 1
}

// caller
i = obtain(&pool, n1)
j = obtain(&pool, n2)                                 // another write of pool.buf
use(&pool.buf[i])                                     // is i still proved in bounds?
```

Trace:
- The join inside `obtain` is the interesting one. The `alloc` edge supplies the
  bound from Rule 16's contract, "ensures result == len_of(deref(entry(a.buf)));
  ensures len_of(a.buf) == result + 1", which gives `result < len_of(a.buf)`
  directly. The reuse edge supplies it from the written test, which Rule 11 admits
  as a "refinement fact from a dominating branch". Rule 12 intersects: "a fact
  survives only if it holds on every incoming edge", and `result < len_of(p.buf)`
  holds on both, so the declared `ensures` is provable and the caller needs no test
  of its own.
- That reuse-edge compare is a cost the rules impose rather than the task: the
  invariant "every handle on the free list is in bounds" is exactly a quantified
  fact over elements, and Rule 11 says "There are no quantified facts over array
  elements ("for all i ...") and no per-slot occupancy facts". One compare per
  allocation, plus an arm that never runs.
- Handle survival across later allocations is the decisive question, and Rule 12
  answers it in its own example: "after the join: `len_of(buf) >= n`, where n was
  `len_of` before / facts about indices below n survive". So `i < len_of(pool.buf)`
  survives the second `obtain` and every later one, and a pool handle is
  dereferenced with no re-test - the difference between one compare per allocation
  and one compare per dereference. For a pool that outgrows its capacity, the
  growing push must carry `ensures len_of(v) >= len_of(deref(entry(v)))` for the
  same conclusion; Rule 11 admits exactly that repair with its clause "unless the
  callee's `ensures` re-establishes it". `truncate` breaks the chain and Rule 16
  says so: "later reads of `a.buf[id]` need `id < len_of` again".
- Occupancy is data, not a hole: Rule 6 guarantees "no program point can observe a
  slot inside the window as empty", so a freed slot still holds a valid `Node` and
  freeing is a slot assignment plus a link into the free list - which is Rule 12's
  "Structures whose occupancy is decided by data keep that occupancy as data", and
  matches its `tags: DynBox<u8>` open-addressing example. With an affine payload the
  free step must be Rule 6's atomic update `buf[k] = f(buf[k])` so the old occupant
  is consumed rather than leaked; the rule shows that form with a single argument
  only, so a free step that must also install a replacement value has no shown

  on it.
- Staleness: Rule 16 says "A stale index that is still in bounds names the current
  occupant of that slot: a logic error, not a memory error. Programs that need to
  detect it keep a generation number as data." The compiler-graph task does need it,
  so the check is a load and a compare per dereference, and its two arms join under
