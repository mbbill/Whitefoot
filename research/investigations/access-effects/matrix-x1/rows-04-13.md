# Interaction matrix under candidate x1: rows 4 and 13

Derived against `CANDIDATE-X1.md` (frozen 2026-09-18) only. Rule 4 is
"References are never stored, returned, or captured into anything that
escapes"; Rule 13 is "Parallel blocks". Cost is runtime performance only.

### 4-4: Rule 4 against itself: passing a reference on, and capturing one in a function value that is only an argument

Question: does the no-escape boundary stay closed when a reference is handed to
a callee that hands it on, and when a reference is captured by a function value
that is passed as an argument but never stored or returned?

Strongest program:
```text
fn for_each<T>(v: &DynBox<T>, f: fn(&T))  reads(v)
{
    i = 0
    while i < len_of(v) { f(&v[i]); i = i + 1 }     // the received reference is passed on again
}

log: DynBox<u64>
h = |e: &Entry| { push_nogrow(&log, e.key) }        // h captures the reference &log
for_each(&table, h)                                 // h is an argument; not stored, not returned
```

Ordinary program (differs materially):
```text
match find(&v, k) { Some(i) => { p = &v[i]; use2(p, &w) }  None => ... }
fn use2(p: &Entry, w: &DynBox<u8>)  writes(p), reads(w)     // p passed on a second time
```

Trace: the ordinary program is Rule 4's own shape — "A reference may be bound to
a local, passed as a call argument, and used within the function that formed it
or received it" — and passing on is unbounded in depth because each callee
merely receives; Rule 10 substitutes actual paths at every level, so the caller
still sees `writes(v[i])`. Accepted, and Rule 4's example already prices it at
"one address computation".
The strongest program turns on the capture clause. Rule 4 body: "It cannot be
assigned into any aggregate (Rule 1), cannot be returned, and cannot be captured
by a function value that is stored or returned." `h` is neither stored nor
returned, so that clause does not reject it. Rule 4's heading says "References
are never stored, returned, or captured into anything that escapes", a different
boundary. Rule 1's closure is over a listed set — "Every struct, enum, tuple,
array, slice-like value, Box, DynBox, and generic instantiation" — which does
not include a function value. Rule 10 says "Function-typed parameters carry a
full signature with its own row and contract, and a call through one uses that
row", and Rule 9 says every effect path "starts at a reference parameter";
`log` is not a parameter of `h`, so `h`'s row cannot name `writes(log)`. If the
capture is admitted as written, the row used at `f(&v[i])` omits a real write,
and both Rule 10.1's pairwise comparison and Rule 13's disjointness judgment
lose a path. If it is not admitted, no clause says so. Ambiguous.

Rewrite and cost: thread the captured state as an explicit parameter, so no
function value ever holds a reference:
```text
fn for_each<T, C>(v: &DynBox<T>, c: &C, f: fn(&T, &C))  reads(v), writes(c)
for_each(&table, &log, record_key)
```
Runtime cost versus a C++ or Rust closure: none. The environment pointer a
closure would carry becomes an argument register, and the callee's row now names
the write, which is strictly better for Rule 13. Extra parameters are not a cost
(protocol 7).

Rules consistent: cannot tell - the heading and the capture clause draw the
boundary at different places for the same program.   Task achievable: rewrite,
at zero runtime cost, under either reading.
Depends on: Rule 1, Rule 9, Rule 10.
Verdict: undecided-rule-gap

### 4-5: Rule 4 and Box: rewriting a subtree that no returned reference may name

Question: with no reference into a Box allowed to leave the frame that formed
it, how does a program replace a child in a heap-linked tree?

Strongest program:
```text
struct Node { key: Int, left: Option<Box<Node>>, right: Option<Box<Node>> }

fn find_slot(root: &Node, k: Int) -> &Option<Box<Node>>      // rejected by Rule 4
fn rebuild(x: own Option<Box<Node>>) -> own Option<Box<Node>>

fn splice(n: &Node, k: Int)  writes(n.left)
{
    n.left = rebuild(n.left)        // replace a Box field in place: is this the atomic update?
}
```

Ordinary program:
```text
p = &(*b).left
c = move b                          // Rule 3: b is a proper prefix of *b
use(p)                              // rejected; re-form from c
```

Trace: Rule 4 rejects `find_slot` - "cannot be returned". Rule 4's stated remedy,
"A function that 'finds' something returns an index or other owned data; the
caller forms the reference", does not reach this case: Rule 7's indexable things
are "an inline `array<T, N>` (constant length, always fully initialized), a
`DynBox<T>` (Rule 6), a range reference into either, and a `const` table", and a
Box chain is none of them, so no owned datum names the found node except a
re-descent recipe. The operation must therefore be pushed into the frame that
owns the path, and that frame must replace a Box-valued field. Rule 6: "There is
no `take` operation and no partial move out of any place: the only ways to move
a value out of storage are consuming a whole local (`move x`), the window
operations, and the atomic update." The atomic update is introduced only as
`buf[k] = f(buf[k])` with "requires k < len_of(buf)", a window slot; the
enumeration lists it separately from "the window operations", which is
consistent with it being place-general, but no sentence says whether a struct
field is an eligible place, and `take`/`put` holes are excluded by "Not in this
candidate". So whether `n.left = rebuild(n.left)` is admitted is not decided by
the text. Rule 12 ("No place is ever partially moved") and Rule 3's move example
are consistent with either reading.

Rewrite and cost: (a) if the atomic update covers a field, `n.left =
rebuild(n.left)` is one pointer-word load and one store, identical to C++
`n->left = f(std::move(n->left))`; zero cost, and every reference formed from
`n.left` beforehand is invalid afterwards (Rule 3), costing one re-formed
address. (b) if it does not, the only remaining forms are rebuilding the path by
value - `own Node` in and out at every level, i.e. a copy of each node on the
path, O(depth) element copies per rewrite that C++ and Rust both avoid - or
moving the whole structure into a Rule 16 pool with `u64` links, which copies
nothing but pays one bounds compare per hop (see 4-11).

Rules consistent: cannot tell - Rule 6's enumeration and its single atomic-update
example do not settle which places the update applies to.   Task achievable:
rewrite; zero cost under (a), O(depth) copies or one compare per hop under (b).
Depends on: Rule 3, Rule 6, Rule 7, Rule 12, Rule 15, Rule 16 (fallback only).
Verdict: undecided-rule-gap

### 4-6: Rule 4 and the DynBox window: an index outlives the element it named

Question: an index is the only locator Rule 4 lets cross a boundary; what does
Rule 6's movable `len_of` boundary do to it?

Strongest program:
```text
n = len_of(v)                       // kept as data, so the fact below mentions no path
i = find(&v, key)?                  // Rule 4: ensures when Some: i < len_of(v), hence i < n
x = pop(&v)                         // writes(v); ensures len_of(v) == len_of(deref(entry(v))) - 1
consume(move x)
push_nogrow(&v, move fresh)         // ensures len_of(v) == len_of(deref(entry(v))) + 1, so len_of(v) == n
charge(&v[i], amount)               // accepted with NO runtime test: i < n == len_of(v)
```

Ordinary program:
```text
i = find(&v, key)?
y = swap_remove(&v, i)              // slot i now holds the former last element
if i < len_of(v) { charge(&v[i], amount) }      // accepted; a different element
```

Trace: Rule 4 forces `find` to yield `u64`. Rule 11: "A fact that mentions a path
is invalidated when that path is written (by statement or call) unless the
callee's `ensures` re-establishes it" - so `i < len_of(v)` dies at `pop`, but
`i < n` is a relation between two integer values and mentions no path, so it
survives every write to `v`. Rule 6's `ensures` clauses on `pop` and
`push_nogrow` then re-derive `len_of(v) == n` by affine arithmetic (Rule 11), so
Rule 7's "requires `i < len_of(buf)`" is discharged statically. The program is
accepted with no compare, and slot `i` now holds an element the search never
saw. Rule 3's protection - "invalidated when any proper prefix of p's path is
written ... Using an invalid reference is rejected" - would have caught exactly
this had the locator been a reference, and Rule 4 is what prevents the locator
from being one across the call that produced it. Rule 12 guarantees the slot
holds a valid value, so there is no memory error and no trap.

Rewrite and cost: pair every returned index with an epoch stored beside the
window, and check it before use:
```text
struct Log { v: DynBox<Entry>, epoch: u64 }         // bumped by every removal
fn find2(l: &Log, key: Int) -> own Option<Stamp>    // Stamp { i: u64, epoch: u64 }
if s.epoch == l.epoch && s.i < len_of(l.v) { charge(&l.v[s.i], amount) }
```
Runtime cost versus C++/Rust: one extra load (the epoch word, adjacent to the
header and normally in the same cache line) plus one compare and one branch per
use, and the writer must supply a behaviour for the stale arm. A C++ or Rust
program that also uses indices pays the same; a Rust program that keeps `&mut
Entry` across the mutation is rejected at compile time for free, and that option
is closed here.

Rules consistent: yes - nothing in Rules 4, 6, 7, 11 or 12 is violated, which is
the point.   Task achievable: yes for the computation, no for the identity
guarantee without the epoch check.
Depends on: Rule 7, Rule 11, Rule 12; same phenomenon at pool scale in 4-16.
Verdict: accepted-unsafe

### 4-7: Rule 4 and bounds: what a returned index proves

Question: does the contract on an index or range returned by a search carry
exactly the fact Rule 7 demands, for a data-determined result?

Strongest program:
```text
fn equal_range(v: &DynBox<Entry>, key: Int) -> own Pair       // Pair { lo: u64, hi: u64 }
    reads(v)
    contract { ensures result.lo <= result.hi; ensures result.hi <= len_of(v); }

r    = equal_range(&v, k)                     // lo, hi are data-determined
part = &v[r.lo..r.hi]                         // Rule 7: requires lo <= hi <= len_of(v)
m    = len_of(part) / 2
par { kernel(&part[0..m], &out[0..m]); kernel(&part[m..len_of(part)], &out[m..len_of(part)]) }
```

Ordinary program:
```text
fn find2(vv: &DynBox<DynBox<Entry>>, k: Int) -> own Pair      // outer i, inner j
    contract { ensures result.i < len_of(vv); /* inner bound? */ }
if r.j < len_of(vv[r.i]) { use(&vv[r.i][r.j]) }
```

Trace: Rule 4 - "returns an index or other owned data" - and Rule 15 - "A
function returns owned values only" - admit `Pair`, which Rule 1 admits because
it holds two `u64`. Rule 11's fact language, "affine comparisons over measures
and integer values", covers both `ensures` clauses, and Rule 7 requires exactly
`lo <= hi <= len_of(buf)` and then gives `len_of(part) == hi - lo` for free, so
the range reference is formed with no runtime test even though nothing static
knows `lo` or `hi`. Rule 13 then splits `part` by an affine midpoint. This is the
designed path and it works end to end.
The nested case is weaker: the inner bound would be `result.j <
len_of(vv[result.i])`, a measure over a path containing the result. Rule 11's
grammar does not obviously admit it and Rule 9's "Signatures never contain index
expressions" governs effect rows rather than contracts, so the conservative
reading costs one test - licensed by Rule 7, "when the proof is unavailable the
program tests the measure, which is ordinary data ... one compare, no trap".

Rewrite and cost: none needed for the range form. For the nested form, one
compare per lookup against a C++ pointer-pair return; the inner header load it
needs is the same load the address computation needs anyway.

Rules consistent: yes.   Task achievable: yes.
Depends on: Rule 1, Rule 11, Rule 13, Rule 15.
Verdict: accepted-fine

### 4-8: Rule 4 and linearity: consuming a resource that no reference may carry out

Question: can a linear value located by a search be serviced in place and
discharged on every exit path, given that nothing may be moved out through a
reference?

Strongest program:
```text
linear type File;  fn close(f: own File)
pool: DynBox<Option<File>>                       // linear by containment (Rule 8)

i = find_idle(&pool)?                            // Rule 4: an index, not a reference
pool[i] = recycle(pool[i])                       // Rule 6 atomic update
fn recycle(x: own Option<File>) -> own Option<File>
    { match x { Some(f) => { close(move f); None }  None => None } }

while len_of(pool) > 0 { s = pop(&pool); discard(move s) }    // drained before scope exit
fn discard(x: own Option<File>) { match x { Some(f) => close(move f)  None => } }
```

Trace: Rule 8 - "Linear values must be consumed by an explicit operation on every
exit path; the compiler never releases them" - and Rule 6 - "where it is linear
the assignment is rejected unless written as the atomic update whose function
consumes the old value" - together make the atomic update the in-place service
form, and it is exactly the form Rule 4 leaves reachable, since the locator is an
index and the value never travels as a reference. `pop` is a window operation
returning `own T`, so `s` is "a whole local" and `move s` is admitted by Rule 6's
enumeration. Rule 11's loop form supplies `len_of(pool) > 0` for `pop`'s
`requires` from the loop condition, as in Rule 11's own example.
A by-reference service is not available: `writes(p)` "covers writing, replacing,
moving out of, and freeing the storage at the path" (Rule 9), but Rule 6's
enumeration of ways to move a value out of storage does not include a reference
target, and Rule 12 forbids the hole that would result. So linear values are
serviced by value or by atomic update, which is the zero-copy form anyway.
Two boundaries this program deliberately avoids, both quoted for the record:
Rule 6 says a linear DynBox "must be truncated to zero by the program before it
can go out of scope", while `truncate`'s contract has no linear-element
`requires` and Rule 8 says "the compiler never releases them"; and Rule 8's own
example writes `close(move c.f)`, a partial move out of a local, against Rule 6's
"no partial move out of any place" and Rule 12's "No place is ever partially
moved". Draining by `pop` and making the element type itself linear keeps the
derivation clear of both.

Rewrite and cost: none needed. One branch on the `Option` per serviced slot,
identical to C++ `std::optional<File>::reset` or Rust `Option::take`; the drain
loop is the destructor loop C++ would run.

Rules consistent: yes for the form used; two sentences pull against each other
just outside it.   Task achievable: yes.
Depends on: Rule 6, Rule 9, Rule 11, Rule 12, Rule 15.
Verdict: accepted-fine

### 4-9: Rule 4 and effect rows: the caller forms the reference, the row names no index

Question: Rule 4 makes the caller form every reference and Rule 9 lets an index
enter an effect only as an argument; do they compose for a callee that must
initialize the slot the caller found?

Strongest program:
```text
fn build_into(slot: &Entry, src: &Src)  writes(slot), reads(src)   // Rule 15's large-value form
push_nogrow(&buf, empty_entry)                                     // make the slot exist
build_into(&buf[len_of(buf) - 1], &s)                              // initialize it in place

put_at(&buf[len_of(buf)], 3)                                       // Rule 9's own example
```

Ordinary program:
```text
fn bump_at(v: &DynBox<Int>, k: u64)  writes(v[k])                  // index supplied as an argument
i = find(&v, a)?;  j = find(&v, b)?
bump_at(&v, i);  bump_at(&v, j)                                    // sequential: fine
```

Trace: the ordinary program is the clean composition. Rule 9 - "An effect row
lists `reads(path)` and `writes(path)` where each path starts at a reference
parameter and may continue through fields, `*`, and whole-index or range
positions supplied as arguments ... Signatures never contain index expressions;
an index enters an effect only through an argument, evaluated once at the call."
Rule 4's index-returning search is precisely the supplier of that argument, so
the two rules reinforce: hoisting the search out of the callee (which Rule 4
forces) is what lets the callee's row stay narrow at `v[k]` instead of widening
to `v`, and a callee that searches internally must declare `writes(v)` and
destroys the caller's disjointness. Pairwise conflict between two such calls is
4-10.
The strongest program hits a contradiction. Rule 9's example forms
`&buf[len_of(buf)]`. Rule 6: "Reading `buf[k]` or forming `&buf[k]` requires the
fact `k < len_of(buf)` (Rule 7)." Rule 7: "buf: DynBox<Int>;  buf[i]  //
requires i < len_of(buf)". `len_of(buf) < len_of(buf)` is false, so the example
and the requirement cannot both stand; and Rule 6 also says slots
`[len_of, cap_of)` "hold nothing" and that `len_of` is "changed only by the
built-in operations below", so a write through such a reference would not move
the boundary. The text neither grants an append-slot reference nor explains the
example. This is load-bearing: that shape is the only one that would let a callee
construct a large element directly in the heap block.

Rewrite and cost: build in a local and move it in - `x = make(&s);
push_nogrow(&buf, move x)` - or push a cheap placeholder and write through
`&buf[len_of(buf) - 1]`, which is in bounds and needs no new rule. The first
costs one copy of `sizeof(Entry)` unless the built-in `push_nogrow` is lowered
so the argument is materialized at its destination, against C++'s `emplace_back`
which constructs there by construction; the second costs one initialization of
the placeholder, which is free when `Entry`'s bulk is a `DynBox` field and is a
full `sizeof(Entry)` store when it is inline.

Rules consistent: no - Rule 9's example contradicts Rule 6's and Rule 7's
forming requirement.   Task achievable: rewrite, at one copy or one placeholder
initialization per element.
Depends on: Rule 6, Rule 7, Rule 10, Rule 15.
Verdict: undecided-rule-gap

### 4-10: Rule 4 and the call-site rule: pairwise disjointness over data-determined indices

Question: when every reference is formed at the call site from an index that only
data determines, what does Rule 10's pairwise check cost?

Strongest program:
```text
perm: DynBox<u64>;  v: DynBox<Entry>
fn swap2(a: &Entry, b: &Entry)  writes(a), writes(b)

for i in 0..n {
    invariant h: n <= len_of(v);
    j = perm[i]                        // requires i < len_of(perm); j is data
    swap2(&v[i], &v[j])                // substituted: writes(v[i]), writes(v[j])
}
```

Ordinary program:
```text
p = &v[i]
push_nogrow(&v, move x)                // writes(v)
use(p)                                 // rejected by Rule 10.3 / Rule 3
```

Trace: Rule 10 - "At a call, substitute the actual argument paths into the
callee's row. Then: 1. Compare the substituted effects pairwise. Two effects on
overlapping paths where at least one is a write must be proved disjoint
(different roots, or indices or ranges proved distinct); otherwise the call is
rejected." Both paths root at `v` and both are writes; `i` and `j = perm[i]` have
no affine relation and Rule 11 offers none that data can supply, since "There are
no quantified facts over array elements" and no fact about `perm`'s contents
exists. Rejected. Rule 10.2 would fold a by-value argument's consumption into the
same comparison; not needed here. Rule 10.3 governs the ordinary program: "A live
reference outside the call whose path has a proper prefix among the call's write
paths becomes invalid after the call (Rule 3)" - `v` is a proper prefix of
`v[i]`, so `p` dies at the push, and Rule 4 forbids parking it anywhere, so it
must be re-formed. Note the narrow case survives: `writes(v[i])` does not have
`v` as a write path, so a bystander `&v[k]` is untouched by `bump_at(&v, i)`.

Rewrite and cost:
```text
if i != j { swap2(&v[i], &v[j]) }      // Rule 11: refinement fact from a dominating branch
```
One compare and one well-predicted branch per swap against C++'s unguarded
`std::swap(v[i], v[j])`, which is correct when `i == j`; zero against safe Rust,
which needs the same guard or `split_at_mut`. No form removes it: the
out-of-place version `out[i] = v[perm[i]]` needs no guard because it has one
write path, but costs a second buffer of `n * sizeof(Entry)` and `n` extra
element copies, which is strictly worse. For the ordinary program, re-forming
`p = &v[i]` after the call costs one header load and one shift-add, which C++
skips when it knows no reallocation occurred; here the callee's row is the only
information, and `push_nogrow` cannot reallocate but says so only in its
contract, not in a way that keeps a reference alive.

Rules consistent: yes - the rejection is exactly the unproved aliasing.
Task achievable: rewrite.
Depends on: Rule 3, Rule 7, Rule 11.
Verdict: rejected-real-cost

### 4-11: Rule 4 and facts: indices stored in bulk carry no invariant

Question: indices are the only locators that may be stored or returned; what can
be proved about them once there are many?

Strongest program:
```text
struct Node { first_edge: u64, n_edges: u64, data: u64 }
nodes: DynBox<Node>;  edges: DynBox<u64>          // Rule 1: targets are data, not references

fn sweep(nodes: &DynBox<Node>, edges: &DynBox<u64>, u: u64) -> u64  reads(nodes), reads(edges)
{
    acc = 0;  e = nodes[u].first_edge;  last = e + nodes[u].n_edges
    while e < last {
        invariant b: last <= len_of(edges);
        t = edges[e]                              // data; nothing static knows its range
        if t < len_of(nodes) { acc = acc + nodes[t].data }    // the test is required
        e = e + 1
    }
    acc
}
```

Trace: Rule 4 forbids an edge holding a reference to its target and Rule 1
forbids storing one in `Node`, so `t` is an integer. Rule 7: "Every index must be
proved in bounds; when the proof is unavailable the program tests the measure,
which is ordinary data." The natural one-line justification - every entry of
`edges` is below `len_of(nodes)` - is a quantified fact over array elements, and
Rule 11 says "There are no quantified facts over array elements ('for all i
...') and no per-slot occupancy facts". Rule 11's available forms are affine
comparisons over measures and integers, refinement facts from a dominating
branch, loop-header invariants and callee contracts; none of them can summarize
`len_of(edges)` values at once. So the fact must be re-established per
dereference, and it can only be re-established by a test.

Rewrite and cost: none removes the test. `len_of(nodes)` is loop-invariant
because `nodes` is only read, so the header load hoists out of the loop; what
remains is one compare and one never-taken branch per edge, plus a written
behaviour for the impossible arm, and the branch splits the loop body so the
gather does not stay straight-line. Against safe Rust the cost is zero - `nodes[t]`
emits the same check - but against C++ or `get_unchecked` it is one compare per
edge, and the candidate has no unsafe escape and no refined index type, so this
is a ceiling rather than a choice. Storing `Box<Node>` targets is not an option
for a shared, cyclic graph (Rule 5 is single-owner), and a range reference
narrows the container, not the element index.

Rules consistent: yes.   Task achievable: yes, at one compare per hop.
Depends on: Rule 1, Rule 5, Rule 7, Rule 16 (when the graph is a pool).
Verdict: rejected-real-cost

### 4-12: Rule 4 and joins: a rebound reference at a loop header

Question: with references neither returned nor stored, a linked walk must be a
rebound local reference; what is its target set at a loop header?

Strongest program:
```text
cur = &head                                  // cur: reference to Option<Box<Node>>
while is_some(cur) {
    touch(cur)                               // writes(*cur)
    cur = &(*content(cur)).next              // rebind: one link longer each iteration
}
```

Ordinary program:
```text
r = find(&v, k)                              // Option<&Entry> is rejected by Rule 1
match r { Some(i) => { p = &v[i]; use(p) }  None => ... }

w = if cond { &v1 } else { &v2 }             // Rule 2: target set {v1, v2}
bump(w)                                      // effect charged to both
```

Trace: Rule 4 forces the walk into one frame - "cannot be returned" closes
`fn next_of(n: &Node) -> &Node`, and "cannot be assigned into any aggregate"
closes a stored cursor - so the only shape left is a reference rebound on a back
edge. Rule 2: "A reference may be rebound. At a control-flow join, a reference
variable's target is the set of paths it may name; every check on it must hold
for every member of the set." Rule 12: "At a join, facts are intersected (a fact
survives only if it holds on every incoming edge); a reference's target set is
the union of its targets (Rule 2)." At the loop header the incoming edges carry
`head`, `head.next`, `head.next.next`, ...; the union is infinite, and no rule in
the file gives a finite representation, a widening, a depth bound, or a rejection.
Every join example in the file is a two-armed `if`.
The ordinary program is fully decided and cheap: Rule 1 rejects `Option<&T>`
("`Option<&T>` // rejected, whatever T is"), `Option<u64>` carries the same word,
and the `Some` arm re-forms the reference for one address computation. The
branch-selected reference is accepted with a two-element target set; because
"every check on it must hold for every member of the set", `bump(w)` is charged
`writes(v1)` and `writes(v2)`, which costs nothing at runtime - proofs are erased
and the selection is a `cmov` exactly as in C++ - but blocks a sibling par arm
that touches `v2`. Duplicating the call into both arms restores precision at zero
runtime cost, since Rule 12 intersects per edge.

Rewrite and cost for the walk: (a) recursion, where each frame's reference
"starts at a local variable or a parameter" (Rule 2) so the target set is a single
path, and Rule 10's "Recursion is checked through contracts, never by unfolding
bodies" keeps checking finite; runtime cost is one call and return per hop unless
the self tail call becomes a jump, which no rule in the file guarantees.
(b) a Rule 16 pool with `u64` links, where nothing is rebound; runtime cost is
one compare per hop (4-11). Against a C++ `for (Node* p = head; p; p = p->next)`
either rewrite adds about one instruction per hop.

Rules consistent: cannot tell - the join rule is stated only for forward joins
and the file's loop examples carry facts, never a reference.   Task achievable:
rewrite, at roughly one instruction per hop.
Depends on: Rule 1, Rule 2, Rule 10, Rule 16 (fallback (b)).
Verdict: undecided-rule-gap

### 4-13: Rule 4 and par: the locate step cannot happen inside the region

Question: Rule 4 puts locating in the caller's frame; what does that do to a
parallel region whose arms must each find their own target?

Strongest program: a dynamic work queue over an irregular frontier.
```text
queue: DynBox<u64>;  g: Graph
fn work(g: &Graph, q: &DynBox<u64>)  writes(q), writes(g.data)   // pops its own next item
par { work(&g, &queue); work(&g, &queue) }
```

Ordinary program:
```text
par { i = find(&v, a); j = find(&v, b) }          // read/read on v, distinct result locals
if i != j { par { bump(&v[i]); bump(&v[j]) } } else { bump(&v[i]) }
```

Trace: Rule 13 - "`par { A; B }` is accepted when A's write paths are disjoint
from B's read and write paths and vice versa, using the same path-overlap and
index/range-disjointness judgment as Rule 10. Read/read overlap is allowed."
Both arms of the strongest program declare `writes(q)` on the same root:
rejected. Nothing in the candidate routes around it - "Not in this candidate"
excludes "channels or atomics", and Rule 14's allocator exemption covers
allocation only. The same rule also forbids fusing a locate into an arm that
writes: `par { i = find(&v, a); bump(&v[j]) }` compares `reads(v)` against
`writes(v[j])`, and `v` is a proper prefix of `v[j]`, so the paths overlap and
one is a write - rejected however the index is chosen. So Rule 4's locate step
must be hoisted out of every region that writes the same container, which is
exactly what the ordinary program does; and hoisting is cheap because Rule 4
already made the locate return an index rather than something that would have to
stay live. The ordinary program is Rule 13's own second example, `par { bump(&v[i]);
bump(&v[j]) } // needs i != j`, with the fact supplied by a dominating branch
(Rule 11).

Rewrite and cost: partition the frontier into disjoint ranges before the region
and give each arm its own range, per Rule 13's "The existing counted-loop forms
(per-element maps, adjacent ranges passed to a helper, admitted reductions) are
expressed with range references". Runtime cost: the split is fixed before the
region begins, so an irregular workload keeps its imbalance and the slowest arm
sets the wall time, where C++ TBB or Rust Rayon re-balances by stealing. The
loss is workload-dependent and unbounded in the worst case (one arm holding the
whole frontier), and it is the already-recorded cost "Lock-free rings are not
expressible; batched fork-join with two buffers is the available form".
Re-partitioning between rounds recovers most of it for a bulk-synchronous
frontier at the price of one extra pass over the frontier per round: `|F|` reads
and writes that the stealing version does not perform. The one-compare guard in
the ordinary program is zero against safe Rust and one compare against C++.

Rules consistent: yes - the rejected form is a genuine race on `queue`.
Task achievable: rewrite for regular and bulk-synchronous work; no for dynamic
load balancing.
Depends on: Rule 9, Rule 10, Rule 11, Rule 14.
Verdict: rejected-real-cost

### 4-14: Rule 4 and the allocator: ownership escapes where a reference may not

Question: does the no-escape rule interfere with a helper that allocates, or with
allocation inside a parallel arm?

Strongest program:
```text
fn build(src: &Src) -> own Box<Node>  reads(src)      // ownership leaves; no reference does
par { a = build(&x)?; b = build(&y)? }                // Rule 14's own example
holder.child = move a                                 // Rule 5: a Box in a field
p = &(*holder.child).left                             // the caller forms its own reference
```

Trace: Rule 14 - "Allocation and release carry no effect entry and never make two
parallel arms conflict ... Addresses are not observable, so allocator concurrency
does not affect program determinism" - so the two arms compare only `reads(x)`
against `reads(y)` and are accepted by Rule 13. Rule 4 restricts references, not
ownership, and Rule 15 admits the owned `Box`, so Rule 5's Box is the escape
hatch Rule 4 leaves open, and it is the same value a C++ factory returns. The
caller then forms whatever reference it wants locally, which Rule 4 permits.
Failure arms: "Allocation returns a `Result` and never traps"; with no
destructors (Rule 8) an early return releases affine values recursively and runs
no user code, while a linear value in scope must be consumed on that path by the
writer's own branch - no runtime flag, matching P8's requirement. What the rules
do not define is what `?` inside a par arm means for the sibling arm; that is
13-14.

Rewrite and cost: none needed for the shape. One cost is worth naming:
`Box::new(v)?` takes `own T`, so a large inline `T` is materialized in a local
and then moved into the heap - one copy of `sizeof(T)` that C++'s placement-new
avoids and that Rust also pays. The zero-cost form under these rules is to keep
the bulk in a `DynBox` field and allocate it directly: `DynBox::new(n)?` and
`DynBox::filled(n, v)?` produce the block with nothing materialized on the stack,
and `filled` needs `T` Copy (Rule 6). The general in-place answer - a callee
initializing the append slot - is blocked by 4-9's contradiction.

Rules consistent: yes.   Task achievable: yes.
Depends on: Rule 5, Rule 8, Rule 13, Rule 15; 13-14 for `?` inside an arm.
Verdict: accepted-fine

### 4-15: Rule 4 and owned returns: selecting one of two places

Question: Rule 4 forbids returning a reference and Rule 15 requires returns to be
owned; what does "pick one of these and act on it" cost?

Strongest program (P9's `pick`):
```text
fn pick(c: Bool, x: &Obj, y: &Obj) -> &Obj                  // rejected
fn pick_tag(c: Bool, x: &Obj, y: &Obj) -> Bool  reads(x), reads(y)     // owned result

t = pick_tag(c, &x, &y)
p = if t { &x } else { &y }                                 // Rule 2: target set {x, y}
update(p)                                                   // charged writes(x) and writes(y)
```

Ordinary program:
```text
fn transform(dst: &Big)  writes(dst)        // Rule 15's in-and-out form
transform(&big)                             // instead of big = transform(move big)
```

Trace: Rule 4 - "cannot be returned"; Rule 15 - "A function returns owned values
only. Positions found by a search are returned as indices with a bounds relation
in `ensures` (Rule 4)." So the selection itself moves to the caller, where Rule 2's
join gives the two-element target set and "every check on it must hold for every
member of the set". At runtime nothing is lost: proofs are erased before
lowering, `p` is one pointer, and the branch is the same select C++ emits for
`c ? &x : &y`. What is lost is effect precision - a sibling par arm touching `y`
is rejected even on the branch that chose `x` - and duplicating the call into
both arms recovers it at no runtime cost, since Rule 12 intersects facts per
edge and each edge then carries a single target.
The ordinary program shows the two rules cooperating rather than fighting: Rule 15
says "Passing a large value in and back out is expressed as a reference parameter
with a `writes` entry, not as move-and-return", which is both the zero-copy form
and the form whose row gives Rule 13 its disjointness (13-15). A `-> own Big`
return remains legal for construction, where there is no incoming value to copy.
The residue is the case where the two candidates live deep inside a callee's data
so the caller cannot name either: no reference may be returned, no index names a
Box-linked place (4-5), and the operation must be pushed into the callee, which
needs 4-4's capture question or an explicit context parameter.

Rewrite and cost: `pick_tag` plus a caller-side select - zero runtime cost
against C++'s returned pointer, one select either way.

Rules consistent: yes.   Task achievable: rewrite, zero cost for caller-visible
places.
Depends on: Rule 2, Rule 12, Rule 13; 4-4 and 4-5 for the deep case.
Verdict: rejected-zero-cost

### 4-16: Rule 4 and pools: an index is not invalidated by removal

Question: with Rule 16's pool, does the Rule 4 index recover what a reference
would have given for a mutable graph with slot reuse?

Strongest program (P3, and the mutable-compiler-graph task):
```text
struct Node { next: u64, prev: u64, data: u64 }     // Rule 1: handles, not references
a: Arena<Node>

m = alloc(&a, node)?                     // Rule 16: ensures result == len_of(deref(entry(a.buf)))
link(&a.buf, p, m); link(&a.buf, m, q)
unlink(&a.buf, m)                        // m leaves the list; its slot joins a free list
k = alloc_reuse(&a, other)?              // reuses slot m
walk(&a.buf, start)                      // a node still holding next == m now walks into k
```

Trace: Rule 16 - "A stale index that is still in bounds names the current
occupant of that slot: a logic error, not a memory error. Programs that need to
detect it keep a generation number as data." Rule 3's protection - "invalidated
when any proper prefix of p's path is written ... Using an invalid reference is
rejected" - never applies, because Rule 4 keeps references out of the structure
entirely: "It cannot be assigned into any aggregate (Rule 1)". So nothing in the
graph is under Rule 3's regime and the silent re-pointing is accepted with no
diagnostic. The engineering task states the opposite requirement - "a relation to
a deleted node must not silently become a relation to a replacement node"
(PROGRAMS.md, mutable compiler graph), and P3 requires "removal invalidates every
path to m". Memory safety is intact throughout: every dereference still proves
`t < len_of(a.buf)` (Rule 7) and Rule 12 guarantees the slot holds a valid value
("a 'logically empty' slot holds a valid value"), so there is no corruption, no
uninitialized read and no trap.
Same cell, opposite direction: Rule 16's contract is strong enough to prove
successive allocations distinct without any runtime check. `i1 = alloc(...)`
gives `i1 == L0` and `len_of(a.buf) == i1 + 1`; the second call's `entry` term
(Rule 11: "the pre-state of a parameter is written `entry(p)`") ties `i2 ==
len_of(deref(entry(a.buf))) == i1 + 1`, so `i1 != i2` is affine and Rule 10.1's
"indices ... proved distinct" is discharged. That is what makes P2's parallel
fill free (13-16).

Rewrite and cost: generation numbers, exactly as Rule 16 says.
```text
struct Handle { idx: u64, gen: u64 }
struct Node { gen: u64, next: Handle, prev: Handle, data: u64 }
if h.idx < len_of(a.buf) && a.buf[h.idx].gen == h.gen { ... }
```
Runtime cost per hop: one extra load (the generation word, normally in the same
cache line as the node) plus one compare and branch, on top of 4-11's bounds
compare; and every stored link grows from 8 to 16 bytes, which doubles the
bandwidth of a link-following traversal and halves the number of edges per cache
line - the dominant cost in pointer-chasing workloads. Against C++ with raw
pointers and slot reuse, safety is equal (both silently re-point) and the
generation word is pure overhead; against a Rust `Vec<Node>`-plus-index pool it
is identical; against Rust references the graph is not expressible at all, so
there is no cheaper safe baseline to lose to.

Rules consistent: yes - Rule 16 states this outcome deliberately.
Task achievable: rewrite, at one load, one compare and 8 extra bytes per link.
Depends on: Rule 16 (provisional pool rule), Rule 1, Rule 3, Rule 7, Rule 11,
Rule 12.
Verdict: accepted-unsafe

### 13-13: par inside par: recursion, nesting and data-determined splits

Question: does a parallel region nest inside a parallel arm, to arbitrary depth,
when the split point is decided by data?

Strongest program: parallel quicksort, pivot position decided at runtime.
```text
fn partition(v: &DynBox<Entry>, lo: u64, hi: u64) -> u64   writes(v[lo..hi])
    contract { requires lo <= hi; requires hi <= len_of(v);
               ensures lo <= result; ensures result < hi; }

fn qs(v: &DynBox<Entry>, lo: u64, hi: u64)  writes(v[lo..hi])
    contract { requires lo <= hi; requires hi <= len_of(v); }
{
    if hi - lo < 2 { return }
    p = partition(&v, lo, hi)
    par { qs(&v, lo, p); qs(&v, p + 1, hi) }
}
```

Ordinary program: parallel mergesort, two containers split the same way.
```text
fn ms(a: &DynBox<Entry>, t: &DynBox<Entry>, lo: u64, hi: u64)  writes(a[lo..hi]), writes(t[lo..hi])
{
    if hi - lo < 2 { return }
    m = lo + (hi - lo) / 2
    par { ms(&a, &t, lo, m); ms(&a, &t, m, hi) }
    merge(&a, &t, lo, m, hi)
}
```

Trace: Rule 9 admits the rows - each path "starts at a reference parameter and
may continue through fields, `*`, and whole-index or range positions supplied as
arguments", and `lo`, `hi`, `p` are arguments, so `writes(v[lo..hi])` contains
no index expression of its own. Rule 13: "`par { A; B }` is accepted when A's
write paths are disjoint from B's read and write paths and vice versa, using the
same path-overlap and index/range-disjointness judgment as Rule 10." The
substituted rows are `writes(v[lo..p])` and `writes(v[p+1..hi])`; Rule 10.1's
"ranges proved distinct" follows from `p < p + 1` together with `partition`'s
`ensures lo <= result` and `ensures result < hi`, all affine comparisons over
integer values (Rule 11). The pivot is data-determined and the proof still goes
through, because the contract - not the value - carries the relation. Rule 10's
"Recursion is checked through contracts, never by unfolding bodies" makes depth
irrelevant: each level re-proves the same two-range disjointness against its own
parameters, so nesting is unbounded at no checking cost. Rule 14 keeps any
allocation inside an arm from conflicting. The mergesort variant shows the same
judgment applied to two roots at once, with the scratch buffer split identically
and no arm-private allocation or copy that the sequential version avoids.
One step the file leaves implicit: Rule 9 requires "every statement's effect ...
be covered by the declared row", so a `par` block nested in an arm must have an
effect of its own; the union of its arms is the only reading consistent with
Rule 9, and it is what lets `writes(v[lo..p]) union writes(v[p+1..hi])` sit
inside the outer `writes(v[lo..hi])`. Rule 13 also defines only the binary form,
so a three-way region is written as nested binary blocks, which under the union
reading compares all three pairwise and costs nothing.
Where nesting stops being derivable from the text: the counted-loop family.
Rule 13's last sentence - "The existing counted-loop forms (per-element maps,
adjacent ranges passed to a helper, admitted reductions) are expressed with range
references." - admits a flat family by naming it. A tiled kernel nests one
adjacent-range loop inside another with a runtime stride, and the cross-iteration
relation `w*s + s <= (w+1)*s` is a product of two program variables, outside
Rule 11's "affine comparisons over measures and integer values"; whether the
named family extends to the nested form is not stated.

Rewrite and cost: none needed for the recursive form - it is the C++ or Rust
divide-and-conquer with the same partition, the same comparisons and the same
available parallelism, and the disjointness proof is erased before lowering. For
a two-level tiling that the family does not reach, the fallback is an outer
`DynBox<DynBox<T>>` of tiles, where arms differ by outer index and distinctness
is the simple affine case; runtime cost is one extra dependent load per tile,
one allocation per tile, and the loss of a single contiguous buffer for any
later full-array pass - real, but small relative to a blocked kernel's own work.

Rules consistent: yes.   Task achievable: yes for recursive divide and conquer;
the nested counted-loop tiling needs the fallback representation.
Depends on: Rule 9, Rule 10, Rule 11, Rule 14.
Verdict: accepted-fine

### 13-14: par and the allocator: two arms that both allocate and both can fail

Question: when both arms allocate and either may fail, what is the joint outcome
of the region?

Strongest program: Rule 14's own example, under real memory pressure.
```text
par { a = build(&x)?; b = build(&y)? }       // each arm allocates; each `?` leaves the function
```

Ordinary program: failure kept inside the arm.
```text
par { ra = build_res(&x); rb = build_res(&y) }     // own Result<Box<Node>, Oom> in each arm
match (ra, rb) { (Ok(a), Ok(b)) => ...
                 (Err(e), Ok(b)) => ...            // b is affine; Rule 8 releases it on the discard path
                 (Ok(a), Err(e)) => ...
                 (Err(e), Err(_)) => ... }         // the writer picks which error is reported
```

Trace: Rule 13's acceptance is immediate. Rule 14: "Allocation and release carry
no effect entry and never make two parallel arms conflict", so the arms compare
only `reads(x)` against `reads(y)`, and "Allocation returns a `Result` and never
traps" makes the failure a value rather than an event.
The gap is what `?` means inside an arm. The file shows the construct
(`par { a = build(&x)?; b = build(&y)? }`) and defines nothing about control flow
leaving an arm: whether the sibling runs to completion, is abandoned or is
joined first; which error is returned when both arms fail; and what becomes of
the sibling's partially built values. Rule 8 covers affine values only "at scope
exit", which presumes the arm's scope exits normally, and a linear value held by
the abandoned arm "must be consumed by an explicit operation on every exit path"
with no exit path defined to speak of. Separately, Rule 14's determinism argument
- "Addresses are not observable, so allocator concurrency does not affect program
determinism" - gives a reason that does not cover failure: under a budget, which
arm gets the memory and therefore which arm returns `Err` is decided by the order
the arms reach the internally synchronized allocator, and that outcome is
observable. The sentence is true of addresses and does not settle the claim it is
attached to.

Rewrite and cost: the ordinary program. Both arms always run to completion, every
allocated value is an owned local that Rule 8 releases recursively on the discard
path, and the reported error is chosen by the writer rather than by the
scheduler. Runtime cost against C++ or Rust: none - the same allocations, the
same parallelism, one extra branch after the join, which a C++ version collecting
two futures also writes. Whether an arm fails at all under pressure remains
allocator-order-dependent, but that is equally true of C++ and Rust and is not a
cost.

Rules consistent: cannot tell for the `?` form; the arm-local form is consistent.
Task achievable: rewrite, at zero runtime cost.
Depends on: Rule 8, Rule 13, Rule 15.
Verdict: undecided-rule-gap

### 13-15: par and owned returns: how a result leaves an arm

Question: with returns owned and no reference allowed to escape, how does a
parallel arm deliver a result, and what does that cost?

Strongest program: parallel filter, output counts decided by the data.
```text
fn count_hits(v: &DynBox<Entry>, lo: u64, hi: u64) -> u64  reads(v[lo..hi])
    contract { requires lo <= hi; requires hi <= len_of(v); ensures result <= hi - lo; }
fn emit(v: &DynBox<Entry>, lo: u64, hi: u64, out: &DynBox<Entry>, olo: u64, ohi: u64)
    reads(v[lo..hi]), writes(out[olo..ohi])
    contract { requires ohi - olo == count_of_hits; requires ohi <= len_of(out); }

par { c1 = count_hits(&v, 0, m); c2 = count_hits(&v, m, n) }          // read/read
out = DynBox::filled(c1 + c2, blank)?
par { emit(&v, 0, m, &out, 0, c1); emit(&v, m, n, &out, c1, c1 + c2) }
```

Ordinary program: an admitted reduction.
```text
par { s1 = sum(&v, 0, m); s2 = sum(&v, m, n) }     // distinct result locals
total = s1 +wrap s2
```

Trace: Rule 13 accepts the first block because `reads(v[0..m])` and
`reads(v[m..n])` are read/read ("Read/read overlap is allowed"), and because the
two arms write two different locals. That last point is load-bearing and the
rules do cover it: Rule 2 says "A path starts at a local variable or a
parameter", so `s1` and `s2` are distinct roots and `par { s = f(&x); s = g(&y) }`
would be rejected on overlapping write paths. Rule 4 fixes the shape of the
boundary: nothing but an owned value or a write through a reference parameter
leaves an arm, so two arms cannot come to alias through a returned locator - the
one hazard a language with returned references has to check here does not exist.
The second block is where Rule 15 pays off. "Passing a large value in and back
out is expressed as a reference parameter with a `writes` entry, not as
move-and-return" produces `writes(out[0..c1])` and `writes(out[c1..c1+c2])`,
adjacent ranges whose disjointness is the affine fact `c1 <= c1` over values
already in registers (Rule 11), so Rule 10.1 is discharged with no runtime check.
Had each arm instead returned `own DynBox<Entry>`, the results would be disjoint
by construction but would cost one allocation per arm plus a concatenation pass
of `c1 + c2` element copies. So the rule that forbids move-and-return for large
values is also the rule that produces the parallel form.
The reduction case is Rule 13's "admitted reductions" clause; `+wrap` is in the
fixed operation table named by the capability floor, and ordinary checked
addition or floating point is not generalized to by this derivation.

Rewrite and cost: none needed. The shape is the standard two-pass parallel
filter - count, prefix, scatter into disjoint ranges - which is what C++ and Rust
write as well; the prefix step is one addition because Rule 13's block is binary.
A single-pass scatter with atomic offsets is cheaper in C++ and is not expressible
here ("Not in this candidate": "channels or atomics"); that cost is booked in
4-13 and 13-16, not in this cell.

Rules consistent: yes.   Task achievable: yes.
Depends on: Rule 2, Rule 4, Rule 10, Rule 11, Rule 15.
Verdict: accepted-fine

### 13-16: par and pools: allocating from one arena, and scattering into one pool

Question: can parallel arms allocate from a shared arena, and can they write
nodes they select by data?

Strongest program: parallel scatter over a pool (histogram, PageRank push).
```text
fn push_edges(nodes: &DynBox<Node>, edges: &DynBox<Edge>, lo: u64, hi: u64)
    reads(edges[lo..hi]), writes(nodes)            // the written index comes from the edge data
par { push_edges(&nodes, &edges, 0, m); push_edges(&nodes, &edges, m, n) }
```

Ordinary program: P2's three independently filled blocks.
```text
i1 = alloc(&a, blank)?;  i2 = alloc(&a, blank)?;  i3 = alloc(&a, blank)?
par { fill(&a.buf[i1]); par { fill(&a.buf[i2]); fill(&a.buf[i3]) } }
```

Trace: the strongest program is rejected by Rule 13 - both arms declare
`writes(nodes)` on the same root, "A's write paths are disjoint from B's read and
write paths" fails on identical paths. Rule 9 cannot narrow the row, because the
written index is read out of `edges` rather than supplied at the call: "an index
enters an effect only through an argument, evaluated once at the call". Rule 11
cannot prove the scattered targets distinct - there are no facts about the
contents of `edges` and "There are no quantified facts over array elements". No
atomic exists to make the conflict legal.
The ordinary program is accepted with no runtime check, and the proof is worth
spelling out because it is Rule 16 earning its place. `alloc` gives `ensures
result == len_of(deref(entry(a.buf)))` and `ensures len_of(a.buf) == result + 1`;
Rule 11's `entry` pre-state ties each call's entry length to the previous call's
`ensures`, so `i2 == i1 + 1` and `i3 == i2 + 1`, all affine. Rule 10.1's "indices
or ranges proved distinct" is then discharged for each pair, and Rule 13 accepts
the nested binary blocks, whose combined effect is the union of the three
`writes(a.buf[ik])` paths. So P2's "`fill(b1) || fill(b2) || fill(b3)` must be
permitted to overlap" holds exactly, with no guard and no metadata read inside
the region.
Two further consequences in the same cell. Parallel allocation from one arena is
rejected, because `alloc` declares `writes(a.buf)` and two arms conflict on it;
and an arm that reads `a.buf[id]` while a sibling calls `truncate(&a.buf, 0)` is
rejected on `reads` against `writes`, so Rule 16's stale-index hazard (4-16) can
never become a data race - it stays a sequential logic error.

Rewrite and cost: for the scatter, (a) privatize - one accumulator array per arm
and a reduction afterwards, costing `P * len_of(nodes) * 8` bytes and a merge
pass, which for a graph with millions of vertices exceeds the traversal itself;
or (b) transpose - build the in-edge list once and pull instead of push, costing
`|E| * 8` extra bytes held permanently plus one transposition pass, after which
the arms write disjoint node ranges and are accepted with no check. Against C++
with one atomic add per edge, (a) costs the reduction and the memory and (b)
costs the transposed structure; both are real and neither disappears with
tuning. For parallel allocation, the rewrite is one arena per arm, which is what
C++ thread-caching allocators do anyway: zero runtime cost, at the price of
separate reservations and some fragmentation.

Rules consistent: yes.   Task achievable: rewrite for regular per-node work and
for independent block filling; no for concurrent scatter or shared-arena
allocation.
Depends on: Rule 16 (provisional pool rule), Rule 9, Rule 10, Rule 11, Rule 14.
Verdict: rejected-real-cost
