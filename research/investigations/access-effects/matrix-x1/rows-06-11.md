# Candidate x1 interaction matrix — row 6 (DynBox window) and row 11 (facts)

Derived against the frozen rule set in `CANDIDATE-X1.md` (2026-09-18) and only that
file; engineering tasks and programs P1-P19 are quoted from `PROGRAMS.md` where a
cell touches them. Nothing under "Not in this candidate", "Pending owner ruling"
(other than Rule 16, where a cell says so) or "Deferred" is used.

Rule 6 = `DynBox<T>` with a compiler-maintained window, window ops, atomic update,
no take, no holes, Vector as library code. Rule 11 = facts, contracts,
invalidation, loop invariants, data tests, no quantified facts.

Cost convention from the protocol: runtime performance only. "move" means one
relocation of `sizeof(T)` bytes, which Rule 1's consequence ("any value can be
relocated by copying its bytes (memmove, realloc), because nothing inside it
points anywhere") makes a plain byte copy with no fixup.

### 6-6: DynBox against itself — growth, nesting, and two windows in one expression

Question: when Rule 6's own operations act on a second DynBox — the Vector growth
path that must reproduce a whole window in a new block, a nested
`DynBox<DynBox<T>>`, and two slots of one window in one expression — does Rule 6
admit the operation, and what does it cost?

Strongest program (Vector growth, affine elements, order is the identity):

```text
struct Vector<T> { buf: DynBox<T> }

fn push<T>(v: &Vector<T>, x: own T) -> Result<Unit, Oom>   writes(v.buf)
{
    if len_of(v.buf) == cap_of(v.buf) {
        nb = DynBox::new<T>(2 * cap_of(v.buf) + 1)?        // cap == 2c+1, len == 0
        move_all(&v.buf, &nb)                              // the contested step
        v.buf = move nb                                    // replaces the block
    }
    push_nogrow(&v.buf, move x)
    Ok
}

// T = Box<Node>: affine, not Copy.  Element e_i must land at index i of nb.
```

Ordinary program (T Copy):

```text
i = 0
while i < len_of(old) {
    invariant a: len_of(nb) == i;
    push_nogrow(&nb, old[i])        // old[i] is a duplication, Rule 8 "Copy values may be duplicated"
    i = i + 1
}
```

Trace:

- Rule 6 asserts the library form exists: "`Vector<T>` is library code: a DynBox
  plus a `push` that, when `len_of == cap_of`, allocates a larger DynBox, moves
  `[0, len_of)` across, and replaces the old one."
- The very next sentence restricts every move out of storage: "There is no `take`
  operation and no partial move out of any place: the only ways to move a value
  out of storage are consuming a whole local (`move x`), the window operations,
  and the atomic update."
- For Copy `T` there is no conflict: `old[i]` is a read, not a move-out (Rule 8),
  `push_nogrow` requires `len_of(nb) < cap_of(nb)` which follows from
  `len_of(nb) == i`, `i < len_of(old)` and `cap_of(nb) >= len_of(old)` by affine
  comparison (Rule 11 invariant form). n copies in ascending order, one block.
- For affine `T`, `old[i]` as a source of an owned value is a partial move out of
  the place `old[i]`, which the quoted sentence forbids. The operations that do
  yield an `own T` are `pop` (the element at `len_of - 1`), `swap_remove(k)` (the
  element at `k`; the rule states only `requires k < len_of(buf)` and
  `ensures len_of(buf) == len_of(deref(entry(buf))) - 1`, the refill of slot `k`
  from the last slot being the name's meaning), and the atomic update, whose
  result "is committed" back to the same slot and therefore cannot empty it.
- So the two sentences do not agree for affine `T`. Reading (a): the growth copy
  is itself part of the window machinery, and "moves `[0, len_of)` across" names a
  bulk relocation licensed by Rule 1's consequence. Reading (b): "`Vector<T>` is
  library code" is literal and `move_all` must be written with the listed
  operations. The rule file does not say which, and the protocol forbids me
  resolving it.

Under reading (b) the task is still expressible, by a schedule that takes the
front half with `swap_remove` and the (now reversed) tail with `pop`:

```text
fn move_all<T>(old: &DynBox<T>, nb: &DynBox<T>)   writes(old), writes(nb)
    contract { requires cap_of(nb) >= len_of(old); ensures len_of(old) == 0; }
{
    n = len_of(old)
    i = 0
    while i + i + 1 < n {                       // slot i still holds e_i
        invariant a: len_of(old) == n - i;
        invariant b: len_of(nb) == i;
        t = swap_remove(old, i)                 // requires i < len_of(old): i < n - i - 1 < n - i
        push_nogrow(nb, move t)
        i = i + 1
    }
    while len_of(old) > 0 {                     // the displaced tail is in descending order
        t = pop(old)                            // requires len_of > 0: the loop condition
        push_nogrow(nb, move t)
    }
}
// n = 6: [0,1,2,3,4,5] -> sr(0)=0 [5,1,2,3,4] -> sr(1)=1 [5,4,2,3] -> sr(2)=2 [5,4,3]
//        -> pop 3, 4, 5.  nb = [0,1,2,3,4,5].  The loop bound 2i+1 < n leaves at most
//        one element between the displaced prefix and the untouched middle, which is
//        exactly what makes the pop phase ascending.
```

Both `requires` are affine comparisons over `len_of`, inside Rule 11's fact forms;
no quantified fact is needed because each step names one index.

Rewrite and cost: reading (a) costs one `memcpy` of `n * sizeof(T)` — parity with
`std::vector`'s reallocation and Rust's `RawVec` copy. Reading (b) costs, per
growth event, about `2.5n` element moves (3 per element in the `swap_remove`
phase: extract, refill, push; 2 per element in the `pop` phase) plus `2n` header
stores that a `memcpy` does not perform, and the loop is not a `memcpy` candidate
because each step's refill depends on the previous length. For a 4 MiB vector of
16-byte elements that is roughly 10 MiB of traffic instead of 4 MiB per doubling.
Nesting and same-expression aliasing need no rewrite (below).

Nested windows, `vv: DynBox<DynBox<T>>`, moving an element between two inner
buffers:

```text
t = pop(&vv[j])                     // writes(vv[j]); requires j < len_of(vv), len_of(vv[j]) > 0
push_nogrow(&vv[i], move t)         // writes(vv[i]); requires i < len_of(vv), len_of(vv[i]) < cap_of(vv[i])
```

accepted with no fact about `i` vs `j` at all, because the two calls are separate
statements and Rule 10's pairwise comparison is "At a call". Written as one
expression, `push_nogrow(&vv[i], pop(&vv[j]))`, Rule 10 clause 2 covers only
"A by-value argument contributes a consumption (`move`) or a read (copy) of its
place" and a call result has no place, so the text does not say whether the inner
`writes(vv[j])` enters the outer call's pairwise comparison. Sequencing it into two
statements removes the question at zero cost, so this does not drive the verdict.

Two slots of one window in one expression:

```text
buf[k] = merge(buf[k], &buf[m])     // fn merge(a: own T, b: &T) -> own T  reads(b)
```

Rule 10 clause 2 makes the by-value argument a consumption of the place `buf[k]`;
clause 1 compares it with `reads(buf[m])` — "indices or ranges proved distinct" —
so the call needs `k != m`. Data-determined `k, m` get it from a dominating test
(Rule 11, "refinement facts from a dominating branch") at one compare, and the
`else` arm has to be written differently anyway.

Rules consistent: no — Rule 6's "Vector is library code ... moves [0, len_of)
across" and Rule 6's "no partial move out of any place" cannot both be read
literally for an affine element type.
Task achievable: rewrite — order-preserving growth exists under either reading;
only its cost differs (1n vs 2.5n moves).
Depends on: Rule 1 (relocatability), Rule 8 (Copy duplication, affine release),
Rule 10 (pairwise, by-value place), Rule 11 (invariants), Rule 14 (fallible
allocation).
Verdict: undecided-rule-gap

### 6-7: window versus indexing and bounds

Question: when `len_of` moves under the program's feet, what does Rule 7's proof
obligation cost per access?

Strongest program (bytecode interpreter: a stack whose depth is decided by data
the compiler cannot see, inside the hot loop):

```text
fn step(code: &DynBox<u8>, stack: &DynBox<i64>, pc: u64) -> u64   reads(code), writes(stack)
{
    op = code[pc]                                  // requires pc < len_of(code)
    if op == ADD {
        if len_of(stack) >= 2 {                    // establishes len_of(stack) > 0 twice over
            a = pop(stack)                         // requires len_of(stack) > 0
            b = pop(stack)                         // requires len_of(stack) > 0: from >= 2 and the ensures
            if len_of(stack) < cap_of(stack) {
                push_nogrow(stack, a +wrap b)      // requires len_of < cap_of
            } else { ... }                         // the overflow outcome, written by the program
        } else { ... }                             // the underflow outcome
    }
    ...
}
```

Ordinary program: a range reference handed to a helper.

```text
part = &buf[lo..hi]                 // requires lo <= hi <= len_of(buf); len_of(part) == hi - lo
part[k]                             // requires k < len_of(part), i.e. k < hi - lo
pop(&buf)                           // writes(buf): buf is a proper prefix of buf[lo..hi]
part[k]                             // rejected, Rule 3: p's proper prefix was written
```

Trace:

- Rule 6: "Reading `buf[k]` or forming `&buf[k]` requires the fact
  `k < len_of(buf)` (Rule 7)", and `len_of` is "a runtime number stored in the
  block header, readable by the program".
- Rule 7: "Every index must be proved in bounds; when the proof is unavailable the
  program tests the measure, which is ordinary data", with the cost stated in the
  rule's own example: "the test establishes the fact; one compare, no trap".
- Rule 11 supplies the fact from the dominating test and kills it again at the next
  write of `stack`: "A fact that mentions a path is invalidated when that path is
  written (by statement or call) unless the callee's `ensures` re-establishes it."
  `pop`'s `ensures len_of(buf) == len_of(deref(entry(buf))) - 1` is what carries
  `len_of(stack) >= 2` forward into `len_of(stack) >= 1` for the second `pop`, so
  the second pop needs no second test.
- Rule 7's range case: `len_of(part) == hi - lo` is fixed at formation, so a helper
  indexing a range proves its bounds against an arithmetic value, not against a
  header load. The rule never states the declared parameter type of a range
  reference (`kernel(&v[0..mid], ...)` in Rule 13 shows the argument, not the
  signature); that is a syntax gap, not a semantic one, since Rule 7 fixes both the
  measure and the obligation.

Rewrite and cost: none needed. Per stack operation the program pays one compare
against a header word plus a well-predicted branch and an explicitly written
outcome arm. A C interpreter that omits the depth check pays zero; any interpreter
that is actually safe (and safe Rust unconditionally) pays the same compare. The
one structural cost is that `len_of` and `cap_of` live in the block header, so the
compare's operand is a load, not a register-resident field as in Rust's `Vec`;
whether that load can be hoisted out of the loop is exactly the open question in
cell 6-11.

Rules consistent: yes — Rule 6 defers the index obligation to Rule 7 and Rule 7
admits the runtime test as ordinary data.
Task achievable: yes — the interpreter runs with one compare per stack operation.
Depends on: Rule 3 (prefix invalidation of the range reference), Rule 11 (test
facts, contract carry-through).
Verdict: accepted-fine

### 6-8: window versus value classes — a DynBox of linear elements

Question: how does a linear element type reach its consuming operation when the
only ways out of a window are `pop`, `swap_remove` and `truncate`?

Strongest program (a growable container of resources, the second engineering task
in PROGRAMS.md, with an early exit):

```text
linear type File;   fn close(f: own File)

files: DynBox<File>                         // linear by containment, Rule 8
...
if error {
    while len_of(files) > 0 {
        t = pop(&files)                     // requires len_of > 0: the loop condition
        close(move t)                       // the explicit consuming operation
    }
    return Err(e)                           // len_of(files) == 0 on this exit path
}
```

Ordinary program: `files[k] = reopen(files[k])`, the atomic update, whose `f`
consumes the old `File` (it may `close` it) and returns a new one.

Trace:

- Rule 8: "Linear values must be consumed by an explicit operation on every exit
  path; the compiler never releases them", and "a struct, array, Box, or DynBox
  containing a linear part is linear".
- Rule 6 agrees that the block is linear and then prescribes one specific
  discharge: "A DynBox whose element type is linear is itself linear (Rule 8) and
  must be truncated to zero by the program before it can go out of scope."
- Those two do not agree. `truncate(&buf, n)` has only
  `requires n <= len_of(buf); ensures len_of(buf) == n`; the elements it drops out
  of the window are, for an affine element type, released by the same machinery as
  "At scope exit the compiler releases slots `[0, len_of)` recursively" — but for a
  linear element type Rule 8 says the compiler never releases them and that a
  `File` must reach `close`. Either `truncate` on a linear-element DynBox is
  rejected (and Rule 6's sentence is wrong about the discharge), or it is accepted
  and silently destroys `n` `File`s without closing them (and Rule 8's guarantee is
  wrong). The rule file does not choose.
- The drain loop above is unambiguous and sufficient: each `pop` is a window
  operation yielding `own File` into a whole local, `close(move t)` is the explicit
  consuming operation, `len_of(files) == 0` holds on every exit path of the loop,
  and the empty block is then affine-only and released by the compiler. Rule 6's
  own assignment clause matches: "where it is linear the assignment is rejected
  unless written as the atomic update whose function consumes the old value".
- Note the shape the rules force on partial failure: there is no way to release
  the block while some slots are still occupied, so an early return has to drain,
  which is exactly what a C++ `vector<File>` destructor does element by element.

Rewrite and cost: the drain loop replaces `truncate(&files, 0)`. Per element: one
`pop` (one move of a `File`-sized value into a local, one header decrement) plus
the `close` call. A C++ `vector<unique_fd>` destructor performs the same per-element
close and no move; the extra move is `sizeof(File)` bytes per element on a path
that already performs a system-call-class operation. Cost: negligible, and no
runtime drop flag or occupancy tag is involved because every slot inside the window
holds a value by Rule 6 ("no program point can observe a slot inside the window as
empty").

Rules consistent: no — Rule 6's "must be truncated to zero" and Rule 8's "the
compiler never releases them" cannot both hold for `DynBox<File>`.
Task achievable: yes — the drain loop discharges every obligation at negligible
cost, whichever way the `truncate` question is ruled.
Depends on: Rule 11 (loop condition as the `requires` fact), Rule 12 (exit paths).
Verdict: undecided-rule-gap

### 6-9: window versus effect rows — an index can only enter through an argument

Question: can a signature express "this helper touches the container and one of its
slots", and can a reference name the slot a push is about to fill?

Strongest program (the rule file's own append-through-a-reference form):

```text
fn put_at(slot: &Int, x: own Int)  writes(slot)
put_at(&buf[len_of(buf)], 3)       // Rule 9's example, verbatim
```

Ordinary program (a compaction helper that wants both the container and a victim
element):

```text
fn compact(buf: &DynBox<Entry>, victim: &Entry)  writes(buf), writes(victim)
compact(&t.slots, &t.slots[i])     // rejected
// rewritten with the index instead of the second reference:
fn compact(buf: &DynBox<Entry>, i: u64)  writes(buf)
    contract { requires i < len_of(buf); }
compact(&t.slots, i)               // accepted
```

Trace:

- Rule 9: "An effect row lists `reads(path)` and `writes(path)` where each path
  starts at a reference parameter ... Signatures never contain index expressions;
  an index enters an effect only through an argument, evaluated once at the call."
  So `compact`'s second parameter is the only way to name a slot in the row, and
  Rule 10 clause 1 then rejects the call: the substituted `writes(t.slots)` and
  `writes(t.slots[i])` are "effects on overlapping paths where at least one is a
  write" and cannot be "proved disjoint (different roots, or indices or ranges
  proved distinct)" because one path is a prefix of the other — Rule 10's own
  `bad(&vv, &vv[0])` example is this case.
- The index rewrite is accepted: one reference parameter, the index as ordinary
  data, and the bound restated as a `requires` (Rule 11 contracts). The callee
  re-forms `&buf[i]` inside itself, where the obligation is discharged by its own
  `requires`.
- The `put_at` example does not typecheck against Rule 6 and Rule 7. Rule 6: "Reading
  `buf[k]` or forming `&buf[k]` requires the fact `k < len_of(buf)` (Rule 7)".
  Rule 9's example forms `&buf[len_of(buf)]`, whose obligation is
  `len_of(buf) < len_of(buf)`. If `buf` were an `array<T, N>` instead, Rule 7's
  "`a: array<Int, 8>; a[i] // requires i < 8`" rejects it for the same reason. So
  either the example is wrong, or forming a reference to the first slot outside the
  window is a further admitted form — which would also contradict Rule 6's "Slots
  `[len_of, cap_of)` hold nothing" and "The boundary `len_of` is ... changed only by
  the built-in operations below", since `put_at` writes a slot without moving the
  boundary. The rule file does not resolve this, and it is the only appending form
  the rule file shows other than `push_nogrow`.

Rewrite and cost: for the compaction helper, pass the index: zero runtime cost —
the callee recomputes `base + i * sizeof(Entry)`, one shift-add, and its `requires`
is discharged at the call site by a fact the caller already had. For appending, use
`push_nogrow(&buf, move x)`, which is the operation Rule 6 provides and which costs
one store plus one header increment; the `put_at` form would cost the same, so
nothing turns on it at runtime — only on whether a legal program can be written
that way at all.

Rules consistent: no — Rule 9's `put_at(&buf[len_of(buf)], 3)` example cannot
satisfy Rule 6's and Rule 7's bound for any indexable thing.
Task achievable: yes — `push_nogrow` appends and the index-parameter form expresses
container-plus-slot helpers, both at zero cost.
Depends on: Rule 6, Rule 7 (bound obligation), Rule 10 clause 1 (prefix overlap),
Rule 11 (`requires`).
Verdict: undecided-rule-gap

### 6-10: window versus the call-site rule — exchanging two elements

Question: with no holes and no `take`, can two slots of one window be exchanged,
and what does Rule 10's pairwise check charge for it?

Strongest program (in-place sort of a buffer of owning elements; `i`, `j` are
decided by the data, `T = Box<Record>` is affine):

```text
fn exchange<T>(a: &T, b: &T)  writes(a), writes(b)      // the C++/Rust shape
exchange(&buf[i], &buf[j])
```

Ordinary program (Copy elements):

```text
t = buf[i]; buf[i] = buf[j]; buf[j] = t                 // three duplications, Rule 8
```

Trace:

- Call site: Rule 10 clause 1 compares `writes(buf[i])` with `writes(buf[j])`;
  they overlap on the root `buf` and must be "proved disjoint (different roots, or
  indices or ranges proved distinct)" — Rule 10's own line
  "`two(&v[i], &v[j]) // accepted only with the fact i != j`". For data-determined
  indices the fact comes from a dominating test (Rule 11), one compare per swap.
  A partition loop that already knows `i < j` carries the fact from its own
  invariant and pays nothing.
- Body: `exchange` cannot be written. Its body needs an owned `T` out of the place
  `*a`, and Rule 6 says "There is no `take` operation and no partial move out of
  any place: the only ways to move a value out of storage are consuming a whole
  local (`move x`), the window operations, and the atomic update." `*a` is neither
  a whole local nor a window slot the callee can name (Rule 9 forbids index
  expressions in the row, and the callee has only a reference to one element), and
  the atomic update commits `f`'s result back into the same slot, so it cannot
  leave a slot free to receive the other element. So the exchange must be written
  at the call site, out of window operations.
- Swap with the last slot is exact and cheap:

```text
// swap buf[i] with buf[len-1]
t = swap_remove(&buf, i)        // requires i < len_of(buf); returns e_i, refills slot i from the last
push_nogrow(&buf, move t)       // requires len_of < cap_of: guaranteed, the length just dropped by one
```

  Three moves: `e_i` out, the last element into slot `i`, `e_i` back into the tail.
  `std::swap` on a movable type is also three moves. Zero cost, and the bound
  obligations are discharged by `swap_remove`'s and `pop`'s `ensures` about
  `len_of`, so no runtime test remains where the C++ form has none either.

- Interior-to-interior exchange has no such route. `swap_remove(j)` refills slot
  `j` from the current last slot, which is a third element; `pop` only reaches the
  last slot; the atomic update can push the old value out through a `writes`
  parameter but must then commit some `T` into the slot, and for affine `T` there
  is no spare value except one already extracted. The best composition is three
  swap-with-last operations:

```text
swap_with_last(&buf, i); swap_with_last(&buf, j); swap_with_last(&buf, i)
```

- Rule 10 clause 3 is the other half of this cell and is favourable: "A live
  reference outside the call whose path has a proper prefix among the call's write
  paths becomes invalid after the call (Rule 3)." So `p = &buf[i]` dies at every
  window call, but the *index* survives, and re-forming `p = &buf[i]` after a push
  is accepted because `push_nogrow`'s `ensures len_of(buf) == len_of(deref(entry(buf))) + 1`
  re-establishes the bound from the pre-call fact. Rust rejects that program
  outright; C++ requires the writer to know that `push_back` invalidates iterators.

Rewrite and cost: for Copy elements, none needed — three duplications, parity with
C++. For affine elements, interior swap costs 9 moves (three swap-with-last
operations at 3 moves each) plus 6 header stores, against 3 moves for `std::swap`
or `slice::swap`: about 3x the byte traffic in a sort's inner loop, and the loop is
no longer a candidate for the two-load/two-store idiom. Sorts whose swap is always
against the partition end (heap sift-down formulated as swap-with-last, Lomuto
partition's final placement) pay nothing. Data-determined `i != j` costs one
predicted compare per swap.

Rules consistent: yes — Rule 6, Rule 9 and Rule 10 agree; the exchange is simply
not among the admitted operations.
Task achievable: rewrite — in-place sorting of affine elements works, at about 3x
the move traffic per interior swap.
Depends on: Rule 3 (invalidation), Rule 6 (window ops, no holes), Rule 9 (no index
expressions in rows), Rule 11 (dominating test, contract carry-through).
Verdict: rejected-real-cost

### 6-11: window measures versus fact invalidation — does writing a slot kill the length fact?

Question: does an effect on `buf[i]` invalidate a fact about `len_of(buf)`, and
therefore does a kernel reload the block header on every iteration?

Strongest program (struct-of-arrays kernel, P5, over heap buffers, with the
per-element update done by a call so the effect is a declared `writes(a[i])`):

```text
fn fma(slot: &f64, x: f64, y: f64)  writes(slot)

n = len_of(a)
if n <= len_of(b) {
    i = 0
    while i < n {
        invariant h: len_of(a) == n;          // the fact under test
        fma(&a[i], b[i], c)                   // call effect: writes(a[i]); requires i < len_of(a)
        i = i + 1
    }
}
```

Ordinary program: the same loop with the element write written inline as
`a[i] = a[i] * b[i] + c` (the atomic update), which raises the identical question
about the statement form.

Trace:

- Rule 7 obliges `i < len_of(a)` at each access; the loop gets it from `i < n` and
  the invariant `len_of(a) == n`. If the invariant survives the iteration, the
  compare is against a register-resident `n` and the bound is provable, so the
  access compiles to a shift-add with no reload and no branch.
- Rule 11 is the whole question: "A fact that mentions a path is invalidated when
  that path is written (by statement or call) unless the callee's `ensures`
  re-establishes it." The fact `len_of(a) == n` mentions the path `a`. The
  statement writes the path `a[i]`. The rule does not say whether writing a
  sub-path counts as writing the path the fact mentions. The two readings are both
  supported by other rules and give different code:
  - Narrow (exact path) reading: only `writes(a)` invalidates it; `writes(a[i])`
    does not. Rule 3 settles the analogous question for references in exactly this
    direction — "Writing the storage at `p`'s path or below it (a content write)
    does not invalidate `p`" — and Rule 6 says `len_of` is "changed only by the
    built-in operations below", none of which is an element write. Under this
    reading the invariant holds, the header is loaded once, and the loop is as fast
    as the C++ form.
  - Overlap reading: invalidation uses the same path-overlap judgment as Rule 10
    clause 1, under which `writes(vv)` and `writes(vv[0])` overlap. Then every
    element write kills `len_of(a) == n`, the invariant cannot be carried, and each
    iteration must reload `len_of(a)` from the block header and re-compare.
- Rule 11 offers no writer-side repair at this point either. Its explicit proof
  steps are "explicit `use` steps inside an `invariant`", which is where the fact
  would be restated — but restating `len_of(a) == n` after it was invalidated is
  not a derivation from surviving facts, it is the fact itself. Nothing in the rule
  file says an invariant may re-assert a fact that the body invalidated.

Rewrite and cost: under the narrow reading, none needed — zero cost against C++ and
against Rust with hoisted bounds checks. Under the overlap reading the only rewrite
is to keep the length in a local and re-derive nothing, which does not help because
the obligation is stated against `len_of(a)`, not against the local; the loop then
pays, per element, one dependent load of the block header word plus one compare and
a branch it cannot fold away. On a kernel whose body is one FMA that is roughly a
doubling of the loop's memory operations and the end of vectorisation, because each
lane's bound would depend on a header re-read. This single ambiguity is worth the
difference between a vectorised kernel and a scalar checked one.

Rules consistent: yes so far — nothing contradicts; the fact language is simply
under-specified on sub-path writes.
Task achievable: undecided — the same source is either a clean vectorised kernel or
a per-element checked loop depending on the reading.
Depends on: Rule 3 (content-write clause, as evidence for the narrow reading),
Rule 6 (`len_of` changed only by window ops), Rule 7, Rule 10 clause 1 (overlap
judgment, as evidence for the wide reading).
Verdict: undecided-rule-gap

### 6-12: window versus joins and the absence of holes

Question: what survives a join when the arms move the window differently, and what
happens to a value that is consumed on one arm only?

Strongest program (open-addressing insert, Rule 12's own representation, where the
arm taken is decided by data and the inserted value is affine):

```text
tags:  DynBox<u8>                  // occupancy is data
slots: DynBox<Entry>               // every slot inside the window holds a valid Entry

fn insert(t: &Table, k: u64, e: own Entry)  writes(t.tags), writes(t.slots)
{
    h = probe(&t.tags, k)                       // returns an index, Rule 4
    if t.tags[h] == EMPTY {
        t.slots[h] = e_of(move e)               // e consumed on this arm
        t.tags[h] = FULL
        t.count = t.count + 1
    } else {
        t.slots[h] = merge(t.slots[h], move e)  // atomic update: e consumed here too
    }
    // join: e is consumed on both arms; count differs; len_of(t.slots) is unchanged
}
```

Ordinary program: the length-moving join from Rule 12's own text,

```text
if cond { push_nogrow(&buf, x) }               // after the join: len_of(buf) >= n
use(&buf[i])                                   // accepted for i < n
pop(&buf)                                      // would need len_of(buf) > 0, which >= n gives only if n > 0
```

Trace:

- Rule 12: "At a join, facts are intersected (a fact survives only if it holds on
  every incoming edge)". Its own example shows the intersection is semantic, not
  syntactic: the then-edge carries `len_of(buf) == n + 1` and the else-edge
  `len_of(buf) == n`, neither of which is `len_of(buf) >= n`, yet the rule states
  "after the join: `len_of(buf) >= n`, where n was `len_of` before" and
  "facts about indices below n survive". So the join takes the least upper bound in
  the affine-comparison lattice, and any bound below `n` is preserved at no cost.
- Rule 12: "No place is ever partially moved: every path is either wholly present
  or the program cannot name it." Rule 6 makes this free for the window:
  "no program point can observe a slot inside the window as empty", so neither arm
  can leave a hole for the other to inherit, and the merge arm is written as the
  atomic update precisely because Rule 6 requires it ("where it is linear the
  assignment is rejected unless written as the atomic update whose function
  consumes the old value").
- The one-arm consumption question: an affine local consumed on one arm and not the
  other is wholly moved on that edge, so after the join "the program cannot name
  it". Rule 8 has the compiler release affine values, and the release point is
  statically the end of the arm on which the value stops being nameable — the
  branch that decides it already exists in the program, so no drop flag is created.
  For a linear local Rule 8 is stricter and correct: "must be consumed by an
  explicit operation on every exit path", so the arm that does not consume is
  rejected by name.
- Occupancy across the join is data by construction: `tags` and `count` are ordinary
  DynBox contents and integers, which is what Rule 12 prescribes — "Structures whose
  occupancy is decided by data keep that occupancy as data" — and Rule 11's "no
  per-slot occupancy facts" therefore costs nothing here, because nothing was asking
  the checker for one.

Rewrite and cost: none needed. The recorded cost of the representation is the one
already on the candidate's list — "Open-addressing hash tables with non-Copy
payloads pay one null check per hit versus hashbrown" — when `slots` is
`DynBox<Option<Entry>>`; with a separate `tags` array (the program above) the check
is the tag compare a Swiss table performs anyway. After a length-moving join the
program pays one compare if it then needs a fact about the top of the window, which
is the same compare the C++ code needs to know whether its `push_back` happened.

Rules consistent: yes.
Task achievable: yes — insert, probe and merge all fit, with the join keeping the
bounds facts that matter.
Depends on: Rule 4 (index-returning probe), Rule 6 (atomic update, no empty slot
inside the window), Rule 8 (affine release, linear obligation), Rule 11 (no
per-slot occupancy facts).
Verdict: accepted-fine

### 6-13: window versus parallel blocks

Question: which parallel shapes over one DynBox survive Rule 13's disjointness, and
what does the rejected shape cost?

Strongest program (parallel scatter into a shared table — a histogram over a large
key space, where the destination index is data):

```text
par {
    scatter(&idx[0..mid],   &hist);      // writes(hist)
    scatter(&idx[mid..n],   &hist);      // writes(hist)
}
fn scatter(ix: &DynBox<u32>, h: &DynBox<u64>)  reads(ix), writes(h)
```

Ordinary program (Rule 13's admitted family, adjacent ranges):

```text
par { kernel(&v[0..mid], &out[0..mid]); kernel(&v[mid..n], &out[mid..n]) }
```

Trace:

- Rule 13: "`par { A; B }` is accepted when A's write paths are disjoint from B's
  read and write paths and vice versa, using the same path-overlap and
  index/range-disjointness judgment as Rule 10." The scatter arms both carry
  `writes(hist)` on the same root with no index in the row at all — Rule 9 forbids
  one ("Signatures never contain index expressions") — so there is nothing to prove
  distinct and the block is rejected. Rule 13's own
  "`par { push(&v, 1); stats(&v) } // rejected`" is the same judgment.
- The ordinary form is accepted by range disjointness: `[0..mid)` and `[mid..n)` are
  proved distinct by endpoint arithmetic, and Rule 7 gives each arm
  `len_of(part) == hi - lo`, so each arm's element bounds are provable inside the
  arm with no header access.
- What a range reference cannot do is move the boundary: `push_nogrow`, `pop`,
  `swap_remove` and `truncate` take `&DynBox<T>`, and Rule 7 lists "a range
  reference into either" as an indexable thing, not as a DynBox. So a parallel arm
  can write elements but can never change `len_of`. That is what makes the admitted
  family safe without any fact about the header, and it costs nothing: the arms do
  exactly the stores the C++ kernel does.
- Rule 14 removes the other possible conflict: "Allocation and release carry no
  effect entry and never make two parallel arms conflict", so each arm may build its
  own DynBox.
- The candidate has no atomics ("channels or atomics" are under "Not in this
  candidate"), so the scatter has exactly one rewrite: privatise and merge.

Rewrite and cost:

```text
par {
    h1 = DynBox::filled(m, 0)?;  scatter(&idx[0..mid], &h1);
    h2 = DynBox::filled(m, 0)?;  scatter(&idx[mid..n], &h2);
}
i = 0
while i < m { invariant q: len_of(h1) == m; hist[i] = h1[i] + h2[i]; i = i + 1 }
```

For a small table this is the same program every correct C++ or rayon histogram
writes, so the cost is zero. For a large or sparse table it is a real cost: `k`
private tables of `m` slots each (memory and a zeroing pass of `k*m` slots) plus a
merge pass of `k*m` adds, against the C++ form's contended
`atomic<u64>::fetch_add` on the shared table, which allocates nothing and touches
only the slots the data actually hits. When `m` is large relative to `n` the atomic
form wins outright, and no rewrite under this candidate recovers it; the remaining
option is a pre-pass that buckets indices by owner (one extra pass over `idx` plus
bucket storage) so that each arm owns a disjoint index range. Both rewrites cost at
least one extra full pass over the data.

For the affine-element parallel append (`par` building two buffers and
concatenating), the concatenation inherits cell 6-6's gap: under reading (a) it is a
`memcpy` per arm, under reading (b) it is the 2.5-moves-per-element schedule.

Rules consistent: yes.
Task achievable: rewrite — parallel histogram and parallel append both work; the
large-table scatter loses to the atomic form with no recovery inside the candidate.
Depends on: Rule 7 (range measure), Rule 9 (no index in rows), Rule 10 (overlap
judgment), Rule 14 (allocation is not an effect), cell 6-6's open reading.
Verdict: rejected-real-cost

### 6-14: window versus one global heap and fallible allocation

Question: what does "one heap, allocation returns a Result, the allocator has no
effect" do to a growable window?

Strongest program (growth inside a parallel arm, with the failure arm having to
leave both the old block and the partially filled new block accounted for):

```text
par {
    build(&left,  &out_l);         // each arm pushes into its own Vector, each push may grow
    build(&right, &out_r);
}
fn build(src: &DynBox<Item>, dst: &Vector<Item>) -> Result<Unit, Oom>  reads(src), writes(dst.buf)
{
    i = 0
    while i < len_of(src) {
        push(dst, transform(src[i]))?      // may allocate a new block; on Err the function returns
        i = i + 1
    }
    Ok
}
```

Trace:

- Rule 14: "Allocation and release carry no effect entry and never make two parallel
  arms conflict", and "Addresses are not observable, so allocator concurrency does
  not affect program determinism". The `par` is then judged only on `dst.buf` and
  `src`, which are disjoint roots between arms, so Rule 13 accepts it. Two arms
  growing simultaneously on one internally synchronised heap is exactly the case
  Rule 14's example blesses: "`par { a = build(&x)?; b = build(&y)? }` // both
  allocate: accepted".
- Rule 6 fixes the block: "`DynBox<T>` owns one heap block of `cap_of` slots, fixed
  at allocation", and growth is "allocates a larger DynBox, moves `[0, len_of)`
  across, and replaces the old one". There is no resize or realloc operation in the
  candidate, so the copy is unconditional.
- Failure: `DynBox::new<T>(n)?` returns `Result`, so the `Err` arm returns before
  `v.buf` is replaced. The old block is still owned and still exactly as long as it
  was; the new block was never bound, or is an affine local released by Rule 8 on
  that path. No fact about the old buffer is disturbed, because Rule 11 invalidates
  a fact only when its path is written and a failed allocation writes nothing.
- The positive consequence for facts: an allocation cannot invalidate anything.
  A program can hold `i < len_of(buf)` across any number of unrelated allocations,
  which in C++ is true by accident and in Rust is enforced by borrow scopes.

Rewrite and cost: none is available for the missing in-place growth, and that is
the cost. `std::vector` cannot extend in place either (it allocates and copies),
but Rust's `RawVec` grows through `realloc`, and for multi-megabyte buffers the
system allocator commonly extends the mapping and copies nothing. Under this
candidate every doubling copies the whole window, so a vector grown to 1 GiB by
repeated pushes moves about 2 GiB of bytes that a `realloc`-based Vec can move
close to none of. That is one fixed extra copy per growth event, amortised O(1) per
push but unbounded in absolute bytes; it compounds with cell 6-6's unresolved
2.5x factor for affine elements. The fallibility itself costs nothing beyond the
branch on `len_of == cap_of` that `push` performs anyway.

Rules consistent: yes.
Task achievable: yes — growth, parallel growth and failure handling all work; only
the in-place extension is unavailable.
Depends on: Rule 8 (affine release on the error path), Rule 11 (allocation
invalidates no fact), Rule 13 (disjoint arms), cell 6-6's open reading.
Verdict: rejected-real-cost

### 6-15: window versus owned returns

Question: what does "return owned values only" cost when the value is a window or a
position inside one?

Strongest program (a helper that both finds and reports, over a buffer too large to
copy):

```text
fn find(v: &DynBox<Entry>, key: Int) -> Option<u64>      // Rule 4's signature
    reads(v)
    contract { ensures when Some: result < len_of(v); }

match find(&v, k) {
    Some(i) => { p = &v[i]; use(p) }                      // no test here: the ensures carries the bound
    None    => ...
}

fn build(n: u64) -> Result<DynBox<Entry>, Oom>            // returns the window by value
fn normalise(buf: &DynBox<f64>)  writes(buf)              // Rule 15's prescribed in-out shape
```

Trace:

- Rule 15: "A function returns owned values only. Positions found by a search are
  returned as indices with a bounds relation in `ensures` (Rule 4)." and "Passing a
  large value in and back out is expressed as a reference parameter with a `writes`
  entry, not as move-and-return."
- The bounds relation is what makes the index form free: `ensures when Some: result
  < len_of(v)` is a Rule 11 fact routed by variant, so the caller forms `&v[i]`
  with no runtime test. Rule 4's own comment states the residual cost: "the caller
  re-derives, one address computation". That is one shift-add against C++ returning
  an `Entry*`.
- Returning a `DynBox<Entry>` by value is cheap for a different reason: Rule 6 puts
  the boundary in the block — "The boundary `len_of` is a runtime number stored in
  the block header" — so the returned value is a single pointer, against Rust's
  three-word `Vec`. The price is paid at every `len_of` read, which is a dependent
  load rather than a register field; see cell 6-11 for whether that load can be
  hoisted.
- The in-out prescription costs nothing for a DynBox (one word either way) and
  avoids a real cost for a large inline `array<T, N>`, where move-and-return has no
  guaranteed zero-copy ABI (PROGRAMS.md: "Large-aggregate ownership round trips have
  no assumed zero-copy ABI"), so `writes(buf)` on a reference is the cheaper form
  the rule names.
- What cannot be returned is any fact about contents: Rule 11's fact forms are
  "affine comparisons over measures and integer values", so `ensures` can say
  `len_of(result) == n` but not "the returned buffer is sorted". This costs nothing
  for safety, because every obligation Rule 7 raises is a measure comparison; it only
  means a binary search over a returned buffer is guarded for bounds and not for
  sortedness, which is a logic property the C++ version does not check either.

Rewrite and cost: none needed. One shift-add per re-derived reference, and one
dependent load per `len_of` read, against the C++ pointer-returning form.

Rules consistent: yes.
Task achievable: yes.
Depends on: Rule 4 (no returned references), Rule 7 (bound obligation), Rule 11
(`ensures when Variant`), cell 6-11 (hoistability of the header load).
Verdict: accepted-fine

### 6-16: window versus pools and arenas (Rule 16, provisional)

Question: does a DynBox used as a pool of handles give the mutable-compiler-graph
task its required behaviour, and what does a handle hop cost?

Strongest program (P3: a graph in a pool with node reuse, and the engineering task's
stated observable "a relation to a deleted node must not silently become a relation
to a replacement node"):

```text
struct Node { next: u64, prev: u64, gen: u32, data: u64 }   // handles are indices, Rule 16
struct Pool { buf: DynBox<Node>, free_head: u64 }

fn alloc(p: &Pool, n: own Node) -> u64   writes(p.buf), writes(p.free_head)
    contract { requires len_of(p.buf) < cap_of(p.buf);
               ensures result == len_of(deref(entry(p.buf))); ensures len_of(p.buf) == result + 1; }

fn remove(p: &Pool, h: u64)  writes(p.buf), writes(p.free_head)
    contract { requires h < len_of(p.buf); }
{
    p.buf[h] = retire(p.buf[h])       // atomic update: consumes the old payload, bumps gen, links the free list
}

// traversal
h = start
while h != NIL {
    if h < len_of(pool.buf) {                     // Rule 7 obligation, every hop
        d = pool.buf[h].data
        h = pool.buf[h].next
    } else { ... }                                // the written outcome arm
}
```

Ordinary program: an arena reset, Rule 16's own shape — `truncate(&a.buf, 0)`, after
which every old handle fails `id < len_of(a.buf)` and the reset is safe by bounds
alone.

Trace:

- Rule 16 (provisional): "A pool is a DynBox plus indices used as handles ... A
  stale index that is still in bounds names the current occupant of that slot: a
  logic error, not a memory error. Programs that need to detect it keep a generation
  number as data." The candidate's safety criterion is met — no memory error is
  reachable, because Rule 7 forces the bound at every dereference and Rule 6
  guarantees that a slot inside the window holds a valid `Node`, never a hole.
- The engineering task's observable is not met by the bare form: after `remove(m)`
  and a reuse of slot `m`, a stored `u64` still naming `m` reads the replacement
  node's fields with no diagnostic anywhere. That is precisely the case P3 names.
  The repair Rule 16 itself points at is the `gen` field, checked at each
  dereference: `if pool.buf[h].gen == expected_gen { ... }`.
- Slot reuse interacts with Rule 6's no-hole guarantee: a removed node's slot keeps
  holding a `Node`, so its affine payload (a `Box`, a child `DynBox`) stays alive
  and its memory stays retained until the slot is overwritten. The atomic update
  `p.buf[h] = retire(p.buf[h])` is the operation that releases it — Rule 6's
  "Assigning `buf[k] = x` where the old value is affine releases the old value" and
  its linear counterpart — so the retirement store is mandatory, not optional, for
  any pool whose nodes own heap data.
- References into the pool do not survive allocation: Rule 16's own comment says
  "valid until `a.buf` is replaced", and Rule 3 is stronger than that in practice,
  since `alloc` declares `writes(a.buf)` and `a.buf` is a proper prefix of
  `a.buf[id]`, so Rule 10 clause 3 kills every live reference into the pool at every
  `alloc` — even the ones the growth demonstrably does not move. The handle survives,
  which is the whole point of the pattern, and re-forming a reference costs one
  shift-add.
- Rule 11 is what makes the per-hop test unavoidable: "There are no quantified facts
  over array elements" and no per-slot occupancy facts, so "every `next` field in
  this pool is a live handle" cannot be stated once and reused. See cell 11-16.
- Parallel node-data maps (P3's "parallel map over all nodes writing data") are
  admitted through range references over the pool's buffer (Rule 13), not through
  handles, since two handle-derived writes have no provable disjointness.

Rewrite and cost: the generation-checked handle. Per graph hop against a C++ raw
pointer chase: one shift-add for `base + h * sizeof(Node)`, one compare against
`len_of(pool.buf)` (a header load, hoistable only if cell 6-11 resolves narrowly)
with a well-predicted branch, and, when identity matters, one load of `gen` from the
node's own cache line plus a compare. On a latency-bound chase the compares hide
under the load, so the honest figure is one extra dependent header load per hop in
the worst reading and about two extra ALU ops in the best, plus 4-8 bytes per node
for `gen`. This is parity with Rust's `slotmap`/`generational-arena`, and it is a
real cost against a C++ compiler IR that chases `Expr*` directly; the density win
(32-bit handles instead of 64-bit pointers) partly repays it.

Rules consistent: yes, and the program is memory-safe by Rule 6 and Rule 7 alone.
Task achievable: rewrite — the mutable compiler graph works, but its stated
observable requires the writer to carry and check generations; without them the
rules silently accept a program that reads a replacement node.
Depends on: Rule 16 (provisional pool rule), Rule 3, Rule 6, Rule 7, Rule 10
clause 3, Rule 11 (no quantified facts), Rule 13.
Verdict: accepted-unsafe

### 11-11: facts against themselves — many facts of one shape cannot become one fact

Question: can the fact language summarise a repeated obligation, or does each
repetition carry its own runtime test?

Strongest program (a validated index array driving a gather, the shape every
interpreter, renderer and sparse kernel uses):

```text
// phase 1: validate once
i = 0
ok = true
while i < len_of(idx) { if idx[i] >= len_of(src) { ok = false }; i = i + 1 }

// phase 2: gather, knowing every entry was checked
if ok {
    j = 0
    while j < len_of(idx) {
        invariant g: len_of(idx) == n;
        out[j] = src[idx[j]]          // requires idx[j] < len_of(src) -- NOT AVAILABLE
        j = j + 1
    }
}
```

Ordinary program: nested loops whose inner invariant depends on the outer one, which
composes without trouble:

```text
r = 0
while r < rows {
    invariant o: len_of(m) == rows * cols;
    c = 0
    while c < cols {
        invariant i1: r * cols + c <= len_of(m);      // affine in r and c
        use(&m[r * cols + c])
        c = c + 1
    }
    r = r + 1
}
```

Trace:

- Rule 11 lists the fact forms: "affine comparisons over measures and integer
  values, refinement facts from a dominating branch, loop-header invariants
  `invariant name: affine_expr compare_op affine_expr`, explicit `use` steps inside
  an `invariant`, and callee contracts." Every form is about one scalar relation.
- The summarising fact phase 2 wants is exactly the one Rule 11 refuses: "There are
  no quantified facts over array elements ("for all i ...") and no per-slot
  occupancy facts; occupancy that is determined by data is stored as data (Rule 6,
  Rule 12)." `ok` is data and survives the join, but `ok == true` is a fact about a
  boolean, not about `idx`'s contents, and no rule turns one into the other.
- So phase 2 must re-test per element, and the rule file's own answer applies:
  Rule 7's "when the proof is unavailable the program tests the measure, which is
  ordinary data ... one compare, no trap".
- Nesting and repetition of *scalar* facts is fine: the multiplication `r * cols` is
  not affine in general, but with `cols` a loop-invariant value the products form an
  affine progression that an invariant can carry, and the inner invariant is proved
  from the outer one by the ordinary intersection at the header. Recursion is the
  same story by Rule 10: "Recursion is checked through contracts, never by unfolding
  bodies", so a recursive descent carries a `requires depth <= 64` (P19) with no
  runtime counter beyond the parameter the program already passes.

Rewrite and cost: fold the validation into the gather —

```text
j = 0
while j < len_of(idx) {
    t = idx[j]
    if t < len_of(src) { out[j] = src[t] } else { ... }
    j = j + 1
}
```

Cost against the C++ gather that validates once and then indexes unchecked: one
compare and one branch per gathered element, an outcome arm per element, and the
loss of a straight vector gather — a masked or per-lane form at best. On a kernel
whose body is one load and one store this is on the order of a 1.5-2x slowdown in
the checked loop, and it is not recoverable inside the candidate, because the only
thing that could remove it is the quantified fact Rule 11 rules out. The validation
pass itself becomes pure waste and should be deleted, which is the honest rewrite.

Rules consistent: yes — Rule 11 is explicit and self-consistent about what it
excludes.
Task achievable: rewrite — the gather runs, with a per-element test the C++ form
does once for the whole array.
Depends on: Rule 7 (test establishes the fact), Rule 10 (recursion through
contracts), Rule 12 (join intersection for `ok`).
Verdict: rejected-real-cost

### 11-12: facts at a join

Question: is the join's fact intersection semantic or syntactic, and can the writer
repair a fact that the intersection drops?

Strongest program (the needed fact is true on both edges but is written differently
on each, and nothing dominates the use):

```text
if c { i = 0 } else { i = k }        // else-edge fact: k < len_of(buf)
// then-edge facts: i == 0, len_of(buf) > 0
// else-edge facts: i == k, k < len_of(buf)
use(&buf[i])                         // requires i < len_of(buf)
```

Ordinary program: Rule 12's own length-moving join,

```text
if cond { push_nogrow(&buf, x) }     // after the join: len_of(buf) >= n
use(&buf[i])                         // accepted for i < n
```

Trace:

- Rule 12: "At a join, facts are intersected (a fact survives only if it holds on
  every incoming edge)". Read syntactically this would drop `i < len_of(buf)` above,
  since neither edge carries that sentence. Read semantically it survives, because
  it holds on both edges.
- Rule 12's own worked example settles the reading: the then-edge has
  `len_of(buf) == n + 1`, the else-edge has `len_of(buf) == n`, and the rule states
  the result is "`len_of(buf) >= n`", a fact present on neither edge. So the
  intersection is the least upper bound in the affine-comparison lattice of Rule 11,
  not a set intersection of written sentences, and `i < len_of(buf)` survives the
  strongest program.
- What does not survive is anything that is not an affine comparison. The
  disjunction "`i == 0` or `i == k`" has no representation in Rule 11's forms, so a
  later step that needs to know which arm ran must read data, not facts — which is
  Rule 12's own instruction: "Structures whose occupancy is decided by data keep that
  occupancy as data."
- The writer has no proof step at an if-join. Rule 11 places explicit steps in one
  location only: "explicit `use` steps inside an `invariant`". So when the automatic
  derivation loses a fact at a plain join, the repair is to restructure into a loop
  with an invariant, or to re-test. The rule file does not state the strength of the
  automatic derivation, so how often that happens is not derivable from the text —
  but it is bounded, because the lattice is fixed and the worked example shows the
  join widening correctly.
- Reference targets behave differently and are stated: Rule 2, "At a control-flow
  join, a reference variable's target is the set of paths it may name; every check on
  it must hold for every member of the set", so `w = if c { &v1 } else { &v2 }` costs
  nothing at runtime and every later obligation is discharged against both members.

Rewrite and cost: when a needed relation falls outside the affine lattice, re-test:
one compare, one branch, one written outcome arm. In the strongest program above
nothing is lost, so the answer is "none needed"; the general repair is the same
compare Rule 7 already charges for an unproved index.

Rules consistent: yes — Rule 12's text and its example agree once "intersected" is
read as the lattice meet.
Task achievable: yes.
Depends on: Rule 2 (join of reference targets), Rule 7, Rule 11 (fact forms,
location of explicit steps).
Verdict: accepted-fine

### 11-13: facts and parallel blocks

Question: where do the facts that admit a `par` come from, and what happens to facts
across the arms?

Strongest program (the disjointness the block needs is decided by data, and each arm
also depends on facts the other arm could in principle disturb):

```text
// i and j come from a work queue; nothing static relates them
if i != j {                                // dominating test: the refinement fact
    par {
        step(&v[i], &table);               // writes(v[i]), reads(table)
        step(&v[j], &table);               // writes(v[j]), reads(table)
    }
    // after the par: both callees' `ensures` hold
} else {
    step(&v[i], &table)
}
```

Ordinary program (Rule 13's range family, where the fact is arithmetic):

```text
par { kernel(&v[0..mid], &out[0..mid]); kernel(&v[mid..n], &out[mid..n]) }
```

Trace:

- Rule 13: accepted "when A's write paths are disjoint from B's read and write paths
  and vice versa, using the same path-overlap and index/range-disjointness judgment
  as Rule 10", and Rule 13's own line "`par { bump(&v[i]); bump(&v[j]) } // needs
  i != j`".
- The fact comes from Rule 11's "refinement facts from a dominating branch": the
  `if i != j` guard dominates the `par`, so `i != j` is in force inside it, which is
  exactly what Rule 10 clause 1 asks for ("indices or ranges proved distinct").
  Nothing in Rule 13 restricts where the fact came from, so a runtime-tested fact
  admits a parallel block just as a statically derived one does.
- `reads(table)` in both arms is fine: "Read/read overlap is allowed" (Rule 13), so
  shared read-only structures need no fact at all.
- Facts after the arms: the rule file does not describe a `par` as a join, and it is
  not one — both arms run. Rule 11's invalidation is enough on its own: a fact
  established in arm A mentions paths that arm B, by Rule 13's own acceptance
  condition, does not write. So no arm can invalidate another arm's facts, and both
  arms' `ensures` hold afterwards. The disjointness condition that admits the block
  is the same condition that makes the fact merge trivial — a clean interaction, and
  it is why no extra rule is needed here.
- Range arms get their per-element bounds from Rule 7's `len_of(part) == hi - lo`
  with no shared header read, so parallel arms never contend on the length word.

Rewrite and cost: none needed for the range family — instruction for instruction the
C++/OpenMP partition. For the data-determined pair the cost is one compare and one
branch before the block, plus a duplicated sequential arm (not a runtime cost under
the protocol). Where the indices genuinely collide the program runs sequentially,
which is the correct behaviour, not a loss.

Rules consistent: yes.
Task achievable: yes.
Depends on: Rule 7 (range measure), Rule 10 clause 1 (the shared judgment), Rule 11
(dominating-branch refinement, invalidation), Rule 13.
Verdict: accepted-fine

### 11-14: facts and the heap

Question: does allocation, failure, or block replacement disturb the fact state?

Strongest program (a growth that both allocates and replaces the block, in the
middle of a loop that is carrying bounds facts, with the failure arm live):

```text
n = len_of(v.buf)
i = 0
while i < n {
    invariant h: i <= len_of(v.buf);
    if len_of(v.buf) == cap_of(v.buf) {
        nb = DynBox::new<T>(2 * cap_of(v.buf) + 1)?    // may fail; writes nothing on failure
        move_all(&v.buf, &nb)                          // writes(v.buf)
        v.buf = move nb                                // replaces the block: every fact naming v.buf dies
    }
    push_nogrow(&v.buf, f(i))
    i = i + 1
}
```

Trace:

- Rule 14: "Allocation and release carry no effect entry and never make two parallel
  arms conflict. Allocation returns a `Result` and never traps. Addresses are not
  observable". No effect entry means no write path, and Rule 11 invalidates a fact
  only when "that path is written", so an allocation invalidates nothing. Facts held
  across `DynBox::new` — including facts about other buffers, and about `v.buf`
  itself — survive intact.
- The replacement, not the allocation, is what costs facts: `v.buf = move nb` writes
  the path `v.buf`, so every fact mentioning it dies, including `len_of(v.buf) == ...`
  and `cap_of(v.buf) == ...`. They are re-established from `move_all`'s and
  `push_nogrow`'s `ensures`, which is what Rule 11's escape clause is for: "unless
  the callee's `ensures` re-establishes it". The loop invariant above is deliberately
  weak (`i <= len_of(v.buf)`) so that it survives both the growth arm and the
  non-growth arm and can be re-proved from the `ensures` on each.
- The failure arm needs nothing: `?` returns before any write, the old block is
  untouched, and `nb` was never bound, so no fact and no ownership obligation is in
  an intermediate state. Rule 8 releases any affine local on that path.
- "Addresses are not observable" is what keeps the fact language sound in parallel:
  no fact can mention an address, so nothing an arm's allocator does can be observed
  by another arm's facts.

Rewrite and cost: none needed. The `ensures`-based re-establishment is compile-time
work only, and the error arm is the `Result` branch the C++ `new`-throws or Rust
`try_reserve` form also has. The only runtime item is the `len_of == cap_of` test,
which `std::vector::push_back` performs identically.

Rules consistent: yes.
Task achievable: yes.
Depends on: Rule 6 (window contracts), Rule 8 (affine release on the error path),
Rule 11 (invalidation and the `ensures` clause), Rule 14.
Verdict: accepted-fine

### 11-15: facts and owned returns

Question: how much of what a callee knows can cross the return boundary, given that
only owned values come back?

Strongest program (a helper that computes a sub-range for its caller to use, so the
caller needs a two-sided relation about a returned aggregate):

```text
struct Span { lo: u64, hi: u64 }

fn window_of(v: &DynBox<Sample>, t: u64) -> Span
    reads(v)
    contract { ensures result.lo <= result.hi; ensures result.hi <= len_of(v); }

s = window_of(&v, t)
part = &v[s.lo..s.hi]          // requires lo <= hi <= len_of(v): both from the ensures
reduce(part)
```

Ordinary program: Rule 4's index-returning search with
`ensures when Some: result < len_of(v)`.

Trace:

- Rule 15: "A function returns owned values only", and Rule 4 rules out the pointer
  form: a "find" returns "an index or other owned data; the caller forms the
  reference".
- Rule 11 says contracts relate results to measures — "Contracts use `requires`,
  `ensures`, and `ensures when Variant:` for result-routed relations" — and facts are
  "affine comparisons over measures and integer values". `result.lo` is an integer
  value named by a path into the returned value, in the same way `result` is in
  Rule 4's own example, so the two-sided relation crosses the boundary and Rule 7's
  range obligation `lo <= hi <= len_of(v)` is discharged with no runtime test.
- What cannot cross is any statement about contents, since Rule 11 excludes
  quantified facts. A function returning a sorted `DynBox` cannot say so. That costs
  nothing for safety — every obligation Rule 7 raises is a measure comparison — and
  it costs nothing at runtime, because a binary search over the returned buffer
  proves its indices from `len_of` alone; sortedness was never checked by the C++
  version either.
- The facts are fragile in exactly the right way: if the caller writes `v` between
  the call and the use, Rule 11 invalidates `result.hi <= len_of(v)` because the fact
  mentions `v`, and the range must be re-derived or re-tested. That matches the
  underlying reality that the window may have shrunk.
- Rule 15's in-out prescription ("Passing a large value in and back out is expressed
  as a reference parameter with a `writes` entry, not as move-and-return") keeps the
  fact story simple too: the callee's `ensures` about `len_of(buf)` names the caller's
  own path, so nothing has to be transported across a return at all.

Rewrite and cost: none needed. Against a C++ helper returning `pair<iterator,
iterator>`, the cost is one shift-add per endpoint when the caller forms the range,
and zero tests, because both endpoint relations arrived as facts.

Rules consistent: yes.
Task achievable: yes.
Depends on: Rule 4, Rule 7 (range obligation), Rule 11 (`ensures`, invalidation),
Rule 15.
Verdict: accepted-fine

### 11-16: facts and pools (Rule 16, provisional) — the invariant that cannot be stated

Question: P3 asks for "next/prev point to live nodes" to be "stated once and reused";
can Rule 11 hold a structural invariant over a pool?

Strongest program (P3's traversal over a pool with reuse, in a hot loop):

```text
// wanted, and not expressible:
//   invariant all_live: for all h in pool.buf, pool.buf[h].next < len_of(pool.buf)

h = start
while h != NIL {
    if h < len_of(pool.buf) {                  // Rule 7 obligation, re-proved every hop
        d = pool.buf[h].data
        h = pool.buf[h].next                   // next is data: nothing is known about it
    } else {
        return Err(Corrupt)                    // an outcome arm the C++ version does not have
    }
}
```

Ordinary program: the same traversal over a pool the caller just built, where the
handles came from `alloc`'s `ensures result == len_of(deref(entry(a.buf)))` and are
therefore in bounds by affine reasoning — one hop deep. The moment a handle is
stored into a node and read back, it is data again and the fact is gone.

Trace:

- Rule 11: "There are no quantified facts over array elements ("for all i ...") and
  no per-slot occupancy facts; occupancy that is determined by data is stored as data
  (Rule 6, Rule 12)." The structural invariant P3 asks for is a quantified fact over
  the pool's elements, so it is refused by name.
- Rule 11's other clause closes the second route: "A fact that mentions a path is
  invalidated when that path is written (by statement or call) unless the callee's
  `ensures` re-establishes it." A handle read out of `pool.buf[h].next` is an integer
  whose relation to `len_of(pool.buf)` was never established in the first place —
  nothing invalidates it, there was nothing to invalidate.
- Rule 16 (provisional) is what makes the resulting program safe rather than merely
  rejected: "A stale index that is still in bounds names the current occupant of that
  slot: a logic error, not a memory error." Combined with Rule 6's guarantee that a
  slot inside the window always holds a valid value, the bounds test is sufficient
  for memory safety, and the generation word covers identity (cell 6-16).
- `alloc`'s `ensures` does reach one hop: `ensures result == len_of(deref(entry(a.buf)))`
  plus `ensures len_of(a.buf) == result + 1` gives `result < len_of(a.buf)` by affine
  reasoning, so the freshly returned handle needs no test. That is the only place the
  fact language helps here.
- Nothing in Rule 11 lets a data structure's own consistency be asserted and reused;
  the `use` steps it does provide live "inside an `invariant`", i.e. at a loop header,
  and can only combine facts that already hold.

Rewrite and cost: the per-hop bounds test above, plus a generation compare when
identity matters. Per hop against a C++ `Node*` chase: one compare against
`len_of(pool.buf)` — a header load, hoistable out of the traversal loop only under
the narrow reading of cell 6-11, and not hoistable at all in a loop that also mutates
the pool — one well-predicted branch, one shift-add for the handle, and an outcome
arm per traversal site. On a pointer-chasing loop the compare hides under the
dependent load, so the measurable cost is small for pure traversal and real for
mutating traversals (list splice, edge insertion), where each hop may reload the
header. The cost is structural: no rewrite inside the candidate removes it, because
the only thing that would is the quantified invariant Rule 11 excludes.

Rules consistent: yes — Rule 11 refuses the invariant explicitly and Rule 16 says
what the program gets instead.
Task achievable: rewrite — the graph traversal runs safely; P3's stated requirement
that the invariant be "stated once and reused" with "no runtime check" is not met.
Depends on: Rule 6 (no empty slot inside the window), Rule 7, Rule 11, Rule 16
(provisional pool rule), cell 6-11 (whether the header load is hoistable).
Verdict: rejected-real-cost
