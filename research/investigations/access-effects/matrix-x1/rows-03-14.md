# Candidate x1 interaction matrix: row 3 (cells 3-3 .. 3-16) and row 14 (cells 14-14 .. 14-16)

Rule 3: reference validity is a fact, killed by prefix writes, moves and frees; a move never re-roots.
Rule 14: one global heap, allocation returns `Result`, the allocator has no effect.

All derivations are against the frozen rule text in `CANDIDATE-X1.md`. Nothing from
"Not in this candidate" is used. Runtime performance is the only cost recorded.

Shared conventions: `v`, `buf`, `out` are `DynBox` values with discharged bounds where
shown; `i`, `j`, `k`, `m` are data-determined `u64` unless a fact is stated; `Entry`,
`Node`, `Frame` are ordinary owned aggregates (Rule 1).

### 3-3: Repeated, chained and loop-carried reference formation

Question: when references are formed from each other, aliased, and re-formed from
themselves inside a loop, does Rule 3's validity fact stay decidable?

Strongest program:

```text
struct Node { key: Int, payload: Int, next: Option<Box<Node>> }   // Rule 1: owned child only

fn set_payload(head: &Box<Node>, k: Int, val: Int)  writes(*head)
{
    p = &*head                                  // p names *head, the first heap Node
    loop {
        if (*p).key == k { (*p).payload = val; return }
        match (*p).next {
            Some(b) => { p = &*b }              // re-formed from p's own path: the path grows by one hop
            None    => { return }
        }
    }
}
```

Ordinary program (decidable, and the behaviour the rule was written for):

```text
p = &v.buf[i]
q = &p.x                 // Rule 2: "a reference extends a path"; q names v.buf[i].x
r = &v.buf[i]            // a second name for the same path; both may be live
v.buf[j] = 5             // Rule 3: "content write on a sibling or the same slot: p stays valid"
bump(&v.buf[i])          // writes(v.buf[i]): p's and r's own path -> they stay valid;
                         // v.buf[i] is a proper prefix of q's path -> q invalid
use(q)                   // rejected
q = &p.x                 // Rule 3: "Validity is re-established only by forming the reference again"
grow(&v)                 // writes(v.buf): a proper prefix of all three -> p, q, r all invalid
```

Trace:

- Rule 1 admits `Option<Box<Node>>`: the child is owned, so `struct Node` is not the
  rejected `struct Bad { r: &Int }` shape.
- Rule 3, content clause, keeps `p` alive across `(*p).payload = val`: "Writing the
  storage at p's path or below it (a content write) does not invalidate p." Nothing in
  the loop writes a prefix of `p`, so per-iteration validity is not the problem.
- Rule 3, prefix clause, decides the ordinary program exactly as the rule file's own
  examples do: `bump` substitutes `writes(v.buf[i])`, which is `p`'s own path and a
  proper prefix of `q`'s; `grow` substitutes `writes(v.buf)`, a proper prefix of all.
- The loop is where the text runs out. Rule 2: "At a control-flow join, a reference
  variable's target is the set of paths it may name; every check on it must hold for
  every member of the set." At the loop header `p`'s target set is
  `{ *head, *(the Some payload of (*head).next), *(the Some payload of ((...)).next), ... }`,
  one member per iteration count, i.e. unbounded. No rule states a finiteness
  requirement, a widening, or any summary form for such a set, and Rule 3 gives no
  abstraction of "some path under `*head`" that a check could be run against. The
  candidate is silent, so this program cannot be traced to accept or reject.
- A second, independent gap blocks the same program earlier: `Some(b) => { p = &*b }`
  needs a path into a variant payload, and Rule 2's grammar has none — "A path starts at
  a local variable or a parameter and continues through fields, `*` (Box content), `[i]`
  (index, Rule 7), or `[lo..hi]` (range, Rule 7)." That gap is derived in 3-12; even
  granting it, the unbounded target set above remains.
- Note what does *not* recur: a symbolic index is one path form, not a set. `p = &buf[i]`
  with `i` rebound each iteration keeps the path at depth 1, so index-carried loops have
  no such problem.

Rewrite and cost: carry an index, not a reference, and let the nodes live in one
`DynBox` (Rule 16's arena-as-usage, and the only form Rule 1 leaves for a mutable graph
anyway):

```text
i = head_idx
loop {
    if nodes[i].key == k { p = &nodes[i]; (*p).payload = val; return }   // path depth 1 every iteration
    if nodes[i].next == NIL { return }
    i = nodes[i].next
}
```

Cost against a C++ pointer chase: the same one dependent load per hop; the address is
`base + i*sizeof(Node)`, a single x86 addressing mode or one AArch64 shifted-register
operand, so no extra instruction on the critical path. The bounds fact `i < len_of(nodes)`
is data-determined here, so Rule 7's test applies unless the writer carries a
`next < len_of(nodes)` invariant; that costs one perfectly predicted compare per hop,
off the load's dependency chain. The alternative rewrite is recursion —
`fn walk(n: &Node, ...)` forms its reference from its own parameter, depth 1 per frame,
and Rule 10's "Recursion is checked through contracts, never by unfolding bodies" makes
it decidable — at one call frame per hop unless the tail call is turned into a loop,
which no rule requires or forbids.

Rules consistent: no ruling available — Rule 2 defines the target set but never bounds
it, and a self-re-formed reference makes it unbounded.
Task achievable: rewrite — index-carried traversal is fully decidable and costs at most
one predicted compare per hop.
Depends on: Rules 1, 2, 7, 10, 16 (for the index rewrite's storage).
Verdict: undecided-rule-gap

### 3-4: Validity across the return boundary references may not cross

Question: with references neither returned nor stored, what carries a located result from
the callee that found it to the caller that writes it, and what invalidates the carrier?

Strongest program (deep structure, separate compilation, the callee has already walked to
the slot):

```text
// C++: Val* p = tree.find(k); *p += 1;      // one descent
fn lookup(t: &Tree, k: Int) -> Option<u64>  reads(t)     // Rule 4: an index, never &Val
fn lookup_update(t: &Tree, k: Int, f: fn(v: &Val) writes(v))  writes(t)   // the inward form
```

Ordinary program (flat container; the index outlives what a pointer would not):

```text
n = len_of(v)
match find(&v, k) {
    Some(i) => {                         // contract { ensures when Some: result < len_of(v); } -> i < n
        push_nogrow(&v, x)               // writes(v); ensures len_of(v) == len_of(deref(entry(v))) + 1 == n + 1
        p = &v[i]                        // Rule 7 needs i < len_of(v): i < n and n + 1 == len_of(v), affine
        bump(p)
    }
    None => ...
}
```

Trace:

- Rule 4 rejects the C++ shape outright: a reference "cannot be assigned into any
  aggregate (Rule 1), cannot be returned, and cannot be captured by a function value that
  is stored or returned."
- For the deep structure the index is not enough on its own: an index into the leaf does
  not name the leaf, because a path to the leaf cannot cross the return either (Rule 1
  forbids an aggregate holding it, Rule 4 forbids returning it). So the caller must
  re-descend — four dependent loads repeated — or the update must go inward.
  Rule 4 permits exactly that: a reference "may be bound to a local, passed as a call
  argument", and Rule 10 gives function-typed parameters "a full signature with its own
  row and contract".
- For the flat container Rule 3 never fires on the index: `i` is a `u64`, not a
  reference. What could fire is Rule 11's fact invalidation — "A fact that mentions a
  path is invalidated when that path is written ... unless the callee's `ensures`
  re-establishes it" — and `push_nogrow`'s `ensures` re-establishes it in affine form,
  so `i < len_of(v)` survives the write that would have dangled a C++ pointer. Rule 1's
  consequence is what makes this sound: "any value can be relocated by copying its bytes".
- The reference `p` formed afterwards dies at the next `writes(v)` (Rule 3, Rule 10.3)
  and is re-formed; see 3-6.

Rewrite and cost: `lookup_update` — the callee forms `&leaf.vals[j]` itself and calls `f`.
Memory traffic is identical to the C++ pointer form: one descent, one write. The residual
is one indirect call per operation where `f` is not a literal at the call site; where it
is, nothing in the rules prevents specialising it to a direct call. The index form, when
the structure is flat, costs one re-formed address (`base + i*scale`, usually folded into
the addressing mode) which correct C++ must also recompute after any operation that may
reallocate.

Rules consistent: yes — Rule 4 removes the carrier, Rule 11 supplies a stronger one for
flat containers, Rule 10 supplies the inward form for deep ones.
Task achievable: rewrite — find-then-write is expressible with no extra memory traffic.
Depends on: Rules 1, 7, 10, 11, 15.
Verdict: rejected-zero-cost

### 3-5: Box moves versus live interior references

Question: does the "a move never re-roots" clause cost memory traffic when a Box is moved
into an aggregate, into a callee, or into an arena while a reference into its content is
live?

Strongest program (build a node, splice it, keep writing it — the ordinary shape of every
list, tree and IR builder):

```text
n = Box::new(Node { key: k, payload: 0, next: None })?   // Rule 5, Rule 14: Result<Box<Node>, Oom>
p = &(*n).payload                    // p names (*n).payload
(*n).next = move head                // a content write below *n: p stays valid (Rule 3)
head = move n                        // n is a proper prefix of (*n).payload -> p invalid
*p = val                             // rejected
```

Second strongest (the rule file's own call-site case, with the task named — prepending):

```text
slot = &(*b).next
put(slot, move b)                    // rejected: "move b writes the prefix b of slot's path (Rule 3)"
```

Third (Box moved into arena storage while an interior reference is live):

```text
p  = &(*boxed).payload
id = alloc(&arena, move boxed)       // Rule 10.2: the by-value argument contributes a consumption of `boxed`;
                                     // `boxed` is a proper prefix of (*boxed).payload -> p invalid (Rule 3, 10.3)
q  = &(*arena.buf[id]).payload       // re-formed through the new owning path
```

Trace:

- Rule 3 states the outcome and the reason in one line: `c = move b` gives "p invalid,
  even though the Node did not move", and "A move never re-roots an existing reference:
  after `w = move v`, references formed from `v` are invalid and are not reinterpreted as
  references into `w`."
- Rule 5 makes the move itself free of memory consequences: "Boxes carry no store or
  region brand and can be moved, stored in aggregates, and returned freely", and the heap
  object is untouched. So the invalidation is a naming rule, not a relocation.
- Rule 10.3 extends the same judgment to calls, and Rule 10's `put` example is the case
  where the *argument* reference is the casualty, because the by-value argument's
  consumption (clause 2) writes its prefix.
- Rule 9 is why the arena case fires: `writes` "covers writing, replacing, moving out of,
  and freeing the storage at the path", so a consumed `own` argument is a write of that
  place for Rule 3's purposes even though no effect row mentions it.

Rewrite and cost:

```text
head = move n;  p = &(*head).payload;  *p = val         // re-form from the new owner
(*b).next = move old_head;  head = move b               // order the field write before the move
q = &(*arena.buf[id]).payload                            // re-form through the arena path
```

Re-forming after a Box move reloads the same pointer value, and that value is in the
register the move just wrote, so the first two rewrites lower to the same stores in the
same order — zero instructions. The arena re-formation is `arena.buf.base + id*scale`,
one addressing mode; a C++ builder that kept `Node*` across the arena insert saves at most
one scaled add. No copy, no branch, no lost parallelism in any of the three.

Rules consistent: yes — Rule 3, Rule 5, Rule 9 and Rule 10's example agree on every case.
Task achievable: yes — list/tree/IR construction is expressible with identical memory
traffic.
Depends on: Rules 1, 9, 10, 14, and Rule 16 for the arena variant only.
Note: reaching a child through `next: Option<Box<Node>>` needs a path into a variant
payload, which Rule 2's grammar does not provide; see 3-12. The three programs above use
a whole-Box field and a whole-slot path, so they do not depend on that gap.
Verdict: rejected-zero-cost

### 3-6: Window operations versus element references

Question: which `DynBox` operations kill element references, which do not, and what does
the forced re-formation cost?

Strongest program (run-length encoder: append while updating the element appended last —
the loop where C++ keeps `Run* last` in a register across `push_back`):

```text
n0 = len_of(runs)
for i in 0..m {
    invariant h: len_of(runs) <= n0 + i;              // Rule 11 loop-header invariant
    if len_of(runs) > 0 {
        last = &runs[len_of(runs) - 1]                // Rule 7: bound from the dominating branch (Rule 11)
        if (*last).v == src[i] {
            (*last).n = (*last).n + 1                 // content write at/below last's path: last stays valid
            continue
        }
    }
    push_nogrow(&runs, Run { v: src[i], n: 1 })       // writes(runs): every element reference invalid
}
```

Ordinary program:

```text
p = &buf[i]
buf[j] = 5            // sibling slot: p valid
buf[i] = f(buf[i])    // atomic update at p's own path: p valid; but &buf[i].field dies (buf[i] is its proper prefix)
pop(&buf)             // writes(buf): p invalid
```

Trace:

- Rule 6 gives every window operation the row `writes(buf)`: `push_nogrow`, `pop`,
  `swap_remove`, `truncate` all declare it, and the `Vector` grow path "allocates a larger
  DynBox, moves `[0, len_of)` across, and replaces the old one".
- Rule 3, prefix clause: `runs` is a proper prefix of `runs[k]` for every k, so every
  element reference dies at every window operation — including `push_nogrow`, which
  `requires len_of(buf) < cap_of(buf)` and therefore provably does not reallocate. Rule 9
  is why the non-reallocating case still counts: `writes` "covers writing, replacing,
  moving out of, and freeing the storage at the path".
- Rule 3, content clause, is what keeps the useful half: "Writing the storage at p's path
  or below it (a content write) does not invalidate p", with the rule's own
  `v.buf[j] = 5` line covering "a sibling or the same slot". Sibling index paths are never
  prefixes of each other, so no amount of element writing by other code disturbs `last`.
- Rule 12 at the join of the `if`: `last` is valid on the no-push edge and invalid on the
  push edge, so it is invalid after the join — "facts are intersected (a fact survives
  only if it holds on every incoming edge)". The loop above re-forms at the top of the
  next iteration, so nothing is lost.
- Rule 6's atomic update `buf[k] = f(buf[k])` is a write at path `buf[k]`: a reference
  into that slot's interior has `buf[k]` as a proper prefix and dies; `&buf[k]` itself is
  the written path, not a proper prefix, so it survives.
- The window boundary itself never lies: `len_of` is "a runtime number stored in the block
  header, readable by the program", and "no program point can observe a slot inside the
  window as empty", so a surviving reference never names a slot the program can see as
  absent.

Rewrite and cost: re-form the element reference after every window operation, as the loop
above already does. `push_nogrow` writes only the header `len` word and one slot; the
block base is provably unchanged (its precondition rules out the grow path), so a lowering
pass keeps the base in a register and the re-formation is `base + idx*scale` — one
addressing mode, zero to one extra ALU operation per iteration. Against C++ that called
`reserve` and cached `Run* last`, that is the whole cost. Against C++ without `reserve`,
the cost is zero: correct C++ must reload after `push_back` too. Where the writer wants
the grow path, `Vector::push`'s replacement invalidates for the same reason C++'s realloc
does.

Rules consistent: yes.
Task achievable: yes — the encoder compiles to the same loads and stores plus at most one
scaled add per iteration.
Depends on: Rules 7, 9, 11, 12.
Verdict: accepted-fine

### 3-7: Validity versus the bounds obligation

Question: can validity and in-bounds-ness diverge — a valid reference naming a slot outside
the window, or a live in-bounds index that yields no valid reference?

Strongest program (open addressing, data-determined probe index):

```text
mask = len_of(tags) - 1                  // len is a power of two by construction
i = h & mask
if i < len_of(tags) {                    // Rule 7: "the test establishes the fact; one compare, no trap"
    p = &slots[i]                        // also needs len_of(slots) == len_of(tags), carried as a fact
    ...
}
part = &buf[lo..hi]                      // Rule 7: requires lo <= hi <= len_of(buf); len_of(part) == hi - lo
other = &buf[hi..n]
fill(other)                              // writes(buf[hi..n]): not a prefix of buf[lo..hi] -> part stays valid
grow(&buf)                               // writes(buf): a proper prefix of both -> both invalid
```

Trace:

- Divergence in one direction is impossible: a valid reference could only name a slot
  outside `[0, len_of)` if `len_of` shrank, and every shrink (`pop`, `swap_remove`,
  `truncate`) declares `writes(buf)` (Rule 6), which is a proper prefix of every element
  path and invalidates by Rule 3. So validity implies in-bounds without a separate check.
- Divergence in the other direction is by design: an in-bounds index gives no reference
  until one is formed, since "Validity is re-established only by forming the reference
  again" (Rule 3). That is what makes the 3-4 and 3-16 index idioms work.
- The mask identity is not a fact this candidate has. Rule 11's forms are "affine
  comparisons over measures and integer values, refinement facts from a dominating branch,
  loop-header invariants ..., explicit `use` steps inside an `invariant`, and callee
  contracts"; `h & (n-1) < n` is bitwise, not affine, and no rule admits a bitwise lemma.
  Rule 7 then applies its stated escape: "when the proof is unavailable the program tests
  the measure, which is ordinary data."
- Range references and element references never invalidate each other, because Rule 3's
  relation is on paths and `buf[lo..hi]` neither extends nor is extended by `buf[k]`.

Rewrite and cost: bind `n = len_of(buf)` once and carry affine relations, exactly as Rule
11's loop example does, so element accesses inside a counted loop need no test at all.
Where the index is genuinely data-determined (hash probes, free lists, decoded offsets) the
cost is one compare and one perfectly predicted branch per access — identical to safe Rust
indexing, one compare more than `hashbrown`'s unchecked path or a C++ raw array access.

Rules consistent: yes — the two obligations are separate but the ordering between them is
forced, so no program can hold a valid out-of-window reference.
Task achievable: yes.
Depends on: Rules 6, 11, 12.
Verdict: accepted-fine

### 3-8: Validity while a linear part is consumed out of an aggregate

Question: when a linear field must be closed, what happens to references into the rest of
the same aggregate — and is the consumption itself admitted?

Strongest program:

```text
linear type File;   fn close(f: own File)
struct Conn { f: File, n: u64 }                // Rule 8: linear by containment

fn finish(c: own Conn) -> u64 {
    p = &c.n                                   // a reference into the non-linear part
    close(move c.f)                            // the form Rule 8 exhibits
    x = *p                                     // valid or not?
    return x
}
```

Trace:

- Rule 8 exhibits this consumption directly:
  "`fn use_it(c: own Conn) { ...; close(move c.f) }   // consuming the struct as a whole and closing its File is required`".
- Rule 6 forbids it: "There is no `take` operation and no partial move out of any place:
  the only ways to move a value out of storage are consuming a whole local (`move x`), the
  window operations, and the atomic update." `c.f` is a field of a local, not a whole
  local, and it is neither a window operation nor an atomic update.
- Rule 12 forbids it again: "No place is ever partially moved: every path is either wholly
  present or the program cannot name it."
- The three sentences cannot all hold, and the answer to my cell's question depends on
  which does. If `move c.f` is admitted, then `c.f` is not a prefix of `c.n`, `p` survives
  by Rule 3's prefix clause, and the cell is accepted at zero cost. If only `move c` is
  admitted, then `c` is a proper prefix of `c.n` and `p` dies — and, more seriously, no
  rule then gives any way to reach the `File` inside an `own Conn` at all, so Rule 8's own
  `Box<File>` line ("linear: must be taken apart and its File closed") names an operation
  the candidate does not define: `*b` is not a whole local either.
- Rule 8's own framing depends on the answer too: "Linear values must be consumed by an
  explicit operation on every exit path; the compiler never releases them." Under the
  strict reading, a linear value that has ever been placed inside an aggregate can never
  be consumed, so the aggregate can never be legally discarded, and the resource-pipeline
  task is not expressible at all.

Rewrite and cost: none derivable without a ruling. If partial move of a linear field is
admitted, there is no cost and no interaction with Rule 3 beyond the sibling-field case
above. If it is not, the only conceivable form is a builtin whole-local destructuring into
its fields, which this candidate does not contain, and whose cost cannot be estimated
against C++'s member destructor because its shape is unknown.

Rules consistent: no — Rule 8's example contradicts Rule 6's and Rule 12's prohibition.
Task achievable: undecided.
Depends on: Rules 6, 12.
Verdict: undecided-rule-gap

### 3-9: Effect-row granularity decides which bystander references survive

Question: does the coarseness of a callee's declared row, and only that, decide which of
the caller's references die — and can a writer always declare finely enough?

Strongest program (separate compilation: the caller sees only rows):

```text
struct Sim { grid: DynBox<f64>, meta: Meta, log: DynBox<Event> }

fn record(m: &Meta, e: own Event)          writes(m)
fn store(l: &DynBox<Event>, e: own Event)  writes(l)
fn touch(g: &DynBox<f64>, i: u64)          writes(g[i])      // Rule 9: a whole-index position supplied as an argument
fn sort(g: &DynBox<f64>)                   writes(g)

p = &s.grid[j]
record(&s.meta, e)     // substituted writes(s.meta): not a prefix of s.grid[j] -> p valid
store(&s.log, e2)      // substituted writes(s.log): disjoint field -> p valid
touch(&s.grid, k)      // substituted writes(s.grid[k]): equals p's path when k == j, otherwise a sibling;
                       // neither is a proper prefix -> p valid (Rule 3 content clause)
sort(&s.grid)          // substituted writes(s.grid): a proper prefix -> p invalid; re-form
```

Trace:

- Rule 9 fixes the vocabulary: paths "start at a reference parameter and may continue
  through fields, `*`, and whole-index or range positions supplied as arguments", and
  "Signatures never contain index expressions; an index enters an effect only through an
  argument, evaluated once at the call."
- Rule 10.3 then does the invalidation with the substituted paths, and Rule 3 supplies
  the prefix relation. Field-granular and argument-index-granular rows therefore leave
  bystander references alone across an opaque call — the caller never inspects the body.
- The cost lives entirely in coarse rows, and Rule 9 forces coarseness in one case: a
  callee that writes an element it *chooses itself* (a hash insert, a free-list pop, a
  search-then-update) cannot name that element in its row, because the index would have to
  be an expression and not an argument. Such a callee declares `writes(t)` and kills every
  element reference the caller holds.
- Rule 9's checking clause ("A function body is checked against its own row") means the
  writer can always split the coarse callee into a `reads` search returning an index and a
  fine `writes(t[i])` writer, which is the shape Rule 4 pushes towards anyway.

Rewrite and cost: split the coarse helper, or re-form after it. The split repeats the
callee's address computation once at the caller: `base + i*scale`, an addressing mode.
Re-forming costs the same. No copy, no branch, no lost parallelism; and the split *gains*
parallelism, since `writes(t[i])` and `writes(t[j])` can be admitted under Rule 13 with a
proved `i != j` where `writes(t)` twice cannot.

Rules consistent: yes.
Task achievable: yes.
Depends on: Rules 3, 4, 10, 13.
Verdict: accepted-fine

### 3-10: Pairwise call-site checks and bystander invalidation together

Question: when two argument paths may be the same slot, do Rule 10's pairwise check and
its bystander clause combine without either admitting an aliased write or killing
references that nothing relocated?

Strongest program (both indices data-determined, callee separately compiled, a third
reference live across the call):

```text
fn merge(dst: &Entry, src: &Entry)   writes(dst), reads(src)

i = find_a(&v, ka)?                       // data-determined
j = find_b(&v, kb)?                       // data-determined
q = &v[m]                                 // bystander, m data-determined
r = &v[i].count                           // a reference under one of the argument paths

merge(&v[i], &v[j])                       // rejected: writes(v[i]) and reads(v[j]) overlap without i != j
```

Ordinary program:

```text
if i != j {
    merge(&v[i], &v[j])                   // Rule 11 refinement fact from the dominating branch
} else {
    merge_self(&v[i])                     // the specialised one-slot body
}
use(q)                                    // valid: v[i] is not a proper prefix of v[m]
use(r)                                    // rejected: v[i] is a proper prefix of v[i].count
```

Trace:

- Rule 10.1: "Two effects on overlapping paths where at least one is a write must be
  proved disjoint (different roots, or indices or ranges proved distinct); otherwise the
  call is rejected." The rule file's own line is the same case:
  `two(&v[i], &v[j]) // accepted only with the fact i != j`.
- Rule 11 supplies that fact only from a dominating branch when the indices come from
  data, since there are no quantified facts to draw on. One compare, one branch.
- Rule 10.3 handles the bystander: "A live reference outside the call whose path has a
  proper prefix among the call's write paths becomes invalid after the call." The write
  path is `v[i]`; `v[m]` is a sibling index path (or the same path, when m == i), never an
  extension of `v[i]`, so `q` survives regardless of what `m` is. That is sound precisely
  because nothing was relocated (Rule 1) and the candidate has no content facts to lose —
  Rule 11: "There are no quantified facts over array elements ... and no per-slot
  occupancy facts."
- Rule 10.3's second sentence saves the arguments themselves: "A reference that is itself
  an argument is the thing being accessed, not a bystander." Without it, `&v[i]` would
  invalidate itself.
- `r` dies and should: `v[i]` is a proper prefix of `v[i].count`, and the callee is free
  to replace the whole `Entry`.
- The container/element pair is rejected outright and stays rejected:
  `bad(&vv, &vv[0]) // rejected: writes(vv) and writes(vv[0]) overlap`.
- Rule 10.2 makes a consumed by-value argument participate in the same comparison, which
  is what rejects the `put(slot, move b)` line derived in 3-5.

Rewrite and cost: the `i != j` branch, plus a specialised single-slot body (duplicated
code is not a cost under this protocol). One compare and one predicted branch per call
against C++, which simply aliases; zero against Rust, whose `get_many_mut` /
`split_at_mut` perform the same test. In the algorithms that actually hit this —
union-find `union`, swap, merge-two-buckets — the `i != j` test is already in the source
for algorithmic reasons, so the real cost is usually zero. For the whole-container case,
pass the index instead of the element reference and let the callee form the reference:
the address is computed once either way.

Rules consistent: yes — Rule 10.3 is Rule 3 restated at a call, and the prefix relation on
paths is what keeps sibling slots from killing each other.
Task achievable: yes.
Depends on: Rules 1, 3, 9, 11, 13.
Verdict: accepted-fine

### 3-11: Can a contract keep a reference alive the way `ensures` keeps a measure fact alive?

Question: Rule 3 opens by calling validity "a fact like any other" — can a callee's
`ensures` therefore re-establish it across a writing call?

Strongest program:

```text
fn refill(b: &DynBox<Int>)  writes(b)
    contract { ensures len_of(b) == len_of(deref(entry(b))); }    // every measure fact preserved

n = len_of(b)
p = &b[i]
refill(&b)            // writes(b)
use(p)                // rejected, although the contract preserved everything statable about b
q = &b[i]             // needs i < len_of(b): from i < n and the ensures, affine -> re-derived free
```

Trace:

- Rule 3 is explicit about the only route back: "Validity is re-established only by forming
  the reference again."
- Rule 11's route for facts does not apply, because there is no validity fact to write: the
  admitted forms are "affine comparisons over measures and integer values, refinement facts
  from a dominating branch, loop-header invariants `invariant name: affine_expr compare_op
  affine_expr`, explicit `use` steps inside an `invariant`, and callee contracts", none of
  which can express `valid(p)`, and no rule gives a syntax for it. Rule 3's "'p is valid'
  is a fact like any other" is therefore loose wording rather than a second mechanism: read
  together, the two rules agree on the outcome, so I treat this as decided rather than a
  gap, while noting the sentence.
- The contrast is the point of the cell: measure facts *do* cross writing calls
  (`ensures` in Rule 6's window operations, the `push_nogrow` derivation in 3-4, Rule 11's
  `invariant h: len_of(buf) == n - i` carrying `pop`'s precondition across a writing call),
  while validity never does. Index-shaped state is contract-carryable; reference-shaped
  state is not.

Rewrite and cost: re-form after the call, and carry the bounds fact through the contract.
Proofs are "erased before lowering" per the project's standing rule, so the invariant and
the contract cost nothing at run time, and the re-formation is one address computation that
the optimiser can usually fold. No branch is introduced, because the fact is proved rather
than tested.

Rules consistent: yes, on the reading above.
Task achievable: yes.
Depends on: Rules 6, 7, 10.
Verdict: accepted-fine

### 3-12: Joins, the absence of holes, and whether a variant payload is a place at all

Question: at a control-flow join, and at a `match` on the representation Rule 12 itself
recommends, is there a path for a reference to name?

Strongest program (Rule 12's own recommendation for non-Copy payloads):

```text
slots: DynBox<Option<Entry>>          // Rule 12: "non-Copy payloads: Option, using a null niche where the type has one"

if i < len_of(slots) {
    match slots[i] {
        Some(e) => { p = &e.count; *p = *p + 1 }    // is `e` a place? is there a path naming it?
        None    => { slots[i] = Some(fresh) }       // whole-slot write: unproblematic (Rule 6)
    }
}
```

Ordinary program (the join half, which is determinate):

```text
w = if cond { &v1 } else { &v2 }      // Rule 2: w's target set is {v1, v2}
if cond2 { u = move v1 }              // v1 moved on one edge only
use(w)                                // rejected
```

Trace:

- The join half is clean. Rule 12: "At a join, facts are intersected (a fact survives only
  if it holds on every incoming edge); a reference's target set is the union of its targets
  (Rule 2)." Rule 2: "every check on it must hold for every member of the set." So `w` is
  rejected because validity fails for `v1` on the moving edge, and Rule 12's no-holes
  clause ("No place is ever partially moved") means there is no intermediate state to
  reason about. Rewrite: duplicate the use into both arms, where each arm's reference has a
  singleton target set — zero runtime cost, and duplicated code is not a cost here.
- The `match` half has no rule. Rule 2's grammar: "A path starts at a local variable or a
  parameter and continues through fields, `*` (Box content), `[i]` (index, Rule 7), or
  `[lo..hi]` (range, Rule 7)." There is no variant-payload component, so nothing names the
  `Entry` inside `slots[i]`.
- Nor can the payload be moved out to work on it: Rule 6, "There is no `take` operation and
  no partial move out of any place: the only ways to move a value out of storage are
  consuming a whole local (`move x`), the window operations, and the atomic update."
  Rule 12's second clause is consistent with the payload simply being unnameable —
  "every path is either wholly present or the program cannot name it" — but then the
  representation Rule 12 recommends for non-Copy payloads is write-only.
- One reading is left open by the text and would save the program: the atomic update
  `slots[i] = f(slots[i])`, whose `f` takes the whole `Option<Entry>` by value and whose
  result is committed with "no program point lies between". Under that reading the task is
  achievable, and the cost is visible: for an `Entry` of w bytes the update moves w bytes
  in and w bytes out per increment, against C++'s single `add` through an iterator. For a
  32-byte `Entry` that is roughly eight extra loads and stores per hit on the hot path of a
  hash table. Rule 6's "no program point lies between" permits, but does not require, an
  in-place lowering that erases those copies, and no rule states that it must.
- Because the resolution changes both acceptance and cost by an order of magnitude on a
  hot path, I do not pick one.

Rewrite and cost (for Copy payloads, where the gap can be sidestepped): Rule 12's other
recommendation — `tags: DynBox<u8>` plus a fully initialised `slots: DynBox<Entry>` where
"a 'logically empty' slot holds a valid value". Then `&slots[i]` is an ordinary index path,
nameable and writable in place, and the cost is the already-recorded one: one byte per slot
and one load plus compare per probe. This is unavailable exactly where the gap bites —
an `Entry` containing a `Box` or a linear part cannot be zero-filled, so the candidate
sends it back to `Option`.

Rules consistent: undecided — the path grammar excludes the payload of the variant that
Rule 12 prescribes for this case.
Task achievable: undecided for non-Copy payloads; the tags-plus-values form covers Copy
payloads at the recorded cost.
Depends on: Rules 2, 6, 7, 11.
Verdict: undecided-rule-gap

### 3-13: References across a `par` block

Question: do references formed before, inside and after a parallel block stay sound, and
does one arm's write invalidate a sibling arm's or the continuation's references?

Strongest program (fork-join over adjacent ranges, a bystander reference live across it,
and an arm that wants to append):

```text
mid = n / 2
lo = &out[0..mid]                 // Rule 7: 0 <= mid <= len_of(out); len_of(lo) == mid
hi = &out[mid..n]
s  = &stats.total                 // a bystander under a different root

par { kernel(&src[0..mid], lo); kernel(&src[mid..n], hi) }      // accepted
*s = *s + 1                       // valid: no prefix of stats.total was written
use(lo)                           // see the wording note below

par { push_nogrow(&out, x); kernel(&src[0..mid], lo) }          // rejected: writes(out) overlaps writes(out[0..mid])
par { a = build(&x)?; b = build(&y)? }                          // accepted: allocation is not an effect
```

Trace:

- Rule 13: "`par { A; B }` is accepted when A's write paths are disjoint from B's read and
  write paths and vice versa, using the same path-overlap and index/range-disjointness
  judgment as Rule 10." `out[0..mid]` and `out[mid..n]` are disjoint by arithmetic, so
  Rule 10.1's "ranges proved distinct" is satisfied — the rule file lists this exact pair
  as accepted.
- Rule 14 keeps the allocating arms independent: "Allocation and release are not effects
  (Rule 14)", and Rule 14 itself: allocation "never make[s] two parallel arms conflict".
  That is what allows each arm to build owned results without a store or region parameter.
- The rejected arm pair is rejected for the right reason and matches the rule's own
  `par { push(&v, 1); stats(&v) }` line: a window operation's `writes(out)` is a proper
  prefix of every range and element path in the sibling.
- References formed inside an arm are ordinary locals; Rule 4 restricts only escape, and
  an arm returns nothing, so an arm may form and use as many as it likes.
- After the block, Rule 3 applies with the block's effects, which are its arms' effects by
  Rule 9's "every statement's effect ... must be covered by the declared row". `s` has a
  different root and survives; a reference under `out` is the subject of the wording note.
- Wording note, non-blocking here: whether writing a *range* path `out[0..mid]`
  invalidates an element reference `&out[k]` with k < mid is not stated. Rule 3's two
  clauses are "any proper prefix of p's path is written" and "Writing the storage at p's
  path or below it (a content write) does not invalidate p", and a range path is neither a
  syntactic prefix of `out[k]` nor `out[k]` itself. Both readings are sound, because a
  range write relocates nothing (Rule 1) and the candidate keeps no content facts
  (Rule 11); under the stricter reading the continuation re-forms `&out[k]` at zero
  runtime cost. I therefore do not mark the cell undecided, but the relation deserves one
  sentence in the rule text.

Rewrite and cost: an arm that grows a shared container stays rejected; the available form
is the one already recorded under "Known costs" — batched fork-join with two buffers, each
arm appending into its own `DynBox` and a merge afterwards. Cost against a single
sequential append: one extra buffer per arm and one merge pass, O(total) copies, unless
the consumer can read the two buffers in sequence, in which case the copies vanish and the
cost is the second buffer's memory. Against a shared C++ `vector` behind a mutex the
rewrite is normally faster (no lock per push); against a shared vector with an atomic bump
index it is comparable in traffic, and the candidate has no atomics anyway.

Rules consistent: yes.
Task achievable: yes for maps, adjacent-range kernels and independent allocation; rewrite
for parallel append into one container.
Depends on: Rules 1, 7, 9, 10, 11, 14.
Verdict: accepted-fine

### 3-14: Allocation, its failure arm, and allocator concurrency versus live references

Question: can an allocation, an allocation failure, or another arm's allocator traffic
invalidate a live reference?

Strongest program (allocate while a reference is live, across a `Result` join, and inside a
parallel block whose sibling allocates too):

```text
p = &node.payload                       // live across everything below

match Box::new(Other { .. }) {          // Rule 14: "Allocation returns a Result and never traps"
    Ok(b)  => { holder = move b }       // writes `holder`: a different root
    Err(e) => { log_oom(&sink, e) }
}
*p = 1                                  // valid on both edges, so valid after the join (Rule 12)

par { a = build(&x)?; b = build(&y)? }  // Rule 14: allocation "never make[s] two parallel arms conflict"
*p = 2                                  // still valid: no arm wrote a prefix of node.payload

push(&v, y)?                            // Vector grow path: allocate, move [0,len) across, replace v.buf
use(&v[0])                              // must be re-formed; every earlier element reference is dead
```

Trace:

- Rule 3 fires only on "any proper prefix of p's path [being] written, moved out of,
  replaced, or freed". An allocation writes no path of the program: the bytes it returns
  were not nameable before, and the allocator's own bookkeeping is outside the path
  language. Rule 14 states the closure explicitly — "Allocation and release carry no effect
  entry", "Addresses are not observable, so allocator concurrency does not affect program
  determinism."
- Rule 12 at the `Result` join intersects facts; validity holds on both edges, so it
  survives. No drop flag or runtime state is needed, because the two edges are distinct
  program points with distinct ownership (Rule 8: affine release at scope exit, "runs no
  user code").
- The one case that does invalidate is not the allocation but the replacement: Rule 6's
  grow path "replaces the old one", and Rule 9 counts replacement as a write, so
  `writes(v.buf)` is a proper prefix of every element path. Note that this fires on the
  `Err` edge too, where nothing was in fact replaced — Rule 3 invalidates "by a statement
  or by a call", and Rule 12 intersects. Conservative, and free: the re-formation is one
  address computation.
- Freeing is the same story from the other side: the free itself carries no effect, but
  the move or scope exit that caused it is a write of the owning path, so references die by
  Rule 3 rather than by anything the allocator did.

Rewrite and cost: none needed for allocation proper. The `?` on every allocation is one
test of the `Ok`/`Err` discriminant — on a `Result<Box<T>, Oom>` the null niche makes that a
compare against zero — plus a perfectly predicted branch. Against C++ `new` with
exceptions, that is one branch per allocation the C++ program does not execute; against
C++ `new(nothrow)`, Rust's `try_reserve`, or any kernel/browser allocator discipline that
handles OOM, it is the same branch. On a per-node build loop where the allocation itself
costs tens of cycles, this is under one percent.

Rules consistent: yes.
Task achievable: yes.
Depends on: Rules 6, 8, 9, 12, 13.
Verdict: accepted-fine

### 3-15: Owned returns, out-parameters, and the caller's live references

Question: does the owned-return discipline force a copy of a large result, and what does
the prescribed out-parameter form do to the caller's references?

Strongest program (a kernel that fills a large aggregate the caller already owns, while the
caller holds a range reference into it):

```text
fn render(out: &Frame, scene: &Scene)   writes(out), reads(scene)     // Rule 15's prescribed shape

row = &out.pix[0..w]
render(&out, &scene)        // writes(out): a proper prefix of out.pix[0..w] -> row invalid (Rule 3, Rule 10.3)
row = &out.pix[0..w]        // re-formed
```

The rejected alternative is the C++ `Frame render(const Scene&)` shape, and the still more
rejected `Val& at(...)`.

Trace:

- Rule 15: "A function returns owned values only", and it steers away from the by-value
  round trip itself: "Passing a large value in and back out is expressed as a reference
  parameter with a `writes` entry, not as move-and-return." PROGRAMS.md records why that
  matters: "Large-aggregate ownership round trips have no assumed zero-copy ABI", so the
  returned `Frame` risks a full byte copy that the out-parameter form never performs.
- Owned returns that are cheap stay cheap: `own DynBox<T>` moves a handle, not the block
  (Rule 6 puts the slots in a heap block; Rule 1's relocation clause applies to the value,
  which is the handle), and `own Box<T>` moves a pointer. So "returns are owned" costs
  nothing for containers and heap nodes — only for large inline aggregates, which Rule 15
  tells the writer not to return.
- Rule 4 covers the other half: "A function that 'finds' something returns an index or
  other owned data; the caller forms the reference", with the bounds relation in `ensures`
  (derived in 3-4).
- Rule 10.3 plus Rule 3 kill exactly the bystanders under the written path and nothing
  else; the argument `&out` itself is "the thing being accessed, not a bystander". A
  reference into a *different* field of the caller's frame survives, because the row names
  `out`, so a finer row (`writes(out.pix)`) would preserve more — the 3-9 lever applies
  here too.

Rewrite and cost: the out-parameter form is C++'s `render(Frame&, const Scene&)` and Rust's
`&mut out`, so there is nothing to pay; the re-formed `row` is one scaled add. A callee
that wants to hand back an interior position returns an index instead, one address
computation at the caller.

Rules consistent: yes.
Task achievable: yes.
Depends on: Rules 1, 3, 4, 6, 10.
Verdict: accepted-fine

### 3-16: When long-lived identity must be an index, what does Rule 3 protect?

Question: Rule 3 protects references, but Rules 1 and 4 mean every long-lived link is an
index — so what happens to the protection, and what does restoring it cost?

Strongest program: P3, a mutable compiler graph with node removal and slot reuse.

```text
struct Arena<T> { buf: DynBox<T> }
struct Node { op: Int, a: u64, b: u64, next_free: u64 }   // edges are handles: Rule 1 forbids stored references

id1 = alloc(&g, Node { .. })          // Rule 16: writes(g.buf); ensures result == len_of(deref(entry(g.buf)));
                                      //                        ensures len_of(g.buf) == result + 1
p   = &g.buf[id1]
id2 = alloc(&g, Node { .. })          // writes(g.buf): a proper prefix of g.buf[id1] -> p invalid (Rule 3)
(*p).a = id2                          // rejected
p   = &g.buf[id1]                     // re-formed; bound from id1 < result2 + 1 == len_of(g.buf), affine
(*p).a = id2

free_node(&g, id1)                    // push id1 onto the free list: writes(g.buf), writes(g.free_head)
id3 = alloc_reuse(&g, Node { .. })    // returns id1 again: the slot is reused
x = g.buf[id1].op                     // reads the NEW occupant
```

Ordinary program: a parallel per-node pass over the same arena.

```text
par { map(&g.buf[0..mid]); map(&g.buf[mid..n]) }     // Rule 13 with arithmetic range disjointness: accepted
```

Trace:

- Rule 3 does its job on references and only on references. Every alloc is `writes(g.buf)`
  (Rule 16's signature) which is a proper prefix of every node path, so no node reference
  survives an allocation, and any attempt to hold one across graph mutation is rejected.
- But the graph's own links are `u64`, because Rule 1 is absolute — "no aggregate ever
  contains a reference", "there is no type parameter, wrapper, or variant payload through
  which a reference can be stored" — and Rule 4 forbids returning or capturing one. So the
  edges get none of Rule 3's protection, and Rule 16 says what replaces it: "A stale index
  that is still in bounds names the current occupant of that slot: a logic error, not a
  memory error."
- P3 requires the opposite ("removal invalidates every path to m"), and the engineering
  task row for the mutable compiler graph requires that "a relation to a deleted node must
  not silently become a relation to a replacement node". Under Rule 16 as written it
  silently does.
- What is *not* lost: memory safety. The read is in bounds by a Rule 7 fact, the slot holds
  a well-typed `Node` (Rule 12: a "logically empty" slot holds a valid value; Rule 6: "No
  slot ever carries a tag"), nothing traps, nothing is uninitialised, and no write can
  corrupt a neighbouring slot. The failure is object identity, at the same level as a C++
  program reusing a pooled object.
- Parallel node work is fine and cheap: the arena is one `DynBox`, so Rule 13's adjacent
  ranges apply directly and P3's "parallel map over all nodes writing data" is achieved at
  zero cost. What is not expressible is allocating inside such a map — both arms would
  declare `writes(g.buf)`, and Rule 13 rejects that. Node creation is therefore a
  sequential phase, as it is in most C++ IR builders anyway.

Rewrite and cost: generation numbers as data, which Rule 16 anticipates — "Programs that
need to detect it keep a generation number as data":

```text
struct Handle { idx: u64, gen: u32 }      // Copy, freely stored in aggregates (Rule 1 is satisfied: no reference)
struct Node   { gen: u32, op: Int, a: Handle, b: Handle }
fn live(g: &Arena<Node>, h: Handle) -> Bool  reads(g)
    contract { ensures when true: h.idx < len_of(g.buf); }
```

Costs against C++'s raw `Node*`: an edge grows from 8 to 12 or 16 bytes, which for a
two-edge IR node is 8-16 more bytes per node and a proportional increase in cache
footprint on a traversal-bound pass; one extra load of the generation word (same cache line
as the node, so usually free) and one compare plus predicted branch per edge followed —
about two compares per node on a two-edge walk. Against a Rust generational arena
(`slotmap` and friends) the cost is exactly zero: it is the same representation. If the
program declines the generation word, the runtime cost is zero and the defect is silent,
which is why the cell is not `accepted-fine`.
Second cost, from Rule 3 rather than Rule 16: re-forming `&g.buf[id]` after each allocation
in a builder loop. The block moves only on growth, so this is `base + id*scale`, one
addressing mode; a C++ builder caching `Node*` saves at most one scaled add per node.

Rules consistent: yes — Rule 16 states its own consequence plainly, and Rule 3 is not
weakened, merely inapplicable to the links.
Task achievable: rewrite — the graph, its mutation and its parallel maps are all
expressible; deletion safety costs the generation word.
Depends on: Rules 1, 3, 4, 6, 7, 10, 12, 13, and Rule 16 (provisional pool rule).
Verdict: accepted-unsafe

### 14-14: One heap against itself — nesting, recursion, failure chains and parallel allocation

Question: repeated, nested, parallel and failing allocation on a single global heap with no
second store: does the rule compose with itself, and what does the absence of a second
store cost?

Strongest program (parallel build, per-node allocation, and a nested failure chain):

```text
fn build(src: &DynBox<u8>, out: &Arena<Node>) -> Result<u64, Oom>   reads(src), writes(out.buf)

par { r1 = build(&src[0..mid], &a1); r2 = build(&src[mid..n], &a2) }   // separate arena roots; both allocate

fn build_tree(d: u64) -> Result<Box<Node>, Oom>
    contract { requires d <= 64; }                                     // P19's declared depth bound
{
    if d == 0 { return Box::new(Node::leaf()) }
    l = build_tree(d - 1)?                    // on Err nothing at this level has been allocated
    r = build_tree(d - 1)?                    // on Err `l` is affine and released at scope exit, recursively
    return Box::new(Node { l: move l, r: move r })
}
```

Trace:

- Rule 14 composes with itself by construction: "There is one heap, provided by the trusted
  base, internally synchronized. Allocation and release carry no effect entry and never
  make two parallel arms conflict." Two allocating arms are therefore always compatible, at
  any nesting depth, and Rule 13's check never has to look at allocation at all.
- The cost of "internally synchronized" is an implementation question the rule leaves open
  in the program's favour: "Addresses are not observable, so allocator concurrency does not
  affect program determinism." Unobservable addresses are exactly the property that
  legalises per-thread caches and size-class free lists inside the trusted base, so the
  parallel allocation cost can match a thread-caching `malloc` (tcmalloc, mimalloc). No
  rule forces a global lock.
- Failure chains nest without state: Rule 8 releases affine values at scope exit
  "recursively (Box, DynBox)" and "runs no user code", so the half-built left subtree on
  the right subtree's `Err` is freed once, with no drop flag, because the arms are distinct
  program points (Rule 12). Nothing is leaked and nothing is freed twice.
- The self-interaction that actually costs is the absence of a second store: "There are no
  store or region parameters anywhere", so there is no type-level scratch heap and no
  one-shot region release. Bump allocation exists only through Rule 16 — "an arena is a
  DynBox used with `push_nogrow` as allocation and `truncate(0)` as reset". If Rule 16 does
  not survive owner ruling, every IR node, AST node and parser temporary is an individual
  `Box::new`, i.e. a general-allocator call of tens of cycles plus per-object header and
  scattered locality, where a C++ compiler front end bump-allocates in three instructions
  and frees the whole pool with one store. That is the single largest performance
  dependency in this cell.
- Arena capacity is "fixed at allocation" (Rule 6), so growth means the `Vector` pattern:
  allocate bigger, move `[0, len_of)` across, replace. This is where Rule 1's relocatability
  pays off and where the candidate beats C++: handles are indices, so they survive the
  move, whereas a C++ pointer arena can never move and must chain blocks instead. The
  cost is amortised one byte-copy per allocated byte across doubling, sequential and
  prefetch-friendly; the C++ chained form copies nothing but fragments and needs a block
  lookup for cross-block work.

Rewrite and cost: reserve the arena to a measured capacity to avoid the growth copies; keep
per-worker arenas rather than one shared arena (see 14-16). Residual costs: one predicted
branch per allocation against throwing `new`; amortised copy on arena growth; and the
Rule 16 dependency above.

Rules consistent: yes.
Task achievable: yes, conditional on Rule 16 for arena-style allocation; without it, per-node
heap allocation is a real and large regression against C++ front ends.
Depends on: Rules 1, 6, 8, 12, 13, and Rule 16 (provisional pool rule).
Verdict: accepted-fine

### 14-15: Allocation failure meets the owned-return discipline

Question: how does "allocation returns a `Result`" compose with "returns are owned",
especially when a linear value is live on the failure arm?

Strongest program:

```text
linear type File;   fn close(f: own File)
fn open(path: &DynBox<u8>) -> Result<File, Err>   reads(path)

fn session(path: &DynBox<u8>, n: u64) -> Result<Conn, Oom> {
    f = open(path)?                        // linear, now live and owed on every exit path
    match DynBox::new<u8>(n) {             // Rule 14: Result on every allocation
        Ok(buf) => { return Ok(Conn { f: move f, buf: move buf }) },
        Err(e)  => { close(move f); return Err(e) }
    }
}
```

Trace:

- Rule 15: "A function returns owned values only." `Conn` is owned and, by Rule 8's
  containment clause, linear, so the obligation travels with the returned value rather than
  being discharged by the callee.
- Rule 8 is what makes the failure arm explicit: "Linear values must be consumed by an
  explicit operation on every exit path; the compiler never releases them." The `Err` arm
  therefore contains the `close` in the source, checked per arm at the Rule 12 join, with
  no drop flag and no runtime state.
- Rule 14's no-effect clause keeps the failure arm from disturbing anything else: the
  allocation writes no path, so facts about `path` (Rule 11) survive both edges.
- Cheap returns: a `DynBox` return moves a handle, a `Box` return moves a pointer, and
  `Result<Box<T>, Oom>` fits the null niche Rule 12 already relies on, so the discriminant
  costs no extra word. Only a large *inline* aggregate would copy, and Rule 15 tells the
  writer to use a `writes` out-parameter instead (3-15).
- The shape Rule 15 forbids that C++ uses freely — returning an iterator or reference into
  the freshly allocated interior — is covered by Rule 4's index form at one address
  computation.

Rewrite and cost: none needed. The explicit `close` on the `Err` arm is code a C++ RAII
path also executes at run time; writing it per arm rather than per type is a source cost,
which this protocol does not count.

Rules consistent: yes.
Task achievable: yes.
Depends on: Rules 4, 6, 8, 11, 12.
Verdict: accepted-fine

### 14-16: One heap plus pools-as-usage against P2

Question: with one heap, no second store and arenas expressed as `DynBox` usage, is P2
derivable — several independently usable blocks, filled in parallel, one released and its
bytes reused, the others unaffected?

Strongest program: P2, written out under the candidate.

```text
struct Arena { buf: DynBox<u8>, head: u64, free: DynBox<Blk> }

fn alloc_bytes(a: &Arena, n: u64) -> Result<u64, Oom>   writes(a.head), reads(a.buf)
    contract { ensures when Ok: result == a.head_entry; ensures when Ok: result + n <= len_of(a.buf); }

a  = Arena { buf: DynBox::filled<u8>(cap, 0)?, head: 0, free: DynBox::new<Blk>(k)? }   // Rule 14: one heap, Result
o1 = alloc_bytes(&a, 64)?
o2 = alloc_bytes(&a, 64)?          // o2 == o1 + 64 from the contracts: affine
o3 = alloc_bytes(&a, 64)?          // o3 == o2 + 64

par { fill(&a.buf[o1..o1+64]);
      par { fill(&a.buf[o2..o2+64]); fill(&a.buf[o3..o3+64]) } }     // P2: "must be permitted to overlap"

free_bytes(&a, o2, 64)             // writes(a.free), writes(a.head)
o4 = alloc_bytes_reuse(&a, 32)?    // comes off the free list: o4's value is data
read(&a.buf[o1..o1+64])            // must still be legal

par { fill(&a.buf[o1..o1+64]); fill(&a.buf[o4..o4+32]) }             // rejected
```

Trace:

- Rule 14 fixes the shape before anything else: one heap, and "There are no store or region
  parameters anywhere". So the arena is a `DynBox` on that heap (Rule 6), its blocks are
  ranges or slot indices into it, and there is no second storage whose disjointness could
  be had from the type.
- The bump-allocated prefix of P2 works and is cheap. The three offsets are related
  affinely through the contracts, so Rule 13's requirement — "using the same path-overlap
  and index/range-disjointness judgment as Rule 10" — is met by Rule 10.1's "ranges proved
  distinct". `par { A; B }` is two-armed; nothing forbids nesting it, and the disjointness
  judgment is unchanged, so a three-way fill is expressible.
- The reuse case is where it fails. Once `o4` comes off the free list its value is data.
  Rule 11 admits "affine comparisons over measures and integer values, refinement facts
  from a dominating branch, loop-header invariants ..., explicit `use` steps ..., and
  callee contracts", and states "There are no quantified facts over array elements ... and
  no per-slot occupancy facts". The invariant that actually holds — every offset on the
  free list is disjoint from every live block — is a quantified fact over the contents of
  `a.free`, so it cannot be stated, and no contract on `alloc_bytes_reuse` can produce a
  disjointness relation against an arbitrary caller-held `o1`. Rule 13 therefore rejects
  the last `par`, which is P2's stated requirement.
- Rule 16 covers the identity half. The pointer form of P2's requirement is actually met,
  and for free: an old reference into the freed block cannot survive, because Rule 4
  forbids storing or returning it and Rule 3 kills it at the `writes(a.head)` of any
  subsequent alloc or free. The *offset* form is not met: a saved `o2` is still in bounds
  and still reads bytes, now belonging to the reused block — "a logic error, not a memory
  error". Detection costs one generation word per block and one compare per use (3-16).
- Reset is the candidate's win: `truncate(&a.buf, 0)` on a Copy element type is a single
  header store — Rule 6, "requires n <= len_of(buf); ensures len_of(buf) == n" — matching a
  C++ bump-arena reset exactly, and for affine elements it is the same recursive release
  C++ destructors would run.

Rewrite and cost, two options:

1. A dominating disjointness test. `if o4 + 32 <= o1 || o1 + 64 <= o4 { par { ... } } else { ...sequential... }`
   gives the refinement fact (Rule 11) at two compares per pair. But `par` is a two-armed
   construct over named arms, so k blocks need k(k-1)/2 statically written tests, and for a
   worker count that is a runtime value the form does not exist at all. This is usable at
   k = 2 or 3, not for a worker pool.
2. The admitted parallel form: partition the arena into k contiguous sub-arenas by
   arithmetic and give each worker its own, so every arm's range is proved disjoint from
   the arithmetic and each worker bump-allocates inside its own slice.
   `par { work(&arenas[0..h]); work(&arenas[h..k]) }` is accepted, each arm's allocations
   touch only its own head, and P2's overlap requirement is met for freshly allocated
   blocks. Costs: each slice must be sized for its worst case, so peak memory rises by
   roughly k times the per-worker imbalance; and a block freed by one worker cannot be
   reused by another without a sequential rebalancing pass, which is real fragmentation,
   not just source awkwardness. Against a C++ shared arena with an atomic bump pointer —
   which this candidate cannot express, having no atomics — the trade is a lock or an
   atomic for memory; against C++ per-thread arenas, which is the common production choice,
   the cost is zero.

Rules consistent: yes — every rejection above is a stated rule doing its job, and no two
rules disagree.
Task achievable: rewrite with a policy change. P2 as written — a free list feeding blocks
that are then filled in parallel — is not achievable; contiguous per-worker sub-arenas
achieve the parallel fill, and generation words achieve the stale-handle refusal.
Depends on: Rules 3, 4, 6, 7, 10, 11, 13, and Rule 16 (provisional pool rule).
Verdict: rejected-real-cost
