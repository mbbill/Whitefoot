# Candidate x1 interaction matrix — row 8 (value classes) and row 9 (effect rows)

Derived against the frozen rule set in `CANDIDATE-X1.md` (2026-09-18) and only that
file; the engineering tasks and programs P1-P19 are quoted from `PROGRAMS.md` where a
cell touches them. Nothing under "Not in this candidate" or "Deferred" is used, and
Rule 16 is used only in cells whose `Depends on` line says so.

Rule 8 = copy / affine / linear value classes, no destructors, linearity declared on
external-resource types and propagating through aggregates. Rule 9 = effect rows on
reference parameters only, paths from a reference parameter through fields, `*`, and
whole-index or range positions supplied as arguments; by-value parameters carry no
entry and the call site records their consumption or read; no index expressions in
signatures.

Cost convention from the protocol: runtime performance only. Verbosity, extra
parameters and duplicated code are not costs. "One move of `T`" means a relocation of
`sizeof(T)` bytes, which Rule 1's consequence ("any value can be relocated by copying
its bytes (memmove, realloc), because nothing inside it points anywhere") makes a
plain byte copy with no fixup.

Shared declarations used below:

```text
linear type File;   fn close(f: own File)
struct Conn { f: File, n: u64 }          // linear by containment (Rule 8)
```

### 8-8: Value classes against themselves — nesting, recursion, and two linear parts in one aggregate

Question: when Rule 8's own classification is applied repeatedly — linear inside
linear, a recursive linear tree, and an aggregate holding two linear parts — can the
program still discharge every obligation Rule 8 imposes?

Strongest program (an aggregate with two independent linear parts, the case where no
ordering trick helps):

```text
struct Pair { a: File, b: File }          // linear by containment, twice

fn close_pair(p: own Pair)
{
    close(move p.a)                       // partial move out of the local p
    close(move p.b)                       // needs p still nameable after the first move
}
```

Ordinary program (a recursive linear tree; at most one field must be moved out per
frame, so the ordering trick is available):

```text
struct Node { f: File, kids: DynBox<Node> }    // both parts linear; Node is linear

fn drain(n: own Node)
{
    while len_of(n.kids) > 0 {
        k = pop(&n.kids)                  // a window operation: own Node out of the block
        drain(move k)
    }
    close(move n.f)                       // the last remaining linear part; n is dead after this
}
```

Trace:

- Rule 8 classifies both programs: "Linearity is declared on external-resource types
  and propagates through aggregates: a struct, array, Box, or DynBox containing a
  linear part is linear." `Pair`, `Node` and `DynBox<Node>` are therefore linear, and
  "Linear values must be consumed by an explicit operation on every exit path; the
  compiler never releases them" applies at every level, recursively.
- The only disassembly form the candidate exhibits is Rule 8's own example line:
  `fn use_it(c: own Conn) { ...; close(move c.f) }   // consuming the struct as a
  whole and closing its File is required`. That licenses moving one field path out of
  an owned local.
- The ordinary program needs nothing more. `&n.kids` is a path from a local through a
  field (Rule 2). `pop` is one of the three admitted ways to move a value out of
  storage — Rule 6: "the only ways to move a value out of storage are consuming a
  whole local (`move x`), the window operations, and the atomic update" — and it
  yields `own Node`, which the recursive call consumes. When the loop exits,
  `len_of(n.kids) == 0`, so Rule 6's "A DynBox whose element type is linear is itself
  linear (Rule 8) and must be truncated to zero by the program before it can go out of
  scope" is satisfied without `truncate` ever releasing a linear element. Only then is
  `move n.f` performed, and nothing names `n` afterwards. Depth is not a problem
  either: a deeper part is reached by first moving the sub-aggregate into a temporary
  (`t = move c.a; close(move t.f)`), so every partial move stays at depth one.
- The strongest program is where the text stops agreeing with itself. Rule 12 says
  "No place is ever partially moved: every path is either wholly present or the
  program cannot name it", and Rule 6 repeats the restriction: "There is no `take`
  operation and no partial move out of any place". Under reading (i) — the sentences
  are literal, and Rule 8's `close(move c.f)` is admissible only because nothing names
  `c` afterwards — `close(move p.a)` makes `p` unnameable, `p.b` can never be reached,
  and `Pair` is a type no program can consume. Under reading (ii) — Rule 8's example
  generalizes and Rule 12's sentence is about storage holes observable at a join
  rather than about the owning local — both lines are accepted. The rule file states
  both sentences and does not rank them, and the protocol forbids me from choosing.

Rewrite and cost: under reading (i) the rewrite is to hold every linear part in a
window instead of a field — `struct Pair { fs: DynBox<File> }` with two elements
drained by `pop` — because the window operations are named move-out forms. That costs,
per element, one relocation of `sizeof(File)` out of the block plus one header store
for `len_of`, against C++'s in-place destructor call which moves nothing, plus the
block's 16-byte header and one dependent load to reach the payload. The same cost
already applies to the accepted ordinary program: draining `n.kids` by `pop` moves
each `Node` out of its slot before `drain` consumes it, where a C++ recursive
destructor reads each element in place. For a tree of `Node` values of 24 bytes and
`n` nodes that is `24n` bytes of extra copy traffic and `n` extra header stores per
teardown. Nothing else in the two programs costs anything: the temporaries introduced
by depth-one destructuring write into places that are dead immediately afterwards and
the backend may elide them, since Rule 14 makes addresses unobservable.

Rules consistent: no — Rule 8's disassembly example and the no-partial-move sentences
of Rules 6 and 12 give opposite answers for an aggregate with two linear parts.
Task achievable: rewrite — a window of linear values is consumable under either
reading, at one element move plus one header store per element.
Depends on: Rule 6 (window operations, the truncate-to-zero obligation), Rule 12 (the
no-partial-move sentence; the join side of the same question is 8-12), Rule 2.
Verdict: undecided-rule-gap

### 8-9: Value classes against effect rows — consuming a contained linear value through a reference parameter

Question: an effect row can only say `reads` and `writes` of a path; can a helper that
receives `&pool` consume one linear element chosen by a data-determined index, and
what does the row have to say about it?

Strongest program (index decided by data, the element removed without disturbing the
index of any other element, all through a separate helper):

```text
fn discard_one(pool: &DynBox<Option<File>>, k: u64)   writes(pool[k])
    contract { requires k < len_of(pool); }
{
    pool[k] = drop_file(pool[k])          // atomic in-place update (Rule 6)
}

fn drop_file(x: own Option<File>) -> own Option<File>     // by value: no effect entry
{
    match x { Some(f) => close(move f);  None => () }
    None
}

k = probe(&pool, key)                     // data-determined, returned as an index (Rule 4)
if k < len_of(pool) { discard_one(&pool, k) }
```

Ordinary program (drain everything, order irrelevant):

```text
fn close_all(buf: &DynBox<File>)   writes(buf)
{
    while len_of(buf) > 0 { f = pop(buf); close(move f) }
}
```

Trace:

- Rule 9 fixes what the row may say: "each path starts at a reference parameter and
  may continue through fields, `*`, and whole-index or range positions supplied as
  arguments", so `writes(pool[k])` is well formed with `k` a by-value parameter — the
  index "enters an effect only through an argument, evaluated once at the call", and
  the signature contains no index *expression*. There is no `consumes` entry and none
  is needed: Rule 9's `writes` "covers writing, replacing, moving out of, and freeing
  the storage at the path".
- The consumption itself is invisible to the row. `drop_file` takes its argument by
  value and Rule 9 says "A by-value parameter has no effect entry: the call site
  records the consumption (for `move`) or the read (for a copy) of the argument's
  place". Inside `discard_one` the consumed place is the slot, and the atomic update
  is the operation that empties and refills it: Rule 6, "`buf[k] = f(buf[k])` //
  atomic in-place update: the old value goes into `f` by value, `f`'s result is
  committed, no program point lies between". Rule 6's assignment sentence forces
  exactly this shape: "Assigning `buf[k] = x` where the old value is affine releases
  the old value; where it is linear the assignment is rejected unless written as the
  atomic update whose function consumes the old value."
- In `close_all` the consumed place is a local, not a path from a reference parameter,
  so `close(move f)` needs no entry at all; the declared `writes(buf)` covers only
  `pop`'s substituted row, as Rule 9's last paragraph requires: "every statement's
  effect and every callee's substituted row must be covered by the declared row".
- One reading has to be settled to get here. Rule 9's `writes` list contains "moving
  out of", which read on its own would allow `fn steal(p: &File) writes(p)` to move
  the caller's `File` out of `*p` and close it. Nothing in Rules 9 or 10 would tell the
  caller that its local was consumed — Rule 10's clause 3 speaks only of reference
  invalidation — so the caller would still owe a `close` on a value that is gone, and
  Rule 8's obligation would be discharged twice. Rule 12's "every path is either
  wholly present or the program cannot name it" rules that reading out: the only
  places a callee may leave empty are those the program can no longer name, which for
  Rule 6 means slots that have left the window (`pop`, `swap_remove`, `truncate`), and
  a caller's local never leaves. So "moving out of" in a row describes the window
  operations and the transient half of an atomic update, never a hole in a place the
  caller still owns. With that reading, a linear value is consumed only through an
  `own` parameter or a window operation, and the strongest program above is the
  general form.
- `Option<File>` is linear: Rule 8's "propagates through aggregates" governs, although
  its list names only "a struct, array, Box, or DynBox"; Rule 1 counts an enum among
  the aggregates. Rule 12 names this representation explicitly for this purpose:
  "`slots: DynBox<Option<Entry>>` // non-Copy payloads: Option, using a null niche
  where the type has one".

Rewrite and cost: none needed for the program as written. Against C++, `discard_one`
costs one branch on the `Option` discriminant plus a store of the whole `Option<File>`
back into the slot, where C++ would call `~File()` in place and clear a separate
bitmap bit — one branch and one byte of state either way, and with a null niche the
tag is free. The `pop`-based drain costs one relocation of `sizeof(File)` per element
against an in-place destructor loop, as in 8-8. The alternative removal form,
`swap_remove(pool, k)`, avoids the `Option` tag entirely but "ensures len_of(buf) ==
len_of(deref(entry(buf))) - 1" by refilling slot `k` from the last slot, which changes
which element every outstanding index names; a pool cannot use it (8-16).

Rules consistent: yes, once "moving out of" is read as bounded by Rule 12's
no-hole sentence; the unbounded reading would accept a double `close`.
Task achievable: yes — removal of a linear element at a data-determined index is
expressible with the atomic update and costs at most one branch.
Depends on: Rule 6 (atomic update, window operations, the linear-assignment
sentence), Rule 12 (no holes, occupancy as data), Rule 4 (search returns an index).
Verdict: accepted-fine

### 8-10: Value classes against the call-site rule — a by-value argument is a write of its place

Question: Rule 10 clause 2 makes a `move` argument an effect in the pairwise
comparison; which transfers of an affine or linear value does that reject, and does
any rejection cost anything at runtime?

Strongest program (moving a Box while a reference derived from it is the other
argument — Rule 10's own linked-list splice, with a linear payload so no copy escape
exists):

```text
struct Node { f: File, next: Option<Box<Node>> }      // linear by containment
fn put<T>(slot: &T, value: own T)   writes(slot)

b: Box<Node>
slot = &(*b).next
put(slot, move b)                    // rejected
```

Second strongest (one call that moves a linear element between two windows, where the
two windows may be the same object):

```text
fn transfer(dst: &DynBox<Conn>, src: &DynBox<Conn>)   writes(dst), writes(src)
    contract { requires len_of(src) > 0; requires len_of(dst) < cap_of(dst); }
{ c = pop(src); push_nogrow(dst, move c) }

transfer(&p, &q)                     // accepted: distinct roots
transfer(&p, &p)                     // rejected: writes(p) against writes(p)
```

Ordinary program (a by-value copy argument that reads the same place a reference
argument writes):

```text
push_nogrow(&buf, buf[0])            // T Copy: rejected, writes(buf) against a read of buf[0]
t = buf[0]; push_nogrow(&buf, t)     // accepted
```

Trace:

- Rule 10 clause 2: "A by-value argument contributes a consumption (`move`) or a read
  (copy) of its place to this comparison." In the first program the consumed place is
  `b`; the other argument's substituted path is `*b.next` (Rule 2: `slot` "names the
  path", it is not storage). Clause 1 then rejects: "Two effects on overlapping paths
  where at least one is a write must be proved disjoint (different roots, or indices
  or ranges proved distinct)". The rule file states the same line as its own example:
  "`put(slot, move b)` // rejected: `move b` writes the prefix `b` of slot's path
  (Rule 3)". Rule 3 gives the reason independently: "It is established when p is
  formed and invalidated when any proper prefix of p's path is written, moved out of,
  replaced, or freed".
- Rule 8 decides what the rewrite may look like. For a Copy payload the value could
  simply be read out first; for `Node`, which is linear by containment, no duplicate
  exists, so the only rewrite is to reorder the transfer so the reference is formed
  after the move:

```text
c = move b                           // b is dead; the heap object did not move
slot = &(*c).next                    // re-formed from the new owner (Rule 3)
put(slot, move c)                    // still rejected: the same prefix problem
```

  which fails for the same reason, and the actual rewrite is to move the value into
  the slot from the outside rather than through a reference to its own interior:

```text
n = Node { f: move f, next: move inner }     // build the successor link before installing
head.next = Some(move Box::new(n)?)          // one whole-place assignment, no aliasing
```

- In `transfer`, both parameters are reference parameters, so Rule 9 gives two write
  entries and clause 1 compares them: `transfer(&p, &p)` substitutes `writes(p)`
  against `writes(p)`, one root, not disjoint, rejected. Moving an element inside one
  window needs a one-parameter helper (`fn rotate(buf: &DynBox<Conn>) writes(buf)`).
  Duplicated code is not a cost under the protocol.
- The ordinary program is rejected by clauses 1 and 2 together — the copy read of
  `buf[0]` overlaps `writes(buf)` and `buf[0]` is below `buf`, so no index
  distinctness is available — and the rewrite hoists the read into a local.
- Rule 10 clause 3 does the remaining bookkeeping for affine values: after
  `transfer(&p, &q)` any live reference formed from `p` or `q` is invalid, because
  `p` is a proper prefix of `p[i]`. References that were arguments are exempt: "A
  reference that is itself an argument is the thing being accessed, not a bystander."

Rewrite and cost: `t = buf[0]; push_nogrow(&buf, t)` performs the identical load and
store the rejected call would have performed; C++'s `v.push_back(v[0])` does the same
work plus a self-aliasing guard in the library, and Rust rejects `v.push(v[0])` and is
rewritten the same way — zero cost, and one guard fewer than C++. The splice rewrite
builds the node with its successor already installed; that is the same number of
stores as the C++ pointer form, because Rule 1's consequence makes a `Box` move a
pointer copy. `transfer(&p, &p)` costs nothing to replace with a single-window helper.

Rules consistent: yes — clause 2 and Rule 3 give the same answer on every line here.
Task achievable: rewrite — every rejection above has a rewrite performing the same
loads and stores.
Depends on: Rule 3 (prefix invalidation), Rule 2 (a reference names a path), Rule 9
(rows of the callees), Rule 5 (Box moves), Rule 6 (window operations).
Verdict: rejected-zero-cost

### 8-11: Value classes against facts — moved values lose their facts, and "still present" is not a fact

Question: Rule 11 lists the admissible fact forms; since none of them mentions
ownership, what happens to facts when an affine value is moved, and how is a linear
value whose consumption is decided by data carried to its consumption point?

Strongest program (consumption decided by data that is gone by the time the value must
be consumed — the case a C++ or Rust compiler covers with a drop flag):

```text
h: Option<File>
if c { h = Some(move f) }                  // keep it for later
else  { close(move f); h = None }          // consume it now; both arms leave f dead

... many statements; c is not recoverable ...

match h { Some(g) => close(move g);  None => () }      // consumed on every exit path
```

Ordinary program (an affine container moved into a field, with a measure fact
established beforehand):

```text
n = len_of(buf)                            // fact: len_of(buf) == n
holder.data = move buf                     // Rule 3: buf is moved
// len_of(holder.data) == n is not available
m = len_of(holder.data)                    // one header load re-establishes it
```

Trace:

- Rule 11 enumerates the fact forms: "affine comparisons over measures and integer
  values, refinement facts from a dominating branch, loop-header invariants ...,
  explicit `use` steps inside an `invariant`, and callee contracts." Consumption state
  is not among them, and Rule 11 also forecloses the obvious workaround: "There are no
  quantified facts over array elements ... occupancy that is determined by data is
  stored as data (Rule 6, Rule 12)." So "f has not been closed yet" cannot be a fact;
  it must be data, and `Option<File>` is the data form Rule 12 names.
- Rule 8 supplies the obligation the program must meet — "Linear values must be
  consumed by an explicit operation on every exit path" — and it is met on both arms of
  the first `if` (`f` is moved into the `Option` or closed) and on both arms of the
  `match` (`g` is closed, or there was nothing). The join question is settled in 8-12.
- In the ordinary program, Rule 11's invalidation clause bites: "A fact that mentions
  a path is invalidated when that path is written (by statement or call) unless the
  callee's `ensures` re-establishes it." `holder.data = move buf` moves `buf`, so
  `len_of(buf) == n` dies, and no rule transports it to `holder.data`. Rule 3 says the
  same thing for references — "A move never re-roots an existing reference: after
  `w = move v`, references formed from `v` are invalid and are not reinterpreted as
  references into `w`" — and facts follow the same pattern here because the rule file
  offers no transport for either.
- The repair is inside Rule 11's own vocabulary: either re-read the measure, which is
  "ordinary data" (Rule 7), or route the move through a helper whose contract carries
  the relation forward:

```text
fn install(h: &Holder, b: own DynBox<Int>)   writes(h.data)
    contract { ensures len_of(h.data) == len_of(b); }     // relates the new place to the argument
```

Rewrite and cost: the `Option<File>` carrier costs one discriminant and one branch at
the consumption point. Rust compiles the same source shape to a stack drop flag and a
branch, and C++'s `std::optional<File>` is byte-for-byte the same; Rust elides the
flag only when the condition is statically known, which is exactly the case this cell
excludes. Cost: zero against the comparable C++ and Rust forms, and where `File` has a
null niche the discriminant is free as well. Re-establishing a measure after a move
costs one load of the block header; in a loop that move would be loop-invariant and the
load is hoistable, and the contract form above removes even that. No allocation, no
copy, no lost parallelism.

Rules consistent: yes — Rule 11's fact list and Rule 8's obligation do not overlap, and
Rule 12 supplies the data representation that bridges them.
Task achievable: yes — data-determined consumption is expressible at the cost of the
same flag C++ and Rust materialize.
Depends on: Rule 12 (occupancy as data), Rule 3 (a move does not re-root), Rule 6
(measures as data), Rule 7.
Verdict: accepted-fine

### 8-12: Value classes against joins — conditional release, loop exits, and no drop flags

Question: a linear value consumed on one arm of a branch and not the other, and an
affine value released inside a loop that exits early — what does Rule 12's join
treatment say, and does the program pay for it?

Strongest program (P8: conditional release, then use of the survivor, then its
release, with the deciding condition unavailable afterwards):

```text
f1: File;  f2: File
if c { close(move f1) } else { close(move f2) }
use(&survivor)                              // which one? not nameable after the join
close(move survivor)
```

Ordinary program (the same task written so that every arm carries its own state):

```text
if c { close(move f1);  use(&f2);  close(move f2) }
else  { close(move f2);  use(&f1);  close(move f1) }
```

Second strongest (a loop with an early exit carrying a linear value and a window of
linear values, both of which must be discharged on every exit path):

```text
h: Option<File> = Some(move f)
while len_of(jobs) > 0 {
    invariant a: len_of(jobs) <= n;
    j = pop(&jobs)                          // own Job out of the window
    if fatal(&j) {
        consume(move j)
        break                               // exit path 1
    }
    consume(move j)
}
while len_of(jobs) > 0 { consume(pop(&jobs)) }     // the window must reach zero either way
match h { Some(g) => close(move g);  None => () }  // exit path 2 uses the same code
```

Trace:

- Rule 12 states the join rule for facts and for places: "At a join, facts are
  intersected (a fact survives only if it holds on every incoming edge) ... No place is
  ever partially moved: every path is either wholly present or the program cannot
  name it." In the strongest program `f1` is present on the `else` edge and gone on the
  `then` edge, and symmetrically for `f2`, so after the join neither path is wholly
  present on every incoming edge and neither can be named. There is nothing for the
  program to call `survivor`; the rule file offers no union of ownership states and
  Rule 11's fact list contains nothing that could record which arm ran ("affine
  comparisons over measures and integer values, refinement facts from a dominating
  branch, loop-header invariants ..., explicit `use` steps ..., and callee contracts").
- Rule 8 then forces the rest: "Linear values must be consumed by an explicit
  operation on every exit path; the compiler never releases them." Because the join
  cannot carry the survivor, each arm must finish its own work before reaching the
  join, which is the ordinary program. This is exactly P8's stated requirement — "no
  runtime drop flag; the writer's own branches carry the state" — met literally.
- The loop case is the same rule applied at the back edge and at every `break`. The
  window is Rule 6 storage, so its obligation is the truncate-to-zero one — "A DynBox
  whose element type is linear is itself linear (Rule 8) and must be truncated to zero
  by the program before it can go out of scope" — discharged by the drain loop that
  both exit paths fall into. `h` carries the deferred file as data, per Rule 12's
  "Structures whose occupancy is decided by data keep that occupancy as data", and the
  final `match` consumes it wholly rather than partially, so the no-partial-move
  sentence is satisfied without relying on the disassembly reading that 8-8 leaves
  open. Nothing here needs a linear field to be moved out of a struct that is used
  again, which is why this cell is decidable and 8-8 is not.
- The invariant `len_of(jobs) <= n` is a Rule 11 loop-header invariant over a measure
  and survives the join by intersection; the `requires len_of(buf) > 0` of `pop` comes
  from the loop condition on each edge, as in Rule 11's own "`while len_of(buf) > 0 {
  pop(&buf) }` // no knowledge: the loop condition is the test".

Rewrite and cost: the ordinary program duplicates the tail of the function into both
arms. The branch on `c` already existed, and each arm executes the same number of
`close` calls and the same `use` as the C++ original; the duplicated code is static
size, not runtime work, and the protocol excludes duplication from the cost account.
Where the deciding condition genuinely must survive to a later point, the `Option`
carrier of the second program costs one discriminant and one branch — the same object
code as Rust's drop flag and as `std::optional` in C++, and free where the payload has
a null niche. The drain loop costs one relocation of `sizeof(Job)` per element against
a C++ destructor loop that reads each element in place (the 8-8 cost), plus one header
store per element. No allocation, no extra indirection, no lost parallelism.

Rules consistent: yes — Rule 12's intersection, Rule 8's every-exit-path obligation and
Rule 11's fact list agree that ownership state is carried by branches or by data.
Task achievable: rewrite — P8 is expressible by arm-local code or an `Option`, at the
cost C++ and Rust pay for the same decision.
Depends on: Rule 11 (fact list, invariants), Rule 6 (window obligations), Rule 2.
Verdict: accepted-fine

### 8-13: Value classes against parallel blocks — parallel teardown and parallel in-place transformation

Question: `par { A; B }` needs disjoint paths; can a set of linear resources be
consumed in parallel, and can linear elements be transformed in place in parallel?

Strongest program (drain one window of linear resources with two workers — the case
where the elements are decided by data and the work per element is real):

```text
buf: DynBox<Conn>                        // linear elements, len_of(buf) == n
par {
    while len_of(buf) > 0 { c = pop(&buf); finish(move c) }      // arm A
    while len_of(buf) > 0 { c = pop(&buf); finish(move c) }      // arm B
}                                        // rejected
```

Ordinary program (in-place transformation of two linear elements, indices from data):

```text
par { buf[i] = step(buf[i]);  buf[j] = step(buf[j]) }            // accepted with i != j
fn step(c: own Conn) -> own Conn                                 // consumes and rebuilds
```

Rewrite of the strongest program (the resources are held in one window per worker):

```text
pools: DynBox<DynBox<Conn>>              // k blocks, decided when the pool is built
par {
    while len_of(pools[0]) > 0 { finish(pop(&pools[0])) }
    while len_of(pools[1]) > 0 { finish(pop(&pools[1])) }
}                                        // accepted: writes(pools[0]) against writes(pools[1]), 0 != 1
```

Trace:

- Rule 13 fixes the test: "`par { A; B }` is accepted when A's write paths are disjoint
  from B's read and write paths and vice versa, using the same path-overlap and
  index/range-disjointness judgment as Rule 10. Read/read overlap is allowed." Both
  arms of the strongest program contain `pop(&buf)`, whose row is `writes(buf)`
  (Rule 6), so the two write paths share a root and Rule 10 clause 1's requirement
  ("must be proved disjoint (different roots, or indices or ranges proved distinct)")
  cannot be met. The rule file's own line is the same shape: "`par { push(&v, 1);
  stats(&v) }` // rejected: writes(v) overlaps reads(v)".
- The rejection is correct rather than conservative: `pop` moves the last element and
  decrements `len_of` in the block header, so two concurrent `pop` calls would race on
  the header and could hand the same element to both arms — a duplicated linear value,
  which Rule 8's "consumed at most once" and the linear obligation both forbid.
- Splitting by range does not rescue it. Rule 7 admits "a range reference into either"
  as an indexable thing with `len_of(part) == hi - lo`, and Rule 13 uses exactly that
  for its accepted kernels, but Rule 6 declares the window operations on `&DynBox<T>`
  and a range reference has no header of its own to move a boundary in. Moving a linear
  value out of a slot needs a window operation — Rule 6: "the only ways to move a value
  out of storage are consuming a whole local (`move x`), the window operations, and
  the atomic update" — so no range-based parallel drain exists.
- The ordinary program passes. The atomic update's write path is `buf[i]`, Rule 6
  requires the update form for a linear old value ("where it is linear the assignment
  is rejected unless written as the atomic update whose function consumes the old
  value"), and `i != j` is exactly the distinctness Rule 13's own line asks for:
  "`par { bump(&v[i]); bump(&v[j]) }` // needs i != j". In a counted per-element map
  the distinctness is the loop index's, and Rule 13 admits that family directly ("The
  existing counted-loop forms (per-element maps, adjacent ranges passed to a helper,
  admitted reductions) are expressed with range references"). `step` takes and returns
  `own Conn`, so Rule 8's at-most-once and every-path obligations hold inside the arm
  with no entry in any row (Rule 9: "A by-value parameter has no effect entry").
- Allocation inside an arm is free of this analysis: Rule 13, "Allocation and release
  are not effects (Rule 14)", so `finish` may allocate and release without making the
  arms conflict.

Rewrite and cost: the `pools` rewrite gives each worker its own block. A worker
receives `&pools[w]` once and then indexes inside it, so the extra level costs one
dependent load per worker, not per element; the per-element work, the header updates
and the number of moves are unchanged from the single-block form. Against C++
(`std::vector<Conn>` destroyed by a parallel `for` with each thread taking a range, or
Rust's `into_par_iter().for_each(drop)`), the difference is that the x1 program must
decide the number of blocks when the pool is built rather than when the loop runs: a
fixed `k` chosen at construction cannot be re-split for a different worker count, so a
workload with an uneven per-resource cost cannot be rebalanced without moving elements
between blocks at one relocation of `sizeof(Conn)` each. For an even workload the cost
is zero. Draining a single existing block in parallel, without such a rebuild, is not
expressible at all.

Rules consistent: yes — Rule 13's disjointness, Rule 6's single-header window and Rule
8's at-most-once rule agree.
Task achievable: rewrite — parallel teardown requires one window per worker, decided
at construction; in-place parallel transformation needs no rewrite.
Depends on: Rule 6 (window operations, atomic update), Rule 10 (overlap judgment),
Rule 7 (range references), Rule 14 (allocation is not an effect), Rule 9.
Verdict: rejected-zero-cost

### 8-14: Value classes against the heap — what happens to a linear value when the allocation carrying it fails

Question: Rule 14 makes every allocation fallible and Rule 8 makes a linear value's
consumption an obligation; when a linear value is moved into an allocation that
returns `Err`, who owes the `close`?

Strongest program (a linear resource installed into a freshly allocated node, on the
failure arm of the allocation — P18's "each may fail: the arm must free nothing twice
and leave earlier blocks owned", with a linear payload):

```text
fn install(f: own File, n: u64) -> Result<Box<Conn>, Oom>
{
    b = Box::new(Conn { f: move f, n: n })?      // Err: the Conn, and the File in it, are gone
    Ok(b)
}
```

Ordinary program (the same task with the allocation separated from the population):

```text
fn install(f: own File, n: u64) -> Result<DynBox<Conn>, Oom>
{
    cell = DynBox::new<Conn>(1)?                 // no linear value is at risk: len_of == 0
    push_nogrow(&cell, Conn { f: move f, n: n }) // requires len_of < cap_of: 0 < 1; cannot fail
    Ok(cell)
}
```

Trace:

- Rule 14 fixes the shape of a failing allocation: "Allocation returns a `Result` and
  never traps", and Rule 5 fixes the payload: "`b = Box::new(Node { ... })?`  //
  allocation can fail: `Result<Box<Node>, Oom>`". The error arm carries `Oom` and
  nothing else, so the argument that was moved in is not handed back.
- Rule 9 records the consumption at the call: "A by-value parameter has no effect
  entry: the call site records the consumption (`move`) ... of the argument's place."
  From the checker's position `f` was consumed by an explicit operation, so Rule 8's
  "Linear values must be consumed by an explicit operation on every exit path" is
  satisfied on both arms and the program is accepted.
- What the accepted program does at runtime is lose the `File`. Rule 8 also says "the
  compiler never releases them", so the compiler does not close it; the trusted base
  received the value and the rule file does not say what it does with it; and no
  program point can name it again. The obligation has evaporated silently on an arm
  that, by Rule 14, every allocation has. Linearity exists to prevent exactly this, and
  the candidate's own criterion is "safety through types and proofs" with resources
  covered by "explicitly linear program values". This is a leak of an obligation, not
  memory corruption, but it is the failure linearity is for.
- Rule 12's no-hole discipline is what makes the ordinary program work instead: an
  empty window is not a hole — Rule 6, "Slots `[0, len_of)` hold values; slots
  `[len_of, cap_of)` hold nothing" — so `DynBox::new<Conn>(1)` allocates without any
  `Conn` existing, and the fallible step happens before the linear value is committed.
  `push_nogrow`'s `requires len_of(buf) < cap_of(buf)` is discharged by
  `DynBox::new`'s postcondition `cap_of == n, len_of == 0` with `n == 1`, an affine
  comparison in Rule 11's fact vocabulary, so there is no runtime check. The push
  itself has no failure arm, so the linear value is never in flight across a fallible
  boundary.
- The same technique does not exist for `Box`: there is no way to allocate a `Box`
  without supplying its value, and an uninitialized `Box` would be a hole, which "Not
  in this candidate" excludes ("`take`/`put` holes").

Rewrite and cost: the `DynBox`-of-one rewrite carries a block header of `len_of` and
`cap_of` — 16 bytes on a 64-bit target — for every cell that a `Box` would have
allocated with no header at all, and every such cell is a separate allocation, so a
tree of `n` linear nodes pays `16n` bytes of extra footprint and the corresponding
cache pressure. The number of dependent loads per hop is unchanged (the payload sits at
a constant offset inside the block), and the bounds fact for slot 0 comes from the
contract, so there is no extra branch. Against C++ (`new Conn{std::move(f), n}` with a
`bad_alloc` path that runs `~File()` as the constructor unwinds) or Rust
(`Box::try_new` returning the value's storage to the caller on failure), the C++ and
Rust forms have no per-node header; the x1 cost is the 16 bytes per linear node. If the
`Err` arm of `Box::new` were specified to return the argument, the rewrite would be
unnecessary and the cost zero.

Rules consistent: no — Rule 5's stated `Err` payload discards a value that Rule 8
requires be consumed by an explicit operation, and the checker sees no violation.
Task achievable: yes — the allocate-then-populate form discharges every obligation on
the failure arm, at 16 bytes of header per linear cell.
Depends on: Rule 5 (Box and its Result), Rule 6 (empty window, push_nogrow), Rule 9
(consumption recorded at the call), Rule 11 (capacity facts), Rule 12 (no holes).
Verdict: accepted-unsafe

### 8-15: Value classes against owned returns — moving a resource through a pipeline

Question: Rule 15 says returns are owned and that a large value should travel as a
reference parameter with `writes` rather than move-and-return; does that work for a
linear value, and what does a per-stage hand-off cost?

Strongest program (the resource-processing pipeline task: a non-Copy resource moves
between stages, every typed outcome returns or finishes it, and the stage may fail):

```text
fn stage1(c: own Conn) -> Result<own Conn, own Conn>      // both arms carry the resource
fn stage2(c: own Conn) -> Result<Unit, own Conn>
fn finish(c: own Conn)                                    // consumes it

match stage1(move c) {
    Ok(c1)  => match stage2(move c1) { Ok(())  => ();  Err(c2) => finish(move c2) }
    Err(c1) => finish(move c1)
}
```

Ordinary program (the in-out form Rule 15 prescribes, for the non-linear part of the
same object):

```text
fn retune(c: &Conn, k: u64)   writes(c.n)                 // no ownership changes hands
```

Trace:

- Rule 15: "A function returns owned values only", and "Passing a large value in and
  back out is expressed as a reference parameter with a `writes` entry, not as
  move-and-return." The second sentence is available for `retune`, which only writes a
  non-linear field, and Rule 9 lets the row name that field ("member paths are
  allowed").
- It is not available for a stage that may consume the resource. A `writes(c)` entry
  covers "writing, replacing, moving out of, and freeing the storage at the path"
  (Rule 9), but replacing a linear value discards the old one, and Rule 8 forbids that:
  "Linear values must be consumed by an explicit operation on every exit path; the
  compiler never releases them." Rule 6 states the same restriction for the one place
  it can arise inside a window: "Assigning `buf[k] = x` where the old value is affine
  releases the old value; where it is linear the assignment is rejected unless written
  as the atomic update whose function consumes the old value." And a `writes(c)` that
  moved the value out and left the caller's local empty is excluded by Rule 12's
  "every path is either wholly present or the program cannot name it" (8-9). So a
  stage that may or may not consume the resource must take it `own` and return it in
  the arms that do not, which is what Rule 15's "returns owned values only" provides.
- Rule 4's search discipline composes with this: "A function that 'finds' something
  returns an index or other owned data; the caller forms the reference", so a pipeline
  that locates a resource in a window returns `Option<u64>` and the caller re-derives
  `&buf[i]`, which Rule 4 prices itself as "one address computation".
- Every arm of the `match` consumes its binding exactly once, satisfying Rule 8 on
  every exit path, and the bindings are whole values out of an owned result, so no
  partial move is involved and 8-8's open question does not reach this cell.

Rewrite and cost: none needed. The cost is the hand-off itself: each stage moves
`sizeof(Conn)` into the callee and each non-consuming arm moves it back out through
the return slot. Rule 1's consequence makes each of these a flat byte copy with no
fixup, and Rule 14's "Addresses are not observable" leaves the ABI free to pass and
return a large owned value through a hidden pointer, so a compiler may lower the whole
chain to zero copies — the same latitude Rust has for a moved `self` and a returned
value under NRVO. Against C++ that mutates the object in place through a `Conn&` and
signals the outcome with a returned enum, the x1 form is identical once that latitude
is taken and costs two relocations of `sizeof(Conn)` per stage if it is not. The
`Result` discriminant is one register, matching the C++ enum. The index-returning
search costs one address computation per lookup against a C++ function returning
`Conn*`, that is one multiply-add on a base pointer already in a register.

Rules consistent: yes — Rule 15's in-out advice applies to the parts a row may write,
and Rule 8 routes ownership changes through owned parameters and returns.
Task achievable: yes — the pipeline task is expressible with no unavoidable runtime
cost beyond the ABI's choice about large owned values.
Depends on: Rule 9 (what a row may write), Rule 12 (no holes), Rule 4 (searches return
indices), Rule 1 (relocation by byte copy), Rule 14 (addresses unobservable).
Verdict: accepted-fine

### 8-16: Value classes against pools and arenas — resetting and reusing slots that hold resources

Question: under the provisional Rule 16 a pool is a `DynBox` plus indices and a reset
is `truncate(0)`; what happens when the elements are linear, and can a freed slot be
reused?

Strongest program (a pool of linear resources with slot reuse and a reset, the case
where a stale index must not silently close someone else's resource):

```text
struct Pool { slots: DynBox<Option<Conn>>, gen: DynBox<u32>, free: DynBox<u64> }

fn acquire(p: &Pool, c: own Conn) -> u64        writes(p.slots), writes(p.free)
    contract { requires len_of(p.free) > 0; ensures result < len_of(p.slots); }
{
    k = pop(&p.free)
    p.slots[k] = fill(p.slots[k], move c)       // atomic update; old value was None
    k
}

fn release(p: &Pool, k: u64)                    writes(p.slots[k]), writes(p.gen[k]), writes(p.free)
    contract { requires k < len_of(p.slots); requires k < len_of(p.gen);
               requires len_of(p.free) < cap_of(p.free); }
{
    p.slots[k] = drop_conn(p.slots[k])          // atomic update: consumes the Conn, stores None
    p.gen[k]   = p.gen[k] + 1                   // reuse is detectable, as data
    push_nogrow(&p.free, k)
}

truncate(&p.slots, 0)                           // the arena reset: rejected while elements are linear
```

Trace:

- Rule 16 defines the pattern: "A pool is a DynBox plus indices used as handles; an
  arena is a DynBox used with `push_nogrow` as allocation and `truncate(0)` as reset. A
  stale index that is still in bounds names the current occupant of that slot: a logic
  error, not a memory error. Programs that need to detect it keep a generation number
  as data."
- The reset does not survive contact with Rule 8. `truncate(&p.slots, 0)` would drop
  the occupants of the truncated slots — Rule 6, "At scope exit the compiler releases
  slots `[0, len_of)` recursively and frees the block", and `truncate`'s `ensures
  len_of(buf) == n` with nothing said about the elements between `n` and the old
  length — while Rule 8 says of linear values "the compiler never releases them". The
  only reading that keeps both rules is that `truncate` past linear elements is
  rejected, which is also what Rule 6's linear-assignment sentence does for a single
  slot. So an arena whose elements are linear is drained element by element and never
  reset in one step. Note that `Option<Conn>` stays linear whether or not its
  occupancy is `None`: Rule 8 classifies types, not values, and the class propagates
  "through aggregates".
- Reuse of a slot works because there are no holes to reuse. Rule 12 supplies the
  representation — "Structures whose occupancy is decided by data keep that occupancy
  as data ... `slots: DynBox<Option<Entry>>` // non-Copy payloads: Option, using a
  null niche where the type has one" — and Rule 6 supplies the only admissible
  transition, the atomic update whose function consumes the old value. A released slot
  therefore holds a valid `None`, never an empty one, so Rule 6's "no program point can
  observe a slot inside the window as empty" holds throughout.
- `release`'s row is legal under Rule 9 because `k` is an argument, not an index
  expression: "an index enters an effect only through an argument, evaluated once at
  the call". That precision is what lets two releases on distinct handles run in one
  `par` block (Rule 13), which a `writes(p.slots)` row would forbid.
- The free list is data, so Rule 11's fact forms suffice: `len_of(p.free) > 0` and
  `k < len_of(p.slots)` are affine comparisons over measures. No quantified fact is
  needed and none is available ("There are no quantified facts over array elements").
  The contract cannot state that the returned handle names a `Some` slot; a consumer
  that needs it branches on the `Option`, which is the Rule 12 answer.

Rewrite and cost: the reset rewrite is a drain loop,
`while len_of(p.slots) > 0 { c = pop(&p.slots); consume_opt(move c) }`, costing one
relocation of `sizeof(Option<Conn>)` and one header store per slot plus one branch on
the discriminant. A C++ arena of objects with non-trivial destructors runs the same
per-object loop, so the comparison is one move per element, not a whole reset; only an
arena of trivially destructible elements gets C++'s single pointer reset, and such
elements are never linear, so that case is unaffected (`truncate(0)` remains a header
store for copy and affine elements). Per-slot occupancy costs one discriminant load and
one branch per access against an unsafe C++ union pool, and nothing against
`std::optional` or Rust's `slotmap`. The generation number is optional and costs four
bytes per slot plus one load and compare per handle dereference for programs that
require the mutable-compiler-graph task's "a relation to a deleted node must not
silently become a relation to a replacement node"; programs that do not need detection
pay nothing, and Rule 16 explicitly leaves the undetected case a logic error.

Rules consistent: yes, once `truncate` over linear elements is read as rejected; the
alternative reading would have the compiler release a linear value.
Task achievable: yes — a pool of linear resources with reuse, detection and teardown is
expressible; only the constant-time reset is lost, and only where destructors would
run anyway.
Depends on: Rule 16 (provisional pool and arena rule), Rule 6 (window operations,
atomic update, truncate), Rule 12 (occupancy as data), Rule 9 (index arguments in
rows), Rule 11 (measure facts), Rule 13 (parallel releases).
Verdict: accepted-fine

### 9-9: Effect rows against themselves — composing rows through a call chain, and two entries in one row

Question: when one function's row must cover the substituted rows of its callees, and
when a single row carries two index-carrying entries, what does Rule 9 force the
writer to declare, and what does that declaration cost the callers?

Strongest program (a helper whose two write paths are decided by data at the caller,
so the callee's row has to name both and the caller has to prove them apart):

```text
fn swap_two(v: &DynBox<Int>, i: u64, j: u64)   writes(v[i]), writes(v[j])
    contract { requires i < len_of(v); requires j < len_of(v); }
{
    t = v[i]
    v[i] = const_of(v[i], v[j])          // atomic updates; each writes one named slot
    v[j] = const_of(v[j], t)
}

sort_step(&v, a, b)                      // a, b from a comparison network: a != b provable
swap_two(&v, p, p)                       // rejected at the call, though the body is sequential
```

Ordinary program (a row that names the container, so callers may alias freely but
nothing can be proved apart):

```text
fn swap_any(v: &DynBox<Int>, i: u64, j: u64)   writes(v)
    contract { requires i < len_of(v); requires j < len_of(v); }
swap_any(&v, p, p)                       // accepted
par { swap_any(&v, a, b); swap_any(&v, c, d) }     // rejected: writes(v) against writes(v)
```

Recursion through rows:

```text
fn walk(n: &Node, d: u64)   writes(n)
    contract { requires d <= 64; }
{
    n.mark = 1                           // write path n.mark, covered by writes(n)
    match n.child { Some(b) => walk(&(*b), d + 1);  None => () }   // substituted writes(*n.child)
}
```

Trace:

- Rule 9's path grammar admits both rows: "each path starts at a reference parameter
  and may continue through fields, `*`, and whole-index or range positions supplied as
  arguments", and the restriction it adds is about the *form* of the index, not its
  presence: "Signatures never contain index expressions; an index enters an effect
  only through an argument, evaluated once at the call." `writes(v[i])` names the
  argument `i`; a row saying `writes(v[i + 1])` or `writes(v[len_of(v)])` would be the
  forbidden shape. The file also demonstrates the other route, passing the slot itself
  as a reference parameter: "`put_at(&buf[len_of(buf)], 3)` // the argument fixes the
  slot at the call; the row itself names no index" — the call-site half of that example
  is taken up in 9-12.
- Body checking is the last paragraph of Rule 9: "A function body is checked against
  its own row: every statement's effect and every callee's substituted row must be
  covered by the declared row." In `swap_two` each atomic update's write path is one of
  the two declared paths. In `walk` the recursive call substitutes `writes(*n.child)`,
  and `n` is a prefix of that path, so `writes(n)` covers it; Rule 10 adds "Recursion
  is checked through contracts, never by unfolding bodies", so the contract `d <= 64`
  is all that crosses the back edge.
- The price of the precise row appears at the caller, not in the body. Rule 10 clause 1
  compares "the substituted effects pairwise", and Rule 9's own `fn update(o: &Obj, c:
  Bool) writes(o.a), writes(o.b)` shows two entries from one row being compared that
  way. So `swap_two(&v, p, p)` substitutes `writes(v[p])` against `writes(v[p])` — one
  root, indices not distinct — and is rejected, although the body performs the two
  updates in sequence and would be harmless. The coarse row has the mirror-image
  defect: `writes(v)` never conflicts with itself inside a single call, so aliasing
  callers are fine, but Rule 13 then rejects every parallel pair because it uses "the
  same path-overlap and index/range-disjointness judgment as Rule 10".
- Nothing in Rule 9 lets one function have both rows, and nothing forbids declaring two
  functions with the same body. The writer therefore ships `swap_two` for callers that
  can prove distinctness and `swap_any` for callers that cannot.

Rewrite and cost: shipping both rows duplicates source, which the protocol excludes
from the cost account, and each caller selects the row it can discharge, so no call
site executes an instruction it would not have executed in C++ or Rust. There is one
case where the duplication does not close the gap: a caller that must alias *and*
parallelize — `par { swap_any(&v, a, b); swap_any(&v, c, d) }` with no distinctness
available — is rejected, and that is the genuine content of 9-13 rather than of this
cell. For the recursion, `writes(n)` on a whole subtree is as coarse as C++'s implicit
"this function may touch anything reachable", so nothing is lost relative to the
baseline; the contract-based recursion check costs nothing at runtime because proofs
are erased.

Rules consistent: yes — the path grammar, the body-covering rule and Rule 10's pairwise
comparison compose without contradiction.
Task achievable: yes — precision is a per-function choice, and both precisions can be
provided at zero runtime cost.
Depends on: Rule 10 (pairwise comparison, recursion through contracts), Rule 6 (atomic
update), Rule 13 (why precision matters), Rule 11 (contracts).
Verdict: accepted-fine

### 9-10: Effect rows against the call-site rule — substituting a reference whose target is a set

Question: Rule 10 substitutes actual argument paths into the callee's row; when the
argument is a reference variable whose target is a set of paths from a join (Rule 2),
what must be proved, and what does the repair cost?

Strongest program (the argument's path is decided by data, and the callee's row is
precise enough that the disjointness question is real):

```text
fn merge(dst: &DynBox<Int>, src: &DynBox<Int>)   writes(dst), reads(src)

w = if c { &v1 } else { &v2 }            // w names one of {v1, v2} (Rule 2)
merge(w, &v1)                            // rejected
```

Ordinary program (the same task with the branch outside the call):

```text
if c { merge(&v1, &v1) }                 // still rejected: one root
else  { merge(&v2, &v1) }                // accepted: different roots
```

Second strongest (a nested call supplying a by-value argument while the same container
is a reference argument):

```text
fn attach(pool: &DynBox<Conn>, c: own Conn)   writes(pool)
attach(&pool, pop(&pool))                // rejected
t = pop(&pool); attach(&pool, move t)    // accepted
```

Trace:

- Rule 10's first instruction is the substitution: "At a call, substitute the actual
  argument paths into the callee's row." For `w` the actual path is not one path.
  Rule 2 settles what that means: "At a control-flow join, a reference variable's
  target is the set of paths it may name; every check on it must hold for every member
  of the set." The member `v1` of the set makes `writes(v1)` collide with `reads(v1)`,
  and clause 1 requires disjointness of "overlapping paths where at least one is a
  write ... (different roots, or indices or ranges proved distinct)"; `v1` against
  `v1` has one root. So the call is rejected on account of a path the program might
  not even take.
- The ordinary program shows that the rejection is not a loss of capability: pushing
  the branch outside the call gives each arm a singleton target set, and the arm that
  is genuinely disjoint is accepted. The arm that is genuinely aliasing stays rejected,
  correctly — `merge(&v1, &v1)` would read and write one container.
- The nested call is clause 2 plus clause 1: "A by-value argument contributes a
  consumption (`move`) or a read (copy) of its place to this comparison", and the
  place of `pop(&pool)`'s result is produced by a call whose substituted row is
  `writes(pool)` (Rule 6), which overlaps the outer call's `writes(pool)`. Sequencing
  the two calls into two statements removes the comparison entirely, because Rule 10
  compares the effects *of one call*.
- Clause 3 then runs on the accepted forms: "A live reference outside the call whose
  path has a proper prefix among the call's write paths becomes invalid after the
  call", so a reference into `v2` formed before `merge(&v2, &v1)` is invalid
  afterwards, while `w` itself, being an argument, is exempt: "A reference that is
  itself an argument is the thing being accessed, not a bystander."
- One point the rule text leaves to Rule 2 rather than to Rule 10: a joined reference
  never has its set narrowed by a later test, because Rule 11's refinement facts are
  "refinement facts from a dominating branch" over integer and measure comparisons,
  not over reference identity. So there is no way to recover precision after the join
  other than duplicating the call.

Rewrite and cost: duplicating the call into the two arms executes exactly the same call
as the joined form would have, on a branch the program already had; the reference
variable is not storage (Rule 2: "A reference variable names a path; it is not storage
of its own"), so nothing is materialized or spilled and the duplication is code size
only. Splitting `attach(&pool, pop(&pool))` into two statements performs the same pop
and the same push in the same order; C++'s equivalent (`v.push_back(std::move(v.back()));
v.pop_back()`) needs the identical sequencing to be correct, and Rust rejects the
one-line form as well. Zero runtime cost in both repairs.

Rules consistent: yes — clause 1 applied to Rule 2's target set is the same test
applied to more paths, and no rule offers a narrowing that would contradict it.
Task achievable: rewrite — branch duplication and statement sequencing recover every
rejected call at no runtime cost.
Depends on: Rule 2 (target sets), Rule 3 (prefix invalidation), Rule 6 (window
operation rows), Rule 11 (what a refinement fact may say).
Verdict: rejected-zero-cost

### 9-11: Effect rows against facts — a coarse row destroys the caller's facts, and `ensures` is the only repair

Question: Rule 11 invalidates a fact whose path is written by a call; since Rule 9 rows
are as coarse as the writer made them, what does a caller lose across a helper call and
what must the helper promise to give it back?

Strongest program (a loop whose invariant and whose bounds facts both cross a helper
that writes one element of the same container, with the index decided by data):

```text
fn scale_one(v: &DynBox<Int>, k: u64, f: Int)   writes(v[k])
    contract { requires k < len_of(v); }         // says nothing about len_of afterwards

n = len_of(v)
m = len_of(idx)
i = 0
while i < m {
    invariant a: len_of(v) == n;                 // must survive every call in the body
    invariant b: len_of(idx) == m;
    k = idx[i]                                   // requires i < len_of(idx): from b and the condition
    if k < n {                                   // refinement fact from a dominating branch
        scale_one(&v, k, 2)                      // requires k < len_of(v): needs a, still alive?
    }
    i = i + 1
}
```

Ordinary program (the helper's row names the whole container, so the invariant has to
be re-established by data on every iteration):

```text
fn scale_any(v: &DynBox<Int>, k: u64, f: Int)   writes(v)
    contract { requires k < len_of(v); }
...
    k = idx[i]
    if k < len_of(v) { scale_any(&v, k, 2) }     // one header load and one compare per iteration
```

Trace:

- Rule 11's invalidation clause is the whole of this cell: "A fact that mentions a path
  is invalidated when that path is written (by statement or call) unless the callee's
  `ensures` re-establishes it." In the ordinary program the substituted write path is
  `v`, the invariant `len_of(v) == n` mentions `v`, and `scale_any`'s contract has no
  `ensures`, so the invariant dies at the first call and cannot be re-proved at the
  loop header. The program compiles only if the writer replaces the fact with a test,
  which Rule 7 licenses — "when the proof is unavailable the program tests the measure,
  which is ordinary data" — at one load of the block header and one compare per
  iteration.
- Two repairs exist and both are inside the rules. The first is the precise row of the
  strongest program: the write path is `v[k]`, which Rule 9 admits because `k` is an
  argument, and the invariant's path is `v`. Rule 3 draws exactly this distinction for
  references — "Writing the storage at p's path or below it (a content write) does not
  invalidate p" — and Rule 12's join example applies the same reasoning to facts:
  "`if cond { push_nogrow(&buf, x) }` // after the join: `len_of(buf) >= n` ... facts
  about indices below n survive", where a whole-container write leaves a length
  relation standing. On that reading a write below `v` leaves `len_of(v) == n`
  standing and no test is needed.
- The second repair is the `ensures`, which the candidate uses for precisely this
  purpose throughout Rule 6: `push_nogrow` carries "ensures len_of(buf) ==
  len_of(deref(entry(buf))) + 1" so that a caller's length fact survives a call that
  writes the whole block. A helper that writes one element can carry
  `ensures len_of(v) == len_of(deref(entry(v)))` and restore the invariant exactly.
- What no row and no contract can restore is a fact about a *sibling* element. After
  any call whose write path is `v` or `v[k]` with `k` not proved distinct from `j`, a
  fact `v[j] == 7` is invalidated, and Rule 11 forecloses the general repair: "There
  are no quantified facts over array elements ('for all i ...')". A program that needs
  element relations across a helper call stores them as data (Rule 12) or re-reads the
  element — one load.
- The contract's own `requires k < len_of(v)` is discharged at the call from the
  dominating branch `k < n` and the invariant `a`, both Rule 11 forms ("refinement
  facts from a dominating branch", "loop-header invariants"), so no bounds check
  reaches the object code, as Rule 7 promises ("one compare, no trap" only where the
  program chose to test).

Rewrite and cost: with the precise row or the `ensures`, the strongest program compiles
to the same loop a C++ version would produce — one load of `idx[i]`, one compare
against a length held in a register, one indexed store — and the bounds proofs are
erased. With neither, the loop pays one extra load of the block header per iteration
because `len_of(v)` must be re-read after each call, plus the compare that C++ would
also perform if it checked; the load is the only true difference, and it cannot be
hoisted because the call is opaque. That is one dependent load per iteration on a
hot loop, which is a real cost, and it is entirely avoidable by writing the `ensures`.

Rules consistent: yes — Rule 11's invalidation, Rule 9's row precision and Rule 6's
contracts form one mechanism.
Task achievable: yes — a helper that preserves a measure says so in `ensures`, and the
caller keeps its invariant with no runtime check.
Depends on: Rule 6 (contract style for window operations), Rule 7 (testing a measure),
Rule 3 (content writes), Rule 12 (join example, occupancy as data).
Verdict: accepted-fine

### 9-12: Effect rows against the absence of holes — Rule 9's own call-site example names a slot outside the window

Question: Rule 9 says an index enters an effect through an argument and illustrates it
by passing a reference to the slot at `len_of(buf)`; can such a reference exist at all
under the window and no-hole rules, and if it can, who moves the boundary?

Strongest program (the rule file's own illustration, put in the context that makes it
do work — appending an element through a helper rather than through `push_nogrow`):

```text
fn put_at(slot: &Int, x: own Int)   writes(slot)

buf: DynBox<Int>                                  // len_of(buf) == L, cap_of(buf) == C, L < C
put_at(&buf[len_of(buf)], 3)                      // Rule 9's example line
// what is len_of(buf) now?
```

Ordinary program (the same append with the operation the window defines):

```text
push_nogrow(&buf, 3)                              // requires len_of(buf) < cap_of(buf)
                                                  // ensures len_of(buf) == len_of(deref(entry(buf))) + 1
```

Trace:

- Rule 9 states the example as accepted: "`put_at(&buf[len_of(buf)], 3)`  // the
  argument fixes the slot at the call; the row itself names no index", and its point —
  that the row stays index-free while the call fixes the slot — is unaffected by which
  slot is chosen.
- Rule 6 forbids forming that particular reference: "Reading `buf[k]` or forming
  `&buf[k]` requires the fact `k < len_of(buf)` (Rule 7)", and Rule 7 repeats it,
  "`buf: DynBox<Int>;  buf[i]   // requires i < len_of(buf)`". The index in the example
  is `len_of(buf)`, for which `k < len_of(buf)` is false by construction. It also uses
  an index expression at the call, which Rule 9 permits ("evaluated once at the call")
  even though a row may not contain one, so the conflict is with Rule 6/7's bounds
  fact, not with Rule 9's own form restriction.
- Rule 12 and Rule 6 also say what the slot at index `L` is: "Slots `[len_of, cap_of)`
  hold nothing", "no program point can observe a slot inside the window as empty", and
  "No place is ever partially moved: every path is either wholly present or the program
  cannot name it". A reference naming a slot that holds nothing is a name for a hole,
  and "Not in this candidate" excludes "`take`/`put` holes" explicitly. If the example
  is accepted, then a hole is nameable, `writes(slot)` is the operation that fills it,
  and nothing in `put_at`'s row or contract advances `len_of`, so after the call the
  block contains a written slot outside the window: invisible to every read, not
  released at scope exit (Rule 6 releases "slots `[0, len_of)`"), and leaked if `Int`
  were replaced by an affine or linear type. If the example is rejected, then Rule 9's
  illustration of its own central clause is not a program, and the only append is
  `push_nogrow`.
- The text supports both and ranks neither. A third reading — that `&buf[len_of(buf)]`
  is admissible only for a callee whose contract advances the boundary — cannot be
  taken from the file either, because Rule 9 gives `put_at` the row `writes(slot)`
  where `slot` is an `&Int`, and a path rooted at that parameter cannot mention
  `len_of` of a block the parameter does not name. The protocol forbids me from
  choosing among the three.

Rewrite and cost: under the rejecting reading the append is `push_nogrow(&buf, 3)`,
which performs one bounds-free store and one header increment — identical object code
to what the `put_at` form would have produced plus the increment that form omits, and
identical to C++'s `v.push_back` on a vector with spare capacity. A caller that wants a
helper to produce the value in place writes
`fn make_and_push(buf: &DynBox<Int>, seed: Int) writes(buf)` and calls `push_nogrow`
inside it; the row is coarser, which costs the parallelism discussed in 9-13 but no
instructions. So whichever reading is chosen, the appending task itself is free; what
the gap decides is whether a reference may ever name storage outside the window, and
therefore whether a hole exists in this candidate at all.

Rules consistent: no — Rule 9's example forms a reference that Rules 6 and 7 require a
falsifiable bounds fact for, and that Rule 12 and the exclusion list describe as a
hole.
Task achievable: yes — appending through `push_nogrow` needs neither the example nor
the reading, at no cost.
Depends on: Rule 6 (window, bounds fact, push_nogrow), Rule 7 (index proofs), Rule 12
(no holes), Rule 10 (the call-site substitution the example illustrates).
Verdict: undecided-rule-gap

### 9-13: Effect rows against parallel blocks — the row is what the parallel check reads

Question: Rule 13 judges arms by their paths, and a path can only be as precise as the
callee's row allows; which parallel programs does that admit, and which ones become
inexpressible?

Strongest program (a scatter whose destination index comes from data — the case where
static analysis provably cannot help, and the one C++ parallelizes on the programmer's
word):

```text
fn emit(out: &DynBox<Int>, d: u64, x: Int)   writes(out[d])
    contract { requires d < len_of(out); }

for i in 0..n {                          // intended as a per-element parallel map
    d = perm[i]                          // a runtime permutation: injectivity is data, not a fact
    if d < len_of(out) { emit(&out, d, src[i]) }
}                                        // rejected as a parallel form: out[d_i] against out[d_j]
```

Ordinary program (the adjacent-range family, P6, and the struct-of-arrays family, P5):

```text
par { kernel(&v[0..mid], &out[0..mid]);  kernel(&v[mid..n], &out[mid..n]) }   // accepted
fn kernel(src: &DynBox<Int>, dst: &DynBox<Int>)   reads(src), writes(dst)

par { pass_a(&cols.a, &cols.c);  pass_b(&cols.b, &cols.e) }                   // accepted
fn pass_a(x: &DynBox<u64>, y: &DynBox<u64>)   writes(x), reads(y)
```

Trace:

- Rule 13 states the test and its source: "`par { A; B }` is accepted when A's write
  paths are disjoint from B's read and write paths and vice versa, using the same
  path-overlap and index/range-disjointness judgment as Rule 10. Read/read overlap is
  allowed." The paths it sees are the substituted rows, so Rule 9's precision is
  directly the parallelism budget: a callee that declares `writes(out)` makes every
  pair of calls conflict, and a callee that declares `writes(out[d])` makes the
  question `d_i != d_j`.
- The ordinary programs pass on the two grounds Rule 10 offers. The range kernels are
  "ranges proved distinct" by affine comparison over `0 <= mid <= n`, and Rule 13
  states the case itself: "`par { kernel(&v[0..mid], &out[0..mid]); kernel(&v[mid..n],
  &out[mid..n]) }` // disjoint ranges: accepted". The struct-of-arrays pair is
  "different roots" once Rule 9's member paths are used — "`fn update(o: &Obj, c: Bool)
  writes(o.a), writes(o.b)` // member paths are allowed" — which is what P5 requires of
  a candidate. Rule 14 keeps allocation out of the comparison, so a kernel that
  allocates a scratch block does not lose its overlap: "Allocation and release are not
  effects (Rule 14)".
- The scatter fails and no repair inside the rules reaches it. The distinctness Rule 10
  wants is `perm[i] != perm[j]` for every pair of iterations, which is a statement over
  all elements of `perm`; Rule 11 excludes exactly that: "There are no quantified facts
  over array elements ('for all i ...') and no per-slot occupancy facts". Passing the
  index in as an argument, which is what makes `emit`'s row precise, does not help,
  because the argument's value is a load from `perm`. Widening the row to
  `writes(out)` removes the question and rejects the pair outright. Rule 12's
  occupancy-as-data answer does not apply either: the problem is not occupancy but
  the identity of two runtime indices.
- Note what is *not* lost: the same-index map `for i in 0..n { out[i] = f(src[i]) }` is
  an admitted per-element family under Rule 13's "existing counted-loop forms
  (per-element maps, adjacent ranges passed to a helper, admitted reductions)", and a
  gather (`out[i] = src[perm[i]]`) is read/read on `src` and same-index on `out`, so
  it parallelizes. Only the scatter, where the *written* index is data, is excluded.

Rewrite and cost: the two rewrites are a partition pass and a sequential fallback. The
partition pass sorts or buckets the pairs `(perm[i], src[i])` by destination block so
each worker writes a range it owns, then each worker's writes are range-disjoint and
Rule 13 accepts them; that adds one full pass over `n` elements, an allocation of an
`n`-element scratch block, and `n` extra stores plus `n` loads, for a kernel whose
original body was one load and one store per element — roughly a threefold increase in
memory traffic before any parallel speedup is counted. The sequential fallback keeps
the single pass and loses the parallelism entirely. The C++ baseline is
`#pragma omp parallel for` over the scatter with the programmer asserting injectivity,
which runs the original single pass in parallel with no extra traffic; safe Rust is in
the same position as x1 and reaches for `unsafe` or the same partition. So the cost
against the C++ form is either the whole parallel speedup or a tripling of memory
traffic plus one `n`-element allocation, whichever the writer prefers.

Rules consistent: yes — Rule 13 reads Rule 9's rows through Rule 10's judgment, and
Rule 11's absence of quantified facts is a deliberate, stated limitation.
Task achievable: no for the parallel data-indexed scatter as written; rewrite only by
changing the algorithm's memory behavior.
Depends on: Rule 10 (overlap and distinctness judgment), Rule 11 (no quantified facts),
Rule 7 (range references and bounds), Rule 14 (allocation is not an effect), Rule 12.
Verdict: rejected-real-cost

### 9-14: Effect rows against the heap — release is not an effect, but a replacement is

Question: Rule 9 says `writes` covers freeing the storage at a path while Rule 14 says
release carries no effect entry; which one governs, and can a growing container be
grown in parallel with work on another container?

Strongest program (two arms that both reallocate, one of which replaces a block that
the other arm's container does not share, with the failure arms visible):

```text
fn push<T>(v: &Vector<T>, x: own T) -> Result<Unit, Oom>   writes(v.buf)
    contract { ensures when Ok:  len_of(v.buf) == len_of(deref(entry(v.buf))) + 1;
               ensures when Err: len_of(v.buf) == len_of(deref(entry(v.buf))); }

par {
    push(&v1, a)?                        // may allocate a larger block and release the old one
    push(&v2, b)?                        // likewise
}                                        // accepted: writes(v1.buf) against writes(v2.buf)
```

Second strongest (the question the two sentences seem to disagree about):

```text
par { drop_block(&h.a);  read_block(&h.a) }      // does release make these disjoint?
fn drop_block(p: &DynBox<Int>)   writes(p)
fn read_block(p: &DynBox<Int>)   reads(p)
```

Trace:

- Rule 14 says of the allocator: "There is one heap, provided by the trusted base,
  internally synchronized. Allocation and release carry no effect entry and never make
  two parallel arms conflict ... Addresses are not observable, so allocator concurrency
  does not affect program determinism." Rule 9 says of a row: "`writes` covers writing,
  replacing, moving out of, and freeing the storage at the path."
- They govern different objects, and the candidate's other rules leave no overlap
  between them. A release can occur in exactly three places. At the scope exit of an
  owning local (Rule 8: "at scope exit the compiler releases their memory recursively
  (Box, DynBox) and runs no user code") — a local is not a path from a reference
  parameter, so Rule 9 has nothing to say about it and Rule 14's exemption is what
  applies. Inside a window operation (Rule 6's `truncate`, or `Vector`'s `push`
  replacing the old block) — there the released storage is reached through a reference
  parameter and the row says `writes(v.buf)`, so Rule 9 applies to the *path* while
  Rule 14 exempts the allocator's own bookkeeping. And inside an assignment that
  replaces an affine place (Rule 6: "Assigning `buf[k] = x` where the old value is
  affine releases the old value") — again a write of a named path. The second program
  is therefore decided by Rule 9, not by Rule 14: `writes(h.a)` against `reads(h.a)`,
  one root, rejected, exactly as Rule 13's own line "`par { push(&v, 1); stats(&v) }`
  // rejected: writes(v) overlaps reads(v)". Rule 14's "never make two parallel arms
  conflict" is about two arms that each allocate, which is the first program and which
  the rule file states outright: "`par { a = build(&x)?; b = build(&y)? }` // both
  allocate: accepted".
- The first program also needs the failure arm to leave the row's promise intact. Rule
  14 gives the shape ("Allocation returns a `Result` and never traps") and Rule 11
  gives the routing ("`ensures when Variant:` for result-routed relations"), so a
  caller keeps a usable length fact on both arms, and Rule 12's join intersection then
  leaves the weaker of the two relations after the `?`. Nothing about the failure arm
  is an effect, so it does not change the parallel judgment.
- One consequence worth stating: because release has no entry, an arm may free
  arbitrarily much memory without appearing in any row, and Rule 13 will still accept
  it. That is sound here only because Rule 4 prevents a reference from escaping the
  function that formed it ("It cannot be assigned into any aggregate (Rule 1), cannot
  be returned, and cannot be captured by a function value that is stored or returned"),
  so no arm can hold a name for storage another arm releases. If references could
  escape, Rule 14's exemption would be a use-after-free.

Rewrite and cost: none needed. Two containers grown in parallel perform the same
allocations, moves and header updates as two C++ `std::vector::push_back` calls on
distinct vectors in two threads; both rely on a thread-safe allocator, and Rule 14's
"internally synchronized" heap is the same assumption C++'s `malloc` makes. The rule
file does not promise per-thread allocator caching, so a contended global lock would be
a real cost, but nothing in the candidate requires one and the C++ baseline has the
same freedom. The rejected second program is a genuine conflict in any language.

Rules consistent: yes — Rule 14 exempts the allocator's internal state, Rule 9 governs
the named path, and Rules 4 and 8 keep the two from meeting.
Task achievable: yes — independent growth, independent release and per-arm failure arms
all parallelize at C++ cost.
Depends on: Rule 13 (parallel judgment), Rule 8 (scope-exit release), Rule 6 (Vector
growth, truncate), Rule 11 (result-routed ensures), Rule 4 (references do not escape).
Verdict: accepted-fine

### 9-15: Effect rows against owned returns — an index is the return value that a row can consume

Question: Rule 15 forbids returning a reference, so a locate-then-modify sequence must
cross the boundary as owned data; does the effect row grammar accept that data, and
does the sequence cost a second lookup?

Strongest program (the get-or-insert path of an open-addressing table, the case where a
C++ or Rust implementation reaches for an `Entry` handle to avoid probing twice):

```text
fn probe(t: &Table, key: u64) -> u64             reads(t.tags), reads(t.slots)
    contract { ensures result < len_of(t.tags); }        // the slot the key occupies or belongs in

fn occupy(t: &Table, k: u64, key: u64, v: own Val)   writes(t.tags[k]), writes(t.slots[k])
    contract { requires k < len_of(t.tags); requires k < len_of(t.slots); }

fn revise(t: &Table, k: u64, d: Int)                 writes(t.slots[k])
    contract { requires k < len_of(t.slots); }

if len_of(t.slots) * 4 < cap_of(t.slots) * 3 {       // no growth can intervene
    k = probe(&t, key)                                // one probe, result is owned data
    if t.tags[k] == EMPTY { occupy(&t, k, key, move v) } else { revise(&t, k, 1) }
}
```

Ordinary program (Rule 15's in-out advice for a large value that does not change
hands):

```text
fn recompute(e: &Entry)   writes(e)               // not: fn recompute(e: own Entry) -> own Entry
```

Trace:

- Rule 15 fixes both halves: "A function returns owned values only. Positions found by
  a search are returned as indices with a bounds relation in `ensures` (Rule 4)", and
  "Passing a large value in and back out is expressed as a reference parameter with a
  `writes` entry, not as move-and-return." Rule 4 gives the same shape with its
  example, "`fn find(v: &DynBox<Entry>, key: Int) -> Option<u64>` ... returns an index,
  never `&Entry`".
- The returned index is exactly the form Rule 9 can consume: "an index enters an effect
  only through an argument, evaluated once at the call", so `occupy`'s row
  `writes(t.tags[k]), writes(t.slots[k])` names the probe's own answer. The two entries
  are compared pairwise by Rule 10 clause 1 and are trivially disjoint (different
  roots, `t.tags` against `t.slots`), which is Rule 9's "member paths are allowed"
  doing the work.
- The bounds proof crosses the boundary as a fact, not as a check: `probe`'s
  `ensures result < len_of(t.tags)` discharges `occupy`'s `requires`, an affine
  comparison over measures in Rule 11's vocabulary, so no compare reaches the object
  code.
- The one thing the caller must guarantee itself is that nothing between the probe and
  the use invalidates the index's meaning. Rule 11 states the invalidation — "A fact
  that mentions a path is invalidated when that path is written (by statement or call)
  unless the callee's `ensures` re-establishes it" — and a growth would write
  `t.slots` wholly; the load-factor test before the probe is a refinement fact from a
  dominating branch that keeps growth out of the region. This is a proof obligation,
  not an instruction.
- The in-out advice of the ordinary program only reaches values whose ownership does
  not change; where it does, Rule 8 and Rule 15 route it through owned parameters and
  returns instead (8-15).

Rewrite and cost: none needed, and the index form is strictly cheaper than the naive
alternative it replaces. A C++ `find`-then-`insert` pair probes twice; Rust's `entry`
probes once but holds a borrow of the map, which Rule 4 forbids. The x1 form probes
once and hands the position across as a `u64`, so the hash and the probe sequence are
paid exactly once, and the only difference from a returned `Entry*` is that each of the
two subsequent calls recomputes `base + k * sizeof(Val)` — one multiply-add against a
base pointer already loaded, and the multiply is a shift for a power-of-two element
size. Rule 4 prices this itself: "the caller re-derives, one address computation". The
in-out form of `recompute` moves nothing at all, against a move-and-return form that
would copy `sizeof(Entry)` twice unless the ABI elided it.

Rules consistent: yes — Rule 15's owned returns, Rule 4's index discipline and Rule 9's
index-carrying rows are one mechanism seen from three sides.
Task achievable: yes — locate-then-modify costs one probe and one address computation,
no second lookup and no bounds check.
Depends on: Rule 4 (searches return indices), Rule 10 (pairwise comparison), Rule 11
(ensures discharging requires, refinement facts), Rule 12 (tags as data).
Verdict: accepted-fine

### 9-16: Effect rows against pools and arenas — allocation writes the whole block, filling writes one slot

Question: under the provisional Rule 16 an arena allocation is `push_nogrow` on the
arena's block, so its row names the whole block; what does that do to references held
across an allocation, and can blocks be filled in parallel?

Strongest program (P2: several blocks allocated from one arena, filled in parallel, one
released and its slot reused, while other blocks stay usable):

```text
struct Arena<T> { buf: DynBox<T> }
fn alloc<T>(a: &Arena<T>, x: own T) -> u64   writes(a.buf)
    contract { requires len_of(a.buf) < cap_of(a.buf);
               ensures result == len_of(deref(entry(a.buf)));
               ensures len_of(a.buf) == result + 1; }

fn fill(a: &Arena<Block>, id: u64, seed: u64)   writes(a.buf[id])
    contract { requires id < len_of(a.buf); }

i1 = alloc(&a, empty_block())                // ensures i1 == L,     len_of == L + 1
i2 = alloc(&a, empty_block())                // ensures i2 == L + 1, len_of == L + 2
i3 = alloc(&a, empty_block())                // ensures i3 == L + 2, len_of == L + 3

par { fill(&a, i1, s1);  fill(&a, i2, s2) }  // accepted: i1 != i2 by affine comparison
par { fill(&a, i1, s1);  alloc(&a, b)? }     // rejected: writes(a.buf[i1]) against writes(a.buf)
```

Second strongest (P3: a graph in the pool, with links written through several paths and
references held across an allocation):

```text
p = &a.buf[i1]                               // valid while i1 < len_of(a.buf)
i4 = alloc(&a, node)                         // writes(a.buf): a.buf is a proper prefix of a.buf[i1]
use(p)                                       // rejected (Rule 3, Rule 10 clause 3)
q = &a.buf[i1];  use(q)                      // re-formed from the index that survived

a.buf[i1].next = i4                          // link writes go through paths, not stored references
a.buf[i4].prev = i1
par { touch(&a.buf[i1]); touch(&a.buf[i4]) } // accepted: i1 != i4 from the alloc contracts
```

Trace:

- Rule 16 defines the arena as "a DynBox used with `push_nogrow` as allocation and
  `truncate(0)` as reset" and gives `alloc` the row `writes(a.buf)` with the two
  `ensures` above. Those postconditions are the whole reason the parallel fill works:
  `i1 == L` and `i2 == L + 1` are affine comparisons over measures, so `i1 != i2` is
  available to Rule 10's "indices or ranges proved distinct", which Rule 13 reuses
  verbatim. Without the `ensures result == len_of(deref(entry(a.buf)))` clause, two
  handles from one arena would be indistinguishable and no two blocks could be filled
  in parallel.
- The rejected pair is a true conflict under the rules as written but not under P2's
  own requirement ("nobody holds A exclusively between operations"). `alloc` writes the
  block header and possibly slot `L`, and `fill` writes slot `i1`, and Rule 9 cannot
  express "writes only the slot at the boundary" because the boundary is `len_of`, an
  index *expression*, which "Signatures never contain". So allocation serializes
  against every fill in the same arena.
- References into the pool do not survive an allocation. Rule 3: validity "is
  invalidated when any proper prefix of p's path is written, moved out of, replaced, or
  freed, by a statement or by a call", and `a.buf` is a proper prefix of `a.buf[i1]`;
  Rule 10 clause 3 restates it for calls. Rule 16 confirms the intended use — "`p =
  &a.buf[id]` // valid until a.buf is replaced; readable while `id < len_of(a.buf)`" —
  so the handle is the index and the reference is re-formed after each allocation. The
  index's own fact, `i1 < len_of(a.buf)`, is not invalidated by the allocation, because
  `alloc`'s `ensures len_of(a.buf) == result + 1` re-establishes a length that only
  grows; Rule 11's "unless the callee's `ensures` re-establishes it" is doing that work.
- Link writes are statements on paths (`a.buf[i1].next = i4`), each needing its bounds
  fact from the alloc contracts, and the graph's edges are indices, which Rule 1
  requires anyway ("no aggregate ever contains a reference"). Rule 16's stale-handle
  position applies to removal: "A stale index that is still in bounds names the current
  occupant of that slot: a logic error, not a memory error. Programs that need to
  detect it keep a generation number as data" — which is the mutable-compiler-graph
  task's requirement that "a relation to a deleted node must not silently become a
  relation to a replacement node", met only if the program pays for the generation.

Rewrite and cost: the allocation/fill conflict is removed by batching — allocate the
blocks the round needs, then fill them in parallel — which costs the serialization of
`k` bump increments (one header load, one compare against `cap_of`, one store each)
