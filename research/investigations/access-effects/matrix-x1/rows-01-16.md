# Candidate x1 interaction matrix, row 1 and cell 16-16

Derived 2026-09-18 against the frozen rule set in `CANDIDATE-X1.md`. Every cell
follows that file's "Protocol for a derivation cell": strongest program first,
rule-by-rule trace with quoted clauses, best rewrite with its runtime cost
against C++ or Rust, rule consistency separated from task achievability, and a
verdict from the fixed vocabulary. Runtime performance is the only cost counted;
extra parameters, extra source and duplicated code are not costs.

Row 1 has one through-line worth stating before the cells. Rule 1 removes
pointer aliasing from the type system, which buys exact effect rows (1-9),
guard-free disjointness (1-9, 1-13) and memmove relocation (1-6) at no runtime
cost. The price is paid in one place only: whenever a program needs a *durable
name* for an object, that name must be owned data, and reifying a pointer as
data costs nothing when the root is statically known (one address computation,
1-3, 1-5, 1-10, 1-15) and costs either an extra branch or an extra dependent
load when the root is not (1-2, 1-4, 1-16). Two cells cannot be decided from the
rule text at all (1-8, 1-12); both concern getting a linear value back out of an
aggregate.

### 1-1: Rule 1 with itself: closure under nesting, recursion and instantiation

Question: does Rule 1's ban on contained references stay consistent and decidable
when aggregates nest arbitrarily deep, recurse through indirection and are
generically instantiated?

Strongest program:

```text
struct Wrap<T>  { x: T }
struct Slot<T>  { w: Wrap<Option<T>> }
struct Cell<T>  { s: Slot<Wrap<T>> }

type Sneak = Cell<Wrap<Slot<&Entry>>>          // a reference five wrappers down

struct Node { value: Int, kids: DynBox<Node> } // recursive through an owned block
struct Tree { root: Option<Box<Node>> }        // recursive through Box

struct Intrusive { next: &Intrusive, data: u64 }   // the C shape we actually want
```

Trace:

- Rule 1, clause 2: "This is recursive and closed under wrapping: there is no
  type parameter, wrapper, or variant payload through which a reference can be
  stored." `Sneak` is rejected at instantiation; the five intervening wrappers
  change nothing, exactly as Rule 1's own line `Option<&T> // rejected, whatever
  T is` shows for one wrapper.
- Rule 1, clause 1: "Every struct, enum, tuple, array, slice-like value, Box,
  DynBox, and generic instantiation holds only owned values." `Node` and `Tree`
  are accepted: `DynBox<Node>` and `Box<Node>` are owned values, and recursion
  through them is recursion through *ownership*, not through a reference.
- Self-interaction, idempotence: the predicate "contains no reference" is
  defined by structural recursion, so applying it to a type all of whose parts
  already satisfy it yields the same answer. Nesting adds no new obligation and
  no new rejection; there is no depth at which the rule changes its mind, and
  no instantiation order that smuggles a reference past it.
- Self-interaction, the consequence: "any value can be relocated by copying its
  bytes (memmove, realloc), because nothing inside it points anywhere." This is
  inductive in the same recursion: if every part is byte-relocatable, so is the
  whole, at every depth. The property therefore survives arbitrary wrapping,
  which is what 1-6 depends on.
- `Intrusive` is rejected by clause 1. This is Rule 1's single-rule content, not
  a self-interaction; its price is derived in 1-5 (what replaces the link) and
  1-16 (what the replacement costs).

Rewrite and cost: `struct Intrusive { next: u32, data: u64 }` in a pool
(Rule 16). Within Rule 1 alone this is a type change with no per-operation cost;
the per-hop accounting is in 1-5 and 1-7.

Rules consistent: yes — the closure is structurally recursive and idempotent, so
Rule 1 composed with itself is Rule 1.
Task achievable: rewrite — self-referential and intrusive shapes need a pool
index, priced in 1-5 and 1-16.
Depends on: Rule 1; Rule 5 and Rule 6 for the accepted recursive forms; Rule 16
for the rewrite.
Verdict: accepted-fine

### 1-2: Rule 1 and Rule 2: reifying a path as data

Question: when a reference is only a local name for a path and no aggregate may
hold one, how does a program carry a *set* of write targets, and what does
re-forming each path cost?

Strongest program: an ordered fixup worklist whose targets sit in different
containers and whose processing order is fixed by the algorithm (a linker
relocation pass, a compiler's pending-patch list).

```text
work: DynBox<&Entry>                 // the C++ shape: vector<Entry*>
q = &work[0]
r = &q                               // the other shape: a reference to a reference
```

Ordinary program:

```text
struct Item { which: u8, idx: u64 }  // owned: legal in any aggregate
work: DynBox<Item>

n = len_of(work)
for t in 0..n {
    invariant ht: t < n;
    it = work[t]                                  // Copy
    if it.which == 0 { fixup(&v1[it.idx]) }
    else             { fixup(&v2[it.idx]) }
}
```

Trace:

- Rule 1, clause 1: "Every struct, enum, tuple, array, slice-like value, Box,
  DynBox, and generic instantiation holds only owned values" rejects
  `DynBox<&Entry>`.
- Rule 2: "A reference variable names a path; it is not storage of its own", and
  its line `&p // rejected: a reference variable is not storage` rejects `&q`.
  So there is no indirect route to a stored reference either.
- Rule 2, join clause: `w = if cond { &v1 } else { &v2 } // w names one of
  {v1, v2}` and "At a control-flow join, a reference variable's target is the
  set of paths it may name; every check on it must hold for every member of the
  set." The multi-root form therefore exists *inside* a function; what Rule 1
  forbids is carrying it across a loop iteration in storage. The `if` in the
  ordinary program is the writer re-creating that same target set explicitly.
- Rule 7: `work[t]` requires `t < len_of(work)`, supplied by the loop bound;
  `v1[it.idx]` requires `it.idx < len_of(v1)`, which is data and must be tested
  or carried by `fixup`'s `requires` from the producer of the worklist.
- Rule 10: each `fixup` call takes one reference, so clause 1's pairwise
  comparison has nothing to compare.

Rewrite and cost: tag plus index per item, dispatched at the use site.

- Single root (the common case): the item is just `u64`, and re-forming
  `&v1[idx]` is one `lea` from a base that is loop-invariant and already in a
  register. Zero extra memory traffic against `vector<Entry*>`, and a `u32`
  index halves the worklist's footprint, which is a win on a large list.
- Several roots with a fixed order (the strongest case): one tag load (same
  cache line as the index) plus one compare plus one branch per item, and the
  branch is badly predicted precisely when the roots interleave, which is when
  a worklist exists at all. Against C++ this replaces "load pointer, store
  through it" with "load pair, dispatch, store through it": +1 compare, +1
  mispredictable branch per item.
- Alternative rewrite with zero cost, when the algorithm tolerates reordering:
  bucket the worklist per root and run one loop per bucket. No tag, no branch,
  better locality than the C++ pointer list. This is available for scatter-like
  fixups and unavailable for order-dependent ones.
- Alternative rewrite by unifying the roots into `DynBox<DynBox<Entry>>` so the
  root also becomes an index: replaces the branch with one extra dependent load
  of the inner block pointer, plus a second bound test. Worse than the tag on
  L1-resident data, better when the dispatch is unpredictable.

Rules consistent: yes — Rule 2 supplies the multi-root *target set* locally and
Rule 1 denies it storage; the two do not contradict, they force the set to be
rebuilt at the use site.
Task achievable: rewrite — the worklist exists, with a branch or an extra load
per item in the multi-root case.
Depends on: Rules 1, 2, 7, 10, 11.
Verdict: rejected-real-cost

### 1-3: Rule 1 and Rule 3: what makes invalidation a local question

Question: with references absent from every aggregate, is Rule 3's invalidation
a purely local flow question, and what does it invalidate that C++ keeps?

Strongest program: references held across operations that write a proper prefix
but relocate nothing.

```text
b = Box::new(Node { value: 1, left: None })?
p = &(*b).left
c = move b                     // Rule 3: b is a proper prefix of *b
use(p)                         // rejected, although the heap Node did not move

v: DynBox<Entry>
p = &v[i]
v[j] = e                       // content write on a sibling, or on i itself
use(p)                         // accepted
push_nogrow(&v, e2)            // writes(v): v is a proper prefix of v[i]
use(p)                         // rejected, although push_nogrow provably cannot reallocate
```

Trace:

- Rule 3: "It is established when p is formed and invalidated when any proper
  prefix of p's path is written, moved out of, replaced, or freed, by a
  statement or by a call." `move b` and `push_nogrow(&v, ...)` both write a
  proper prefix; both kill `p`.
- Rule 3: "Writing the storage at p's path or below it (a content write) does
  not invalidate p." So `v[j] = e` leaves `p` valid for every `j`, including
  `j == i`. C++ agrees; safe Rust does not (it refuses the second access
  entirely), so this cell is one place where the candidate is strictly more
  permissive than Rust at equal safety.
- Rule 3: "A move never re-roots an existing reference: after `w = move v`,
  references formed from `v` are invalid and are not reinterpreted as
  references into `w`." So even the byte-identical case must be re-formed.
- Rule 9: `push_nogrow(buf: &DynBox<T>, x: own T) writes(buf)` names the whole
  buffer. Its contract `requires len_of(buf) < cap_of(buf)` guarantees no
  reallocation, and its `ensures` speaks only of `len_of`, but the effect row
  has no finer path than `buf`, so the prefix test fires. Rule 9's paths
  "continue through fields, `*`, and whole-index or range positions supplied as
  arguments" — there is no path naming the block header alone.
- The Rule 1 contribution, which is the point of the cell: because no aggregate
  holds a reference (Rule 1) and no reference escapes (Rule 4), the set of live
  references at any program point is exactly the set of live reference
  *variables* of the current function. Invalidation is therefore decided by
  walking local bindings against the statement's write paths — no heap alias
  analysis, no whole-program information, and nothing changes when the
  invalidating call is separately compiled, because its row is its interface.

Rewrite and cost: re-form the reference after the invalidating statement.

```text
c = move b;          p = &(*c).left      // same address
push_nogrow(&v, e2); p = &v[i]           // reload the block pointer, one lea
```

- The `move` case costs zero: the move is a register copy and the re-formed path
  computes the same address from the same register.
- The `push_nogrow` case costs one load of the block pointer plus one `lea` per
  re-formation, and the block pointer is already hot because the push just used
  it. In a loop that pushes every iteration this is one extra ALU op per
  iteration; in a loop that does not push it hoists out entirely.
- No extra branch, no copy, no allocation. Against C++ holding `Entry*` across a
  `push_back` into reserved capacity: zero measurable difference.

Rules consistent: yes.
Task achievable: rewrite, at zero runtime cost.
Depends on: Rules 1, 3, 4, 9.
Verdict: rejected-zero-cost

### 1-4: Rule 1 and Rule 4: no returned reference, no stored cursor

Question: when a search may not return the reference it found and no struct may
hold one, what does the caller pay to reach the found object, and can a cursor
exist at all?

Strongest program: a cursor into a Box-linked search tree, carried across
unrelated work (P4).

```text
struct Cursor { at: &Node }                  // rejected
fn find(root: &Node, k: Int) -> &Node        // rejected
fn finder(root: &Node) -> fn() -> &Node      // rejected
```

Ordinary program: the two forms that remain.

```text
// (a) fuse the search and the use into one function
fn find_update(root: &Node, k: Int, f: fn(own u64) -> own u64)  writes(root)
{
    n = &root                                 // one descent
    loop { if k == n.key { n.data = f(n.data); return }
           n = if k < n.key { &(*n.left) } else { &(*n.right) } }
}

// (b) return replayable owned data and re-walk
fn find_path(root: &Node, k: Int) -> own Path   reads(root)
    contract { ensures result.depth <= 64; }
pth = find_path(&root, k)                     // descent 1
n = &root
for s in 0..pth.depth { invariant hs: s < pth.depth;
    n = if bit(pth.turns, s) == 0 { &(*n.left) } else { &(*n.right) } }   // descent 2
```

Trace:

- Rule 4: "It cannot be assigned into any aggregate (Rule 1), cannot be
  returned, and cannot be captured by a function value that is stored or
  returned." All three wanted forms die on that one sentence.
- Rule 4: "A function that 'finds' something returns an index or other owned
  data; the caller forms the reference", and Rule 15: "Positions found by a
  search are returned as indices with a bounds relation in `ensures`."
- Rule 1: the `Cursor` struct is additionally rejected by "no aggregate ever
  contains a reference", so no amount of function-level cleverness recovers it.
- Rule 10: "Function-typed parameters carry a full signature with its own row
  and contract, and a call through one uses that row." This is what makes form
  (a) checkable modularly: `f`'s row is part of `find_update`'s interface and
  the body is checked once against it, no unfolding.
- Rule 2: form (b)'s re-walk is an ordinary path; each `*` is a Box
  dereference, i.e. a dependent load.

Rewrite and cost:

1. Form (a), fused: zero cost when `f` is specialized or inlined — the same
   machine code C++ writes with a lambda. One indirect call per hit when it is
   not specialized. This is the right form whenever the found position is used
   once, immediately.
2. Form (b), re-walk: a *second* full descent — `d` dependent, frequently
   cache-missing loads for a tree of depth `d`. Against C++'s `Node* find(...)`
   followed by a write through the returned pointer, this doubles the cost of
   the lookup, and the lookup's cost is exactly its dependent-load chain. This
   is a real, large cost, and it is the price of the *strongest* case: a
   position that must survive work unrelated to the container.
3. Form (c), pool (Rule 16): the node is named by a `u64` handle, which is owned
   Copy data, so it may be returned (Rule 15), stored in a `Cursor` struct
   (Rule 1 permits it, it is not a reference) and kept across arbitrary work.
   Re-forming `&pool.buf[h]` is one `lea` plus the Rule 7 bound test. This is
   the only form in which P4's stored cursor exists at all, and it costs one
   compare and one predicted branch per use against C++'s stored `Node*`.

So: a durable position into a Box-linked structure is not expressible and its
replacement costs a second descent; a durable position into a pool-backed
structure is expressible at about one compare per use. The candidate therefore
pushes every structure that needs cursors, back edges or external indexes onto
Rule 16, which is provisional.

Rules consistent: yes — Rule 4's own escape clause names Rule 1 as its reason,
and the two agree on every form tried here.
Task achievable: rewrite — fused for one-shot use, pool for a durable cursor;
the literal "hold a pointer into a heap tree across unrelated work" is not
achievable without Rule 16.
Depends on: Rules 1, 2, 4, 7, 10, 15; Rule 16 for the only durable-cursor form.
Verdict: rejected-real-cost

### 1-5: Rule 1 and Rule 5: one owner per heap object, so no cycles and no sharing

Question: with Box the only pointer and each Box owning exactly one object, can
a structure with back edges or sharing exist, and what does the substitute cost
per hop?

Strongest program: P3's doubly linked node list with removal and reuse.

```text
struct Node { next: Option<Box<Node>>, prev: ???, data: u64 }
// prev: &Node        rejected by Rule 1
// prev: Box<Node>    a second owner of the same object: not producible
```

Ordinary program:

```text
struct Node { next: u32, prev: u32, data: u64 }      // NIL = 0xFFFF_FFFF
g: DynBox<Node>

// insert m between a and b: four ordinary statements, not one call (see 1-10)
g[a].next = m;  g[m].prev = a;  g[m].next = b;  g[b].prev = m;
```

Trace:

- Rule 1: "no aggregate ever contains a reference" rejects `prev: &Node`.
- Rule 5: "`Box<T>` owns exactly one heap object of fixed size", and Rule 8:
  affine values are "consumed at most once". Two Box fields naming one object
  cannot be produced — `Box::new` allocates a fresh object, and there is no
  operation that duplicates a Box. A cycle through owning edges would require a
  value to be reachable from itself, and Rule 8's scope-exit clause "the
  compiler releases their memory recursively" has no terminating meaning on
  such a shape. So the cyclic form is not rejected by a clause; it cannot be
  written down.
- Rule 5's positive half is worth stating: "Boxes carry no store or region brand
  and can be moved, stored in aggregates, and returned freely", so single-owner
  trees and forward-only lists — Rule 1's own `struct Node { value: Int, left:
  Option<Box<Node>> }` — are the full expressive range of Box for linked data,
  with no annotation, no region parameter and no lifetime.

Rewrite and cost: index links inside one `DynBox<Node>` (Rule 16).

- Per hop, C++: load an 8-byte pointer field, dereference it — one dependent
  load.
- Per hop, WF: load a 4-byte index field, compute `base + idx*sizeof(Node)` with
  `base` loop-invariant and in a register, dereference — one dependent load plus
  one `lea`, plus the Rule 7 bound test priced separately in 1-7.
- Node footprint falls by 8 bytes for a doubly linked node (two `u32` instead of
  two 8-byte pointers), which raises cache density on exactly the traversals
  that dominate; on a list that misses L2 this is a net win.
- Allocation changes character: nodes come from the pool rather than from the
  heap, so the per-node `Box::new` and its `Result` branch disappear and freeing
  a node is a free-list push. That is faster than C++'s per-node `new`/`delete`
  and equal to a C++ pool allocator.

Net sequential cost against a C++ pointer list: one `lea` per hop, offset by a
smaller node. Zero to favourable. The real costs of this rewrite live elsewhere:
the bound test (1-7), object identity after reuse (1-16, 16-16) and parallel
allocation (1-16).

Rules consistent: yes.
Task achievable: rewrite, at zero runtime cost for the traversal itself.
Depends on: Rules 1, 5, 8; Rule 16 for the pool.
Verdict: rejected-zero-cost

### 1-6: Rule 1 and Rule 6: growth is a memmove, and the layout it costs

Question: does value-only containment turn DynBox growth into a pure byte move,
and what data layout does it make inexpressible?

Strongest program: growing a vector whose element is a large aggregate holding
owning pointers.

```text
struct Entry { name: DynBox<u8>, body: Box<Node>, n: u64 }    // affine, no references inside
v: DynBox<Entry>                                              // len_of == cap_of

// Vector::push, library code per Rule 6
nb = DynBox::new<Entry>(2 * cap_of(v))?
move_range(&nb, &v, 0, len_of(v))        // one memmove of len*sizeof(Entry)
v = move nb                              // the old block is released, its slots were moved
```

Trace:

- Rule 1, consequence: "any value can be relocated by copying its bytes
  (memmove, realloc), because nothing inside it points anywhere." This is what
  licenses the single `memmove` over a `DynBox` of non-trivial elements.
- Rule 6: "`Vector<T>` is library code: a DynBox plus a `push` that, when
  `len_of == cap_of`, allocates a larger DynBox, moves `[0, len_of)` across, and
  replaces the old one." The relocation is the specified mechanism, not an
  optimization.
- Rule 6: slots "`[len_of, cap_of)` hold nothing", so growth copies `len`
  elements, never `cap` — the reserved tail costs address space and untouched
  pages only.
- Rule 8: the moved-from block's slots are not released individually; they were
  consumed once by the move, so no per-element teardown runs.

Cost against C++: `std::vector<Entry>` must move-construct every element on
growth, because `Entry` has a non-trivial move constructor (it owns a buffer and
a pointer), then run a destructor on every moved-from source. WF does one
`memmove` and nothing else. This is a win of the same kind Rust's `Vec` has;
WF equals Rust and beats C++ here. It also makes `realloc`-style in-place growth
legal in principle, where C++ must refuse it for non-trivially-relocatable types.

The cost side, same cell: the layout Rule 1 forbids.

```text
struct SSO { ptr: &u8, inline: array<u8,16>, n: u64 }   // rejected: contains a reference,
                                                        // and it would point into itself
enum Str { Small(array<u8,15>, u8), Large(DynBox<u8>) } // the available form
```

Rule 1 rejects the self-pointer form, which is exactly the representation
libstdc++'s `std::string` uses to make `data()` branch-free. The available form
is the tagged one, which is libc++'s shape: reading the data pointer costs one
test plus one predicted branch (or a `cmov`) per access, and in exchange the
type stays memmove-relocatable, which libstdc++'s does not. So against libc++ the
cost is zero; against libstdc++ it is one branch per `data()` and a win on every
vector growth. No general-purpose type in the candidate can place a pointer to
its own bytes, so every small-buffer optimization pays the tagged form.

Rules consistent: yes — Rule 6's relocation clause is only sound because of
Rule 1's consequence clause, and they are stated in agreement.
Task achievable: yes.
Depends on: Rules 1, 6, 8, 14.
Verdict: accepted-fine

### 1-7: Rule 1 and Rule 7: every reified link pays a bound

Question: once a position is an index rather than a reference, who proves the
bound at each hop of a traversal whose links come from data?

Strongest program: traverse a pool-backed list whose `next` field is loaded from
memory, so no static fact about it exists anywhere.

```text
struct Node { next: u32, data: u64 }
g: DynBox<Node>
i = head
while i != NIL {
    d = consume(g[i].data)        // Rule 7: requires i < len_of(g) — nothing establishes it
    i = g[i].next                 // the next value of i is data, not arithmetic
}
```

Ordinary program: the accepted form.

```text
n = len_of(g)                     // one header load, loop-invariant
i = head
while i != NIL {
    if i < n {                    // Rule 7: "the test establishes the fact"
        d = consume(g[i].data)
        i = g[i].next
    } else {
        return Err(Corrupt)       // an arm that cannot be proved unreachable
    }
}
```

Trace:

- Rule 7: "Every index must be proved in bounds; when the proof is unavailable
  the program tests the measure, which is ordinary data", and its line
  `if i < len_of(buf) { use(&buf[i]) } // the test establishes the fact; one
  compare, no trap`.
- Rule 11: "There are no quantified facts over array elements ('for all i ...')
  and no per-slot occupancy facts". The invariant that would discharge every hop
  at once — "every stored `next` is less than `len_of(g)`" — is exactly a
  quantified fact over elements, so it cannot be written, let alone proved or
  carried by a container's interface.
- Rule 11's available forms do not substitute: a loop-header `invariant name:
  affine_expr compare_op affine_expr` cannot re-establish `i < n` at the bottom
  of the body, because the new `i` comes from a load and is not an affine
  function of the loop variables; the dominating-branch refinement is precisely
  the runtime test above.
- Rule 12: "Structures whose occupancy is decided by data keep that occupancy as
  data" is the candidate's general answer to data-determined structure, but a
  *bound on a stored index* has no data form other than the test itself.
- Rule 1 is what created the obligation: a C pointer carries its own validity,
  an index does not, so banning the pointer converts a type-level fact into a
  per-use proof obligation.

Rewrite and cost: the guarded form above.

- One compare against a loop-invariant register plus one perfectly predicted
  branch per hop. `n` is `len_of(g)`, a block-header field, loaded once because
  `g` is not written inside the loop.
- Against C++ pointer chasing: +2 µops per hop. The compare sits on the
  dependent chain but adds no memory access, and the predicted branch lets the
  next load issue speculatively, so on a traversal that misses cache the added
  latency is approximately zero; on an L1-resident traversal it is measurable
  and it inhibits vectorization of index-gather loops.
- Against safe Rust (`g[i]`): identical — Rust emits the same bounds check and
  has the same escape hatch missing without `unsafe`.
- The dead arm is not a runtime cost, but it is a semantic one: the traversal
  cannot be proved total, and the writer must invent a behaviour for a state the
  program's own invariant forbids. A masked form (`i & (cap-1)` with a
  power-of-two capacity) does not help: Rule 11's facts are "affine comparisons
  over measures and integer values", and a bitwise AND is not an affine
  expression, so the mask buys no fact.

Rules consistent: yes.
Task achievable: rewrite, with a small but unavoidable per-hop cost and an
unprovable error arm.
Depends on: Rules 1, 7, 11, 12; Rule 16 for the pool shape.
Verdict: rejected-real-cost

### 1-8: Rule 1 and Rule 8: emptying a container of linear resources

Question: when a linear resource is reachable only by containment, how is a
`DynBox` of them emptied, and does `truncate` release linear values?

Strongest program: a growable container of open files that must be emptied on an
early exit (task row "growable container of resources", P8).

```text
linear type File;  fn close(f: own File)
bufs: DynBox<File>                     // linear by containment
...
if error {
    truncate(&bufs, 0)                 // does this close ten Files? is it even accepted?
    return Err(e)
}
```

Trace:

- Rule 8: "Linear values must be consumed by an explicit operation on every exit
  path; the compiler never releases them."
- Rule 8: "Linearity is declared on external-resource types and propagates
  through aggregates: a struct, array, Box, or DynBox containing a linear part
  is linear." With Rule 1, containment is the *only* way a `File` can be inside
  a container at all, so this propagation is unavoidable for any resource
  collection.
- Rule 6: "At scope exit the compiler releases slots `[0, len_of)` recursively
  and frees the block. A DynBox whose element type is linear is itself linear
  (Rule 8) and must be truncated to zero by the program before it can go out of
  scope."
- Rule 6 specifies `truncate` only as `fn truncate<T>(buf: &DynBox<T>, n: u64)
  writes(buf) contract { requires n <= len_of(buf); ensures len_of(buf) == n; }`
  — nothing about the fate of slots `[n, len_of)`.

Ambiguity, quoted verbatim:

> "A DynBox whose element type is linear is itself linear (Rule 8) and must be
> truncated to zero by the program before it can go out of scope."

Read as naming the `truncate` operation defined four lines above it,
`truncate(&bufs, 0)` releases ten linear `File` values, contradicting Rule 8's
"the compiler never releases them" and mirroring the release behaviour Rule 6
explicitly refuses for the assignment case ("where it is linear the assignment
is rejected unless written as the atomic update whose function consumes the old
value"). Read as loose language for "the program must reduce `len_of` to zero
using its own consuming operations", the status of `truncate(&bufs, 3)` on a
linear element type is stated nowhere: it is neither accepted nor rejected by
any clause.

Decisive case: `bufs` holds ten `File`s and the program calls
`truncate(&bufs, 3)`. Under the first reading seven files are closed by the
compiler; under the second the call is rejected; the text supports neither over
the other. Resolving it is outside a derivation cell.

Available form under either reading, and its cost:

```text
while len_of(bufs) > 0 { close(pop(&bufs)) }     // Rule 11: "no knowledge: the loop
                                                  // condition is the test"
```

`pop` is Rule 6's window operation returning `own T` with `requires len_of(buf) >
0`, discharged by the loop condition; Rule 8's "explicit operation on every exit

holds under either reading. Cost: one `close` per element in a loop — byte for
byte what `~std::vector<File>` and Rust's `Drop` emit. Zero.

Rules consistent: not decidable from the text for this case.
Task achievable: yes — the `pop` loop empties the container at zero runtime cost
regardless of how the ambiguity is resolved.

### 1-9: Rule 1 and Rule 9: the effect row is exact because no value can alias

Question: does banning contained references make a declared effect path an exact
and complete description of everything a call can reach?

Strongest program: P5's eight columns behind one struct, with the kernel
separately compiled.

```text
struct Cols { a: DynBox<u64>, b: DynBox<u64>, c: DynBox<u64>, d: DynBox<u64>,
              e: DynBox<u64>, f: DynBox<u64>, g: DynBox<u64>, h: DynBox<u64> }

fn kernel(c: &Cols, n: u64)
        writes(c.a), writes(c.b),
        reads(c.c), reads(c.d), reads(c.e), reads(c.f), reads(c.g), reads(c.h)
    contract { requires n <= len_of(c.a); requires n <= len_of(c.b);
               requires n <= len_of(c.c); /* ... six more ... */ }
{
    for i in 0..n {
        invariant hi: i < n;
        c.a[i] = f1(c.a[i], c.c[i], c.d[i])
        c.b[i] = f2(c.b[i], c.e[i], c.f[i], c.g[i], c.h[i])
    }
}
```

Trace:

- Rule 9: "An effect row lists `reads(path)` and `writes(path)` where each path
  starts at a reference parameter and may continue through fields, `*`, and
  whole-index or range positions supplied as arguments", and its line
  `fn update(o: &Obj, c: Bool) writes(o.a), writes(o.b) // member paths are
  allowed`. The eight member paths are exactly this form.
- Rule 1 supplies the decisive property: `c.a` and `c.c` are distinct owned
  `DynBox` values, and because "no aggregate ever contains a reference" there is
  no value of any type, at any instantiation, that could make the two blocks be
  the same block. Two member paths under one parameter are therefore disjoint
  *by the type rule*, with no analysis, no annotation and no runtime guard.
- Rule 9: "A function body is checked against its own row: every statement's
  effect and every callee's substituted row must be covered by the declared
  row." The row is complete, not approximate: everything the body can reach is
  reached through `c` by fields and indices, or is a by-value parameter, which
  "has no effect entry", or is allocation, which carries none (Rule 14). There
  is no ambient state and no global in the candidate through which a callee
  could touch something its row omits.
- Rule 6: `c.a[i] = f1(c.a[i], ...)` is the atomic in-place update — "the old
  value goes into `f` by value, `f`'s result is committed, no program point lies
  between" — and since `u64` is Copy the plain assignment form is equally
  available. Rule 7 supplies `i < len_of(c.a)` from `i < n` and the `requires`.

Cost: the eight-way non-aliasing conclusion is exactly what `__restrict__` buys
in C and what an unannotated C++ compiler must either prove, guard at runtime,
or give up vectorizing for. WF gets it from Rule 1 for free, at every call site,
across separate compilation. Equal to Rust's `&mut [u64]` parameters; better than
unannotated C++ by the cost of the overlap guards that C++ emits.

Residual, recorded honestly: aliasing does not vanish, it becomes visible.
Two *indices* into the same `DynBox` can still name one slot, and Rule 9 admits
index paths supplied as arguments (`put_at(&buf[len_of(buf)], 3) // the argument
fixes the slot at the call; the row itself names no index`). That residue is
what Rule 10 checks pairwise (1-10) and what a pool reintroduces at scale
(1-16).

Rules consistent: yes — Rule 9's completeness claim for the row is only true
because of Rule 1, and the two rules are stated in agreement.
Task achievable: yes.
Depends on: Rules 1, 6, 7, 9, 14.
Verdict: accepted-fine

### 1-10: Rule 1 and Rule 10: the pairwise check meets index aliasing

Question: with pointer aliasing gone and index aliasing left, what does Rule
10's pairwise comparison cost on a call that touches several slots of one
container?

Strongest program: P3's insert-between expressed as one helper call over a pool,
where all three handles come from data.

```text
fn link(g: &DynBox<Node>, a: u64, m: u64, b: u64)
        writes(g[a]), writes(g[m]), writes(g[b])
    contract { requires a < len_of(g); requires m < len_of(g); requires b < len_of(g); }
{ g[a].next = m; g[m].prev = a; g[m].next = b; g[b].prev = m; }

m = pop_free(&freelist)          // a handle from data
link(&g, x, m, z)                // the call site
```

Trace:

- Rule 9: "Signatures never contain index expressions; an index enters an effect
  only through an argument, evaluated once at the call." `writes(g[a])` with `a`
  a parameter is well formed, so per-slot effects are expressible at all.
- Rule 10, clause 1: "Compare the substituted effects pairwise. Two effects on
  overlapping paths where at least one is a write must be proved disjoint
  (different roots, or indices or ranges proved distinct); otherwise the call is
  rejected." Three write paths on one root demand three distinctness facts:
  `x != m`, `m != z`, `x != z`. Rule 10's own example is the same shape:
  `two(&v[i], &v[j]) // accepted only with the fact i != j`.
- Rule 11 cannot supply them: the handles come from a free list and there is no
  quantified fact ("the free list never returns a handle already linked"), so
  the call is rejected as written. Rule 1 is why the situation exists at all —
  had the links stayed references, the C++ form would pass three `Node*` and no
  rule would ask anything.
- Rule 10, clause 3: "A live reference outside the call whose path has a proper
  prefix among the call's write paths becomes invalid after the call" — the
  write paths here are `g[a]`, `g[m]`, `g[b]`, whose proper prefixes are `g`,
  so a bystander `p = &g[t]` survives the call for every `t`: its prefix `g` is
  not among the write paths. That is more permissive than it first looks and
  matters for traversal code that inserts while walking.

Rewrites:

1. **Four ordinary statements in the caller, no call at all.** Rule 10 governs a
   call: "At a call, substitute the actual argument paths into the callee's
   row." Two consecutive *statements* are not compared pairwise by any clause,
   and Rule 3 keeps a reference valid across a write to its own path or below
   ("Writing the storage at p's path or below it (a content write) does not
   invalidate p"). So the four stores stand, in source order, with the same
   semantics C++ has when the handles happen to coincide. Cost: zero — the same
   four stores, plus the Rule 7 bound tests already counted in 1-7.
2. **Keep the helper, coarsen the row to `writes(g)`.** One effect, so clause 1
   has nothing to compare and the call is accepted with no facts. Cost: zero
   sequentially. The loss is that no caller can overlap this call with any other
   access to `g` under Rule 13, which matters only for parallel construction
   (priced in 1-16).
3. **Prove the facts by testing:** `if x != m && m != z && x != z { link(...) }
   else { ... }`, with Rule 11's "refinement facts from a dominating branch"
   supplying them. Cost: 3 compares, 3 branches and a duplicated else arm per
   insert, against zero in C++. Strictly worse than rewrites 1 and 2 and never
   necessary.

Best rewrite and cost: rewrite 1 or 2, at zero runtime cost against the C++
insert. The structural point to record is the asymmetry: the fine-grained row
(`writes(g[a]), writes(g[m])`) is the one that buys parallelism and the one that
charges distinctness proofs; the coarse row (`writes(g)`) is free sequentially
and forfeits all overlap. The candidate makes the library author choose once per
function, and the choice is invisible at the call site except as acceptance.

Rules consistent: yes.
Task achievable: rewrite, at zero cost.
Depends on: Rules 1, 3, 7, 9, 10, 11, 13; Rule 16 for the pool shape.
Verdict: rejected-zero-cost

### 1-11: Rule 1 and Rule 11: a value-only structure cannot carry its own invariant

Question: can a multi-part owned structure carry a relation between its parts
across a call boundary, given that facts attach to paths and there is no type
invariant?

Strongest program: the P5 kernel called on a `Cols` that was just taken out of a
container, so no fact about it survives.

```text
cols = pop(&pending)             // own Cols; the eight lengths are unknown here
kernel(&cols, n)                 // requires n <= len_of(cols.a), ... eight clauses
holder.cols = move cols          // and now nothing is known about holder.cols either
```

Ordinary program: the same structure built in the same fact chain.

```text
fn build(out: &Cols, n: u64)  writes(out)
    contract { ensures len_of(out.a) == n; ensures len_of(out.b) == n;
               /* ... six more ... */ }
build(&cols, n)?
kernel(&cols, n)                 // all eight requires discharged, no runtime test
```

Trace:

- Rule 11: "Facts are the existing WF forms: affine comparisons over measures
  and integer values, refinement facts from a dominating branch, loop-header
  invariants ..., explicit `use` steps inside an `invariant`, and callee
  contracts." There is no type-level or struct-level invariant form, so "all
  eight columns have equal length" is never a property of `Cols`; it is only
  ever a fact about a particular path.
- Rule 11: "A fact that mentions a path is invalidated when that path is written
  (by statement or call) unless the callee's `ensures` re-establishes it", and
  Rule 9: "`writes` covers writing, replacing, moving out of, and freeing the
  storage at the path." So `holder.cols = move cols` kills every fact about
  `cols` (it is moved out of) and establishes none about `holder.cols` (it is
  written). No clause transports a fact along a move, even though Rule 1 makes
  the move a byte copy of a value whose measures are unchanged. That is a real
  consequence of the two rules meeting, and it is decided, not ambiguous: facts
  follow paths, values do not carry them.
- The recovery is the dominating-branch refinement:

```text
n = len_of(cols.a)
if n <= len_of(cols.b) && n <= len_of(cols.c) && /* ... */ {
    kernel(&cols, n)
} else { return Err(Ragged) }
```

Rewrite and cost: against C++, where a class invariant is established by the
constructor and checked never:

- 8 header loads, 8 compares and 1 branch, **once per boundary crossing**, not
  per element. The eight `len_of` values are in the block headers the kernel
  will touch anyway, so the loads are not extra memory traffic in any loop that
  follows.
- Hoistable out of any loop that does not rewrite `cols`; invisible in the
  ordinary program above, where the facts arrive from `build`'s `ensures` and
  nothing is tested at runtime at all.
- The cost is therefore proportional to the number of places where a structure
  enters the program without provenance — deserialization, a heterogeneous
  container, a separately compiled entry point — and zero everywhere else.

Rules consistent: yes.
Task achievable: yes — at a constant, hoistable test per opaque boundary.
Depends on: Rules 1, 9, 11, 15.
Verdict: accepted-fine

### 1-12: Rule 1 and Rule 12: getting two linear parts out of one aggregate

Question: when an owned aggregate holds more than one linear part, how is each
part consumed, given that no place is ever partially moved?

Strongest program:

```text
linear type File;  fn close(f: own File)
struct Pair { in_f: File, out_f: File, n: u64 }      // linear by containment (Rule 8)

fn finish(c: own Pair) {
    close(move c.in_f)
    close(move c.out_f)          // is c.out_f still nameable here?
}
```

Trace:

- Rule 8 writes exactly this shape itself: `struct Conn { f: File, n: u64 }` and
  `fn use_it(c: own Conn) { ...; close(move c.f) } // consuming the struct as a
  whole and closing its File is required`. So `move c.f` is a form the candidate
  uses.
- Rule 12: "No place is ever partially moved: every path is either wholly
  present or the program cannot name it."
- Rule 6: "There is no `take` operation and no partial move out of any place:
  the only ways to move a value out of storage are consuming a whole local
  (`move x`), the window operations, and the atomic update." `c` is the local;
  `c.in_f` is a part of it, not a whole local, and it is not a window operation
  or an atomic update.
- "Not in this candidate" excludes "`take`/`put` holes", so a hole in `c` after
  the first `close` is not available as an answer.

Ambiguity, quoted verbatim, two sentences that cannot both be read literally for
this program:

> Rule 8: "fn use_it(c: own Conn) { ...; close(move c.f) }   // consuming the
> struct as a whole and closing its File is required"

> Rule 6: "There is no `take` operation and no partial move out of any place:
> the only ways to move a value out of storage are consuming a whole local
> (`move x`), the window operations, and the atomic update."

Reading A — `move c.f` is a whole-local consumption written through a field: the
statement consumes `c` entirely, closes its `File` and releases the affine
remainder. Then the second `close(move c.out_f)` is rejected because `c` is
already gone, and **a struct with two linear fields can never be finished**.
Reading B — `move c.f` names the field and the rest of `c` remains nameable.
Then Rule 12's "no place is ever partially moved" is false for exactly this
case and the rule set has re-introduced the hole that "Not in this candidate"
excludes.

Decisive program: the `Pair` above. The text gives no third reading and no
tie-breaker, so the cell stops here.

Rewrite and cost, under the worse reading (A): keep at most one linear part per
aggregate and thread the parts as separate locals, or store the pair as two
parallel `DynBox`es instead of one `DynBox<Pair>`. Runtime cost: zero for
locals; for the container case, one extra index computation per access to reach
two blocks instead of one, and two block headers instead of one in cache — no
extra dependent load, since both base pointers are loop-invariant.

Decided by the same two rules, and worth recording as a positive: P8's
conditional release needs no drop flag.

```text
if c { close(move a); s = move b } else { close(move b); s = move a }
use(&s); close(move s)
```

Rule 12: "At a join, facts are intersected (a fact survives only if it holds on
every incoming edge)"; both arms leave exactly `s` live and both consumed the
other resource, so the join is uniform and Rule 8's "explicit operation on every
exit path" is satisfied statically. C++ needs a destructor plus, in the general
case, a runtime drop flag; WF emits neither. That part of the cell is a win.

Rules consistent: not decidable for an aggregate with two linear parts.
Task achievable: yes under either reading — at worst the aggregate is split,
at zero runtime cost.
Depends on: Rules 1, 6, 8, 12.
Verdict: undecided-rule-gap

### 1-13: Rule 1 and Rule 13: free disjointness for fields, none for scatter

Question: does value-only containment hand `par` its disjointness for nothing,
and where does it still fail?

Strongest program: a parallel scatter under a data-determined permutation —
histogram assembly, radix partition, graph relaxation.

```text
perm: DynBox<u32>          // injective by construction elsewhere in the program
in:   DynBox<u64>
out:  DynBox<u64>

par over w in 0..k {                                  // the C++/OpenMP form
    for t in lo(w)..hi(w) { out[perm[t]] = f(in[t]) }
}
```

Ordinary program (the shape that is accepted):

```text
par { kernel(&in[0..mid], &out[0..mid]); kernel(&in[mid..n], &out[mid..n]) }
par { kernel_a(&cols.a, &cols.c); kernel_b(&cols.b, &cols.e) }
par { s1 = stats(&v); s2 = stats(&v) }
par { a = build(&x)?; b = build(&y)? }
```

Trace:

- Rule 13: "`par { A; B }` is accepted when A's write paths are disjoint from
  B's read and write paths and vice versa, using the same path-overlap and
  index/range-disjointness judgment as Rule 10."
- Rule 10, clause 1: disjointness comes from "different roots, or indices or
  ranges proved distinct". Arm `w` writes `out[perm[t]]` for every `t` in its
  chunk, so the needed fact is "for all `t` in chunk `w1` and `t'` in chunk
  `w2`, `perm[t] != perm[t']`".
- Rule 11: "There are no quantified facts over array elements ('for all i ...')
  and no per-slot occupancy facts". The fact cannot be stated, so it cannot be
  proved, so the `par` is rejected. Injectivity of a stored permutation is
  precisely the class of knowledge the fact language excludes.
- No escape: "channels or atomics" are listed under "Not in this candidate", and
  the candidate has no runtime traps, so neither a synchronized scatter nor a
  checked one is available.
- The accepted shapes above, by contrast, need nothing from the writer. The
  range case is Rule 13's own example (`par { kernel(&v[0..mid], &out[0..mid]);
  kernel(&v[mid..n], &out[mid..n]) } // disjoint ranges: accepted`), whose
  disjointness is affine in the split point. The field case is decided by Rule
  1: distinct members are distinct blocks and *no value in the language can make
  them alias*, so the conclusion needs no annotation, no guard and no
  whole-program view. The read/read and both-allocate cases are Rule 13's and
  Rule 14's own examples.

Rewrites for the scatter, with cost:

1. **Bucket by destination first.** One counting pass over `n` (read `perm`,
   increment `k` counters), a prefix sum over `k`, then one pass writing each
   `t` into its destination bucket; then `par` over `k` buckets with
   `&out[lo_w..hi_w]` range effects, whose disjointness is affine in the prefix
   sums (Rule 11) and therefore accepted. Cost against the C++ form: two extra
   full passes over `n` and `n` extra `u32` of memory before any useful work
   starts. When the scatter body is cheap — and a scatter is used precisely when
   it is — this is a 2x to 3x slowdown, and it converts a streaming kernel into
   one with a materialized intermediate.
2. **Run the scatter sequentially.** Loses `k`-way parallelism outright.
3. **Give each arm its own `out` block and merge.** Another `n`-sized pass and
   `k * n`-worth of extra memory in the general case; only viable when the
   output is sparse.

Best rewrite: (1) when `k` is small relative to `n`, (2) otherwise. Either way
the cost is real and unavoidable under Rule 11 as frozen. Safe Rust is in the
same position (it needs `split_at_mut`-style partitioning or `unsafe`); C++ with
the programmer's promise is not.

Rules consistent: yes.
Task achievable: rewrite, with real cost for scatter; accepted at zero cost for
field-disjoint, range-disjoint, read/read and allocation-only arms.
Depends on: Rules 1, 10, 11, 13, 14.
Verdict: rejected-real-cost

### 1-14: Rule 1 and Rule 14: fallible allocation, effect-free allocator, no cleanup code

Question: with one heap, fallible allocation and an allocator that carries no
effect, can a value-only program build and tear down aggregates across failure
paths without cleanup code and without losing overlap?

Strongest program: P18 — several allocations under a budget, each of which may
fail, inside the construction of one aggregate, in two parallel arms.

```text
struct Pair { l: Option<Box<Node>>, r: Option<Box<Node>> }

fn build_pair(x: &Input, y: &Input, out: &Pair)  reads(x), reads(y), writes(out)
{
    par {
        a = build_tree(&x)?     // many Box::new / DynBox::new inside, any may fail
        b = build_tree(&y)?
    }
    out.l = Some(move a); out.r = Some(move b)
}
```

Trace:

- Rule 14: "Allocation and release carry no effect entry and never make two
  parallel arms conflict", with its example `par { a = build(&x)?; b =
  build(&y)? } // both allocate: accepted`. Rule 13 therefore has only
  `reads(x)` against `reads(y)` to compare, which are different roots and, by
  Rule 1, cannot be made to alias by any value. The arms are accepted with no
  writer input.
- Rule 14: "Allocation returns a `Result` and never traps", so every `Box::new`
  and `DynBox::new` is `?`-propagated. Rule 14: "Addresses are not observable,
  so allocator concurrency does not affect program determinism" — which is what
  makes the parallel arms deterministic despite an internally synchronized
  shared heap.
- Rule 8: on a failure arm, whatever `build_tree` had already allocated is an
  affine value, and "at scope exit the compiler releases their memory
  recursively (Box, DynBox) and runs no user code". P18's requirement — "the arm
  must free nothing twice and leave earlier blocks owned" — holds by affinity,
  with no written cleanup, no drop flag and no unwinding machinery.
- Rule 1 is what makes that recursive release correct and cheap: the released
  value is a tree of owned parts with no references into or out of it, so the
  release walk is exactly the ownership tree, decided statically from the type.
- Rule 14: "There are no store or region parameters anywhere", so neither arm
  carries an allocator argument that the other would have to be proved disjoint
  from. A design with an explicit store parameter would have made both arms
  write the same store and forced them into sequence.

Cost against C++/Rust:

- One predicted branch per allocation for the `Result`. `Result<Box<T>, Oom>`
  has a null niche, so it is one pointer wide and the test is a null test — the
  same instruction C++ emits for `new(nothrow)`, and one more than Rust's
  aborting `Box::new`. In exchange the program handles OOM without a trap.
- The recursive scope-exit release is the same walk a chain of `unique_ptr`
  destructors performs; no user code runs in either.
- Reservation works: `DynBox::new<T>(n)` gives "`cap_of == n, len_of == 0`", so a
  large capacity is reserved without touching the pages and `push_nogrow`
  commits slots one at a time. This is C++'s `reserve()` shape at C++'s cost.
- The one real loss: `cap_of` is "fixed at allocation", so there is no in-place
  grow. A C++ arena built on `mmap` reserve-then-commit extends without copying;
  a WF `Vector` must allocate a new block and memmove `len` elements (amortized
  O(1), with 2x peak footprint at the instant of growth). `std::vector` and
  Rust's `Vec` pay exactly this, so the loss is only against an address-space
  reserving allocator, which the candidate cannot express because there are no
  region or store parameters.

Rules consistent: yes.
Task achievable: yes.
Depends on: Rules 1, 5, 6, 8, 13, 14.
Verdict: accepted-fine

### 1-15: Rule 1 and Rule 15: handing back positions instead of references

Question: since returns are owned and no aggregate may hold a reference, how
does a function hand back two independently writable parts of one container, and
what does the caller pay?

Strongest program: P1 — split a container into two exclusively writable
positions, write both in parallel, read a third slot, then push.

```text
fn split_two(v: &DynBox<u64>, i: u64, j: u64) -> (&u64, &u64)     // rejected
fn take_two(v: &DynBox<u64>, i: u64, j: u64) -> (own u64, own u64) // a hole: not available
```

Ordinary program: the accepted form.

```text
fn choose(v: &DynBox<u64>, seed: u64) -> own u64   reads(v)
    contract { ensures result < len_of(v); }

i = choose(&v, s1); j = choose(&v, s2)
if i != j {
    par { bump(&v[i]); bump(&v[j]) }      // Rule 13 + Rule 10.1 with the branch fact
} else {
    bump(&v[i])
}
r = v[k]                                   // needs only k < len_of(v)
push_nogrow(&v, x)                         // legal; nothing live is invalidated
```

Trace:

- Rule 15: "A function returns owned values only." Rule 4: a reference "cannot
  be assigned into any aggregate (Rule 1), cannot be returned". A tuple of two
  references is rejected twice over — as an aggregate containing references
  (Rule 1) and as a returned reference (Rule 4) — and "slice types as
  first-class values" is under "Not in this candidate", so a returned range is
  out as well.
- Rule 6: "There is no `take` operation and no partial move out of any place",
  and "Not in this candidate" excludes `take`/`put` holes, so `take_two` has no
  meaning here either.
- Rule 4's prescribed pattern supplies the replacement: "A function that 'finds'
  something returns an index or other owned data; the caller forms the
  reference", with Rule 15 adding "Positions found by a search are returned as
  indices with a bounds relation in `ensures`". `ensures result < len_of(v)`
  means the caller needs no bound test at all — the fact arrives with the value.
- Rule 10, clause 1 and Rule 13 require `i != j` for the parallel pair; Rule 11's
  "refinement facts from a dominating branch" supplies it from the `if`.
- Two of P1's stated requirements are *weaker* under this candidate than P1
  assumed. "Read `v[k]` for a runtime `k` is legal iff `k` is provably not `i`
  and not `j`" — sequentially, the read needs only its bound (Rule 7), because
  nothing was taken out (Rule 12: "No place is ever partially moved: every path
  is either wholly present or the program cannot name it") and a content write
  does not invalidate anything (Rule 3). And "put both parts back before push"
  disappears entirely: there is nothing to put back; `push_nogrow` merely
  invalidates any reference still naming a slot (Rule 3), which the writer
  re-forms.
- Rule 15's large-value clause covers the other half of the cell: "Passing a
  large value in and back out is expressed as a reference parameter with a
  `writes` entry, not as move-and-return", i.e. `fn fill(out: &array<f64,1024>)
  writes(out)`.

Rewrite and cost:

- The caller re-forms `&v[i]` where C++ would hold a `u64*`: one `lea` from a
  base already in a register, no extra memory access, no branch.
- The `i != j` compare is one instruction, and C++ needs the same knowledge to
  run the two writes in parallel — it simply takes it on trust rather than
  branching on it. Where `i != j` is known by construction the branch does not
  exist.
- For the large-aggregate return, the out-parameter form *guarantees* the copy
  elision that C++ gets only when NRVO applies, so the candidate is at worst
  equal and often better.

Rules consistent: yes.
Task achievable: rewrite, at zero runtime cost.
Depends on: Rules 1, 3, 4, 6, 7, 10, 11, 12, 13, 15.
Verdict: rejected-zero-cost

### 1-16: Rule 1 and Rule 16: the index is the only durable name, and the pool is one root

Question: when references cannot be stored, a pool index is the only durable
name for an object — what does that name cost once the pool must also grow and
be written concurrently?

Strongest program: parallel construction of one compiler IR graph, where arms
create nodes and rewrite node data at the same time (task row "mutable compiler
graph", P3).

```text
struct Node  { op: u32, a: u32, b: u32, data: u64 }
struct Arena { buf: DynBox<Node> }

fn alloc(a: &Arena, x: own Node) -> u64   writes(a.buf)
    contract { requires len_of(a.buf) < cap_of(a.buf);
               ensures result == len_of(deref(entry(a.buf)));
               ensures len_of(a.buf) == result + 1; }

fn set_data(a: &Arena, i: u64, d: u64)    writes(a.buf[i])
    contract { requires i < len_of(a.buf); }

par { id = alloc(&g, n); set_data(&g, other, d) }        // rejected
p = &g.buf[i]; id = alloc(&g, n); use(p)                 // rejected
```

Trace:

- Rule 16: "A pool is a DynBox plus indices used as handles." The handle is a
  `u64` — owned, Copy, storable in any aggregate under Rule 1, returnable under
  Rule 15, and immune to Rule 3's invalidation because it is not a reference.
  This is the *only* mechanism in the candidate that gives an object a name that
  outlives the statement that formed it, which is why cells 1-2, 1-4 and 1-5 all
  land here.
- Rule 9: `alloc` must declare `writes(a.buf)`. It changes `len_of`, which Rule 6
  places "in the block header", and Rule 9's paths "continue through fields,
  `*`, and whole-index or range positions supplied as arguments" — there is no
  path naming the header alone, and no index argument describes it.
- Rule 13 with Rule 10, clause 1: `writes(a.buf)` and `writes(a.buf[i])` overlap
  on the same root with a write on both sides, and no index can be proved
  distinct from "the whole buffer". Rule 10's own example is this exact shape:
  `bad(&vv, &vv[0]) // rejected: writes(vv) and writes(vv[0]) overlap`. So
  allocation cannot overlap any other access to the pool.
- Rule 3 gives the sequential half: `g.buf` is a proper prefix of `g.buf[i]`, so
  every outstanding reference into the pool dies at each `alloc`, including
  `push_nogrow`-style allocation that provably cannot reallocate (same
  conservatism as 1-3).
- Rule 16's reference clause confirms it: "`p = &a.buf[id]` // valid until
  `a.buf` is replaced; readable while `id < len_of(a.buf)`" — the handle
  survives what the reference does not.

Rewrites:

1. **Phase separation.** Allocate all nodes in a sequential phase, then map over
   them in a parallel phase with range effects (`par { work(&g.buf[0..mid]);
   work(&g.buf[mid..n]) }`, Rule 13's own accepted example). Cost: the
   construction phase is serial. For a parallel frontend that creates and
   rewrites nodes in the same traversal — the normal shape — this serializes the
   dominant phase.
2. **Pre-fill so allocation stops being a whole-buffer write.**
   `g.buf = DynBox::filled(cap, NIL_NODE)?` keeps `len_of == cap_of` for the
   pool's whole life, occupancy becomes data (Rule 12: "Structures whose
   occupancy is decided by data keep that occupancy as data"), and "allocation"
   becomes `writes(g.buf[free])`, a per-slot effect that *can* be proved
   disjoint. But the free-list head is shared state, so the arms now collide on
   `writes(g.free_head)`; per-arm free lists remove that collision and restore
   the first one, because the two arms' slot indices come from data and Rule 11
   has no quantified fact to prove them distinct. Net: still rejected, at the
   cost of `cap * sizeof(Node)` committed up front.
3. **One pool per arm.** Distinct roots, so everything is accepted by Rule 10's
   "different roots". The handle must become `(arena_id, slot)`, and a traversal
   hop becomes: load the pair, load `arenas[arena_id].buf`'s block pointer
   (**one extra dependent load**), then index and bound-test. This is exactly the
   "one extra dependent memory access per hop" the candidate already records
   under known costs, now paid on every edge of the graph rather than only at
   allocation.

Best rewrite and cost against C++: a C++ parallel frontend uses one bump arena
per thread and raw `Node*`; hops cost one dependent load and cross-arena edges
cost nothing extra. Rewrite 3 costs one extra dependent load per hop for the
life of the graph; rewrite 1 costs the parallelism of construction. There is no
zero-cost form.

Worth recording alongside: `Box::new` in parallel arms is free (Rule 14 — the
global heap is "internally synchronized" and allocation "carries no effect
entry"), so a node-per-`Box` graph parallelizes its *allocation* where a pool
does not. The pool wins locality and loses concurrency; the candidate makes that
a per-structure choice rather than a language-wide one, which is a good property
even though neither option matches the C++ baseline on both axes.

Rules consistent: yes.
Task achievable: rewrite, with real cost for concurrent construction; the
sequential single-pool case is accepted at the zero cost derived in 1-5.
Depends on: Rule 16 (provisional), Rules 1, 3, 9, 10, 11, 12, 13, 14, 15.
Verdict: rejected-real-cost

### 16-16: Rule 16 with itself: slot reuse meets arena reset

Question: when two pool usages compose — per-slot reuse through a free list and
whole-arena reset through `truncate` — does a handle still name what the program
thinks it names, and what does detection cost?

Strongest program: an arena reset between compiler passes, with handles surviving
in a side table and slot-level reuse inside each pass.

```text
struct Arena { buf: DynBox<Node> }
side: DynBox<u64>                    // handles kept across the reset: owned data, entirely legal

// pass 1
h  = alloc(&a, n1)                   // h == 7
side[t] = h                          // Rule 1 permits this: a handle is a value
free_slot(&a, h)                     // free list: slot 7 is reusable
h2 = alloc(&a, n2)                   // returns 7 again: ABA within one pass
...
truncate(&a.buf, 0)                  // Rule 16's reset between passes

// pass 2
for .. { alloc(&a, ...) }            // len_of climbs back past 7
x = a.buf[side[t]]                   // in bounds, initialized, correctly typed, wrong object
```

Trace:

- Rule 16: "A stale index that is still in bounds names the current occupant of
  that slot: a logic error, not a memory error. Programs that need to detect it
  keep a generation number as data." The rule is explicit, so the program above
  is accepted as written; the cell's job is to price the composition, not to
  dispute the ruling.
- Rule 16's reset line: "`truncate(&a.buf, 0)` // reset: elements released;
  later reads of `a.buf[id]` need `id < len_of` again." So immediately after the
  reset, handle 7 *is* caught — by the Rule 7 bound test, which fails. Once pass
  2 has allocated eight nodes, the same handle passes the same test and reads a
  live node of the wrong identity. **Detection is load-dependent**: it fires on
  small inputs and stops firing on large ones, which is the worst possible shape
  for a latent defect, and it is a direct product of Rule 16 composed with
  itself (the reset shrinks the window, the refill restores it).
- Memory safety survives intact, and this must be said precisely. Rule 6: every
  slot in `[0, len_of)` holds a value and "no program point can observe a slot
  inside the window as empty", so there is no uninitialized read. Rule 7's test
  keeps the access in bounds. Rule 12: "every path is either wholly present or
  the program cannot name it", so there is no hole to observe. Rule 8 survives
  too: a stale handle used with `swap_remove` removes the *wrong* linear value,
  never the same one twice, so nothing is duplicated or leaked. None of the
  candidate's stated safety properties — memory corruption, data races,
  uninitialized reads, silent overflow, unproved partial operations — is
  violated. What is lost is object identity, which Rule 16 reclassifies as a
  logic error by design.
- The self-interaction proper: the two reuse mechanisms need *different*
  detectors and one erases the other's data. Per-slot generation counters live
  in the slots, and `truncate(&a.buf, 0)` releases the slots, taking the
  counters with them; an arena-level epoch survives the reset but says nothing
  about slot reuse inside a pass. Neither alone is sufficient once both usages
  are present, and nothing in Rule 16 warns the writer of that.
- One more composition worth noting: pool-of-pools. `DynBox<Arena<T>>` relocates
  the inner `Arena` headers on growth, which Rule 1's consequence clause makes
  safe (byte relocation), and inner handles are indices, so they are unaffected.
  Nesting pools is sound; it is only the identity question that compounds.

Rewrite and cost: carry both detectors.

```text
struct Slot  { gen: u32, node: Node }
struct Arena { buf: DynBox<Slot>, epoch: u32, next_gen: u32 }
struct H     { idx: u32, gen: u32, epoch: u32 }        // owned: storable, returnable

fn get(a: &Arena, h: H) -> Option<u64>   reads(a)
    contract { requires h.idx < len_of(a.buf); }
{
    s = a.buf[h.idx]
    if s.gen == h.gen && a.epoch == h.epoch { Some(s.node.data) } else { None }
}
// reset: truncate(&a.buf, 0); a.epoch = a.epoch + 1     — still O(1)
```

- Reset stays O(1) because the epoch is one counter; bumping a per-slot
  generation across the whole pool would have made reset O(cap), which is the
  naive fix and is much worse.
- Per dereference, against C++'s raw `Node*`: one generation load (same cache
  line as the node, so no extra miss), one epoch load (arena header, cache-hot),
  two compares, one branch, plus the caller's handling of the `Option` — a
  second branch on the hot path or a `None` arm that must invent behaviour. The
  Rule 7 bound compare is already counted in 1-7.
- Handle footprint grows from 8 bytes (`Node*`) to 12, which costs real
  bandwidth in a large side table or edge list.
- Against safe Rust: identical. This is what `slotmap` does and it is the only
  safe form available there either.
- Against C++ that also wants detection (a generational handle map): identical.
- Against C++ raw pointers: two loads, two compares and one to two branches per
  dereference that C++ does not pay — C++ pays instead with undefined behaviour
  on precisely the same mistake, and with a use-after-free where WF has a
  well-defined read of the wrong object.

Rules consistent: yes — Rule 16 composes with itself without contradiction. Both
the free list and the reset are "usage", nothing forbids using both, and the
result is well defined at every step.
Task achievable: yes for a memory-safe pool at the costs derived in 1-5, 1-7 and
1-16; rewrite for the identity guarantee P3 demands, since "removal invalidates
every path to m" is not delivered by the rules and must be delivered by the
program's own data.
Depends on: Rule 16 (provisional), Rules 1, 6, 7, 8, 11, 12, 15.
Verdict: accepted-unsafe — accepted by the rules and memory-safe in the
candidate's own sense, but the rules admit a program whose handles silently name
the wrong object, and the only check that ever fires (the bounds test) fires
non-deterministically with input size.
