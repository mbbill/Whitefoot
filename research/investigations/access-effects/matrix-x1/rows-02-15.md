### 2-2: Rebinding a reference from itself: loop-carried paths

Question: when a reference is rebound in a loop to a path expressed through
its own current path, what is its target set at the loop header?

Strongest program:

```text
// Node { value: Int, next: Option<Box<Node>> }; walk an owned list iteratively
fn sum(head: &Node) -> Int  reads(head)
{
    s = 0
    p = head                          // p names the path head
    while is_some((*p).next) {
        s = s + (*p).value            // content read at p's path
        p = &*((*p).next)             // rebind: p names head.next.*, then head.next.*.next.*, ...
    }
    return s + (*p).value
}
```

Ordinary program (only if it differs materially):

```text
q = p                                 // aliasing: both live
r = &p.x                              // extension
&p                                    // rejected
w = if cond { &v1 } else { &v2 }      // one join: finite set { v1, v2 }
```

Trace: Rule 2 clause 1, "A path starts at a local variable or a parameter and
continues through fields, `*` (Box content), `[i]` (index, Rule 7), or
`[lo..hi]`", and "A reference variable names a path; it is not storage of its
own". Because p is not storage, `p = &*((*p).next)` can only mean that p now
names the path obtained by substituting p's current path, so at iteration k p
names `head.(next.*)^k`. Rule 2's join clause then applies at the loop header:
"At a control-flow join, a reference variable's target is the set of paths it
may name; every check on it must hold for every member of the set." That set
is infinite here. The rule file gives no finite representation of a target
set, no widening, no depth bound, and no clause that rejects an unbounded set.
Under a widening reading every member satisfies Rule 3 (no proper prefix of
any member is written) and Rule 4 (p never escapes), so the loop is accepted
and erases to plain pointer chasing; under a literal finite-set reading the
loop has no representable target and the program cannot be checked. The rule
text decides neither. The ordinary forms above are all decided by Rule 2's own
examples: `q = p` is allowed ("q names the same path; both may be live"), `&p`
is rejected, `r = &p.x` extends the path, and a finite number of joins gives a
finite product set, whose size is a checker cost and not a runtime cost
(protocol item 7).

Rewrite and cost: if unbounded target sets are not admitted, two rewrites
exist. (a) Recursion re-roots the path at each frame's parameter, so every
frame's target set has depth at most two: `fn sum_from(n: &Node) -> Int
reads(n) { ... sum_from(&*((*n).next)) }`. Cost versus the C++ `while (p) p =
p->next` loop: one call and return per element, because the rule file states no
tail-call guarantee. (b) Arena plus handles (Rule 16): the base load hoists out
of the loop, leaving one shift/add per hop, plus one bounds compare per hop
because the stored handle's range is data and Rule 11 excludes quantified facts
over elements.

Rules consistent: yes for finite sets; the file does not say what a
loop-carried self-rebinding produces.   Task achievable: rewrite, at one call
frame or one compare per hop.
Depends on: Rule 3, Rule 4, Rule 5, Rule 11, and Rule 16 for the index rewrite.
Verdict: undecided-rule-gap

### 2-3: Target sets and validity invalidation

Question: when a reference's target is a set, which member's invalidation
kills it?

Strongest program:

```text
w = if cond { &v1 } else { &v2 }      // Rule 2: target set { v1, v2 }
p = &w.buf[i]                          // target set { v1.buf[i], v2.buf[i] }
grow(&v1)                              // declares writes(v1.buf)
use(p)
```

Trace: Rule 3, "It is established when p is formed and invalidated when any
proper prefix of p's path is written, moved out of, replaced, or freed, by a
statement or by a call." `v1.buf` is a proper prefix of `v1.buf[i]`, so the
member `v1.buf[i]` is invalid after the call. Rule 2's join clause, "every
check on it must hold for every member of the set", makes "p is valid" a check
that fails, so `use(p)` is rejected on every run, including the runs where
cond was false and p actually named `v2.buf[i]`. Rule 3's other clause keeps
the sibling case alive: "Writing the storage at p's path or below it (a content
write) does not invalidate p", so `v1.buf[j] = 5` does not kill p.

Rewrite and cost: duplicate the branch so each arm carries a single-target
reference (duplicated code is free under protocol item 7):

```text
if cond { p = &v1.buf[i]; grow(&v1); p = &v1.buf[i]; use(p) }
else     { p = &v2.buf[i]; grow(&v1); use(p) }
```

The else arm costs nothing. The then arm re-forms p, which is one load of
`v1.buf`'s base and one shift/add; a correct C++ program must also re-derive
the pointer after a reallocating grow, so the cost versus correct C++ is zero.

Rules consistent: yes, the union of targets and the universal check compose
without residue.   Task achievable: rewrite, zero cost.
Depends on: Rule 9 (grow's row), Rule 12 (join).
Verdict: rejected-zero-cost

### 2-4: A reference captured by a non-escaping function value has no declarable effect

Question: may a function value capture a reference when it is neither stored
nor returned, and if so how is the captured access declared?

Strongest program (the P6 and P16 closure witness):

```text
h = |part: &DynBox<u8>| helper(part, input)     // input: &Input, captured; h is neither stored nor returned
for w in 0..k { h(&out[w*s .. (w+1)*s]) }
par { h(&out[0..s]); h(&out[s..2*s]) }
```

Ordinary program:

```text
fn find(v: &DynBox<Entry>, key: Int) -> Option<u64>  reads(v)   // Rule 4's own form
match find(&v, k) { Some(i) => { p = &v[i]; ... }  None => ... }
w = match col { 0 => &c.a, 1 => &c.b, ... }      // selecting among heterogeneous places
```

Trace: Rule 4 says a reference "cannot be assigned into any aggregate (Rule 1),
cannot be returned, and cannot be captured by a function value that is stored
or returned." The qualifier "that is stored or returned" leaves capture by a
non-escaping function value off the forbidden list. Rule 9's heading and first
sentence are exhaustive the other way: "Effects are declared only on reference
parameters" and "An effect row lists `reads(path)` and `writes(path)` where each
path starts at a reference parameter". The captured `input` is not a parameter
of h, so h's row cannot name it. Rule 10 then judges each call of h by that
row, "Function-typed parameters carry a full signature with its own row and
contract, and a call through one uses that row", and Rule 13 judges the par
block "using the same path-overlap and index/range-disjointness judgment as
Rule 10". So either Rule 4's qualifier is exhaustive and captured accesses are
invisible to the Rule 10 and Rule 13 comparisons, or Rule 9 is exhaustive and a
function value capturing a reference cannot be given a row at all, making Rule
4's qualifier dead text. The file does not say which. The ordinary program is
decided: returning a reference is rejected, Rule 4's index form re-derives the
address at the caller in one shift/add that the C++ callee performed anyway,
and the heterogeneous selection is duplicated into one arm per place, which is
free and hands the backend better disjointness facts than a C++ pointer chosen
by a jump table.

Rewrite and cost: pass the captured reference as an ordinary parameter, `fn h(part: &DynBox<u8>, input: &Input) writes(part), reads(input)`, and supply it
at each call. Extra parameters are not a cost (protocol item 7), the row
becomes complete, and the generated code is identical. So the task survives
under either reading at zero runtime cost.

Rules consistent: not decidable from the text; the two exhaustive-sounding
clauses overlap.   Task achievable: rewrite, zero cost.
Depends on: Rule 9, Rule 10, Rule 13, Rule 1.
Verdict: undecided-rule-gap

### 2-5: References into Box contents under moves and runtime selection

Question: does a reference into heap content survive a move of the owning Box,
and what happens when the Box itself is chosen at runtime?

Strongest program:

```text
b1: Box<Node>;  b2: Box<Node>
p = if c { &*b1 } else { &*b2 }     // Rule 2: target set { *b1, *b2 }
holder.child = move b1              // whole-local move (Rule 5)
use(p)
```

Trace: Rule 5, "`*b` is a path (Rule 2)", and Rule 3's own worked example,
"`c = move b` // b is a proper prefix of `*b`: p invalid, even though the Node
did not move", together with "A move never re-roots an existing reference:
after `w = move v`, references formed from `v` are invalid and are not
reinterpreted as references into `w`." The member `*b1` is invalid after the
move, and Rule 2's every-member clause makes `use(p)` rejected on both runs.
Rule 5's "the heap object did not move" is what makes the rewrite free.

Rewrite and cost:

```text
if c { holder.child = move b1; p = &*holder.child; use(p) }
else  { holder.child = move b1; use(&*b2) }
```

Cost: zero. The re-formed reference is the same address; at worst it is one
load of `holder.child`, which the C++ program performs too when it re-reads the
field. A separate loss belongs to Rule 1 rather than to this pair: a Box graph
cannot carry parent or back edges, since a field may not hold a reference and a
second owning Box would duplicate ownership. That rewrite is handles into a
pool (cell 2-16), costing one shift/add plus one bounds compare per hop.

Rules consistent: yes.   Task achievable: rewrite, zero cost for the Box case.
Depends on: Rule 1, Rule 3, Rule 16 for the back-edge case.
Verdict: rejected-zero-cost

### 2-6: A window operation invalidates every reference into the container

Question: can a reference into a DynBox slot survive a window operation on a
different slot?

Strongest program:

```text
n = len_of(buf)
if i < n { p = &buf[i] }        // Rule 7 establishes i < len_of(buf); i is data-determined
v = pop(&buf)                   // writes(buf)
use(p)                          // the C++ equivalent of this stays valid
```

Ordinary program:

```text
p = &buf[j]
buf[k] = f(buf[k])              // atomic in-place update at a slot
use(p)                          // still valid
```

Trace: Rule 9 forbids a signature from naming the slot, "Signatures never
contain index expressions; an index enters an effect only through an argument,
evaluated once at the call", so `pop`, `push_nogrow`, `swap_remove` and
`truncate` can declare nothing finer than `writes(buf)` (Rule 6 shows exactly
these rows). Rule 3 then invalidates p, because `buf` is a proper prefix of
`buf[i]`. The ordinary program is accepted by the same rule read the other way:
the atomic update writes at `buf[k]`, which is either a different index from
`buf[j]` (not a prefix) or p's own path, and "Writing the storage at p's path or
below it (a content write) does not invalidate p". So only the header-changing
operations invalidate references, and they invalidate all of them.

Rewrite and cost: keep the index, re-form after the call, and re-prove the
bound. `pop`'s `ensures len_of(buf) == len_of(deref(entry(buf))) - 1` plus a
caller-bound integer `n = len_of(buf)` (an integer fact mentions no path, so
Rule 11 does not invalidate it) gives `len_of(buf) == n - 1`; the fact in hand
is `i < n`, and `i < n - 1` does not follow, so the data-determined case must
test: `if i < len_of(buf) { p = &buf[i]; use(p) } else { ... }`. Cost per
re-form versus C++, where `pop_back` leaves a reference to element `i < n-1`
valid and the pointer stays in a register: one load of the block base, one
shift/add, one compare and a branch whose else arm must be written. In a
scan-while-popping loop that is one compare and one address recomputation per
iteration. Versus safe Rust the compare is already paid by indexing, so only
the base reload remains.

Rules consistent: yes; the coarse effect is forced by Rule 9 and the
invalidation by Rule 3.   Task achievable: rewrite, with a residual compare.
Depends on: Rule 3, Rule 7, Rule 9, Rule 11.
Verdict: rejected-real-cost

### 2-7: What `[i]` in a path denotes after `i` changes

Question: is the index in a formed reference's path the value at formation or
the current value of the index variable?

Strongest program:

```text
p = &buf[i]          // Rule 2: "p names the path v.buf[i]"
i = i + 1            // i is an ordinary integer local
put_at(p, 7)         // fn put_at(slot: &Int, x: own Int)  writes(slot)
```

Ordinary program:

```text
part = &buf[lo..hi]                      // requires lo <= hi <= len_of(buf)
q = &part[k]                             // requires k < len_of(part); len_of(part) == hi - lo
r = if c { &buf[0..mid] } else { &buf[mid..n] }
s = &r[k]                                // every member: needs k < mid and k < n - mid
```

Trace: Rule 2 states "p = &v.buf[i]  // p names the path v.buf[i]", and the
path text contains the variable `i`. Rule 3's invalidation list is closed:
"invalidated when any proper prefix of p's path is written, moved out of,
replaced, or freed" - the proper prefixes of `buf[i]` are `buf` and its
prefixes, not `i`. So writing `i` is not an invalidation event, yet under a
symbolic reading it changes which slot p names, and under a snapshot reading it
does not. The two readings put the 7 in different slots and substitute
different paths into Rule 10's pairwise comparison. The only nearby text is
Rule 9's "an index enters an effect only through an argument, evaluated once at
the call", which fixes evaluation at a call site and says nothing about
reference formation in a statement. The ordinary program is decided: Rule 2
admits `[lo..hi]` as a path element and Rule 7 supplies both bounds and
`len_of(part) == hi - lo`, and a joined range reference must satisfy the bound
for every member, so the joined form needs the stronger `k < min(mid, n-mid)`.

Rewrite and cost: for the index question, bind a fresh integer and never mutate
it, `i0 = i; p = &buf[i0]`, which makes both readings agree; zero cost. For the
joined range, duplicate the branch so each arm carries its exact bound; zero
cost, and the duplicated arms give the backend exact range facts that the C++
pointer form does not carry.

Rules consistent: the two readings are each internally consistent and
observably different.   Task achievable: rewrite, zero cost.
Depends on: Rule 3, Rule 9, Rule 10.
Verdict: undecided-rule-gap

### 2-8: Consuming a linear value that a reference names

Question: how is a linear value consumed when it sits in a place that a
reference names rather than in a whole local?

Strongest program:

```text
linear type File;  fn close(f: own File)
struct Conn { f: File, n: u64 }      // linear by containment (Rule 8)
b: Box<Conn>                          // linear: Rule 8 says Box<File> "must be taken apart"
p = &(*b).f                           // Rule 2 path through Box content
close(move (*b).f)                    // ?
```

Ordinary program:

```text
pool: DynBox<Conn>
c = swap_remove(&pool, k)             // k data-determined; requires k < len_of(pool)
close(move c.f)                       // c is a whole local: Rule 6's first admitted move form
if cond { use_it(move conn1) } else { use_it(move conn2) }   // selection duplicated, not a reference
```

Trace: Rule 8 requires the consumption, "Linear values must be consumed by an
explicit operation on every exit path; the compiler never releases them", and
its own example asserts the capability: "`Box<File>` // linear: must be taken
apart and its File closed". Rule 6 closes the list of operations that can do
it: "There is no `take` operation and no partial move out of any place: the
only ways to move a value out of storage are consuming a whole local
(`move x`), the window operations, and the atomic update." `move (*b).f` is a
partial move out of the place `*b`; `move *b` is not a whole local; the window
operations belong to DynBox; and the atomic update `buf[k] = f(buf[k])` needs a
DynBox slot and must commit a value of the same type back, so it cannot
consume. Rule 8's example therefore names an operation that Rule 6's exhaustive
clause does not provide, and the rule file supplies no other. The ordinary
program is decided and is the whole answer for the non-Box cases: a reference
never consumes anything, the window operation `swap_remove` moves a linear
element out of a data-determined slot, and a runtime choice between two linear
locals is duplicated into branches, which is free.

Rewrite and cost: hold linear resources in a DynBox or as whole locals rather
than in a Box. Versus C++ `unique_ptr<Conn>`, one shared block replaces one
allocation per object, which is equal or fewer allocations; `swap_remove` costs
one struct move per removal where C++'s destructor moves nothing, and that is
the same move C++ pays for swap-and-pop_back on a vector.

Rules consistent: not for a linear value inside a Box; Rule 8 demands an
operation Rule 6's closed list withholds.   Task achievable: rewrite, at one
struct move per removal.
Depends on: Rule 5, Rule 6, Rule 12 (no partial moves).
Verdict: undecided-rule-gap

### 2-9: How an index reaches an effect row, and what a set-valued argument substitutes

Question: may a reference name the slot at `len_of(buf)` when the index is
supplied as a call argument, and how does a set-valued reference substitute
into a callee's row?

Strongest program (the rule file's own example):

```text
fn put_at(slot: &Int, x: own Int)  writes(slot)
put_at(&buf[len_of(buf)], 3)       // Rule 9's example: "the argument fixes the slot at the call"
```

Ordinary program:

```text
fn kernel(dst: &DynBox<Int>, src: &DynBox<Int>)  writes(dst), reads(src)
w = if c { &a } else { &b }
kernel(w, &third)                   // accepted: writes({a,b}) against reads(third), different roots
kernel(w, &a)                       // rejected: the member pair (a, a) is a write/read overlap
```

Trace: Rule 7 states the requirement for forming the reference, "Reading
`buf[k]` or forming `&buf[k]` requires the fact `k < len_of(buf)` (Rule 7)",
which for `k = len_of(buf)` is `len_of(buf) < len_of(buf)`, false. Rule 6 makes
that slot empty, "Slots `[0, len_of)` hold values; slots `[len_of, cap_of)`
hold nothing", and names the sanctioned way to fill it, `push_nogrow`. Rule 9's
example nevertheless forms exactly that reference and passes it to a `writes`
row. Either Rule 7's requirement has an unstated write-only exception for the
first free slot, or Rule 9's example is not a program. The file does not say.
The ordinary program is decided: Rule 10 clause 1 says "substitute the actual
argument paths into the callee's row" and then "Two effects on overlapping
paths where at least one is a write must be proved disjoint (different roots,
or indices or ranges proved distinct)", and Rule 2's every-member clause makes
the substituted write set `{a, b}` collide with `reads(a)` on one member. Two
properties worth recording on the positive side: a callee is checked once
against its own row ("A function body is checked against its own row"), and its
parameters are roots, so a caller's target sets never cross a signature and
separate compilation is untouched by Rule 2.

Rewrite and cost: for the first free slot, use `push_nogrow(&buf, x)` with its
`requires len_of(buf) < cap_of(buf)`, which is the same store plus one header
increment that a C++ `push_back` into reserved capacity performs; zero cost.
For the colliding call, hoist the branch above the call so each arm passes
single-target references; zero cost.

Rules consistent: not as written; Rule 9's example contradicts Rule 7's
formation requirement.   Task achievable: rewrite, zero cost.
Depends on: Rule 6, Rule 7, Rule 10.
Verdict: undecided-rule-gap

### 2-10: Call-site pairwise checks lose the correlation between two set-valued references

Question: can two references that a program knows are never equal be passed to
one call when each is only known as a set or as a data-determined index?

Strongest program:

```text
fn two_write(x: &Buf, y: &Buf)  writes(x), writes(y)
// perm is a permutation held as data; the program knows it is injective
two_write(&bufs[perm[i]], &bufs[perm[j]])
```

Ordinary program:

```text
for round in 0..rounds {
    src = if round % 2 == 0 { &a } else { &b }
    dst = if round % 2 == 0 { &b } else { &a }
    step(src, dst)                  // fn step(s: &Grid, d: &Grid) reads(s), writes(d)
}
```

Trace: Rule 10 clause 1, "Compare the substituted effects pairwise. Two effects
on overlapping paths where at least one is a write must be proved disjoint
(different roots, or indices or ranges proved distinct); otherwise the call is
rejected." In the strongest program both effects have root `bufs` and the
indices are values loaded from data, so distinctness is not available. The
ground a C++ programmer uses is that `perm` is injective, which is a quantified
fact over elements, and Rule 11 excludes it: "There are no quantified facts over
array elements ("for all i ...") and no per-slot occupancy facts". Rejected. In
the ordinary program Rule 2's join gives `src` the set `{a, b}` and `dst` the
set `{a, b}`, and the every-member clause finds the pair `(a, a)` with a write;
Rule 2 gives each reference a set and no relation between two references' sets,
so "src and dst are never the same grid" is not expressible. Rejected. Rule 10
clause 3 is not the obstacle here, and clause 2 would add the same comparison
for a by-value argument.

Rewrite and cost: for the permutation pair, test at the call site, which Rule 11
admits as "refinement facts from a dominating branch":

```text
pi = perm[i];  pj = perm[j]
if pi != pj { two_write(&bufs[pi], &bufs[pj]) } else { one_write(&bufs[pi]) }
```

Cost: one compare and one branch per call pair, plus a second body for the
aliased arm, which is free. C++ makes the call with no compare on the strength
of the injectivity it cannot state to the compiler either. For the double
buffer, unroll by two:

```text
for pair in 0..rounds/2 { step(&a, &b); step(&b, &a) }
if rounds % 2 == 1 { step(&a, &b) }
```

Cost: none, and strictly fewer instructions than the C++ pointer swap per
round, with exact disjointness facts where the C++ pointers give the backend
none.

Rules consistent: yes.   Task achievable: rewrite; zero cost for correlated
selection, one compare per pair for data-determined indices.
Depends on: Rule 2, Rule 9, Rule 11, and Rule 13 which reuses this judgment.
Verdict: rejected-real-cost

### 2-11: Do facts proved about a reference's target survive the join?

Question: at a join, are facts attached to the member the edge established them
for, or normalized to concrete paths and then intersected?

Strongest program:

```text
if c { truncate(&v1, 8); w = &v1 } else { truncate(&v2, 8); w = &v2 }
// join: target set { v1, v2 }
for k in 0..8 { bump(&w[k]) }        // every member must satisfy k < len_of(member)
```

Trace: the two clauses meet in Rule 12, "At a join, facts are intersected (a
fact survives only if it holds on every incoming edge); a reference's target
set is the union of its targets (Rule 2)", and in Rule 2, "every check on it
must hold for every member of the set". Reading A normalizes facts to concrete
paths before intersecting: edge 1 carries `len_of(v1) == 8` and edge 2 carries
`len_of(v2) == 8`, the intersection carries neither, and the loop is rejected
because `k < len_of(v2)` is unknown on the member `v2`. Reading B keeps the
pairing an edge established: the member `v1` arrives only on the edge that
proved `len_of(v1) == 8` and the member `v2` only on the other, so joining
member-wise leaves `len_of == 8` for every member and the loop is accepted. The
rule file states the union rule for targets and the intersection rule for
facts, and never says whether a fact belongs to the edge's member or to the
whole joined set. Rule 11's invalidation clause, "A fact that mentions a path is
invalidated when that path is written", does not settle it either, since
neither truncate writes the other buffer.

Rewrite and cost: duplicate the loop into both arms, which works under either
reading and costs nothing. The alternative that does not duplicate is a hoisted
runtime test, `n = len_of(w); if n >= 8 { for k in 0..8 { bump(&w[k]) } }`,
costing one header load and one compare outside the loop, where C++ pays
neither.

Rules consistent: not decidable from the text for this case.   Task
achievable: rewrite, zero cost by duplication.
Depends on: Rule 6 (truncate's ensures), Rule 7, Rule 12.
Verdict: undecided-rule-gap

### 2-12: Validity at a join when one edge destroys the root

Question: what does the join rule do to a reference whose root is consumed on
one incoming edge, and can a reference ever observe a hole?

Strongest program:

```text
b: Box<Node>
p = &(*b).left            // Rule 2 path through Box content
if c { sink(move b) }     // whole-local move on one edge only
use(p)
```

Trace: Rule 3 makes validity a fact, "'p is valid' is a fact like any other",
and on the taken edge `b` is a proper prefix of `(*b).left` that was moved out,
so p is invalid there and valid on the other edge. Rule 12's first clause, "a
fact survives only if it holds on every incoming edge", removes the validity
fact at the join, so `use(p)` is rejected. This is the conservative but correct
outcome: no drop flag and no per-path validity bit exists at runtime, and
Rule 3 says "Validity is re-established only by forming the reference again."

Rule 12's second clause is where this pair is in harmony rather than in
tension: "No place is ever partially moved: every path is either wholly present
or the program cannot name it." Because a reference names a path, and every
nameable path holds a whole value, a reference can never observe a hole; that
is exactly what makes Rule 3's content-write clause safe, and it is why no
occupancy tag is needed for the storage a reference names (Rule 6: "no program
point can observe a slot inside the window as empty"). An adjacent question
that belongs to Rule 8 with Rule 12 rather than to this cell: whether the
conditional whole-local move is itself admitted, given that Rule 8 has the
compiler release affine values at scope exit and the file states no per-path
release discipline and no drop flag.

Rewrite and cost: duplicate the branch, `if c { sink(move b) } else { use(&(*b).left) }`; the reference is formed only where the root survives.
Cost: none, and no runtime flag is introduced, which is what the P8 witness
asks for ("no runtime drop flag; the writer's own branches carry the state").

Rules consistent: yes for the reference side.   Task achievable: rewrite, zero
cost.
Depends on: Rule 3, Rule 5, Rule 8.
Verdict: rejected-zero-cost

### 2-13: par with set-valued and data-indexed references

Question: which parallel shapes survive when the arms' targets are selected by
a condition or by data?

Strongest program:

```text
// scatter: each arm appends to the bucket named by data
par { append(&bufs[owner[0]], x0); append(&bufs[owner[1]], x1) }
// and its loop form: for each element, write out[perm[i]]
```

Ordinary program:

```text
par { kernel(&v[0..mid], &out[0..mid]); kernel(&v[mid..n], &out[mid..n]) }   // accepted
a_ref = if c { &x } else { &y };  b_ref = if c { &y } else { &x }
par { writeK(a_ref); writeK(b_ref) }                                         // rejected
par { s1 = stats(&v); s2 = stats(&v) }                                       // accepted: read/read
par { a = build(&x)?; b = build(&y)? }                                       // accepted: Rule 14
```

Trace: Rule 13, "`par { A; B }` is accepted when A's write paths are disjoint
from B's read and write paths and vice versa, using the same path-overlap and
index/range-disjointness judgment as Rule 10. Read/read overlap is allowed."
In the scatter both arms write under root `bufs` at indices loaded from data,
so Rule 10 clause 1's "indices or ranges proved distinct" is unavailable, and
the general ground - that `owner` is injective - is a quantified fact over
elements, which Rule 11 excludes. Rejected. The scatter loop form is also
outside the families Rule 13 names, "The existing counted-loop forms
(per-element maps, adjacent ranges passed to a helper, admitted reductions)",
since it is neither a same-index map nor an adjacent-range split. In the
ordinary program the adjacent ranges are accepted from the arithmetic of
`0 <= mid <= n` with Rule 7's range requirement, the read/read case is accepted
verbatim, allocation in both arms is accepted by Rule 14 ("Allocation and
release carry no effect entry and never make two parallel arms conflict"), and
the condition-selected pair is rejected for the same reason as cell 2-10: Rule 2
gives each reference a set and no relation between the two sets, so the member
pairs `(x, x)` and `(y, y)` are unrefuted write/write overlaps.

Rewrite and cost, in order of preference:

1. Hoist the condition outside the par: `if c { par { writeK(&x); writeK(&y) } } else { par { writeK(&y); writeK(&x) } }`. Zero cost, full
   parallelism, and a branch the program already had.
2. Invert the scatter into a gather: instead of `out[perm[i]] = f(src[i])`,
   write `out[i] = f(src[inv[i]])` and split the writes into adjacent ranges,
   `par { fill(&out[0..mid], &src, &inv[0..mid]); fill(&out[mid..n], &src, &inv[mid..n]) }`. The writes are then same-index within each range and the
   arbitrary indices appear only in reads, where overlap is allowed. Cost: one
   n-element inverse-permutation array and one O(n) pass to build it whenever
   the permutation changes, and zero when the program already maintains the
   inverse; the memory traffic turns random writes into random reads, which is
   usually equal or better on real hardware.
3. Pairwise runtime tests before the par, `if owner[0] != owner[1] { par ... } else { sequential }`. Cost: k(k-1)/2 compares for k arms and the whole
   fallback arm loses its parallelism whenever any pair collides.
4. A private DynBox per worker plus a merge pass: one extra allocation per
   worker and one O(n) merge, the form the rule file already records as the
   available shape ("Lock-free rings are not expressible; batched fork-join
   with two buffers is the available form").

Versus C++, which runs the scatter directly on the strength of injectivity it
cannot state either, and versus safe Rust, which also cannot express it without
`split_at_mut` gymnastics or unsafe: the WF cost is the inverse permutation, so
one extra array and one extra pass, not the parallelism itself.

Rules consistent: yes; Rule 13 reuses Rule 10's judgment without adding a new
one.   Task achievable: rewrite, at one inversion pass.
Depends on: Rule 7, Rule 10, Rule 11, Rule 14.
Verdict: rejected-real-cost

### 2-14: Allocation under live references

Question: does allocation, which has no effect entry, disturb a live reference
or a parallel arm that holds one?

Strongest program:

```text
p = &a.buf[i]
b = Box::new(Node { ... })?             // Rule 14: allocation has no effect entry
par { q = DynBox::new<Int>(m)?; s = stats_at(p) }
use(p)
r = grow(&a)?                            // declares writes(a.buf); fails and returns Err
use(p)                                   // rejected even on the failure arm
```

Trace: Rule 3's invalidation list is closed over writes, moves, replacements
and frees of a proper prefix of p's path, and an allocation writes no path the
program can name, so p survives it. Rule 14 settles the parallel arm, "Allocation
and release carry no effect entry and never make two parallel arms conflict",
and "Addresses are not observable, so allocator concurrency does not affect
program determinism", so the par block is accepted with a live reference in one
arm. Freeing a value the program can name is not covered by this exemption:
Rule 9 puts it in the row, "`writes` covers writing, replacing, moving out of,
and freeing the storage at the path", so a callee that frees a reachable path
declares it and Rule 3 invalidates references into it. The last two lines are
the conservative edge: a row holds for the whole call, so `writes(a.buf)`
invalidates p on the failure arm as well, even though `grow` wrote nothing
there.

One requirement on the trusted base that the rules imply without stating:
because validity depends only on the program's paths, the allocator may never
relocate a live block. Rule 5 states the adjacent case, "the heap object did not
move" when its Box moves, but the file never states it for the allocator. A
relocating allocator would make Rule 3 unsound rather than ambiguous, so the
only consistent reading is the non-relocating one and I do not treat it as a
gap.

Rewrite and cost: on the failure arm, re-form `p = &a.buf[i]`, one base load and
one shift/add on a cold path; the bound `i < len_of(a.buf)` is needed again and
is either carried as an integer fact or tested once. C++ keeps the pointer.
Negligible and off the hot path.

Rules consistent: yes.   Task achievable: yes.
Depends on: Rule 3, Rule 5, Rule 9, Rule 13.
Verdict: accepted-fine

### 2-15: In-and-out through a reference whose target is a set

Question: does Rule 15's in-and-out form survive a destination that is only
known as a set of paths, and what does "returns owned values only" cost when
the result must land in a place a reference names?

Strongest program:

```text
fn build_into(out: &Matrix, n: u64)  writes(out)     // Rule 15's prescribed in-and-out form
w = if c { &s1.m } else { &s2.m }                     // Rule 2: target set { s1.m, s2.m }
build_into(w, n)                                      // substituted writes({ s1.m, s2.m })
```

Ordinary program:

```text
s1.m = build(n)?                     // move-and-return form of the same task
fn step(p: &T)  writes(p)            // in-place transformer, the callback shape Rule 15 implies
buf[k] = f(buf[k])                   // Rule 6's atomic update: the only read-modify-write over a place
```

Trace: Rule 15 states both halves, "A function returns owned values only" and
"Passing a large value in and back out is expressed as a reference parameter
with a `writes` entry, not as move-and-return." Rule 10 clause 1 compares
effects pairwise at one call, so a row with a single write effect has no
partner and the set-valued target raises no disjointness obligation; Rule 2's
every-member clause is satisfied because every member is a live, writable path
whose validity was established when `w` was bound. Rule 3 then invalidates,
after the call, every other live reference whose path has a proper prefix in
`{ s1.m, s2.m }`, which is the correct conservative outcome on both arms.

Cost: zero, and strictly better than the alternative. The move-and-return form
copies a large aggregate, since the candidate assumes no zero-copy ABI for
aggregate ownership round trips, and the in-out form removes that copy exactly
as a C++ out-parameter or placement construction does.

Where the pair does bite: a result that must land in a place a reference names
and whose type differs from what the place holds cannot be produced in place.
Rule 6's atomic update is the only read-modify-write over a place, it exists
only for a DynBox slot, and it must commit a value of the same type ("the old
value goes into f by value, f's result is committed"). For a struct field the
rewrite is the in-place transformer signature, which is free. For a
type-changing transform the value must become a whole local, moved out at the
top and the new value written back, costing one struct move in and one out
versus C++'s in-place field replacement, or zero when the place is a DynBox
slot and the transform preserves the type.

Rules consistent: yes.   Task achievable: yes, at zero cost for the in-out
form.
Depends on: Rule 2, Rule 3, Rule 6, Rule 10.
Verdict: accepted-fine

### 2-16: A reference into a pool slot, and what a handle names after reuse

Question: what happens to a reference into a pool slot across allocation and
reset, and does a reference formed from a stale handle stay safe?

Strongest program (the P3 graph and the P2 arena, from the caller's side):

```text
struct Arena<T> { buf: DynBox<T> }                    // Rule 16: pool is usage, not a type
id1 = alloc(&a, Node { next: NIL, data: 0 })          // writes(a.buf)
p   = &a.buf[id1]                                      // requires id1 < len_of(a.buf)
id2 = alloc(&a, Node { next: id1, data: 1 })          // writes(a.buf): p is invalid after this
work(p)                                                // rejected
truncate(&a.buf, 0)                                    // P2's release and reuse
id3 = alloc(&a, Node { next: NIL, data: 7 })          // id3 == id1 numerically
q   = &a.buf[id1]                                      // accepted: a valid reference to the new occupant
```

Ordinary program:

```text
set_next(&a.buf[x], id2)                               // writes(a.buf[x]): one call, one effect
set_prev(&a.buf[y], id2)                               // a later call: Rule 10 is per call
r = &a.buf[x];  a.buf[y] = f(a.buf[y])                 // content write at a sibling slot: r stays valid
```

Trace:

- Rule 16 supplies the shape, "A pool is a DynBox plus indices used as handles;
  an arena is a DynBox used with `push_nogrow` as allocation and `truncate(0)`
  as reset", with `alloc` declaring `writes(a.buf)`. This cell depends on that
  provisional rule.
- Rule 2 makes `a.buf[id1]` an ordinary path, "continues through fields, `*`
  (Box content), `[i]` (index, Rule 7)", so a pool slot is reached by exactly
  the same machinery as any other index, and Rule 7 requires
  `id1 < len_of(a.buf)` at every formation.
- Rule 3 is what costs: `a.buf` is a proper prefix of `a.buf[id1]`, and `alloc`
  declares `writes(a.buf)`, so every live reference into the pool is invalidated
  by every allocation, which is what Rule 16's own comment says - "valid until
  `a.buf` is replaced; readable while `id < len_of(a.buf)`". A C++ pool holds a
  raw pointer across an allocation when the block does not move.
- The ordinary program is accepted by Rule 3's content-write clause: a write at
  `a.buf[y]` is not a prefix of `a.buf[x]`, and each of the two link updates is
  a separate call, so Rule 10's pairwise comparison never sees them together.
  Four link writes for an insertion are four calls with one effect each.
- Rule 16's identity clause is the safety-relevant part of the last two lines:
  "A stale index that is still in bounds names the current occupant of that
  slot: a logic error, not a memory error." The reference `q` is well formed,
  points at initialized storage of the right type, and is safe by every rule in
  the candidate; it simply denotes a different node than the writer meant.
  Rule 6 guarantees the slot is not empty ("no program point can observe a slot
  inside the window as empty"), and `truncate` released the old occupant, so
  there is no double release and no dangling address. P2's requirement that a
  reference into released storage be refused afterwards is therefore met only
  while the handle is outside the window.

Rewrite and cost, against a C++ pool of raw pointers:

- Hold handles, not references, across allocations, and re-form the reference
  after each one: one base load plus one shift/add per re-formation, plus the
  bound. The bound is free when the writer binds `n = len_of(a.buf)` before the
  allocation, since `id1 < n` is an integer fact that no write invalidates and
  `alloc`'s `ensures len_of(a.buf) == result + 1` re-derives `id1 < len_of(a.buf)`.
- Per traversal hop, where the next handle comes out of a node field: one bounds
  compare, because "every stored handle is in bounds" is a quantified fact over
  elements and Rule 11 excludes it. This is the same compare priced in cell
  15-16 and it is the dominant cost of the pool rendering.
- Where the program must detect reuse, one generation word per slot and one
  compare per dereference, which a generational C++ or Rust arena pays too.

Rules consistent: yes, given Rule 16; the stale handle is a logic error by that
rule's own statement and breaks no memory or type rule.
Task achievable: rewrite - the pool, its references and its reuse all work,
with the identity guarantee P2 asks for replaced by an explicit generation
word.
Depends on: Rule 16 (provisional pool rule), Rule 3, Rule 6, Rule 7, Rule 10,
Rule 11.
Verdict: rejected-real-cost

### 15-15: Composing owned returns: chains, recursion, and selecting one of two large values

Question: what does "returns owned values only" cost when owned returns feed
owned returns - through a selection, through a call chain, and through
recursion?

Strongest program:

```text
// C++ would write Big& choose(Big& a, Big& b, bool c)
fn choose(a: own Big, b: own Big, c: Bool) -> own Big
{ if c { return move a } else { return move b } }     // both consumed, the loser released
```

Ordinary program:

```text
fn a_into(out: &Big)  writes(out) { b_into(out) }     // one destination threaded down the chain
fn rewrite(t: own Tree) -> own Tree                    // Tree rooted in a Box: pointer-sized return
fn f(out: &Big) -> u64  writes(out)                    // large part out by reference, small part returned
```

Trace: Rule 15, "A function returns owned values only", with Rule 4, a
reference "cannot be returned". So a selection that C++ expresses as a returned
reference must consume both candidates and return one; the other is released by
Rule 8 as an affine value, and the return moves a large inline aggregate.
Rejected as written, in the sense that the zero-copy C++ shape is unavailable.
The composition cases are accepted: Rule 15's in-out form chains, because
`out` is a reference parameter that may be passed on as a call argument
(Rule 4: a reference "may be bound to a local, passed as a call argument"), and
recursion composes because each frame returns owned data and Rule 10 checks
recursion "through contracts, never by unfolding bodies".

Rewrite and cost:

1. Put the candidates in one indexable place and return the position, which is
   Rule 4's and Rule 15's own prescription: `fn choose_at(v: &DynBox<Big>, c: Bool) -> u64  reads(v)  contract { ensures result < len_of(v); }`, then
   `p = &v[k]` at the caller. Zero copies; one shift/add at the caller that the
   C++ callee performed anyway before returning its pointer.
2. Thread one destination through the chain with `writes(out)`, so no level
   copies; this matches C++'s out-parameter chain and beats a return that the
   ABI does not elide.
3. If the selected value must afterwards be moved out, Rule 6's admitted moves
   apply: `swap_remove` from a DynBox is one element move, the same move C++
   pays for swap-and-pop_back; from two separate locals, duplicate the branch
   and `move` the whole local in each arm, which is the same copy C++ performs
   when NRVO fails on a conditional return.
4. A Box-rooted tree makes every recursive `own Tree` return pointer-sized, so
   the recursive tree-transformation task carries no copy cost; an inline
   `array<T, N>` payload returned through k frames copies k times unless the
   writer uses form 2, and switching to form 2 is free.

The only shape with no zero-cost rewrite is selection behind an abstraction
boundary where the candidates cannot share a container: the callback inversion,
`with_chosen(&a, &b, c, f)` with `f` a function-typed parameter (Rule 10), costs
one indirect call per selection unless it is inlined, and the rule file promises
no specialization. Putting the candidates in one container removes that, so it
is a layout choice, not a runtime cost.

Rules consistent: yes.   Task achievable: rewrite, zero cost.
Depends on: Rule 4, Rule 6, Rule 8, Rule 10.
Verdict: rejected-zero-cost

### 15-16: Owned returns as pool handles

Question: does "positions come back as indices with a bounds relation" compose
with the pool-as-usage rule well enough to build and traverse a mutable graph
at C++ cost?

Strongest program (the P3 graph and the P2/P18 arena, built recursively):

```text
struct Arena<T> { buf: DynBox<T> }
struct Node { left: u64, right: u64, data: u64 }      // handles, never references (Rule 1)

fn alloc<T>(a: &Arena<T>, x: own T) -> u64   writes(a.buf)
    contract { requires len_of(a.buf) < cap_of(a.buf);
               ensures result == len_of(deref(entry(a.buf)));
               ensures len_of(a.buf) == result + 1; }

fn build(a: &Arena<Node>, d: u64) -> Result<u64, Full>   writes(a.buf)
    contract { ensures when Ok: result < len_of(a.buf); }
{
    if d == 0 { return Ok(leaf(a)?) }
    l = build(a, d - 1)?
    n = len_of(a.buf)                                  // bind the measure as data
    r = build(a, d - 1)?
    if len_of(a.buf) < cap_of(a.buf) {
        return Ok(alloc(a, Node { left: l, right: r, data: 0 }))
    }
    return Err(Full)
}

// traversal at the caller: the caller forms every reference itself (Rule 4)
h = root
while h != NIL {
    if h < len_of(a.buf) { p = &a.buf[h]; work(p); h = (*p).left } else { break }
}
```

Trace, in order:

- Rule 15 and Rule 4 fix the interface: "Positions found by a search are
  returned as indices with a bounds relation in `ensures` (Rule 4)", so `build`
  and `alloc` return `u64` and the caller forms `&a.buf[h]`. The one address
  computation the caller pays is the one the C++ callee performed before
  returning its pointer.
- Rule 16 supplies the pool itself, "A pool is a DynBox plus indices used as
  handles; an arena is a DynBox used with `push_nogrow` as allocation and
  `truncate(0)` as reset", and its `alloc` contract above is quoted from that
  rule. This cell therefore depends on the provisional rule.
- Rule 10's recursion clause, "Recursion is checked through contracts, never by
  unfolding bodies", means `alloc`'s `requires len_of(a.buf) < cap_of(a.buf)`
  must be re-proved at each allocation site. After two recursive `build` calls
  the only facts about `a.buf` are `build`'s own `ensures`, which does not bound
  a subtree's growth; the natural precondition would be
  `len_of(a.buf) + 2^d <= cap_of(a.buf)`, and Rule 11 admits only "affine
  comparisons over measures and integer values", so it is not statable. The
  writer therefore tests capacity before each allocation - which is exactly what
  a C++ bump allocator does - and returns a typed failure, which Rule 14
  requires of allocation anyway ("Allocation returns a `Result` and never
  traps"). Zero cost.
- Rule 11's invalidation, "A fact that mentions a path is invalidated when that
  path is written ... unless the callee's `ensures` re-establishes it", kills
  `l < len_of(a.buf)` at the next allocation. Recovering it is free if the
  writer binds the measure as data first: `n = len_of(a.buf)` gives the integer
  fact `l < n`, which mentions no path and so survives, and `alloc`'s
  `ensures len_of(a.buf) == result + 1` with `result == n` re-derives
  `l < len_of(a.buf)`. The `len_of` read is a header load the program has just
  written, so it folds.
- Rule 3 costs one re-formation per allocation: `alloc` declares
  `writes(a.buf)`, `a.buf` is a proper prefix of `a.buf[h]`, so every live
  reference into the pool dies at each allocation and the traversal re-forms
  `&a.buf[h]` afterwards - one base load plus one shift/add, where a C++
  pointer graph holds its pointer across an allocation.
- Rule 16's identity statement is where the P2 requirement is not met: "A stale
  index that is still in bounds names the current occupant of that slot: a
  logic error, not a memory error." After `truncate(&a.buf, 0)` the bounds
  facts die with the write, so a stale handle is refused while it is outside the
  window, but once new allocations pass it again the same handle silently names
  a new occupant. This is memory-safe and type-safe; it is the identity
  guarantee that is weaker, and P2's "every old pointer into b2 must be refused
  afterwards" is not delivered by handles alone.

Rewrite and cost, against a C++ pointer graph:

- Per traversal hop: one shift/add on a base that hoists while no allocation
  intervenes, plus one bounds compare, because the next handle comes out of a
  node field and "every stored handle is in bounds" is a quantified fact over
  elements that Rule 11 excludes. This is the P3 witness's "the invariant
  next/prev point to live nodes is stated once and reused", and it cannot be
  stated once here. The power-of-two trick `h & (cap - 1)`, which would replace
  the compare with one AND and no branch, is not an affine comparison, so the
  quoted fact language does not admit it.
- Per allocation: one capacity compare, which C++ pays too; plus one reference
  re-formation for any traversal in flight.
- Per identity check, only where the program needs to detect reuse: one
  generation word per slot and one compare per dereference - the same price a
  generational C++ or Rust arena pays, and nothing where detection is not
  wanted.
- Parallel node-data work stays available in the admitted shapes: adjacent
  ranges `par { map(&a.buf[0..mid]); map(&a.buf[mid..len]) }` are accepted by
  Rule 13, while a parallel map that follows handles is the scatter case of cell
  2-13.

Rules consistent: yes, given Rule 16; the residual cost comes from Rule 11's
exclusion of quantified facts, not from Rule 15 or Rule 16.
Task achievable: rewrite - the graph is built, traversed and reset with owned
handles, with weaker identity than P2 asks for.
Depends on: Rule 16 (provisional pool rule), Rule 1, Rule 3, Rule 4, Rule 6,
Rule 10, Rule 11, Rule 13, Rule 14.
Verdict: rejected-real-cost

## Summary of this sheet

- Decided and free: 2-3, 2-5, 2-12, 15-15 (rejections with zero-cost
  duplication or index rewrites), 2-14 and 2-15 (accepted as written).
- Decided with a real runtime cost: 2-6 (one compare and one address
  recomputation per re-form after any window operation), 2-10 (one compare per
  call-site pair on data-determined indices), 2-13 (an inverse-permutation array
  and pass to turn a scatter into a gather), 15-16 (one bounds compare per
  traversal hop).
- Undecided under the frozen text: 2-2 (unbounded loop-carried target set),
  2-4 (a captured reference has no declarable effect), 2-7 (whether a path's
  index is a snapshot), 2-8 (no admitted operation takes a linear value out of a
  Box), 2-9 (Rule 9's `&buf[len_of(buf)]` example against Rule 7's formation
  requirement), 2-11 (whether a fact at a join belongs to the edge's member).
- The recurring source of real cost in row 2 is not Rule 2 itself. Rule 2's
  target sets cost nothing that duplicating a branch does not remove. The cost
  comes from Rule 11's exclusion of quantified facts over elements, which makes
  every data-determined index pay a compare, and from Rule 9's ban on index
  expressions in signatures, which forces container-wide write effects.
