# Interaction matrix under candidate x1: rows 7 and 10

Derived against `CANDIDATE-X1.md` (frozen 2026-09-18). Rule 7 is what may be
indexed, the obligation to prove every index in bounds, and range references.
Rule 10 is the call-site rule: pairwise comparison of substituted effects,
by-value consumption, bystander invalidation, and function-typed parameters that
carry their own row. Cells follow the rule file's "Protocol for a derivation
cell". Only runtime performance counts as a cost; verbosity, extra parameters and

## Row 7 - indexable things, proved bounds, range references

### 7-7: Indexing on top of indexing: nested containers, ranges of ranges, recursive subdivision

Question: does the bounds obligation compose when an index feeds another index,
when a range reference is subdivided again, and when the subdivision recurses?

Strongest program:
```text
// ragged two-level data, both levels data-determined, plus recursive subdivision
vv: DynBox<DynBox<f64>>              // rows of different runtime lengths

fn row_work(row: &DynBox<f64>)  writes(row)
{
    n = len_of(row)
    if n > 1 {
        mid = n / 2
        par { row_work(&row[0..mid]); row_work(&row[mid..n]) }   // range of a range, recursively
    } else if n == 1 {
        row[0] = kern(row[0])
    }
}

for i in 0..len_of(vv) {
    m = len_of(vv[i])                 // a measure of an indexed path
    for j in 0..m {
        vv[i][j] = kern(vv[i][j])     // two proofs per element: i < len_of(vv), j < len_of(vv[i])
    }
    row_work(&vv[i])
}
```

Ordinary program (differs materially: one fixed level, constant bound):
```text
a: array<Int, 8>
for i in 0..8 { a[i] = a[i] + 1 }     // i < 8 from the counted loop
b: Box<array<Int, 8>>
(*b)[i]                                // Rule 7: "indexed through the path `(*b)[i]` and is not a separate case"
```

Trace:
- Rule 7 enumerates the indexable things: "Indexable things: an inline
  `array<T, N>` (constant length, always fully initialized), a `DynBox<T>`
  (Rule 6), a range reference into either, and a `const` table." `vv` is a
  `DynBox`, `vv[i]` is a `DynBox`, so both levels are indexable. Rule 1 permits
  the nesting because a `DynBox<DynBox<f64>>` holds only owned values.
- Outer index: Rule 7, "Every index must be proved in bounds". `i < len_of(vv)`
  comes from the counted loop `for i in 0..len_of(vv)` as a refinement fact of a
  dominating construct (Rule 11, "refinement facts from a dominating branch").
- Inner index: the needed fact is `j < len_of(vv[i])`. `m = len_of(vv[i])` is a
  measure applied to the path `vv[i]`; Rule 11 admits "affine comparisons over
  measures and integer values" and does not restrict the argument of a measure to
  a root. `j < m` and `m == len_of(vv[i])` give the fact.
- The write `vv[i][j] = kern(vv[i][j])` is Rule 6's atomic in-place update at a
  path below `vv[i]`. It does not disturb `m`: Rule 11 invalidates a fact only
  "when that path is written", and the path written is `vv[i][j]`, not `vv[i]`.
  A window operation on `vv[i]` would be `writes(vv[i])` and would kill `m`; none
  occurs. So the row length is loaded once per row, exactly as in C++.
- Range of a range: Rule 2's path grammar is recursive - a path "continues
  through fields, `*` (Box content), `[i]` (index, Rule 7), or `[lo..hi]` (range,
  Rule 7)" - so `&row[0..mid]` where `row` already names `vv[i][lo..hi]` is a
  path. Rule 7 supplies the arithmetic at each level: "requires lo <= hi <=
  len_of(buf); len_of(part) == hi - lo", so `len_of(row[0..mid]) == mid` and the
  recursive call's own `len_of(row)` is again affine in the parent's.
- Recursion: Rule 10's closing clause, "Recursion is checked through contracts,
  never by unfolding bodies", so `row_work` is checked once against
  `writes(row)`; the recursive calls substitute `row[0..mid]` and `row[mid..n]`
  into that row.
- Disjointness of the two arms is Rule 13 with "the same path-overlap and
  index/range-disjointness judgment as Rule 10", i.e. Rule 10 clause 1's "indices
  or ranges proved distinct". Here both subranges share the prefix `row`, and
  `0 <= mid` and `mid <= n` are in scope, so adjacency decides them. No
  flattening across levels is needed because the siblings are compared under the
  same parent.
- One gap appears only for a comparison across levels. Rule 10 clause 1 gives no
  rule for normalizing a nested range path such as `vv[i][lo..hi][a..b]` against
  a reference formed directly as `&vv[i][c..d]`; the affine flattening
  `lo+a .. lo+b` is obvious but unwritten. Nothing in the program above needs it.

Rewrite and cost: none needed. Per row: one load of `len_of(vv[i])`, which C++
also performs for a `vector<vector<double>>`. Per element: no test, because both
bounds are loop facts. The recursion pays the same call overhead as the C++
divide-and-conquer form.

Rules consistent: yes - the path grammar, the measure vocabulary and the range
arithmetic compose at every level without extra rules.
Task achievable: yes - ragged two-level iteration and recursive range
subdivision are expressible at C++ cost.
Depends on: Rule 1, Rule 2, Rule 6, Rule 10, Rule 11, Rule 13.
Verdict: accepted-fine

### 7-8: Proving a bound in order to consume: indexed access to affine and linear elements

Question: can an element selected by a runtime index be consumed, when the
element type is affine, and when it is linear?

Strongest program:
```text
// a pool of linear resources with stable handles: closing one must not move the others
linear type File;  fn close(f: own File)
pool: DynBox<Option<File>>            // slot k stays slot k forever
k = pick(...)                          // data-determined

fn close_it(x: own Option<File>) -> own Option<File>
{ match x { Some(f) => { close(move f); None }   None => None } }

if k < len_of(pool) { pool[k] = close_it(pool[k]) }     // atomic update consumes the old value
...
// scope exit: every slot now holds None. What discharges those values?
```

Ordinary program (differs materially: drain order is free, no holes):
```text
files: DynBox<File>
while len_of(files) > 0 { close(pop(&files)) }          // len_of(files) > 0 is the loop condition
// or, removing one element chosen at runtime, order irrelevant:
if k < len_of(files) { close(swap_remove(&files, k)) }
```

Trace:
- The bound is Rule 7: "Reading `buf[k]` or forming `&buf[k]` requires the fact
  `k < len_of(buf)`", discharged by the dominating test, which Rule 7 describes as
  "the test establishes the fact; one compare, no trap".
- Consuming the element cannot be a move out of the slot: Rule 6, "There is no
  `take` operation and no partial move out of any place: the only ways to move a
  value out of storage are consuming a whole local (`move x`), the window
  operations, and the atomic update." `pool[k]` is none of the first two, so the
  atomic update is the only form, and Rule 6 says so directly for linear
  elements: "where it is linear the assignment is rejected unless written as the
  atomic update whose function consumes the old value". `close_it` consumes it.
  The ordinary program uses the window operations `pop` and `swap_remove`
  instead, whose `requires` clauses are the same bound facts.
- So far so good. The gap is what `None` is. Rule 8 says "Linearity is declared
  on external-resource types and propagates through aggregates: a struct, array,
  Box, or DynBox containing a linear part is linear." Enums and tuples are absent
  from that list, while Rule 1, listing the same kinds of aggregate, writes
  "Every struct, enum, tuple, array, slice-like value, Box, DynBox, and generic
  instantiation" and explicitly closes over "variant payload". The omission
  decides this cell and cuts both ways:
  - If the Rule 8 list is exhaustive, `Option<File>` is not linear. Then
    `x: Option<File>` holding `Some(f)` may be dropped without closing `f`, and
    linearity is escapable by wrapping any linear value in a one-variant enum.
    That is the accepted-unsafe branch, and it is not a corner: Rule 12 recommends
    exactly this representation - "slots: DynBox<Option<Entry>> // non-Copy
    payloads: Option, using a null niche where the type has one".
  - If `Option<File>` is linear by containment, then every `None` is a linear
    value, and Rule 8 requires that "Linear values must be consumed by an explicit
    operation on every exit path; the compiler never releases them." No rule
    supplies an operation that consumes a linear-typed value whose linear part is
    absent. Rule 6's instruction for the container, "A DynBox whose element type
    is linear is itself linear (Rule 8) and must be truncated to zero by the
    program before it can go out of scope", does not help: `truncate` is defined
    only by `requires n <= len_of(buf); ensures len_of(buf) == n`, and the rule
    never says what happens to the slots it drops. If `truncate` releases them,
    it releases linear values and contradicts Rule 8; if it rejects linear
    elements, the sentence quoted above demands an impossible step.
- The ordinary program escapes both horns because nothing is ever `None`: every
  element is a bare `File` and every consumption is a window operation that
  removes the slot. It is accepted, and its cost is exactly the C++ loop.

Rewrite and cost: for drain or stack discipline, the ordinary program - zero cost
versus `while (!v.empty()) close(v.pop_back())`. For the stable-handle pool there
is no rewrite that keeps slot identity: `swap_remove` relocates the last element
into slot `k`, so every other handle held by the program silently changes meaning,
which is the identity failure P2 and P3 forbid. The only identity-preserving
rewrite is a parallel `DynBox<u8>` of liveness bytes plus a `DynBox<File>` whose
dead slots still hold real `File` values - i.e. resources that are kept open
because there is no representable hole - which does not implement the task at
all.

Rules consistent: no - Rule 8's propagation list omits enums, and either reading
(enum escapes linearity, or `None` is an undischargeable linear value)
contradicts another rule.   Task achievable: undecided - drain works today;
stable-handle linear pools wait on this ruling.
Depends on: Rule 1, Rule 6, Rule 8, Rule 12.
Verdict: undecided-rule-gap

### 7-9: Effects on reference parameters versus indices: where the index is evaluated

Question: can a callee's effect row describe an access at an index, and if not,
does hoisting the index to the call site cost anything?

Strongest program:
```text
// a stencil arm that reads the whole column and writes one slot of the output,
// with the written index chosen by the caller and the read span by the callee
fn step(all: &DynBox<f64>, out: &f64)  reads(all), writes(out)

par { step(&v, &out[i]); step(&v, &out[j]) }          // needs i != j, nothing else

// the form the rule appears to forbid:
fn step_i(all: &DynBox<f64>, out: &DynBox<f64>, i: u64)  reads(all), writes(out[i])
```

Trace:
- Rule 9's first sentence permits an index in a row: "An effect row lists
  `reads(path)` and `writes(path)` where each path starts at a reference
  parameter and may continue through fields, `*`, and whole-index or range
  positions supplied as arguments." Its last sentence appears to forbid it:
  "Signatures never contain index expressions; an index enters an effect only
  through an argument, evaluated once at the call", and the worked example ends
  "// the argument fixes the slot at the call; the row itself names no index".
  The reconciling reading is that `writes(out[i])` with `i` a parameter is a
  "whole-index position supplied as an argument" while `writes(out[i+1])` or
  `writes(out[len_of(out)])` is an index expression. The text does not settle it.
- The ambiguity does not decide the cell, because the slot-reference form is
  always available and is the form Rule 9 itself demonstrates:
  `put_at(&buf[len_of(buf)], 3)`. Substituting `&out[i]` for `out` turns
  `writes(out)` into `writes(out[i])` at the call, which is what Rule 10 clause 1
  then compares. The address is computed once at the call, which Rule 9 states as
  "evaluated once at the call".
- Rule 13 then admits the `par` block: `writes(out[i])` versus `writes(out[j])`
  needs "indices or ranges proved distinct", and `reads(v)` versus `reads(v)` is
  read/read, which Rule 13 allows explicitly.
- The only price of the slot form is that the callee can no longer compute the
  index itself. When it must - a scatter whose targets come from data - the row
  collapses to `writes(dst)` over the whole container, and Rule 10 clause 3 then
  invalidates every outside reference into `dst`, and Rule 13 rejects any sibling
  arm touching `dst`. The caller's remedy is to hand the callee a range it may
  own outright: `scatter(&dst[0..mid], ...)`, which costs one add per call.
- Rule 9's body check, "every statement's effect and every callee's substituted
  row must be covered by the declared row", is what forces a callee that touches
  a container-wide path to say so, and is why a slot-level row cannot hide a
  container-level write.

Rewrite and cost: hoist the index into a slot or range reference argument. Cost
against C++ passing `double* out_i` or `out + lo`: none - the same address
arithmetic, folded into the callee's addressing modes, and no runtime test,
because the bound was proved where the reference was formed.

Rules consistent: yes for the derivation, with one unresolved question of form
(whether `writes(out[i])` may be written in a signature) that changes no
acceptance and no cost.   Task achievable: yes - slot and range arguments express
every effect shape the row cannot name.
Depends on: Rule 2, Rule 10, Rule 13.
Verdict: accepted-fine

### 7-10: Two indexed arguments to one call: proving distinctness

Question: can a call take two references into the same container when at least
one is written, and what does the proof of distinctness cost when the indices come
from data?

Strongest program:
```text
// apply a permutation in place; the element type is affine, so no copy exists
v:    DynBox<Box<Node>>
perm: DynBox<u64>                      // data; contents unknown to the compiler

fn swap_slots(a: &Box<Node>, b: &Box<Node>)  writes(a), writes(b)

for i in 0..len_of(v) {
    j = perm[i]                        // needs i < len_of(perm); a runtime value
    swap_slots(&v[i], &v[j])           // rejected: writes(v[i]) and writes(v[j]) overlap unprovably
}
```

Ordinary program (differs materially: the order relation is a loop fact):
```text
lo = 0; hi = len_of(v) - 1
while lo < hi {
    swap_slots(&v[lo], &v[hi])         // accepted: lo < hi proves the indices distinct
    lo = lo + 1; hi = hi - 1
}
```

Trace:
- Both references are formed under Rule 7's obligation; `i < len_of(v)` is the
  loop fact and `j < len_of(v)` must be tested, since `perm[i]` is data and Rule
  11 rules out a fact about what the array contains (7-11).
- Rule 10 clause 1 governs the call: "Compare the substituted effects pairwise.
  Two effects on overlapping paths where at least one is a write must be proved
  disjoint (different roots, or indices or ranges proved distinct); otherwise the
  call is rejected." The substituted row is `writes(v[i]), writes(v[j])`; the
  paths share the root `v`, both are writes, and `i != j` is not derivable from
  anything - it is a property of the permutation data. Rejected. Rule 10's own
  example states the same requirement: "two(&v[i], &v[j]) // accepted only with
  the fact i != j".
- In the ordinary program the dominating loop condition `lo < hi` is a refinement
  fact under Rule 11 and settles distinctness, so the two-pointer partition, the
  heap sift, and every reversal loop are accepted verbatim.
- Rule 10 clause 2 matters when one side is by value: `swap_in(&v[i], move x)`
  contributes "a consumption (`move`) or a read (copy) of its place" for `x`, so
  passing an element of the same container by value - `swap_in(&v[i], move
  v_local)` - is compared against `writes(v[i])` on its own place, not on `v`.
- For a Copy element type the call is not needed at all: `t = v[i]; v[i] = v[j];
  v[j] = t` is three statements, each with a single effect, and Rule 10's pairwise
  comparison never runs. For an affine element type this rewrite is unavailable -
  Rule 6: "no partial move out of any place" - so the two-reference call is the
  only shape.

Rewrite and cost: guard the call with the missing fact, and make the equal case a
no-op, which is semantically what a self-swap is:
```text
if i < j { swap_slots(&v[i], &v[j]) } else if j < i { swap_slots(&v[j], &v[i]) }
// the third arm, i == j, does nothing
```
Cost against `std::swap(v[i], v[perm[i]])` on `vector<unique_ptr<Node>>`: one
compare and one unpredictable branch per swap, on top of the three pointer moves
the C++ form performs. Safe Rust pays the same compare if it uses
`slice::swap`'s index form - `swap` there takes indices precisely to avoid the
two-borrow problem - so the delta is against C++ only. There is no cheaper
rewrite: building a permuted copy costs an allocation plus `n` extra moves, and
the atomic-update form needs an `Option` hole per element (7-8).

Rules consistent: yes - the rejection is exactly the aliasing question C++ leaves
to the programmer.   Task achievable: rewrite - one compare and branch per swap
of non-Copy elements; zero cost for Copy elements and for every loop whose
indices carry an order relation.
Depends on: Rule 6, Rule 7, Rule 11.
Verdict: rejected-real-cost

### 7-11: Bounds facts against the fact vocabulary: what cannot be said about data

Question: when an index is read out of memory, can any fact discharge its bound,
or must every such access test?

Strongest program:
```text
// gather: the canonical case where static analysis provably cannot help
src: DynBox<f64>;  idx: DynBox<u64>;  dst: DynBox<f64>
for t in 0..len_of(idx) {
    dst[t] = src[idx[t]]               // needs idx[t] < len_of(src): a property of the contents of idx
}
```

Ordinary program (differs materially: the index is produced by arithmetic the
writer controls):
```text
// open-addressing probe; Rule 12's representation, masked start, linear probing
m = len_of(tags)                       // power of two
i = hash(key) & (m - 1)
if i < m {                             // the mask does not prove it; one test per lookup
    loop {
        if tags[i] == EMPTY { break }
        if slots[i].key == key { return Some(i) }
        i = i + 1
        if i == m { i = 0 }            // i < m carried affinely from here on
    }
}
```

Trace:
- Rule 7: "Every index must be proved in bounds; when the proof is unavailable
  the program tests the measure, which is ordinary data."
- Rule 11 fixes what a proof may be: "Facts are the existing WF forms: affine
  comparisons over measures and integer values, refinement facts from a
  dominating branch, loop-header invariants ..., explicit `use` steps inside an
  `invariant`, and callee contracts", and then closes the only door that would
  serve the gather: "There are no quantified facts over array elements ("for all
  i ...") and no per-slot occupancy facts; occupancy that is determined by data
  is stored as data".
- So no invariant can say "every entry of `idx` is below `len_of(src)`", and no
  validating pre-pass can hand its conclusion to the consuming loop: the
  conclusion it would have to carry is precisely the forbidden quantified fact.
  A cheap summary does not rescue it either - `max_idx < len_of(src)` is a legal
  affine fact, but `idx[t] <= max_idx` is again a fact about an element.
- Therefore the loop body is rejected as written, and the accepted form is the
  test, one per gathered element.
- The ordinary program shows where the boundary sits. `i = hash(key) & (m-1)` is
  not an affine expression, so Rule 11 gives no fact from the mask and the lookup
  pays one test. But once inside the loop, `i = i + 1` with the dominating `i < m`
  and the wrap `if i == m { i = 0 }` are affine, so the probe sequence itself
  proves its own bound and no test appears in the probe loop. The remaining cost
  is the one the candidate already records: "Open-addressing hash tables with
  non-Copy payloads pay one null check per hit versus hashbrown".
- Rule 11 gives no rule for a saturating form either: whether `j = min(idx[t],
  len_of(src) - 1)` establishes `j < len_of(src)` depends on whether `min` is a
  modelled affine operation, which the fact vocabulary does not say.

Rewrite and cost:
```text
n = len_of(src)
for t in 0..len_of(idx) {
    j = idx[t]
    if j < n { dst[t] = src[j] } else { dst[t] = 0.0 }   // the writer chooses the out-of-range value
}
```
Cost against the C++ gather: one compare plus one branch per element. The branch
is data-dependent, so on an unsanitized input it also mispredicts; when the
compiler turns it into a select the cost is one extra ALU operation per element
and a second load address, which on a memory-bound gather is small but on a
cache-resident gather is measurable. Against safe Rust the delta is zero - `src[j]`
there compiles to the same compare - and against C++ with `-fsanitize=bounds` it
is also zero. The else arm is extra source, which is not a cost, but it does
change behaviour where C++ has undefined behaviour.

Rules consistent: yes - Rule 7 demands a proof and Rule 11 declines to invent one;
the two agree that the answer lives in data.
Task achievable: rewrite - every data-sourced index costs one test at its use.
Depends on: Rule 6, Rule 7, Rule 12.
Verdict: rejected-real-cost

### 7-12: Bounds facts and joins: what survives a merge, and what a multi-target reference means

Question: does a proved bound survive a control-flow join, and what does
`len_of(p)` mean when `p` may name either of two containers?

Strongest program:
```text
// one loop body serving two pools of different length, chosen once per call
small: DynBox<Entry>;  large: DynBox<Entry>
pool = if c { &small } else { &large }        // Rule 2: target set {small, large}
k = pick(...)                                  // data-determined

if k < len_of(pool) {                          // one runtime load of the measure of whichever pool
    work(&pool[k])
}

// and: a bound established on one edge only
if k < len_of(small) { use(&small[k]) } else { report() }
...
use(&small[k])                                 // rejected here: the fact did not survive the join
```

Trace:
- The second half is decided by Rule 12: "At a join, facts are intersected (a
  fact survives only if it holds on every incoming edge)". `k < len_of(small)`
  holds on the then-edge and not on the else-edge, so it is gone after the join
  and Rule 7's obligation is unmet at the later use.
- The positive direction of the same rule is what makes ordinary code work. Rule
  12's own example, "if cond { push_nogrow(&buf, x) } // after the join:
  len_of(buf) >= n ... facts about indices below n survive", means a conditional
  growth does not cost the loop its bounds. Likewise, when both edges assign a
  different index that each proved in bounds, `k < len_of(buf)` holds on both
  edges and survives, so the common `k = if c { i } else { j }` shape needs no
  re-test.
- The first half turns on Rule 2: "At a control-flow join, a reference variable's
  target is the set of paths it may name; every check on it must hold for every
  member of the set." Applied to the runtime test `k < len_of(pool)`, this reads
  two ways. Operationally the test loads the measure of the pool actually named
  and establishes what the following index needs. Read strictly, the check on
  `pool` must hold for every member, i.e. the program would need `k <
  len_of(small)` and `k < len_of(large)`, which the single test does not give.
  The rule does not say whether a runtime test on a multi-target reference
  discharges the obligation for the target actually named.
- That ambiguity is not decisive, because the rewrite that avoids multi-target
  references entirely is free (below), and the rest of the cell is settled.
- Rule 3 combines with Rule 12 cleanly in the other direction: validity "is a
  fact like any other", so a reference invalidated on one incoming edge is
  invalid after the join, with no rule of its own required.

Rewrite and cost: hoist the test so it dominates every use, or duplicate the
body per arm so no reference has two targets:
```text
if c { if k < len_of(small) { work(&small[k]) } }
else  { if k < len_of(large) { work(&large[k]) } }
```
Cost against the C++ form that keeps one `Pool* pool`: zero. The branch on `c`
already existed; moving the uses inside it removes an indirection rather than
adding one, and the duplicated body is source, which the criteria exclude from
cost. Where the selection is per element rather than per phase, the duplication
happens inside the loop and the branch is the same branch C++ executes.

Rules consistent: yes, with one unwritten case (what a runtime measure test on a
multi-target reference proves).   Task achievable: rewrite - hoisting or
duplicating costs nothing at runtime.
Depends on: Rule 2, Rule 3, Rule 7, Rule 11.
Verdict: rejected-zero-cost

### 7-13: Ranges and `par`: which parallel shapes the bounds discipline admits

Question: which parallel decompositions does the range-reference form express,
and what happens when the output index is computed from data?

Strongest program:
```text
// parallel histogram / bucket scatter: the destination index is data
keys: DynBox<u32>;  hist: DynBox<u32>          // B buckets, B large
par {
    for t in 0..mid        { b = bucket(keys[t]); hist[b] = hist[b] + 1 }
    for t in mid..len_keys { b = bucket(keys[t]); hist[b] = hist[b] + 1 }
}
```

Ordinary program (differs materially: the decomposition is arithmetic):
```text
// P5 struct-of-arrays kernel, and P6 adjacent ranges
struct Cols { a: DynBox<u64>, b: DynBox<u64>, c: DynBox<u64>, d: DynBox<u64> }
fn kern(a: &DynBox<u64>, b: &DynBox<u64>, c: &DynBox<u64>)  writes(a), reads(b), reads(c)

par { kern(&s.a[0..mid], &s.c[0..mid], &s.d[0..mid])
      kern(&s.a[mid..n], &s.c[mid..n], &s.d[mid..n]) }
```

Trace:
- Rule 13's acceptance test is "`par { A; B }` is accepted when A's write paths
  are disjoint from B's read and write paths and vice versa, using the same
  path-overlap and index/range-disjointness judgment as Rule 10. Read/read
  overlap is allowed."
- The ordinary program passes twice over. Within an arm the four columns are
  distinct fields, and Rule 10 clause 1's own example settles that shape:
  "two(&a.x, &a.y) // accepted: distinct fields", so no runtime alias guard and
  no runtime disambiguation is needed - this is P5's requirement, and it is met
  better than by a C++ compiler, which must either guard or be told with
  `__restrict`. Across arms the ranges `[0..mid]` and `[mid..n]` are adjacent,
  which Rule 13 states as an admitted shape: "par { kernel(&v[0..mid],
  &out[0..mid]); kernel(&v[mid..n], &out[mid..n]) } // disjoint ranges:
  accepted".
- P6's runtime worker count is the counted-loop form Rule 13 names: "The existing
  counted-loop forms (per-element maps, adjacent ranges passed to a helper,
  admitted reductions) are expressed with range references." A `k`-way split with
  `k` a runtime value is also reachable without that family, by recursive halving
  - the `par` in 7-7's `row_work` - at log-depth call overhead.
- P15's reductions land in the same admitted table; the candidate keeps the
  restriction, "admitted reductions", so a wrapping or bitwise or min/max
  recombination is accepted and a floating-point sum is not, exactly as PROGRAMS
  records.
- The strongest program fails clause 1. Both arms' write paths are `hist[b]` with
  `b` computed by `bucket(keys[t])` inside the arm. Rule 10 clause 1 demands
  "indices or ranges proved distinct"; `b` is data, and Rule 11 forbids the fact
  that would separate the two key spans' bucket sets ("There are no quantified
  facts over array elements"). Rejected, correctly - this is a genuine race.
- There is no atomic escape: "channels or atomics" are listed under "Not in this
  candidate", so the C++ answer of a relaxed atomic increment per element is not
  available at any price.

Rewrite and cost: privatize and merge.
```text
h0 = DynBox::filled(B, 0u32)?;  h1 = DynBox::filled(B, 0u32)?
par { count(&keys[0..mid], &h0);  count(&keys[mid..n], &h1) }
for b in 0..B { hist[b] = h0[b] + h1[b] }
```
Cost against the C++ atomic-increment form: `k` private tables of `B` counters,
so `k*B` extra words of memory and a merge pass of `k*B` adds and loads. For the
small-`B` case this is what a tuned C++ histogram does anyway, so the cost is
zero; for large `B` (a 2^20-bucket radix pass, a sparse accumulation) the private
tables do not fit in cache and the merge dominates, so the parallel form is worse
than the sequential one and the practical answer is to stay sequential - a real
loss of the available parallelism. Note also that `filled` is what makes the
private tables indexable at all, which carries its own cost (7-14).

Rules consistent: yes - the rejection is a real race and the accepted shapes are
the ones whose disjointness is arithmetic.
Task achievable: rewrite for small bucket counts at zero cost; for large bucket
counts the parallel form is lost.
Depends on: Rule 6, Rule 10, Rule 11, Rule 14.
Verdict: rejected-real-cost

### 7-14: A freshly allocated block has no indexable slots

Question: after `DynBox::new(n)`, what can be indexed, and how is an output
buffer of `n` elements produced - in particular in parallel?

Strongest program:
```text
// parallel construction of n owned objects into one buffer: the AST-building shape
out = DynBox::new<Box<Node>>(n)?               // cap_of == n, len_of == 0
par { build_into(&out[0..mid], &src[0..mid])   // rejected at the range, not at the body
      build_into(&out[mid..n], &src[mid..n]) }
```

Ordinary program (differs materially: Copy elements, so the window can be opened
in one step):
```text
out = DynBox::filled(n, 0.0)?                  // len_of == n
par { kernel(&src[0..mid], &out[0..mid]); kernel(&src[mid..n], &out[mid..n]) }
```

Trace:
- Rule 6 fixes the initial window: "buf = DynBox::new<T>(n)? // cap_of == n,
  len_of == 0". Rule 7's range form "requires lo <= hi <= len_of(buf)", so with
  `len_of(out) == 0` the only formable range is empty and `&out[0..mid]` is
  rejected for any positive `mid`. Nothing about the body matters; the argument
  cannot be formed.
- The window opens only through the operations Rule 6 lists. `push_nogrow` is
  declared `writes(buf)` and its `ensures len_of(buf) == len_of(deref(entry(buf)))
  + 1` shows why it cannot be parallelized: every push writes the same header
  path, so two pushes in different `par` arms overlap on `buf` and Rule 13
  rejects them. Filling by pushing is inherently sequential.
- The one bulk opener is restricted by element class: "buf = DynBox::filled(n,
  v)? // T Copy: cap_of == len_of == n, every slot holds v". For `Box<Node>`,
  for `Option<Box<Node>>`, and for every affine or linear element type there is no
  `filled`, hence no way to reach `len_of == n` except `n` sequential pushes.
- So the rule set admits parallel map into a fresh buffer exactly when the
  element type is Copy, and never otherwise.
- For the Copy case the cost is the fill itself. `filled(n, 0.0)` writes `n`
  slots that the kernel then overwrites. The compiler cannot elide it: proving
  that the kernel overwrites every slot is a quantified fact over elements, which
  Rule 11 refuses ("There are no quantified facts over array elements").
- Rule 14 is not the obstacle anywhere here: "Allocation and release carry no
  effect entry and never make two parallel arms conflict", so the arms may
  allocate freely; the obstacle is the window, not the heap.

Rewrite and cost:
- Copy elements: `filled` then range-split. Cost against C++ `malloc(n*8)`
  followed by the kernel: one extra streaming pass of `n` stores over the output
  buffer, i.e. up to 50% more write traffic on a memory-bound kernel and an
  extra `n*sizeof(T)` bytes of bandwidth. Against Rust's `vec![0.0; n]` the cost
  is zero, since safe Rust has the same initialization requirement.
- Non-Copy elements: each arm builds its own `DynBox`, then the results are
  concatenated sequentially by `pop`/`push_nogrow`. Cost against the C++
  `vector<unique_ptr<Node>>` filled by `k` threads into disjoint index ranges:
  one extra allocation per arm, `n` extra element moves in the merge, and the
  merge itself is sequential, so by Amdahl the parallel section is capped. The
  alternative that avoids the merge - keeping the `k` per-arm buffers and
  addressing elements as (arm, offset) - pays one extra dependent load on every
  later access to the structure, forever.

Rules consistent: yes - the window rule and the bounds rule agree; the
consequence is simply severe.
Task achievable: rewrite - parallel fill of Copy data costs one initialization
pass; parallel construction of owned objects into one buffer is not expressible
and its rewrite pays a merge or a permanent indirection.
Depends on: Rule 6, Rule 11, Rule 13, Rule 14.
Verdict: rejected-real-cost

### 7-15: Owned returns and the index protocol

Question: when a helper cannot return a reference into the caller's data, what
replaces it and what does the replacement cost?

Strongest program:
```text
// the three shapes C++ returns by reference: an element, a split, a choice
fn find(v: &DynBox<Entry>, key: Int) -> Option<u64>  reads(v)
    contract { ensures when Some: result < len_of(v); }

fn split_point(v: &DynBox<Int>) -> u64  reads(v)
    contract { ensures result <= len_of(v); }

fn pick_side(c: Bool) -> u8                      // which container, not a reference into one

match find(&v, k) { Some(i) => { p = &v[i]; bump(p) }  None => {} }

mid = split_point(&v)
par { work(&v[0..mid]); work(&v[mid..len_of(v)]) }

side = pick_side(c)
if side == 0 { for t in 0..n { step(&x[t]) } } else { for t in 0..n { step(&y[t]) } }
```

Trace:
- Rule 15: "A function returns owned values only. Positions found by a search are
  returned as indices with a bounds relation in `ensures` (Rule 4)." Rule 4 gives
  the same signature verbatim and comments on the caller's obligation: "caller
  re-derives, one address computation".
- The bound arrives with the result: Rule 11 admits "callee contracts" as facts,
  and `ensures when Some: result < len_of(v)` is exactly Rule 11's "result-routed
  relations" form. So `&v[i]` is formed with no runtime test - the match on the
  `Option` is the only branch, and C++'s `find` returning an iterator branches on
  the end sentinel in the same place.
- The split replaces `split_at_mut`. `mid <= len_of(v)` comes from the contract,
  so both ranges are formable and Rule 13's adjacency argument admits the `par`.
  No reference crossed the signature; the caller formed both ranges itself.
- The choice replaces a function returning one of two pointers (P9's `pick`).
  Returning an owned tag and branching once outside the loop duplicates the loop
  body, which the criteria explicitly do not count: "verbosity, extra parameters,
  and duplicated code are not costs". The branch is hoisted, so the loop bodies
  are identical to the C++ ones and each keeps a single-target reference, which
  also avoids the multi-target checks of 7-12.
- Where the selection is per element rather than per phase, no returned reference
  was ever involved - the writer indexes the chosen container inside the loop -
  so the shape does not arise.
- One unwritten point: the contracts above measure a reference parameter,
  `len_of(v)`. Whether an `ensures` may measure an owned result - `fn build(n:
  u64) -> own DynBox<Int> ensures len_of(result) == n` - is not exemplified
  anywhere in the rule file. If it may not, a caller must load `len_of` once
  before its first index, which is one compare hoisted out of any loop.

Rewrite and cost: the index protocol above. Cost against the C++ reference
returns: the re-derived address `&v[i]` is a base-plus-scaled-index form that
folds into the consuming load or store's addressing mode on both x86-64 and
AArch64, so it is not an instruction; the bounds fact rides in the contract, so
there is no test; the hoisted branch replaces an indirect access with a direct
one. Zero.

Rules consistent: yes.   Task achievable: rewrite - the three reference-returning
shapes all have zero-cost index or tag forms.
Depends on: Rule 4, Rule 11, Rule 13.
Verdict: rejected-zero-cost

### 7-16: Bounds proofs over pool and arena handles (provisional Rule 16)

Question: what does a handle dereference cost when handles are stored in the data
structure itself, and can the arena keep a reference alive across its own growth?

Strongest program:
```text
// P3: a compiler graph in an arena, handles stored in node fields
struct Node { next: u64, prev: u64, data: u64 }
struct Arena<T> { buf: DynBox<T> }
g: Arena<Node>

// traversal: every hop dereferences a handle that came out of memory
h = start
loop {
    if h >= len_of(g.buf) { break }          // the test Rule 7 demands, once per hop
    acc = acc + g.buf[h].data
    h = g.buf[h].next                         // the next handle is data
}

// builder: hold a reference to the parent while allocating a child
p = &g.buf[parent]
id = alloc(&g, Node { next: 0, prev: 0, data: d })   // writes(g.buf)
(*p).next = id                                        // rejected: p was invalidated by the call
```

Trace:
- Rule 16 supplies the shape: "A pool is a DynBox plus indices used as handles",
  with `fn alloc<T>(a: &Arena<T>, x: own T) -> u64 writes(a.buf)` and the comment
  "p = &a.buf[id] // valid until a.buf is replaced; readable while id <
  len_of(a.buf)".
- Traversal: `g.buf[h]` needs `h < len_of(g.buf)` (Rule 7). `h` came from
  `g.buf[h_prev].next`, i.e. from data, and Rule 11 forbids the invariant that
  would discharge it once and for all: "There are no quantified facts over array
  elements ("for all i ...")". P3's stated requirement, "the invariant 'next/prev
  point to live nodes' is stated once and reused", is therefore not expressible.
  Every hop tests.
- The test cannot be hoisted out of the loop, because the fact it establishes is
  about `h`, and `h` is reassigned from memory each iteration; the new `h` carries
  no fact. Nor does a power-of-two capacity help: masking is not an affine
  operation in Rule 11's vocabulary, so `h & (N-1) < N` is not derivable (7-11).
- Builder: `alloc` declares `writes(a.buf)`, and Rule 10 clause 3 applies - "A
  live reference outside the call whose path has a proper prefix among the call's
  write paths becomes invalid after the call (Rule 3)." `g.buf` is a proper
  prefix of `g.buf[parent]`, so `p` dies at every allocation. This is not
  conservatism: Rule 6's `Vector` growth "allocates a larger DynBox, moves
  `[0, len_of)` across, and replaces the old one", so the address really can move.
- Identity: Rule 16 states "A stale index that is still in bounds names the
  current occupant of that slot: a logic error, not a memory error." P2's
  requirement - "every old pointer into b2 must be refused afterwards" - and P3's
  - "removal invalidates every path to m" - are therefore not delivered by the
  rules; Rule 16 says the program buys them as data if it wants them: "Programs
  that need to detect it keep a generation number as data."
- Memory safety itself is never at risk: the slot is in bounds, initialized, and
  of the right type, so the failure mode is a wrong answer, not corruption.

Rewrite and cost:
- Traversal: as written, with the bound test in the loop. Cost against the C++
  `Node*` chase: one compare and one well-predicted branch per hop, plus one
  writer-supplied dead arm. The pointer chase is latency-bound, so the compare
  usually hides under the dependent load - but the branch also blocks the
  compiler from software-pipelining two hops. Against safe Rust with
  `arena[h as usize]`, zero.
- Builder: re-form the reference after each allocation, `p = &g.buf[parent]`,
  which additionally needs `parent < len_of(g.buf)` again - the call wrote
  `g.buf`, so Rule 11 invalidated that fact too unless `alloc`'s contract
  re-establishes it. Rule 16's contract does re-establish enough: `ensures
  len_of(a.buf) == result + 1` together with the pre-state bound gives the
  parent's bound back with no test, so the cost is the address recomputation,
  which folds into the following store. Effectively zero here, one compare
  wherever the contract is weaker.
- Identity: a generation counter per slot and per handle. Cost against C++'s raw
  pointer: 4 to 8 extra bytes per node and per handle, one extra load, one
  compare and one branch per dereference, and a second dead arm. This is the real
  price of P2's and P3's requirement under this candidate.

Rules consistent: yes - Rule 16 is coherent with Rules 6, 7 and 10; it declines a
guarantee rather than contradicting one.
Task achievable: rewrite - graph and pool code works, at one compare per handle
hop, and at an extra load and compare per hop if stale-handle detection is
required.
Depends on: Rule 6, Rule 7, Rule 10, Rule 11, Rule 16 (provisional pool rule).
Verdict: rejected-real-cost

## Row 10 - the call-site rule against itself and the rest

### 10-10: Calls inside calls: parameters as roots, recursion, and the effects a row cannot name

Question: does the call-site rule stay sound when a call is nested inside another
call - in the callee's body, in an argument position, and through a
function-typed parameter?

Strongest program:
```text
// a call through a function-typed parameter whose passed function reaches
// storage that its row cannot mention
fn apply(f: fn())                              // f's row is empty: it has no reference parameters
{ f() }                                        // Rule 9 body check: apply's row is empty and is satisfied

v: DynBox<Int>
p = &v[i]                                      // i < len_of(v) proved
h = || { push(&v, 7) }                          // captures a reference to v; push is writes(v)
apply(h)                                       // substituted row: nothing. No write path is recorded.
use(p)                                         // accepted by every rule below, and reads freed memory
```

Ordinary program (differs materially: everything the call touches is a
parameter):
```text
fn outer(a: &DynBox<Int>, b: &DynBox<Int>)  writes(a), reads(b)
{ inner(a, b) }                                 // inner: writes(p), reads(q)

fn merge(dst: &DynBox<Int>, x: &DynBox<Int>, y: &DynBox<Int>)  writes(dst), reads(x), reads(y)
merge(&out[0..n], &v[0..m], &v[m..n])           // accepted
merge(&v[0..n],   &v[0..m], &v[m..n])           // rejected: writes(v[0..n]) overlaps reads(v[0..m])

fn qsort(part: &DynBox<Int>)  writes(part)      // recursive; checked once against its row
```

Trace:
- The ordinary program is sound, and the argument is worth stating because it is
  what the whole rule rests on. Inside `outer`, the call `inner(a, b)` must pass
  Rule 10 clause 1, which offers "different roots" as a discharge. `a` and `b`
  are distinct parameters, hence syntactically distinct roots - yet at runtime
  they could be the same storage, so this step is only sound because `outer`'s own
  row, `writes(a), reads(b)`, forced every caller of `outer` through the same
  clause 1 comparison. Rule 9's body check closes the loop: "every statement's
  effect and every callee's substituted row must be covered by the declared row",
  so a body that touches `b` at all must declare it, and declaring it is what
  obliges the caller to prove the separation. Nothing in a body can reach storage
  the row does not name - provided the row can name everything the body reaches.
- Recursion needs no unfolding: Rule 10's closing clause, "Recursion is checked
  through contracts, never by unfolding bodies", and `qsort`'s recursive calls
  substitute subranges into `writes(part)`, whose disjointness is the arithmetic
  of 7-7.
- The strongest program breaks the proviso. Rule 4 permits the capture: its title
  is "References are never stored, returned, or captured into anything that
  escapes" and its body says a reference "cannot be captured by a function value
  that is stored or returned" - `h` is neither stored nor returned, it is passed,
  which Rule 4's first sentence permits ("A reference may be bound to a local,
  passed as a call argument"). Rule 1's closure over aggregates does not cover
  it either: its list is "Every struct, enum, tuple, array, slice-like value,
  Box, DynBox, and generic instantiation", and a function value is not among
  them.
- But Rule 9 fixes the row's grammar as "each path starts at a reference
  parameter", and a captured reference is not a parameter of `h`. So the effect
  `writes(v)` performed by `h` is not merely omitted by a sloppy writer; it is
  inexpressible. Rule 10's clause for this case, "Function-typed parameters carry
  a full signature with its own row and contract, and a call through one uses
  that row", then uses a row that is correct for the declared parameters and
  silent about the capture.
- Consequently Rule 10 clause 3 finds no write path at the call to `apply`, so
  `p` is not invalidated, and Rule 3's invalidation - "invalidated when any proper
  prefix of p's path is written, moved out of, replaced, or freed, by a statement
  or by a call" - never fires, because from the checker's point of view no call
  wrote `v`. The `use(p)` reads through a reallocated block. This is a
  use-after-free with no rule violated, and it needs no parallelism (the `par`
  version is 10-13).
- The alternative reading, that Rule 1's "no aggregate ever contains a reference"
  extends to a closure environment, closes the hole completely: then a passed
  function value may capture only owned values, and P16's `let h = |slice|
  helper(slice, input)` must pass `input` as a further parameter of the
  function-typed parameter instead. Rule 4's "that is stored or returned"
  qualifier is hard to read as anything but a deliberate permission, so the plain
  reading is the unsafe one.
- One further nesting case is simply unwritten: a call appearing in an argument
  position, `combine(&v, sum(&v))`. Rule 10 clause 2 covers only a value
  argument's place - "A by-value argument contributes a consumption (`move`) or a
  read (copy) of its place to this comparison" - and says nothing about an
  argument that is itself a call with its own row. Desugaring to `t = sum(&v);
  combine(&v, t)` is free, so the ambiguity costs nothing, but the rule as
  written does not say which effects enter the pairwise comparison.

Rewrite and cost: forbid a captured reference in a function value, and give the
function-typed parameter the reference as a parameter, so its row can name it:
```text
fn apply1(f: fn(x: &DynBox<Int>) writes(x), arg: &DynBox<Int>)  writes(arg)
{ f(arg) }
apply1(push7, &v)                               // now writes(v) is on the row, and p dies correctly
```
Cost against the C++ lambda capturing `v` by reference: zero. The captured
pointer becomes an argument register; extra parameters are explicitly not a cost
under these criteria. Every P16 shape - `map_nodes`, `kernel<E>`, P6's `h` -
survives the change.

Rules consistent: no - Rule 4 permits a capture whose effects Rule 9's row
grammar cannot express, and Rule 10 then checks a row that is silently
incomplete.   Task achievable: yes, and the safe form costs nothing, so the hole
should be closed by extending Rule 1 or deleting Rule 4's qualifier.
Depends on: Rule 1, Rule 3, Rule 4, Rule 6, Rule 9.
Verdict: accepted-unsafe

### 10-11: Contracts across the call boundary: which facts die and which are rebuilt

Question: after a call, which of the caller's bounds and measure facts survive,
and can a callee hand back the facts its writes destroyed?

Strongest program:
```text
// in-place partition, then a parallel recursion that needs both endpoints back
fn partition(part: &DynBox<Int>, pivot: Int) -> u64  writes(part)
    contract { ensures result <= len_of(part);
               ensures len_of(part) == len_of(deref(entry(part))); }

fn qsort(part: &DynBox<Int>)  writes(part)
{
    n = len_of(part)
    if n > 1 {
        mid = partition(part, choose(part))     // writes(part): kills every fact mentioning part
        // n is recovered from the second ensures; mid <= n from the first
        par { qsort(&part[0..mid]); qsort(&part[mid..n]) }
    }
}

// and the facts that must survive untouched
m = len_of(other)
k < len_of(meta.index)
compact(&part)                                  // writes(part)
use(&other[m - 1]); use(&meta.index[k])         // both still proved: different paths
```

Trace:
- Rule 11 is the invalidation rule: "A fact that mentions a path is invalidated
  when that path is written (by statement or call) unless the callee's `ensures`
  re-establishes it." `n = len_of(part)` mentions `part`, `partition` declares
  `writes(part)`, so `n == len_of(part)` is gone; only the `ensures` restores it.
  Without the second `ensures` line the range `&part[mid..n]` cannot be formed at
  all, since Rule 7 requires `mid <= n <= len_of(part)`.
- With it, both range formations are proof-only: `mid <= len_of(part)` from the
  first `ensures`, `len_of(part) == n` from the second, and `0 <= mid`. No
  runtime test is emitted, and Rule 13's adjacency judgment admits the `par`.
  This is why a writing callee under this candidate must publish a measure
  relation: `writes` is a total demolition of the caller's knowledge about that
  path, and `ensures` is the only rebuilding tool.
- `entry(p)` is what makes the relation statable: Rule 11, "the pre-state of a
  parameter is written `entry(p)`", used exactly as Rule 6 uses it in
  `push_nogrow`'s `ensures len_of(buf) == len_of(deref(entry(buf))) + 1`.
- The second half is where this rule set beats a C++ compiler. `writes(part)`
  invalidates facts about `part` and nothing else. It cannot reach `other`,
  because Rule 1 guarantees "no aggregate ever contains a reference" - there is no
  pointer inside `part` through which `other` could be touched - and it cannot
  reach the sibling field `meta.index`, because `part` and `meta.index` are
  non-overlapping paths. So a caller keeps every unrelated bound across an
  arbitrary call, which is PROGRAMS' CALL-6 anchor, "retain the facts unrelated to
  the call's effects". A C++ compiler must re-load `other.size()` after an opaque
  call unless it proves no-alias; here the guarantee is structural.
- Field granularity holds in the same way: a call declaring `writes(o.a)` (Rule
  9's `update` example, "fn update(o: &Obj, c: Bool) writes(o.a), writes(o.b)")
  leaves facts about `o.c` alive.
- Rule 10's function-typed clause extends this to callbacks: "Function-typed
  parameters carry a full signature with its own row and contract, and a call
  through one uses that row", so a generic algorithm reasons from the callback's
  declared contract instead of specializing. The caveat of 10-10 applies - a
  captured reference is outside the row - and here it shows up as a fact the
  caller wrongly keeps.
- One shape is unavailable and worth naming: a callee whose writes are
  conditional on a runtime value can only route its `ensures` through its result,
  since Rule 11 offers "`ensures when Variant:` for result-routed relations". A
  function that sometimes grows a buffer must therefore return the outcome and
  the caller must branch on it - the same branch C++ writes - rather than
  declaring a disjunction.

Rewrite and cost: none needed; the discipline is to publish a measure relation on
every writing signature. Cost against C++: zero, and strictly better where an
opaque call would otherwise force a reload of a length or a re-check of a bound.

Rules consistent: yes - `writes`, `entry` and `ensures` form a closed loop, and
Rule 1 is what makes the invalidation set exactly the declared paths.
Task achievable: yes.
Depends on: Rule 1, Rule 7, Rule 9, Rule 13.
Verdict: accepted-fine

### 10-12: Call-site checks over multi-target references: the double-buffer idiom

Question: what happens to the pairwise check when a reference argument may name
either of two containers, as in a ping-pong iteration?

Strongest program:
```text
// Jacobi / double-buffered stencil, the shape every iterative solver is written in
a = DynBox::filled(n, 0.0)?;  b = DynBox::filled(n, 0.0)?
fn stencil(src: &DynBox<f64>, dst: &DynBox<f64>)  reads(src), writes(dst)

for t in 0..steps {
    if t % 2 == 0 { src = &a; dst = &b } else { src = &b; dst = &a }
    stencil(src, dst)                           // rejected
}
```

Ordinary program (differs materially: no reference is ever rebound):
```text
for t in 0..steps/2 { stencil(&a, &b); stencil(&b, &a) }
if steps % 2 == 1 { stencil(&a, &b) }
```

Trace:
- Rule 2 makes the join explicit: "At a control-flow join, a reference variable's
  target is the set of paths it may name; every check on it must hold for every
  member of the set", and Rule 12 repeats it: "a reference's target set is the
  union of its targets (Rule 2)". After the `if`, `src` names one of `{a, b}` and
  `dst` names one of `{a, b}`.
- Rule 10 clause 1 must then prove `writes(dst)` disjoint from `reads(src)`. The
  check has to hold for every member pair, which includes `dst = a, src = a`.
  Same root, one is a write, no index or range separates them, so the call is
  rejected. The checker is right about the pairs it must consider and wrong about
  the program, which never executes the bad pair - the correlation between the two
  target sets is exactly what a union of independent target sets discards.
- No rule provides a correlated or tagged target set, and none is needed:
  unrolling by two removes the join, so each `stencil` call sees single-target
  references.
- The same loss appears without `par` anywhere, so it is a sequential
  expressiveness question, not a parallelism one.
- Two neighbouring join questions resolve cleanly, and are worth recording here
  because they are the ones that would have cost something:
  - Conditional consumption. `if c { sink(move x) }` contributes, by Rule 10
    clause 2, "a consumption (`move`) ... of its place" on one edge only. Rule 12
    intersects, so `x` is unusable after the join, and for an affine `x` the
    compiler's release can be placed at the end of the other arm rather than
    after the join - no drop flag, P8's requirement, zero cost. For a linear `x`
    Rule 8 demands consumption "on every exit path", so the writer supplies the
    `else` arm; the branch already existed.
  - A reference invalidated on one edge. Rule 3 says validity "is a fact like any
    other", so Rule 12's intersection kills it after the join with no extra rule.
- A harder variant does survive: when the two buffers live in a container and are
  selected by index, `stencil(&bufs[i], &bufs[j])`, the target sets are single
  but distinctness of `i` and `j` must be proved. `i = t % k` and `j = (t+1) % k`
  give nothing affine, but writing the call under a dominating comparison does:
  `if i < j { stencil(&bufs[i], &bufs[j]) } else if j < i { stencil(&bufs[i],
  &bufs[j]) }` - the same argument expressions, a different proof in each arm.
  That costs one compare and one branch per whole sweep, which is nothing beside
  the sweep.

Rewrite and cost: unroll the iteration by two, with a tail for an odd `steps`.
Cost against the C++ `std::swap(src, dst)` loop: negative - the unrolled form
deletes the per-iteration parity branch and the two pointer stores, and gives the
backend two call sites with known arguments instead of one with unknown ones.
Duplicated source is not a cost under these criteria.

Rules consistent: yes - the union of target sets is a deliberate
over-approximation, and it rejects rather than admits.
Task achievable: rewrite - double buffering costs nothing once the loop is
unrolled by two.
Depends on: Rule 2, Rule 3, Rule 8, Rule 12.
Verdict: rejected-zero-cost

### 10-13: Rows, `par`, and the function-typed parameter: what the disjointness test is allowed to trust

Question: does `par`'s disjointness test see everything a parallel arm can reach,
given that the arms are calls and that a call may go through a function-typed
parameter?

Strongest program:
```text
// P6 with P16's callback: k workers each running a passed function over its range
fn run2(f: fn(s: &DynBox<u8>) writes(s), x: &DynBox<u8>, y: &DynBox<u8>)  writes(x), writes(y)
{ par { f(x); f(y) } }                          // arms: writes(x) and writes(y); the caller proved them disjoint

input: DynBox<u8>;  out: DynBox<u8>
h = |s| { helper(s, &input) }                    // captures a reference to input: reads(input), unnamed
run2(h, &out[0..mid], &out[mid..n])              // accepted: the ranges are adjacent

// now the unsafe variant, identical in every rule-visible respect
g = |s| { compress_into(s, &scratch) }           // captures &scratch: writes(scratch), unnamed
par { run2(g, &out[0..mid], &out[mid..n]) ; touch(&scratch) }   // accepted: no rule sees writes(scratch)
```

Ordinary program (differs materially: everything an arm touches is an argument):
```text
par { kernel(&v[0..mid], &out[0..mid]); kernel(&v[mid..n], &out[mid..n]) }
par { s1 = stats(&v); s2 = stats(&v) }           // read/read
par { a = build(&x)?; b = build(&y)? }           // both allocate
par { sink(move p); sink(move q) }               // two consumptions of distinct places
par { push(&v, 1); stats(&v) }                   // rejected: writes(v) overlaps reads(v)
```

Trace:
- Rule 13's test is stated over paths: "`par { A; B }` is accepted when A's write
  paths are disjoint from B's read and write paths and vice versa, using the same
  path-overlap and index/range-disjointness judgment as Rule 10." The arms here
  are calls, so an arm's paths are its substituted row - Rule 10's first sentence,
  "At a call, substitute the actual argument paths into the callee's row."
- The ordinary program is entirely settled by that. Adjacent ranges are disjoint;
  two reads overlap harmlessly ("Read/read overlap is allowed"); allocation is
  excluded by Rule 14, "Allocation and release carry no effect entry and never
  make two parallel arms conflict"; and a growing call beside a reading call is
  rejected, which Rule 13 spells out itself.
- By-value consumption in an arm is only reachable through the import clause:
  Rule 13 says the judgment is "the same ... as Rule 10", and Rule 10 clause 2 is
  where a consumption enters - "A by-value argument contributes a consumption
  (`move`) or a read (copy) of its place to this comparison." Read that way,
  `par { sink(move p); use(&p) }` is rejected, which is the needed answer. Rule
  13's own sentence mentions only "write paths" and "read and write paths", so the
  import is an inference rather than a statement.
- A bystander reference behaves correctly across arms: `p = &v[i]; par {
  grow(&v); use(p) }` is rejected because the second arm's read path `v[i]`
  overlaps the first arm's write path `v` - clause 3's post-call invalidation is
  not even needed, the pairwise test suffices.
- The strongest program is where it breaks, for the reason derived in 10-10: Rule
  9 requires that "each path starts at a reference parameter", so a reference
  captured by the passed function is unnameable, while Rule 10's clause
  "Function-typed parameters carry a full signature with its own row and contract,
  and a call through one uses that row" makes the checker rely on that row. Inside
  `run2` the two arms are `writes(x)` and `writes(y)`, proved disjoint by the
  caller - but both arms additionally write `scratch` through `g`'s capture, and
  every level of the check is blind to it. The result is a genuine data race
  between the two arms, and a second race between `run2` and `touch(&scratch)`.
  Nothing in `par`, in the row, or in the call-site comparison is violated.
- The benign-looking first closure `h` is the same construct: it is sound only
  because both arms happen to read `input`. Nothing distinguishes the two cases
  to the checker, which is what makes this a rule hole rather than a writer
  error.
- Note that this is the only route by which two `par` arms can reach a common
  path, because Rule 1 removes references from every aggregate: without captures,
  an arm can touch only what its arguments name.

Rewrite and cost: as in 10-10, the captured reference becomes a parameter of the
function-typed parameter, so its effect is on the row:
```text
fn run2(f: fn(s: &DynBox<u8>, aux: &DynBox<u8>) writes(s), reads(aux),
        x: &DynBox<u8>, y: &DynBox<u8>, aux: &DynBox<u8>)  writes(x), writes(y), reads(aux)
{ par { f(x, aux); f(y, aux) } }
```
Now `reads(aux)` appears in both arms (allowed) and, in the unsafe variant, the
row would say `writes(aux)` in both, which Rule 13 rejects on the spot. Cost
against the C++ lambda: zero - the captured pointer becomes an argument register,
and extra parameters are excluded from cost by the criteria.

Rules consistent: no - Rule 4's permitted capture is invisible to Rule 9's row
grammar, and Rule 13 trusts that row.   Task achievable: yes at zero cost once
captures are parameters; until then the parallel forms this candidate is built
around are unsound in the presence of a capturing callback.
Depends on: Rule 1, Rule 4, Rule 9, Rule 10, Rule 14.
Verdict: accepted-unsafe

### 10-14: Allocation failure at a call, and the heap that is not an effect

Question: how does a failing allocation inside a called arm interact with the
call-site rule, with linear obligations, and with a sibling `par` arm?

Strongest program:
```text
// P18: several allocations, each of which may fail, with a linear resource already held
fn build(src: &DynBox<Int>) -> Result<own DynBox<Int>, Oom>  reads(src)

f: File                                          // linear, already open
par { a = build(&x)?; b = build(&y)? }           // Rule 14's own example, with `?` in both arms
close(move f)
```

Ordinary program (differs materially: sequential, single failure point):
```text
match build(&x) {
    Ok(a)  => { use(&a); close(move f) }         // every exit path consumes f
    Err(e) => { close(move f); return Err(e) }
}
```

Trace:
- The call-site side is simple and holds. Rule 14: "Allocation and release carry
  no effect entry and never make two parallel arms conflict", so `build`'s row is
  just `reads(src)`, the two arms read different containers, and Rule 13 accepts.
  `Box::new` and `DynBox::new` return `Result`, so there is no trap and no hidden
  control flow at the allocation itself.
- Release through a path is a different matter and is an effect, by Rule 9's
  definition: "`writes` covers writing, replacing, moving out of, and freeing the
  storage at the path." So the `Vector` growth of Rule 6, which frees the old
  block, is `writes(buf)` and conflicts as expected; only the allocator's own
  bookkeeping is exempt. The two statements are consistent: Rule 14 exempts the
  heap, not the program's storage.
- Determinism is claimed for the exempt part - "Addresses are not observable, so
  allocator concurrency does not affect program determinism" - and that claim is
  sound for addresses.
- The gap is the control flow. Rule 14's own example writes `?` inside both arms:
  "par { a = build(&x)?; b = build(&y)? }     // both allocate: accepted". Rule 13
  defines `par` only by its acceptance condition and says nothing about an arm
  that exits early. Three things are therefore unstated, and the program above
  cannot be given a meaning without them:
  1. whether the sibling arm runs to completion when one arm propagates, and so
     whether the writes the sibling's row promised have happened at the point
     control leaves the block;
  2. which error value is produced when both arms fail - if it is whichever
     finishes first, the "determinism" sentence above is violated by an
     observable value, not by an address;
  3. whether the bindings `a` and `b` of a completed arm exist on the propagating
     path, which decides whether an affine result is released and whether a
     linear one can still be consumed.
- The linear side of P18 is decidable, and passes: Rule 8 requires that "Linear
  values must be consumed by an explicit operation on every exit path; the
  compiler never releases them", so `?` - which manufactures an exit path - cannot
  be used while a linear value is live unless the desugaring consumes it, and the
  writer therefore writes the `match` of the ordinary program. That is the branch
  C++ writes too, so the cost is zero. But this is exactly the place where point
  3 above bites: a linear value produced inside a `par` arm cannot be shown to be
  consumed on the propagating path, so `par` plus `?` plus linearity has no
  derivable answer at all.

Rewrite and cost: for the sequential shape, none needed - explicit `match` arms,
zero cost. For the parallel shape there is a rewrite that avoids the unstated
semantics entirely: let each arm produce a `Result` value rather than propagate,
and join afterwards:
```text
par { ra = build(&x); rb = build(&y) }           // both arms always complete
match (ra, rb) { (Ok(a), Ok(b)) => ... , ... }   // one deterministic decision point
```
Cost against the C++ form that aborts the other thread on failure: the sibling's
work is not cancelled, so a failing run does the full work of both arms once.
Allocation failure is off the hot path, so this is zero in practice.

Rules consistent: undetermined - Rule 13 defines `par` only as an acceptance
test, while Rule 14's example relies on `?` inside an arm.
Task achievable: yes for the sequential shape; the parallel shape needs a ruling
on early exit before it can be derived at all.
Depends on: Rule 6, Rule 8, Rule 9, Rule 13.
Verdict: undecided-rule-gap

### 10-15: Owned results, container-level rows, and the reader who was not in the call

Question: when a helper returns an owned index rather than a reference, does the
caller's other reference survive the call that produced it?

Strongest program:
```text
// P11: a write-once cache, many readers, one lazy writer per slot, keys from data
cache: DynBox<Entry>                             // fully initialized (Rule 12), occupancy in a tag column
tags:  DynBox<u8>

fn get_or_fill(cache: &DynBox<Entry>, tags: &DynBox<u8>, k: u64) -> u64
    writes(cache), writes(tags)
    contract { requires k < len_of(cache); ensures result == k;
               ensures len_of(cache) == len_of(deref(entry(cache))); }

p = &cache[i]                                    // a reader on another slot, i data-determined
j = get_or_fill(&cache, &tags, k)                // writes(cache)
read(p)                                          // rejected: p is a bystander over a written prefix
```

Ordinary program (differs materially: the effect is declared on the slot):
```text
fn fill_slot(slot: &Entry, tag: &u8, key: Int)  writes(slot), writes(tag)

p = &cache[i]
if i != k { fill_slot(&cache[k], &tags[k], key) ; read(p) }   // accepted: distinct indices
else      { fill_slot(&cache[i], &tags[i], key) ; read(&cache[i]) }
```

Trace:
- Rule 15 forces the shape: "A function returns owned values only. Positions
  found by a search are returned as indices with a bounds relation in `ensures`."
  So `get_or_fill` hands back `k`, and the caller forms `&cache[k]` itself with
  the bound carried by `ensures result == k` plus the `requires`.
- The reader dies on clause 3: "A live reference outside the call whose path has
  a proper prefix among the call's write paths becomes invalid after the call
  (Rule 3). A reference that is itself an argument is the thing being accessed,
  not a bystander." `cache` is a proper prefix of `cache[i]`, so `p` is
  invalidated - even though the callee touched only slot `k`, because the row it
  declared was container-wide. P11's stated question, "whether a reader may hold
  a pointer to a slot across another slot's fill", is answered: only if the row
  is written at slot granularity and the indices are proved distinct.
- The slot-granular row is available by Rule 9's argument-supplied paths and its
  `put_at(&buf[len_of(buf)], 3)` example, so the ordinary program's
  `fill_slot(&cache[k], ...)` substitutes to `writes(cache[k])`, and clause 3
  then invalidates only references under `cache[k]`. With `i != k` in hand from
  the dominating comparison, `p` survives.
- Two prices come with that granularity. First, the callee can no longer resize
  or rehash - a slot reference cannot reach the container - so the growth path
  must be a separate, container-level call, at which point every reader's
  reference legitimately dies. Second, `i != k` must be proved, and both indices
  are hash values, so the writer supplies the comparison.
- Rule 10 clause 2 also matters for the value that goes in: `fill_slot(..., move
  e)` contributes "a consumption (`move`) ... of its place", which is compared
  against `writes(cache[k])` - distinct places, accepted - so handing an owned
  entry to a slot-level writer is clean.
- Rule 15's other sentence, "Passing a large value in and back out is expressed
  as a reference parameter with a `writes` entry, not as move-and-return", is what
  keeps this from costing a copy: the entry is built in place through the slot
  reference rather than returned by value, which matters because PROGRAMS records
  that "Large-aggregate ownership round trips have no assumed zero-copy ABI".

Rewrite and cost: the ordinary program - slot-level rows plus an explicit index
comparison. Cost against the C++ cache that keeps an `Entry*` across a fill of
another slot: one compare and one branch per fill when the reader's index cannot
be related to the writer's, plus the duplicated body (free). Where the comparison
fails, the reference must be re-formed after the call - an addressing-mode
recomputation, not an instruction - but its bound must also be re-proved, which
the `ensures len_of(cache) == len_of(deref(entry(cache)))` line supplies without
a test. So the residual runtime cost is exactly the one comparison, per fill, not
per read.

Rules consistent: yes - clause 3 is exactly as coarse as the row it reads, which
is the intended design.
Task achievable: rewrite - one compare per lazy fill; without the slot-level row
the reader must re-derive after every call.
Depends on: Rule 4, Rule 7, Rule 9, Rule 11, Rule 12.
Verdict: rejected-real-cost

### 10-16: Calls over a pool: allocation as a container write, and the parallel node map (provisional Rule 16)

Question: under the arena-as-usage rule, what do the call-site checks cost a
program that allocates while it traverses, and can node work still run in
parallel?

Strongest program:
```text
// P3 and P2 together: build and edit a graph in an arena, then map over nodes in parallel
struct Node { next: u64, prev: u64, data: u64 }
struct Arena<T> { buf: DynBox<T> }
fn alloc<T>(a: &Arena<T>, x: own T) -> u64  writes(a.buf)
    contract { requires len_of(a.buf) < cap_of(a.buf);
               ensures result == len_of(deref(entry(a.buf))); ensures len_of(a.buf) == result + 1; }

fn link(from: &Node, to: &Node, id_from: u64, id_to: u64)  writes(from), writes(to)

// (i) insert between two existing nodes, both chosen by data
link(&g.buf[a], &g.buf[b], a, b)                 // rejected unless a != b is proved

// (ii) allocate while holding a reference to the parent
p = &g.buf[parent]
id = alloc(&g, Node { next: 0, prev: 0, data: d })     // writes(g.buf): p dies here
(*p).data = id                                          // rejected

// (iii) parallel map over the live nodes, reached by traversal
par { work(&g.buf[h1]); work(&g.buf[h2]) }              // rejected: h1 != h2 not provable
```

Ordinary program (differs materially: the arena is addressed as a dense range):
```text
par { map_range(&g.buf[0..mid], &live[0..mid]); map_range(&g.buf[mid..n], &live[mid..n]) }
// each arm skips slots whose liveness byte is 0
```

Trace:
- Rule 16 gives the arena its shape and its `alloc` row, `writes(a.buf)`, and
  states the identity position: "A stale index that is still in bounds names the
  current occupant of that slot: a logic error, not a memory error."
- (i) is Rule 10 clause 1 verbatim: two write paths sharing the root `g.buf`,
  separated only by "indices or ranges proved distinct". In a doubly linked
  insert the two endpoints are distinct by construction but that construction is
  data. The workaround is not the comparison but the statement form: two
  sequential calls, `set_next(&g.buf[a], id)` then `set_prev(&g.buf[b], id)`,
  each carrying a single effect, never enter the pairwise comparison at all. Rule
  10's test is per call, so link editing costs nothing once it is written one
  write per call. That is a pure source change.
- (ii) is Rule 10 clause 3 - `g.buf` is a proper prefix of `g.buf[parent]`, so
  the reference is invalidated by the allocation. It must be: Rule 6's growth
  "allocates a larger DynBox, moves `[0, len_of)` across, and replaces the old
  one", so the parent really may have moved. The rewrite is to hold the handle
  rather than the reference and re-form after the call, and Rule 16's `ensures
  len_of(a.buf) == result + 1` restores the parent's bound with no test, since
  `parent < len_of(entry) <= result < len_of(a.buf)`.
- (iii) is Rule 13 with Rule 10's judgment, and it fails for the same reason as
  7-10: handles pulled out of node fields carry no distinctness fact, and Rule 11
  supplies none ("There are no quantified facts over array elements"). P3's
  requirement, "parallel data writes are permitted by distinctness of nodes", is
  therefore not met through traversal order.
- The ordinary program recovers the parallelism by giving up traversal order:
  adjacent ranges over the dense slot space are disjoint by arithmetic, which
  Rule 13 admits. The liveness column is data, as Rule 12 requires - "occupancy
  that is determined by data is stored as data".
- Freed-slot identity remains the candidate's declared hole. P2's requirement
  that "every old pointer into b2 must be refused afterwards" is refused by Rule
  16 on purpose; memory safety is untouched, because the slot is in bounds,
  initialized and correctly typed, but a stale handle silently reads a
  replacement node.

Rewrite and cost, per item:
- (i) one write per call: zero.
- (ii) handle plus re-formed reference: zero instructions where the contract
  restores the bound, since the address recomputation folds into the following
  store; one compare wherever the callee's contract is weaker than Rule 16's.
- (iii) dense range map plus a liveness byte: one load, one compare and one
  predictable branch per slot, and the arm visits free slots too, so the work is
  proportional to `cap_of` rather than to the live count. Against a C++ parallel
  walk of a free-list-managed pool this is roughly the same test; against a C++
  parallel walk over a compact live array it is the fragmentation factor, which
  the writer controls by compacting.
- Identity, where the task needs it: a generation word per slot and per handle -
  one extra load, one compare, one branch per dereference, plus 4 to 8 bytes per
  node and per handle.

Rules consistent: yes - Rule 16 composes with Rules 10, 11 and 13 without
contradiction; it withholds a guarantee rather than breaking one.
Task achievable: rewrite - the graph, its edits and a parallel node map are all
expressible; traversal-ordered parallelism is lost, and stale-handle detection is
paid in data.
Depends on: Rule 6, Rule 7, Rule 10, Rule 11, Rule 12, Rule 13, Rule 16
(provisional pool rule).
Verdict: rejected-real-cost
